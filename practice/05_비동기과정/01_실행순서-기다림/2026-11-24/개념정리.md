## 1단계: 동기 실행 — 위에서부터 한 줄씩, 함수는 끝나야 다음 줄

Node는 파일을 위에서부터 한 줄씩 실행해요. 파이썬 스크립트와 같아요. 한 줄이 끝나야 다음 줄로 가요. 계산하는 줄이면 계산이 끝나고 결과가 변수에 들어간 다음에야 다음 줄이 실행돼요.

함수를 부를 때도 같아요. `const result = calculate();`를 만나면 Node는 `calculate` 안으로 들어가서 그 안의 줄을 차례로 실행해요. `return`을 만나면 값을 가지고 부른 자리로 돌아와 `result`에 넣고, 그제야 다음 줄로 가요. 함수가 끝날 때까지 바깥 코드는 한 줄도 진행하지 않아요.

이렇게 **부른 작업이 끝나고 결과를 받은 다음에 다음 코드로 가는 방식**을 **동기**라고 해요. 지금까지 쓴 코드는 거의 다 동기였어요. 그래서 출력 순서가 코드에 적은 순서와 같았어요.

`return`은 값을 돌려주면서 함수를 그 자리에서 끝내요. `return` 아래에 줄을 더 써도 실행되지 않아요.

### ▶ 직접 해 보기 — `order.js`
`order.js` 내용을 전부 바꾸고 실행해요 (강의 2장 코드).
```javascript
function calculate() {
  console.log("2. 함수 실행");

  return 10 + 20;
}

console.log("1. 시작");

const result = calculate();

console.log("3. 계산 결과:", result);
console.log("4. 끝");
```
```text
1. 시작
2. 함수 실행
3. 계산 결과: 30
4. 끝
```
함수는 위쪽에 정의했지만, 정의만 해서는 실행되지 않아요. `calculate()`를 부른 줄에서 실행돼서 `2. 함수 실행`이 `1. 시작` 다음에 나와요.

**바꿔 보기** (강의의 직접 바꿔보기): 출력문 세 줄을 넣고, **실행 전에 순서를 먼저 적어 본 다음** 실행해요.
- `return 10 + 20;` 바로 위에 `console.log("함수 안: return 바로 전");`
- `return 10 + 20;` 바로 아래에 `console.log("함수 안: return 다음 줄");`
- `const result = calculate();` 바로 아래에 `console.log("함수 밖: calculate() 바로 다음 줄");`

```text
1. 시작
2. 함수 실행
함수 안: return 바로 전
함수 밖: calculate() 바로 다음 줄
3. 계산 결과: 30
4. 끝
```
`함수 안: return 다음 줄`은 찍히지 않아요. `return`에서 함수가 끝났기 때문이에요. 확인했으면 세 줄을 지워요.

## 2단계: `setTimeout()`은 멈춤이 아니라 예약

프로그램에는 결과가 나오기까지 시간이 걸리는 작업이 있어요. 서버에 학생 목록을 요청하면 네트워크를 오가는 시간이 걸리고, 파일을 읽으면 저장 장치에서 읽는 시간이 걸려요. 오늘 중요한 건 작업이 빠른지 느린지가 아니라, **그 작업을 기다리는 동안 다른 코드가 어떻게 되는지**예요. 서버 없이 이걸 보려고 타이머를 써요.

```javascript
setTimeout(실행할함수, 지연시간);
```

첫 번째 값은 나중에 실행할 함수, 두 번째 값은 기다릴 시간이에요. 시간은 **밀리초**(ms) 단위라서 `1000`이 1초예요.

파이썬의 `time.sleep(3)`을 떠올리면 헷갈려요. `time.sleep(3)`은 그 자리에서 3초 멈췄다가 다음 줄로 가요. `setTimeout`은 멈추지 않아요. "3초 뒤에 이 함수를 실행해 줘"라고 **예약만** 하고 바로 다음 줄로 가요. 예약된 함수는 3초가 지난 뒤에 실행돼요.

그래서 아래 코드는 `1. 시작` → `3. 끝` → `2. 타이머 실행` 순서로 찍혀요. 코드에 붙인 번호는 출력 순서를 정하지 않아요. Node가 실제로 실행한 순서대로 찍힐 뿐이에요.

이렇게 **결과를 그 자리에서 받지 않고, 작업이 끝났을 때 실행할 코드를 연결해 두었다가 나중에 이어서 처리하는 방식**을 **비동기**라고 해요. 1단계의 동기와 짝이 되는 말이에요.

하나 더 볼 것이 있어요. `3. 끝`이 찍힌 뒤에도 터미널 프롬프트가 바로 돌아오지 않아요. 예약한 타이머가 남아 있으면 Node는 프로그램을 끝내지 않고 기다렸다가, 타이머 함수까지 실행한 뒤에 끝내요.

### ▶ 직접 해 보기 — `timer.js`
강의 3장의 이름 있는 함수 버전이에요.
```javascript
console.log("1. 시작");

function timer() {
  console.log("2. 타이머 실행");
}

setTimeout(timer, 3000);

console.log("3. 끝");
```
```text
1. 시작
3. 끝
```
약 3초 뒤:
```text
2. 타이머 실행
```
강의는 같은 코드를 화살표 함수로도 썼어요. `function timer() { … }`를 지우고 `setTimeout(() => { console.log("2. 타이머 실행"); }, 3000);`로 써도 결과가 같아요.

**바꿔 보기**
- 걸린 시간을 재 봐요. `Date.now()`는 지금 시각을 밀리초 숫자로 돌려줘요. 시작할 때 적어 둔 값을 빼면 그동안 지난 시간이 나와요. 파일 내용을 아래로 바꿔요.
  ```javascript
  const start = Date.now();

  console.log("1. 시작");

  function timer() {
    console.log("2. 타이머 실행:", Date.now() - start, "ms 뒤");
  }

  setTimeout(timer, 3000);

  console.log("3. 끝:", Date.now() - start, "ms 뒤");
  ```
  ```text
  1. 시작
  3. 끝: 1 ms 뒤
  2. 타이머 실행: 3003 ms 뒤
  ```
  `3. 끝`은 시작하자마자 찍혔어요. 예약하는 줄이 3초를 기다리지 않았다는 뜻이에요. ms 숫자는 실행할 때마다 조금씩 달라요 (두 번째 실행은 `2 ms`, `3003 ms`였어요).
- `setTimeout(timer, 3000);`을 `setTimeout(timer(), 3000);`으로 바꿔요 (괄호 추가).
  ```text
  1. 시작
  2. 타이머 실행
  TypeError [ERR_INVALID_ARG_TYPE]: The "callback" argument must be of type function. Received undefined
  ```
  `2. 타이머 실행`이 3초를 기다리지 않고 바로 찍히고, 그다음 오류가 나서 프로그램이 멈춰요. `3. 끝`은 찍히지 않아요. 왜 그런지는 3단계에서 봐요. 괄호를 지워 되돌려요.

## 3단계: 콜백 함수 — 전달하는 것과 부르는 것

`setTimeout(timer, 3000)`에서 `timer`처럼 **다른 코드에 넘겨 두고, 그 코드가 나중에 부르게 하는 함수**를 **콜백 함수**라고 해요.

여기서 괄호가 중요해요. `timer`는 함수 그 자체예요. `timer()`는 함수를 **지금 바로 실행하고, 돌려준 값**이에요. `setTimeout(timer(), 3000)`이라고 쓰면 Node는 `setTimeout`에 값을 넘기기 전에 `timer()`부터 실행해요. 그래서 `2. 타이머 실행`이 바로 찍혀요. `timer`는 `return`이 없어서 `undefined`를 돌려주고, `setTimeout`은 함수 대신 `undefined`를 받아요. 그래서 "callback 자리에는 함수가 와야 하는데 `undefined`를 받았다"는 오류가 났어요.

React에서도 같은 구분을 했어요. `<button onClick={handleClick}>`은 함수를 넘겨서 클릭할 때 실행되게 하고, `onClick={handleClick()}`은 화면을 그릴 때 바로 실행해 버렸죠.

그런데 **콜백이라고 모두 나중에 실행되는 건 아니에요.** 배열의 `map()`도 함수를 넘겨받아요. 하지만 `map()`은 받은 함수를 **그 자리에서** 항목마다 실행하고, 다 끝나면 새 배열을 돌려줘요. 그래서 `map()` 다음 줄은 `map()`이 끝난 다음에 실행돼요. 함수를 넘겼다는 것만으로 비동기라고 판단하면 안 되고, **넘긴 함수가 언제 실행되는지**를 봐야 해요.

### ▶ 직접 해 보기 — `callback.js`
타이머에 넘긴 콜백과 `map()`에 넘긴 콜백이 언제 실행되는지 비교해요.
```javascript
function showMessage() {
  console.log("타이머가 부른 showMessage");
}

console.log("1. 예약 전");

setTimeout(showMessage, 2000); // 함수를 넘기기만 해요 (괄호 없음)

console.log("2. 예약 후");

const numbers = [1, 2, 3];

const doubled = numbers.map((number) => {
  console.log("map 콜백 실행:", number);
  return number * 2;
});

console.log("3. map 결과:", doubled);
```
```text
1. 예약 전
2. 예약 후
map 콜백 실행: 1
map 콜백 실행: 2
map 콜백 실행: 3
3. map 결과: [ 2, 4, 6 ]
타이머가 부른 showMessage
```
`map` 콜백 세 번은 `3. map 결과` 앞에 찍혔어요. 그 자리에서 실행된 거예요. 타이머 콜백은 파일의 모든 줄이 끝나고 약 2초 뒤에 찍혔어요.

**바꿔 보기**
- `setTimeout(showMessage, 2000);`을 `showMessage();`로 바꿔요. 함수를 지금 부르는 코드라서 `1. 예약 전` 바로 다음 줄에 `타이머가 부른 showMessage`가 찍히고, 프로그램도 2초를 기다리지 않고 바로 끝나요. 되돌려요.

## 4단계: 0초 타이머도 지금 코드가 다 끝난 뒤에 실행된다

기다릴 시간을 `0`으로 주면 어떻게 될까요? "0초 뒤에 실행"이니 그 자리에서 바로 실행될 것 같지만, 그렇지 않아요.

`setTimeout`은 시간이 얼마든 콜백을 **예약 목록에 올려 두기만** 해요. Node는 `node 파일.js`로 시작한 코드를 파일 맨 아래 줄까지 다 실행한 다음에야 예약 목록을 확인해요. 그래서 `0`으로 예약해도 그 콜백은 파일의 마지막 줄보다 뒤에 실행돼요. 사이에 반복문이 있든, 함수 호출이 있든, 지금 실행 중인 코드가 먼저 끝까지 가요. 실행 중인 코드를 중간에 끊고 타이머 콜백을 끼워 넣는 일은 없어요. 참고로 Node는 `0`을 1밀리초로 바꿔서 처리해요.

출력 순서를 예상할 때는 이렇게 적어 보면 돼요.

1. 파일을 위에서부터 읽으면서 **바로 실행되는 줄**을 순서대로 적어요. `console.log`, 함수를 부르면 그 함수 안의 줄, `map` 콜백이 여기에 들어가요.
2. `setTimeout`을 만나면 그 콜백은 적지 않고 옆에 따로 모아 둬요.
3. 파일 끝까지 다 적었으면, 모아 둔 콜백을 **기다릴 시간이 짧은 것부터**, 시간이 같으면 **예약한 순서대로** 이어서 적어요.

### ▶ 직접 해 보기 — `zero.js`
실행하기 전에 위 방법으로 출력 순서를 먼저 적어 보고, 실행해서 맞춰 봐요.
```javascript
console.log("첫 줄");

setTimeout(() => {
  console.log("타이머 콜백");
}, 0);

for (let i = 1; i <= 3; i++) {
  console.log("반복", i);
}

console.log("마지막 줄");
```
```text
첫 줄
반복 1
반복 2
반복 3
마지막 줄
타이머 콜백
```
`setTimeout`은 두 번째 줄에 있지만, 콜백은 맨 마지막에 찍혔어요.

**바꿔 보기**: 하나씩 바꾸고, 실행 전에 순서를 먼저 적어 봐요.
- (강의의 직접 바꿔보기) `}, 0);`을 `}, 1000);`으로 바꾸고, 맨 아래에 `console.log("추가한 줄");`을 넣어요. → `첫 줄`, `반복 1~3`, `마지막 줄`, `추가한 줄`이 바로 찍히고, 약 1초 뒤 `타이머 콜백`이 찍혀요. 타이머 콜백은 파일 맨 아래에 추가한 줄보다도 뒤예요. 되돌려요.
- 첫 번째 `setTimeout` 블록 바로 아래에 두 번째 타이머를 넣어요.
  ```javascript
  setTimeout(() => {
    console.log("두 번째 타이머 콜백");
  }, 0);
  ```
  → `마지막 줄`까지는 그대로이고, 그 뒤에 `타이머 콜백`, `두 번째 타이머 콜백` 순서로 찍혀요. 시간이 같으면 예약한 순서대로 실행돼요.
- 이어서 첫 번째 타이머의 `0`만 `50`으로 바꿔요. → 마지막 두 줄이 `두 번째 타이머 콜백`, `타이머 콜백` 순서로 바뀌어요. 기다릴 시간이 짧은 쪽이 먼저예요. 두 번째 타이머를 지우고 `50`을 `0`으로 되돌려요.
- 함수 안에서 예약해도 규칙이 같은지 봐요. 파일 내용을 아래로 바꿔요.
  ```javascript
  function later() {
    console.log("later 함수 실행");
    setTimeout(() => {
      console.log("later 안에서 예약한 타이머");
    }, 0);
    console.log("later 함수 끝");
  }

  console.log("첫 줄");
  later();
  console.log("마지막 줄");
  ```
  → `첫 줄`, `later 함수 실행`, `later 함수 끝`, `마지막 줄`, `later 안에서 예약한 타이머` 순서예요. `later()`를 부르면 함수 안의 줄은 바로 실행되지만(1단계), 그 안에서 예약한 타이머 콜백은 파일이 다 끝난 뒤에 실행돼요.

## 5단계: 블로킹·논블로킹은 다른 질문이다

동기·비동기와 비슷하게 들리지만 다른 것을 묻는 말이 있어요. **블로킹**과 **논블로킹**이에요.

- 동기·비동기는 "작업의 **결과를** 그 자리에서 받고 넘어가는가, 나중에 이어서 처리하는가?"를 물어요.
- 블로킹·논블로킹은 "작업을 기다리는 동안 **실행 흐름이 붙잡혀서** 다른 코드를 못 하는가?"를 물어요.

여기서 **스레드**라는 말이 나와요. 스레드는 코드를 한 줄씩 실행해 나가는 실행 흐름 하나예요. Node.js는 우리가 쓴 JavaScript 코드를 기본적으로 스레드 하나로 실행해요. 그래서 이 과정에서는 "그 스레드가 기다리는 동안 다음 코드를 실행할 수 있는가?"를 봐요.

**블로킹**은 작업이 끝나기를 기다리느라 그 스레드가 다음 코드를 진행하지 못하는 상황이에요. 파이썬의 `time.sleep(2)`가 그래요. 2초 동안 그 아래 줄로 못 가요. **논블로킹**은 기다리는 동안 스레드를 붙잡아 두지 않는 방식이에요. `setTimeout`이 그래요. 예약만 하고 스레드는 바로 다음 코드를 실행했죠.

아래 두 파일은 둘 다 "2초를 기다린다"는 코드지만 결과가 달라요. 하나는 타이머로 기다리고, 하나는 `while` 반복으로 2초가 될 때까지 계속 시각을 검사해요. `while` 쪽은 2초 동안 스레드가 반복문에 붙잡혀서 그 아래 줄로 못 가요.

블로킹이라고 컴퓨터 전체가 멈추는 건 아니에요. 브라우저나 VS Code는 그대로 움직여요. 붙잡히는 건 그 Node 프로그램의 JavaScript 실행 흐름이에요. 실제 파일 읽기로 블로킹을 보는 건 03회차에서 해요.

### ▶ 직접 해 보기 — `nonblocking.js`, `blocking.js`
```javascript
// nonblocking.js — 타이머로 2초 기다리기
const start = Date.now();

setTimeout(() => {
  console.log("나중에 실행:", Date.now() - start, "ms 뒤");
}, 2000);

console.log("지금 진행할 수 있는 작업:", Date.now() - start, "ms 뒤");
```
```text
지금 진행할 수 있는 작업: 0 ms 뒤
나중에 실행: 2002 ms 뒤
```
```javascript
// blocking.js — 반복문으로 2초 기다리기 (관찰용, 실제로는 이렇게 쓰지 않아요)
const start = Date.now();

const endTime = Date.now() + 2000;

while (Date.now() < endTime) {
  // 2초가 될 때까지 조건만 계속 검사해요
}

console.log("반복으로 2초 기다림 끝:", Date.now() - start, "ms 뒤");

console.log("지금 진행할 수 있는 작업:", Date.now() - start, "ms 뒤");
```
```text
반복으로 2초 기다림 끝: 2000 ms 뒤
지금 진행할 수 있는 작업: 2001 ms 뒤
```
`지금 진행할 수 있는 작업`이 첫 파일은 0 ms에, 두 번째 파일은 2001 ms에 찍혔어요. 두 번째 파일은 2초 동안 스레드가 붙잡혀 있었어요.

**바꿔 보기**
- `blocking.js`의 `2000`을 `10000`으로 바꾸고 실행한 뒤, 10초를 기다리지 말고 터미널에서 `Ctrl + C`를 눌러요. 프로그램이 바로 끝나요. JavaScript 스레드가 반복문에 붙잡혀 있어도 터미널과 운영체제는 따로 움직이니까 끝낼 수 있어요. `2000`으로 되돌려요.

## 6단계: 오래 걸리는 계산은 타이머도 늦춘다 — 이벤트 루프

4단계에서 0초 타이머는 "지금 코드가 다 끝난 뒤"에 실행됐어요. 그러면 지금 코드가 오래 걸리면 어떻게 될까요? 강의의 `busy.js`가 이걸 확인해요. 5단계의 `while` 반복을 그대로 써요.

- `Date.now()`는 지금 시각을 밀리초 숫자로 돌려줘요.
- `const endTime = Date.now() + 2000;`은 지금부터 2초 뒤의 시각이에요.
- `while (Date.now() < endTime) { }`는 그 시각이 될 때까지 조건 검사를 계속 반복해요.

이 반복문은 쉬면서 기다리는 코드가 아니에요. CPU를 계속 쓰면서 스레드를 2초 동안 붙잡아요. 0초 타이머는 1밀리초 뒤에 이미 실행할 준비가 됐지만, 스레드가 반복문을 돌고 있어서 실행할 수 없어요. 타이머는 실행 중인 JavaScript를 중간에 끊지 못해요. 그래서 반복이 끝나고 `3. 반복 종료`가 찍힌 다음에야 타이머 콜백이 실행돼요.

이 흐름을 맡는 구조가 **이벤트 루프**예요. Node는 이런 순서로 움직여요.

1. 지금 코드(`node 파일.js`로 시작한 파일)를 끝까지 실행해요. 그동안 `setTimeout`을 만나면 예약 목록에 올려요.
2. 지금 코드가 끝나면 예약 목록을 봐요. 시간이 다 된 콜백이 있으면 실행해요.
3. 그 콜백이 끝나면 다시 예약 목록을 봐요. 이걸 반복해요.
4. 기다리는 예약이 하나도 없으면 프로그램을 끝내요.

실제 Node는 작업 종류별로 단계가 더 있지만, 지금은 두 가지만 기억하면 돼요. 타이머를 예약했다고 지금 코드가 멈추지는 않아요. 그리고 지금 코드가 스레드를 오래 붙잡으면, 시간이 다 된 콜백도 늦어져요. 그래서 `setTimeout`의 지연 시간은 "정확히 이때 실행"이 아니라 "적어도 이만큼 지난 뒤 실행"이라는 뜻이에요.

시간을 늦추고 싶을 때 이런 `while` 반복을 쓰면 안 돼요. 그동안 다른 콜백이 하나도 실행되지 못해요. `busy.js`는 실행 순서를 관찰하려고 일부러 만든 예제예요.

### ▶ 직접 해 보기 — `busy.js`
강의 7장 코드예요.
```javascript
console.log("1. 시작");

setTimeout(() => {
  console.log("2. 타이머 콜백 실행");
}, 0);

const endTime = Date.now() + 2000;

while (Date.now() < endTime) {
  // 실행 순서를 관찰하기 위한 반복입니다.
}

console.log("3. 반복 종료");
```
```text
1. 시작
```
약 2초 뒤:
```text
3. 반복 종료
2. 타이머 콜백 실행
```

**바꿔 보기**
- 0초 타이머가 실제로 언제 실행됐는지 재 봐요. 맨 위에 `const start = Date.now();`를 넣고, 두 출력문을 `console.log("2. 타이머 콜백 실행:", Date.now() - start, "ms 뒤");`, `console.log("3. 반복 종료:", Date.now() - start, "ms 뒤");`로 바꿔요.
  ```text
  1. 시작
  3. 반복 종료: 2001 ms 뒤
  2. 타이머 콜백 실행: 2001 ms 뒤
  ```
  0초로 예약한 콜백이 2001 ms 뒤에 실행됐어요. 숫자는 실행할 때마다 몇 ms씩 달라져요.
- 이어서 `const endTime` 줄부터 `while` 블록 끝까지 지워요. → `3. 반복 종료: 1 ms 뒤`, `2. 타이머 콜백 실행: 2 ms 뒤`. 스레드를 붙잡는 코드가 없으면 0초 타이머는 거의 바로 실행돼요. 되돌려요.

## 7단계: 이미 써 본 `await`와 연결하기

Node 04회차에서 쓴 요청 코드를 다시 볼게요 (강의 9장).

```javascript
async function loadStudents() {
  const response = await fetch(
    "http://localhost:8080/api/students"
  );

  const students = await response.json();

  console.log(students);
}
```

`8080/api/students`는 Spring 06회차 서버의 학생 API 주소예요. Node 과정에서는 같은 흐름을 `http://localhost:3000/students`로 썼어요. 주소만 다르고 `await` 흐름은 같아요.

이 함수는 응답이 올 때까지 `await` 다음 줄로 가지 않아요. 그런데 이 "기다림"은 5단계의 `while`과 달라요. `await`를 만나면 **그 함수만** 거기서 멈추고, 함수를 부른 바깥 코드로 돌아가 다음 줄을 계속 실행해요. 결과가 준비되고 지금 실행 중인 코드가 끝나면, 함수가 멈췄던 다음 줄부터 이어서 실행돼요. 스레드는 그동안 붙잡혀 있지 않아요.

하나 더 있어요. `async` 함수를 부르면 첫 번째 `await`를 만나기 전까지의 줄은 **부르자마자 바로** 실행돼요. 1단계에서 본 보통 함수 호출과 같아요. 함수가 멈추는 건 `await`를 만난 그 줄부터예요.

그래서 "`await`가 있다 → 프로그램 전체가 멈춘다"라고 판단하면 출력 순서를 틀려요. 대신 두 가지를 나눠서 물어요. 어느 함수가 기다리는가? 그동안 스레드는 다른 코드를 실행할 수 있는가?

서버 없이 이 흐름을 보려고, 1초 뒤에 끝나는 작업을 만드는 `wait` 함수를 써요. `wait` 안의 `new Promise` 모양은 02회차에서 배워요. 지금은 `await wait(1000);`을 "1초짜리 작업이 끝날 때까지 이 함수만 기다린다"로 읽으면 돼요. 파이썬을 안다면 `asyncio`의 `await asyncio.sleep(1)`과 같은 생각이에요.

### ▶ 직접 해 보기 — `await-order.js`
실행 전에 네 줄의 순서를 먼저 적어 봐요.
```javascript
// ms 밀리초 뒤에 끝나는 작업을 만들어요. 모양은 02회차에서 배워요.
function wait(ms) {
  return new Promise((resolve) => {
    setTimeout(resolve, ms);
  });
}

async function loadStudents() {
  console.log("함수 안: 요청 보냄");

  await wait(1000);

  console.log("함수 안: 응답 받음");
}

console.log("함수 부르기 전");

loadStudents();

console.log("함수 밖: 기다리는 동안 실행");
```
```text
함수 부르기 전
함수 안: 요청 보냄
함수 밖: 기다리는 동안 실행
함수 안: 응답 받음
```
`함수 안: 요청 보냄`은 `await` 앞이라 부르자마자 찍혔어요. `await`에서 함수가 멈추자 바깥의 `함수 밖: 기다리는 동안 실행`이 찍혔고, 약 1초 뒤 `함수 안: 응답 받음`이 찍혔어요.

**바꿔 보기**
- `await wait(1000);`을 `await wait(0);`으로 바꿔요. → 출력 순서가 그대로예요. 기다릴 시간이 0이어도 `await` 다음 줄은 바깥 코드가 다 끝난 뒤에 실행돼요. 02회차 5단계에서 더 자세히 봐요. 되돌려요.
- 맨 위에 `const start = Date.now();`를 넣고, `함수 안: 응답 받음` 출력문을 `console.log("함수 안: 응답 받음:", Date.now() - start, "ms 뒤");`로 바꿔요. 그리고 파일 맨 아래에 3초 반복을 붙여요.
  ```javascript
  const endTime = Date.now() + 3000;

  while (Date.now() < endTime) {
    // 함수 밖에서 3초 동안 실행 스레드를 붙잡아요
  }

  console.log("함수 밖: 3초 반복 끝:", Date.now() - start, "ms 뒤");
  ```
  ```text
  함수 부르기 전
  함수 안: 요청 보냄
  함수 밖: 기다리는 동안 실행
  함수 밖: 3초 반복 끝: 3001 ms 뒤
  함수 안: 응답 받음: 3001 ms 뒤
  ```
  함수가 기다리던 1초는 진작 지났지만, 바깥 코드가 스레드를 붙잡고 있어서 이어서 실행하지 못했어요. 6단계와 같은 이유예요. 추가한 줄을 지워요.
- `async function loadStudents()`에서 `async`를 지워요.
  ```text
  SyntaxError: await is only valid in async functions and the top level bodies of modules
  ```
  함수 안에서 `await`를 쓰려면 그 함수에 `async`가 있어야 해요. 이건 문법 오류라서 Node가 실행 전에 찾아내요. 그래서 `함수 부르기 전`도 찍히지 않아요. 되돌려요.

## 마무리: `final.js` 한 번 실행에 일어나는 일

오늘 본 것을 한 파일에 모았어요. 실행 전에 순서를 먼저 적어 보고 실행해요.

```javascript
const start = Date.now();

function wait(ms) {
  return new Promise((resolve) => {
    setTimeout(resolve, ms);
  });
}

async function loadStudents() {
  console.log("함수 안: 요청 보냄");

  await wait(500);

  console.log("함수 안: 응답 받음:", Date.now() - start, "ms 뒤");
}

console.log("시작");

setTimeout(() => {
  console.log("0초 타이머:", Date.now() - start, "ms 뒤");
}, 0);

const doubled = [1, 2, 3].map((number) => number * 2);
console.log("map 결과:", doubled);

loadStudents();

console.log("함수 밖: 다음 줄");

const endTime = Date.now() + 1000;

while (Date.now() < endTime) {
  // 1초 동안 실행 스레드를 붙잡아요
}

console.log("반복 끝:", Date.now() - start, "ms 뒤");
```

```text
시작
map 결과: [ 2, 4, 6 ]
함수 안: 요청 보냄
함수 밖: 다음 줄
반복 끝: 1001 ms 뒤
0초 타이머: 1001 ms 뒤
함수 안: 응답 받음: 1001 ms 뒤
```

위에서부터 이렇게 실행돼요.

1. `start`에 지금 시각을 적고, `wait`와 `loadStudents` 함수를 정의해요. 정의만 해서는 아무것도 실행되지 않아요.
2. `시작`을 찍어요.
3. `setTimeout`이 콜백을 0초로 예약 목록에 올리고, 바로 다음 줄로 가요 (2·4단계).
4. `map`이 콜백을 그 자리에서 세 번 실행해 `[2, 4, 6]`을 만들고, `map 결과`를 찍어요 (3단계).
5. `loadStudents()`를 불러요. 첫 `await` 앞의 `함수 안: 요청 보냄`이 바로 찍혀요. `wait(500)`이 500ms 타이머를 예약하고, `await`에서 함수가 멈춰요. 실행은 함수를 부른 자리로 돌아와요 (7단계).
6. `함수 밖: 다음 줄`을 찍어요.
7. `while` 반복이 스레드를 1초 동안 붙잡아요. 그사이 0초 타이머와 500ms 타이머 모두 시간이 다 되지만, 실행되지 못해요 (5·6단계).
8. `반복 끝: 1001 ms 뒤`를 찍어요. 파일의 마지막 줄이라 지금 코드가 끝나요.
9. 이벤트 루프가 예약 목록을 봐요. 시간이 짧은 0초 타이머부터 실행해 `0초 타이머: 1001 ms 뒤`를 찍어요 (4·6단계).
10. 500ms 타이머가 실행되면 `wait(500)`이 끝나요. 멈춰 있던 `loadStudents`가 `await` 다음 줄부터 이어서 `함수 안: 응답 받음`을 찍어요.
11. 남은 예약이 없으니 프로그램이 끝나요.

## 다음 회차와 연결

7단계와 마무리에서 `wait` 함수 안의 `new Promise((resolve) => { … })`를 설명 없이 썼어요. 02회차에서 이 모양을 배워요. **Promise**는 나중에 준비되는 결과를 다루는 객체이고, `resolve`는 그 결과가 준비됐다고 알리는 함수예요. 타이머 콜백 안에서 `return`한 값은 왜 바깥으로 나오지 않는지, 결과를 `.then()`과 `await`로 받는 방법, 실패했을 때 `.catch()`와 `try/catch/finally`로 처리하는 방법도 봐요. 마지막에는 1초짜리 작업 두 개를 차례로 기다리면 약 2초, `Promise.all()`로 함께 시작하면 약 1초 걸리는 것을 직접 재요.

오늘 정한 규칙은 02회차에서도 그대로 써요. `await` 다음 줄, `.then()`에 넘긴 함수도 "지금 실행 중인 코드가 다 끝난 뒤"에 실행돼요.

| 실행하자마자 `SyntaxError`만 나오고 출력이 하나도 없음 | 문법 오류는 실행 전에 검사함. 오류 위쪽에 찍힌 파일 이름과 줄 번호 확인 (7단계) |
| `await` 다음 줄이 바깥 코드보다 늦게 찍힘 | 정상. `await`는 그 함수만 멈춤 (7단계) |
