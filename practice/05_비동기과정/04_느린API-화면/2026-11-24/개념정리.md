## 들어가며

**🧭 맥락 — 지금 어디쯤**

Node과정 04회차에서 React 화면이 Express 서버(3000)에 `fetch`로 학생 목록을 요청했어요. 화면이 처음 나타날 때 `useEffect`로 요청하고 로딩·오류·빈 목록을 보여 줬죠. 그때 서버는 바로 응답해서 로딩 문구는 거의 보이지 않았어요.

비동기과정 03회차에서는 서버 쪽을 봤어요. `setTimeout`으로 3초를 기다리는 `/slow-nonblocking`은 기다리는 동안 다른 요청도 처리했고, `while`로 3초 계산하는 `/slow-blocking`은 다른 요청까지 늦췄어요.

04회차에서 기다리는 쪽은 **브라우저 화면**이에요. 서버가 일부러 3초 늦게 응답하게 만들고, 그 3초 동안 화면이 어떻게 보여야 하는지 만들어요. 아무 안내가 없으면 사용자는 버튼이 안 눌린 줄 알고 여러 번 눌러요. 오늘 만드는 화면은 이렇게 동작해요.

- 버튼을 눌러야 요청해요 (`useEffect` 없음).
- 요청 중에는 "서버 응답을 기다리는 중입니다."를 보여 주고, 요청 버튼을 누를 수 없게 막아요.
- 성공하면 목록, 학생이 없으면 "등록된 학생이 없습니다.", 실패하면 오류 안내를 보여 줘요.
- 기다리는 동안에도 다른 버튼(카운터)은 눌려요.

마지막 7단계에서는 같은 "3초 기다림"이 Node.js 서버와 Spring MVC 서버에서 어떻게 다른지 비교해요.

팀 프로젝트(실시간 채팅)에서도 같은 구조를 써요. 지난 메시지를 불러오는 동안 로딩을 보여 주고, 메시지를 보내는 중에는 전송 버튼을 막아 같은 메시지가 두 번 가지 않게 하고, 서버가 꺼졌으면 안내를 보여 줘요.

## 1단계: 느린 API — 타이머 콜백에서 응답한다

🧭 03회차 `/slow-nonblocking`과 같은 방식이에요. 이번에는 응답이 글자가 아니라 학생 목록 JSON이에요.

실제 서버도 느릴 때가 있어요. DB에서 많은 데이터를 찾거나, 다른 서버에 다시 요청하거나, 네트워크가 느릴 때예요. 내 컴퓨터에서는 응답이 너무 빨라서 그런 상황을 보기 어려워요. 그래서 일부러 3초 늦게 응답하는 서버를 만들어요.

방법은 `res.json(students)`를 바로 부르지 않고 `setTimeout` 콜백 안에서 부르는 거예요. 핸들러는 타이머를 예약하고 바로 끝나요. 3초 뒤 콜백이 실행되면서 응답을 보내요. 03회차에서 본 것처럼 반복문으로 3초 계산하는 게 아니라서, 기다리는 동안에도 서버는 다른 요청을 받아요. 7단계에서 다시 재 봐요.

`cors`는 Node과정 04회차에서 쓴 패키지예요. `5173`에서 열린 화면이 `3002` 서버의 응답을 읽으려 하면, 브라우저는 서버가 허락했는지 확인해요. 주소의 포트가 다르면 다른 출처로 보기 때문이에요. `cors({ origin: "http://localhost:5173" })`는 응답에 "`5173`에서 온 화면은 읽어도 된다"는 머리글(`Access-Control-Allow-Origin`)을 붙여요. curl이나 주소창으로 직접 열 때는 이 검사를 하지 않아요.

### ▶ 직접 해 보기 — `slow-server.js` (강의 코드, 주소 하나)

`_async연습장`에 새 파일 `slow-server.js`를 만들어요.

```javascript
const express = require("express");
const cors = require("cors");

const app = express();
const PORT = 3002;

app.use(
  cors({
    origin: "http://localhost:5173"
  })
);

const students = [
  { id: 1, name: "한코딩" },
  { id: 2, name: "이학생" },
  { id: 3, name: "박학생" }
];

app.get("/students", (req, res) => {
  console.log("학생 목록 요청 도착");

  setTimeout(() => {
    console.log("학생 목록 응답");

    res.json(students);
  }, 3000);
});

app.listen(PORT, () => {
  console.log(`서버 실행 중: http://localhost:${PORT}`);
});
```

```bash
node slow-server.js
```

```text
서버 실행 중: http://localhost:3002
```

브라우저 새 탭에서 `http://localhost:3002/students`를 열면 3초쯤 로딩이 돌다가 학생 목록 JSON이 보여요. 서버 터미널에는 `학생 목록 요청 도착`이 바로, `학생 목록 응답`이 3초 뒤에 찍혀요.

터미널을 하나 더 열어(+) curl로 시간과 머리글을 봐요. `-i`는 응답 머리글까지 보여 줘요.

```bash
curl -s -w "  (%{time_total}초)\n" http://localhost:3002/students
```

```text
[{"id":1,"name":"한코딩"},{"id":2,"name":"이학생"},{"id":3,"name":"박학생"}]  (3.015855초)
```

```bash
curl -s -i http://localhost:3002/students
```

```text
HTTP/1.1 200 OK
X-Powered-By: Express
Access-Control-Allow-Origin: http://localhost:5173
Vary: Origin
Content-Type: application/json; charset=utf-8
…
[{"id":1,"name":"한코딩"},{"id":2,"name":"이학생"},{"id":3,"name":"박학생"}]
```

**바꿔 보기**
- `app.use(` … `);` 다섯 줄을 지우고 서버를 다시 켜서 `curl -s -i` → `Access-Control-Allow-Origin` 줄과 `Vary: Origin` 줄이 사라져요. curl은 그래도 데이터를 받지만, 3단계 화면에서는 브라우저가 응답을 읽지 못하게 막아서 오류 안내가 떠요. 되돌리고 서버를 다시 켜요.

## 2단계: 오류 응답 API — `res.status(500)`

🧭 화면에서 실패를 처리하려면 실패하는 요청이 필요해요. 서버가 꺼진 경우(6단계)와 다른 종류의 실패예요.

서버에 연결은 됐는데 요청 처리가 실패할 때가 있어요. 그러면 서버는 **상태 코드**로 실패를 알려요. 상태 코드는 응답 첫 줄의 세 자리 숫자로, 결과가 어땠는지 나타내요. `200`은 성공, `404`는 그런 주소가 없음, `500`은 서버 안에서 오류가 남이에요. Express는 따로 정하지 않으면 `200`을 보내요. `res.status(500)`은 상태 코드를 `500`으로 정하고, 이어서 `.json({ message: … })`로 오류 설명을 보내요.

중요한 점은, 이때도 서버는 **응답을 보냈다**는 거예요. 서버는 켜져 있고, "실패했다"는 내용의 응답이 정상적으로 도착해요. 6단계에서 이 차이를 화면에서 확인해요.

### ▶ 직접 해 보기 — `/students-error` 추가

`slow-server.js`의 `app.listen(` 바로 위에 붙여 넣고 서버를 다시 켜요 (`Ctrl + C` → `node slow-server.js`).

```javascript
app.get("/students-error", (req, res) => {
  setTimeout(() => {
    res.status(500).json({
      message: "학생 목록 처리 중 오류가 발생했습니다."
    });
  }, 1500);
});
```

```bash
curl -s -i -w "\n(%{time_total}초)\n" http://localhost:3002/students-error
```

```text
HTTP/1.1 500 Internal Server Error
X-Powered-By: Express
Access-Control-Allow-Origin: http://localhost:5173
Vary: Origin
Content-Type: application/json; charset=utf-8
…
{"message":"학생 목록 처리 중 오류가 발생했습니다."}
(1.515867초)
```

첫 줄이 `500 Internal Server Error`이고, 1.5초 뒤에 오류 설명 JSON이 왔어요. 이 경로는 `console.log`가 없어서 서버 터미널에는 아무것도 안 찍혀요.

**바꿔 보기**
- 없는 주소 `curl -s -i http://localhost:3002/student` (`s` 빠뜨림) → `HTTP/1.1 404 Not Found`와 `<pre>Cannot GET /student</pre>`가 든 HTML. 만들지 않은 주소에는 Express가 404를 보내요. 6단계에서 화면으로도 확인해요.

## 3단계: 버튼으로 요청하고, state 다섯 개로 상황을 나눈다

🧭 Node과정 04에서는 화면이 처음 나타날 때 `useEffect`로 요청했어요. 이번에는 **버튼을 눌렀을 때만** 요청해요.

사용자의 클릭은 이벤트 핸들러에서 처리하니까, 요청도 클릭할 때 부르는 함수 `loadStudents(path)` 안에서 해요. 그래서 `useEffect`는 쓰지 않아요. `onClick={() => loadStudents("/students")}`처럼 화살표 함수로 감싼 건, 값을 넘겨서 불러야 하기 때문이에요. `onClick={loadStudents("/students")}`라고 쓰면 화면을 그릴 때 바로 실행돼 버려요 (React과정 07).

화면이 구분해야 하는 상황은 요청 전·요청 중·실패·빈 결과·성공이에요. 이걸 state 다섯 개로 나눠요. `students`(받은 목록, 처음 `[]`), `isLoading`(요청 중인지, 처음 `false`), `error`(화면에 보여 줄 오류 문장, 처음 `""`), `hasLoaded`(조회에 성공한 적 있는지, 처음 `false`), 그리고 5단계에서 설명할 `count`예요. `isLoading`이 처음 `false`인 건 버튼을 누르기 전에는 요청 중이 아니기 때문이에요. 처음부터 요청하던 Node과정 04는 `true`였어요.

`hasLoaded`가 따로 필요한 이유가 있어요. `students`가 `[]`인 경우는 두 가지예요. 아직 요청을 안 해서 비어 있을 수도 있고, 요청했는데 학생이 한 명도 없어서 비어 있을 수도 있어요. `students.length === 0`만으로는 둘을 구분할 수 없어서, "성공한 적 있다"를 따로 기록해요.

`loadStudents`는 네 부분으로 나뉘어요. ① **시작**: `setIsLoading(true)`로 로딩을 켜고, 이전 오류·결과를 지워요 (`setError("")`, `setHasLoaded(false)`, `setStudents([])`). ② **성공**: `try` 안에서 `fetch`로 요청하고, `response.ok`로 성공 응답인지 확인한 뒤(6단계), JSON을 받아 `setStudents(data)`, `setHasLoaded(true)`. ③ **실패**: 중간에 오류가 나면 `catch`로 와서 Console에 오류를 찍고 화면용 문장을 `setError`에 넣어요. ④ **마무리**: `finally`에서 `setIsLoading(false)`. 성공해도 실패해도 꼭 실행돼요 (02회차 `try/catch/finally`). `catch (error)`의 `error`는 그 블록 안에서만 쓰는 오류 객체이고, state `error`와 이름만 같은 다른 값이에요.

함수 첫 줄의 `if (isLoading) { return; }`은 이미 요청 중이면 아무것도 하지 않고 끝내는 검사예요. 4단계에서 자세히 봐요.

### ▶ 직접 해 보기 — `SlowStudentList.jsx` 1단계 (강의 실습 2 + 확인용 줄)

`_react연습장`에 새 파일 `src/components/SlowStudentList.jsx`를 만들어요. 강의 실습 2 코드에 **확인용 줄** 하나를 더했어요. state 값을 글자로 보여 주는 줄이에요. JSX는 `true`·`false`를 화면에 안 그려서 `String()`으로 글자로 바꿨어요. 4단계에서 파일 전체를 바꾸면서 없어져요.

```jsx
import { useState } from "react";

function SlowStudentList() {
  const [students, setStudents] = useState([]);
  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState("");
  const [hasLoaded, setHasLoaded] = useState(false);

  async function loadStudents(path) {
    if (isLoading) {
      return;
    }

    setIsLoading(true);
    setError("");
    setHasLoaded(false);
    setStudents([]);

    try {
      const response = await fetch(
        `http://localhost:3002${path}`
      );

      if (!response.ok) {
        throw new Error(
          `학생 목록 요청에 실패했습니다. 상태 코드: ${response.status}`
        );
      }

      const data = await response.json();

      setStudents(data);
      setHasLoaded(true);
    } catch (error) {
      console.error(error);

      setError(
        "학생 목록을 불러오지 못했습니다. 서버와 요청 주소를 확인해주세요."
      );
    } finally {
      setIsLoading(false);
    }
  }

  return (
    <section>
      <h2>학생 목록 조회</h2>

      <button
        type="button"
        onClick={() => loadStudents("/students")}
      >
        학생 목록 불러오기
      </button>

      {/* 확인용 줄 (강의 코드에 없음): state 값을 글자로 보여 줘요 */}
      <p>
        isLoading: {String(isLoading)} / hasLoaded: {String(hasLoaded)} /
        학생 {students.length}명 / error: {error}
      </p>
    </section>
  );
}

export default SlowStudentList;
```

## 4단계: 요청 중 버튼 막기와 화면 표시 순서

🧭 3단계 화면은 요청 중인지 사용자가 알 수 없고, 버튼도 계속 눌려요. 이번 단계에서 둘 다 고쳐요.

**버튼 막기.** 버튼에 `disabled={isLoading}`을 붙이면, `isLoading`이 `true`인 동안 버튼이 비활성화돼서 눌러도 아무 일이 없어요. 버튼 글자도 `{isLoading ? "불러오는 중..." : "학생 목록 불러오기"}`로 바꿔서 지금 요청 중임을 보여 줘요. 오류 실험용 **오류 응답 테스트** 버튼(`/students-error` 요청)도 추가하고, 같이 `disabled={isLoading}`을 붙여요. 한 요청이 진행되는 동안 두 요청 버튼을 모두 막는 거예요.

그러면 함수 첫 줄의 `if (isLoading) return;`은 왜 남겨 둘까요? 강의는 이걸 **보조** 검사라고 해요. 함수 안의 `isLoading`은 그 함수가 만들어진 렌더링 때의 값이에요 (React과정 07 state 스냅샷). 따로따로 누른 두 번의 클릭이라면, 두 번째 클릭 전에 화면이 다시 그려져서 새 함수는 `isLoading`이 `true`인 걸 봐요. 그래서 이 검사만으로도 두 번째 요청이 막혀요 (아래 바꿔 보기에서 확인해요). 하지만 한 번의 클릭 안에서 `loadStudents`를 두 번 부르면, 둘 다 같은 렌더링의 `false`를 봐서 요청이 두 번 가요. 복사본에서 `onClick` 안에 `loadStudents("/students");`를 두 번 넣어 보니 실제로 요청이 두 번 갔어요. 그래서 화면에서는 `disabled`가 주된 막기예요.

그리고 `disabled`는 **화면에서만** 막는 거예요. 사용자가 개발자 도구로 요청을 직접 보내거나, 새로고침 후 다시 보낼 수도 있어요. 회원 가입이나 결제처럼 두 번 실행되면 곤란한 작업은 서버에서도 중복을 막도록 따로 만들어야 해요.

**화면 표시 순서.** 버튼 아래에는 상황에 맞는 문단 하나만 보여 줘요. 삼항 연산자를 이어 써서 위에서부터 차례로 확인해요 (React과정 06). ① `isLoading`이면 로딩 안내 → ② 아니고 `error`가 있으면 오류 안내 → ③ 아니고 `hasLoaded`면 학생 수가 0인지 보고 "등록된 학생이 없습니다." 또는 목록 → ④ 다 아니면(아직 안 불렀으면) 시작 안내. 순서가 중요해요. 로딩 중인지를 가장 먼저 봐야 이전 오류나 이전 목록이 로딩 중에 섞여 보이지 않아요. `role="status"`는 화면 읽기 프로그램에 "상태 안내"라고, `role="alert"`는 "주의가 필요한 안내"라고 알려 주는 속성이에요. 보이는 모양은 바뀌지 않아요.

### ▶ 직접 해 보기 — `SlowStudentList.jsx` 최종 (강의 실습 3, 전체 바꾸기)

강의 최종 코드예요. 맨 아래 카운터(`count`, 숫자 증가 버튼)는 5단계에서 설명해요. 파일 전체를 바꿔요.

```jsx
import { useState } from "react";

function SlowStudentList() {
  const [students, setStudents] = useState([]);
  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState("");
  const [hasLoaded, setHasLoaded] = useState(false);
  const [count, setCount] = useState(0);

  async function loadStudents(path) {
    if (isLoading) {
      return;
    }

    setIsLoading(true);
    setError("");
    setHasLoaded(false);
    setStudents([]);

    try {
      const response = await fetch(
        `http://localhost:3002${path}`
      );

      if (!response.ok) {
        throw new Error(
          `학생 목록 요청에 실패했습니다. 상태 코드: ${response.status}`
        );
      }

      const data = await response.json();

      setStudents(data);
      setHasLoaded(true);
    } catch (error) {
      console.error(error);

      setError(
        "학생 목록을 불러오지 못했습니다. 서버와 요청 주소를 확인해주세요."
      );
    } finally {
      setIsLoading(false);
    }
  }

  return (
    <section className="slow-student-list">
      <h2>느린 학생 목록 API</h2>

      <div className="request-buttons">
        <button
          type="button"
          onClick={() => loadStudents("/students")}
          disabled={isLoading}
        >
          {isLoading
            ? "불러오는 중..."
            : "학생 목록 불러오기"}
        </button>

        <button
          type="button"
          onClick={() => loadStudents("/students-error")}
          disabled={isLoading}
        >
          오류 응답 테스트
        </button>
      </div>

      {isLoading ? (
        <p role="status">
          서버 응답을 기다리는 중입니다.
        </p>
      ) : error ? (
        <p role="alert">{error}</p>
      ) : hasLoaded ? (
        students.length === 0 ? (
          <p>등록된 학생이 없습니다.</p>
        ) : (
          <ul>
            {students.map((student) => (
              <li key={student.id}>
                {student.name}
              </li>
            ))}
          </ul>
        )
      ) : (
        <p>버튼을 눌러 학생 목록을 조회해주세요.</p>
      )}

      <div className="counter-area">
        <p>카운터: {count}</p>

        <button
          type="button"
          onClick={() =>
            setCount((prevCount) => prevCount + 1)
          }
        >
          숫자 증가
        </button>
      </div>
    </section>
  );
}

export default SlowStudentList;
```

저장하고 브라우저에서 해 봐요.
1. 처음 → 버튼 **학생 목록 불러오기**, **오류 응답 테스트**와 "버튼을 눌러 학생 목록을 조회해주세요.", "카운터: 0"
2. 학생 목록 불러오기 → 바로 첫 버튼 글자가 **불러오는 중...**으로 바뀌고 두 요청 버튼이 비활성화돼요. 문단은 "서버 응답을 기다리는 중입니다."
3. 그 상태에서 두 요청 버튼을 눌러 봐요 → 아무 일도 없어요. 서버 터미널의 `학생 목록 요청 도착`도 한 번뿐이에요.
4. 약 3초 뒤 → 한코딩·이학생·박학생 목록, 두 버튼이 다시 눌려요.
5. 빈 목록: `slow-server.js`의 `const students = [` … `];`를 잠시 `const students = [];`로 바꾸고 서버를 다시 켠 뒤 불러오기 → 3초 뒤 "등록된 학생이 없습니다." 확인하면 원래 세 명으로 되돌리고 서버를 다시 켜요.

**바꿔 보기** (하나씩 하고 되돌려요)
- 두 요청 버튼의 `disabled={isLoading}` 줄을 지우기 → 로딩 중에도 버튼이 흐려지지 않고 눌려요. 그래도 불러오기를 다시 눌렀을 때 요청은 한 번만 가요. 함수 첫 줄 `if (isLoading)` 검사가 막았어요.
- 위 상태에서 `if (isLoading) {` … `}` 세 줄까지 지우기 → 빠르게 두 번 누르면 서버 터미널에 `학생 목록 요청 도착`이 두 번 찍혀요.
- `} finally {`를 `}`로 바꾸고, 그 아래 `setIsLoading(false);`와 `}` 두 줄을 지우기 → 3초가 지나도 "서버 응답을 기다리는 중입니다."와 비활성 버튼이 그대로예요. 목록은 도착했지만 로딩을 끄는 줄이 없어서, 표시 순서 ①에서 계속 걸려요.

## 5단계: 기다리는 동안 다른 버튼 누르기 — 카운터

🧭 01회차부터 본 "`await`는 그 함수 안만 기다린다"를 화면에서 확인해요.

`loadStudents` 안의 `await fetch(…)`는 응답이 올 때까지 **그 함수의 다음 줄**을 미뤄요. 그동안 브라우저의 JavaScript 실행 스레드는 비어 있어서, 다른 클릭이나 다른 state 변경을 처리할 수 있어요. 이걸 보려고 요청과 상관없는 카운터를 붙였어요. `const [count, setCount] = useState(0);`와 맨 아래 `counter-area` 부분이에요.

`setCount((prevCount) => prevCount + 1)`은 이전 값을 받아 1 더한 값으로 바꾸는 함수형 업데이트예요 (React과정 07). 카운터 버튼에는 `disabled={isLoading}`을 **붙이지 않아요**. 요청과 상관없는 기능이니 기다리는 동안에도 써야 하기 때문이에요. 막아야 하는 건 같은 요청을 또 보내는 버튼뿐이에요.

정리하면 두 가지가 달라요. 조회 함수의 진행이 기다리는 것과, 실행 스레드가 막히는 것이에요. 요청 함수는 3초를 기다리지만 실행 스레드는 막히지 않아요.

### ▶ 직접 해 보기 — 4단계 파일 그대로

1. 학생 목록 불러오기 → 로딩 문구가 보이는 동안 **숫자 증가**를 세 번 → "서버 응답을 기다리는 중입니다." 아래에서 "카운터: 3"으로 바로바로 바뀌어요.
2. 약 3초 뒤 → 목록이 나오고 "카운터: 3"은 그대로예요.

**바꿔 보기**
- 숫자 증가 버튼의 `type="button"` 아래에 `disabled={isLoading}`을 넣기 → 로딩 중에는 숫자 증가도 비활성화돼서, 세 번 눌러도 "카운터: 0"이에요. 기다림과 상관없는 기능까지 막으면 이렇게 돼요. 되돌려요.

## 6단계: HTTP 오류 응답과 응답을 받지 못한 것은 다르다

🧭 2단계에서 만든 `/students-error`(서버가 500을 보냄)와, 서버를 꺼서 응답이 아예 없는 경우를 비교해요.

`fetch()`는 서버가 **응답을 보내기만 하면** 성공으로 끝나요. 상태 코드가 500이어도 `fetch()` 자체는 실패하지 않아요. 그래서 상태 코드를 직접 확인해야 해요. `response.ok`는 상태 코드가 200~299이면 `true`, 아니면 `false`예요. `if (!response.ok)`에서 `throw new Error(…)`로 오류를 직접 던지면 `catch`로 넘어가요. `response.status`에는 상태 코드 숫자가 들어 있어서 오류 문장에 넣었어요.

서버가 꺼져 있으면 연결 자체가 안 돼요. 받은 응답이 없으니 상태 코드도 없어요. 이때는 `fetch()`가 실패(Promise 거부)해서 바로 `catch`로 가요.

두 경우 모두 `catch`에 와서 같은 안내 문장을 보여 주지만, 원인이 달라요. 원인은 Console의 오류와 Network 탭으로 구분해요.

### ▶ 직접 해 보기 — 오류 응답과 연결 실패

1. **오류 응답 테스트** → 로딩 문구, 약 1.5초 뒤 "학생 목록을 불러오지 못했습니다. 서버와 요청 주소를 확인해주세요." 버튼은 다시 눌려요. Console에는 우리 코드가 던진 오류가 찍혀요.
   ```text
   Error: 학생 목록 요청에 실패했습니다. 상태 코드: 500
   ```
2. 이어서 **학생 목록 불러오기** → 오류 안내가 사라지고 3초 뒤 목록이 나와요. 시작할 때 `setError("")`로 지웠기 때문이에요.
3. 서버 터미널에서 `Ctrl + C`로 서버를 끄고 **학생 목록 불러오기** → 기다리지 않고 바로 같은 오류 안내가 떠요. Chrome Console에는 `Failed to fetch`가 들어간 `TypeError`가 보여요. 서버를 다시 켜고(`node slow-server.js`) 누르면 정상으로 돌아와요.
4. 개발자 도구 **Network** 탭에서 세 요청을 비교해요. `students`는 `200`, `students-error`는 `500`이고, 서버를 끈 상태의 요청은 상태 코드 없이 실패(`(failed)`)로 보여요.

**바꿔 보기** (하나씩 하고 되돌려요)
- `if (!response.ok) {` … `}` 다섯 줄을 지우고 오류 응답 테스트 → 1.5초 뒤 **화면 전체가 하얘지고** Console에 `TypeError: students.map is not a function`이 찍혀요. 500 응답도 `fetch`는 성공이라, 오류 설명 객체 `{ message: … }`가 `students`에 저장됐어요. 객체에는 `map`이 없어서 목록을 그리다가 멈췄어요.
- 첫 버튼의 `loadStudents("/students")`를 `loadStudents("/student")`로 → 바로 오류 안내, Console에 `Error: 학생 목록 요청에 실패했습니다. 상태 코드: 404`. 주소를 잘못 쓴 실수도 같은 흐름으로 잡혀요.

## 7단계: Node.js와 Spring MVC에서의 기다림

🧭 03회차의 블로킹·논블로킹을 Spring과정 02회차의 Spring MVC 서버와 비교해요.

두 서버 모두 응답이 3초 늦을 수 있어요. 다른 건 **기다리는 동안 무엇이 붙잡혀 있느냐**예요.

이번 Node.js 서버는 `setTimeout`으로 타이머를 예약하고 핸들러를 끝내요. 하나뿐인 JavaScript 실행 스레드는 3초 동안 비어 있어서 다른 요청을 처리해요. 반대로 03회차 `/slow-blocking`처럼 `while`로 3초를 보내면 그 하나뿐인 스레드가 붙잡혀서 다른 요청이 모두 기다려요.

Spring MVC는 방식이 달라요. Spring Boot에 들어 있는 Tomcat은 요청 처리용 스레드를 여러 개 두고(기본 최대 200개), 요청마다 스레드 하나를 맡겨요. 컨트롤러에서 `Thread.sleep(3000);`을 실행하면 **그 요청을 맡은 스레드**가 3초 동안 기다려요. 다른 요청은 남은 다른 스레드가 처리해요. 그래서 다른 요청에도 응답하지만, 이유가 Node.js와 달라요. Node.js는 스레드 하나를 비워서, Spring MVC는 스레드를 여러 개 둬서 처리해요. Spring MVC의 스레드 구성에는 다른 방식도 있지만, 강의는 이 일반적인 방식으로 비교해요.

어느 서버든 브라우저 입장에서는 응답이 3초 뒤에 와요. 그래서 서버를 어떻게 만들든 화면에는 로딩·실패 안내가 필요해요.

### ▶ 직접 해 보기 — 요청 두 개를 겹쳐 보내기

서버를 켜 둔 채 세 번째 터미널에 한 줄로 붙여 넣어요. 03회차 6단계와 같은 방법이에요. `-o /dev/null`은 받은 JSON을 출력하지 않게 해요.

```bash
curl -s -o /dev/null -w "첫 번째  (%{time_total}초)\n" http://localhost:3002/students & sleep 1; curl -s -o /dev/null -w "두 번째  (%{time_total}초)\n" http://localhost:3002/students; wait
```

```text
[1] 83424
첫 번째  (3.010672초)
[1]  + done       curl -s -o /dev/null -w "첫 번째  (%{time_total}초)\n" …
두 번째  (3.003540초)
```

1초 간격으로 보낸 두 요청이 각각 3초씩 걸렸어요. 서버 터미널은 `학생 목록 요청 도착` → (1초 뒤) `학생 목록 요청 도착` → `학생 목록 응답` → (1초 뒤) `학생 목록 응답` 순서예요. 두 타이머가 함께 기다렸어요.

**바꿔 보기** — 서버를 블로킹으로 바꿔 보기
- `/students` 핸들러의 `setTimeout(() => {` … `}, 3000);`을 아래로 바꾸고 서버를 다시 켜요. 03회차 `/slow-blocking`과 같은 확인용 코드예요.
  ```javascript
  const endTime = Date.now() + 3000;
  while (Date.now() < endTime) {
    // 3초 동안 실행 스레드를 붙잡아요 (확인용)
  }
  console.log("학생 목록 응답");

  res.json(students);
  ```
  같은 curl → `첫 번째  (3.005088초)`, `두 번째  (5.005499초)`. 두 번째 요청은 1초에 도착했지만, 첫 번째 계산이 끝난 3초부터 자기 3초를 시작해서 6초에 끝났어요. 서버 로그도 `요청 도착` → `응답` → `요청 도착` → `응답`으로 하나씩 처리돼요. 확인하면 `setTimeout` 코드로 되돌리고 서버를 다시 켜요.

## 마무리: 학생 목록 불러오기를 한 번 누르면

1. 처음 그릴 때 state는 `students` `[]`, `isLoading` `false`, `error` `""`, `hasLoaded` `false`, `count` `0`이에요. 표시 순서 ④에 걸려 "버튼을 눌러 학생 목록을 조회해주세요."가 보여요.
2. 학생 목록 불러오기를 누르면 `loadStudents("/students")`가 실행돼요. `isLoading`이 `false`라서 첫 검사를 지나가요.
3. `setIsLoading(true)`와 초기화 세 줄로 state 변경을 예약하고, `fetch`로 `http://localhost:3002/students` 요청을 보내요. `await`에서 함수가 멈추고 클릭 처리가 끝나요.
4. React가 다시 그려요. `isLoading`이 `true`라서 두 요청 버튼은 비활성, 첫 버튼 글자는 "불러오는 중...", 표시 순서 ①의 로딩 안내가 보여요.
5. 서버는 요청을 받아 `학생 목록 요청 도착`을 찍고 3초 타이머를 예약해요. 그동안 서버도 브라우저도 실행 스레드가 비어 있어요. 숫자 증가를 누르면 카운터가 바로 바뀌어요.
6. 3초 뒤 서버의 타이머 콜백이 `학생 목록 응답`을 찍고 JSON을 보내요. CORS 머리글이 있어서 브라우저가 응답을 화면 코드에 넘겨요.
7. `await fetch` 다음 줄부터 이어서 실행돼요. `response.ok`가 `true`라서 `throw` 없이 `await response.json()`으로 배열을 받고, `setStudents(data)`, `setHasLoaded(true)`를 해요.
8. `finally`의 `setIsLoading(false)`까지 실행돼요. React가 다시 그리면 표시 순서 ③에서 학생이 3명이라 목록을 그리고, 두 버튼은 다시 눌려요.
9. 실패했다면 7번에서 `catch`로 가서 `setError(…)`를 하고, 8번의 `finally`는 똑같이 실행돼요. 다시 그리면 표시 순서 ②의 오류 안내가 보여요.

| 오류 문장 · 증상 | 먼저 볼 곳 |
