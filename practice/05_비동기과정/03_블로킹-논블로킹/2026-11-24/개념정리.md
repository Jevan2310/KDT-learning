## 1단계: 무엇이 멈추는지 보는 질문 — CPU 작업과 I/O 작업

🧭 01회차의 "블로킹·논블로킹"을 오늘은 파일과 서버로 확인해요. 먼저 무엇을 볼지 정해요.

Node.js는 우리가 쓴 JavaScript를 **실행 스레드** 하나에서 실행해요. 실행 스레드는 코드를 한 줄씩 차례로 실행하는 흐름이에요. 한 번에 한 줄만 실행할 수 있어서, 어떤 줄이 오래 걸리면 그동안 다른 JavaScript 코드는 실행되지 못해요. 이 상태를 **블로킹**이라고 해요. 컴퓨터 전체가 멈추는 게 아니에요. 그 Node.js 프로그램의 JavaScript 실행이 붙잡히는 거예요. 반대로 기다리는 동안 실행 스레드를 놓아주고 다른 코드를 실행하게 하는 방식이 **논블로킹**이에요.

오래 걸리는 작업은 두 종류로 나눠요. **CPU 작업**은 프로세서가 직접 계산하는 일이에요. 반복문으로 많이 계산하기, 큰 데이터 변환하기 같은 거예요. 계산하는 동안 실행 스레드가 계속 바빠요. **I/O 작업**(Input/Output, 입력·출력)은 프로그램 바깥과 데이터를 주고받는 일이에요. 파일 읽기, 네트워크 통신, DB 통신이에요. 이때는 디스크나 상대 서버가 일하는 동안 결과를 **기다리는 시간**이 생겨요. 이 기다림을 실행 스레드가 붙잡힌 채로 보내느냐, 놓아주고 다른 코드를 실행하느냐가 오늘의 비교예요.

출력 순서를 예상할 때는 이 순서로 생각해요. 오늘 예시 전부에 맞아요.

1. 위에서부터 **바로 실행되는 줄**에 차례로 번호를 붙여요.
2. 콜백 함수(`setTimeout`이나 `readFile`에 넘긴 함수) 안의 줄과 `await` 다음 줄은 건너뛰고 "나중" 목록에 적어요. 0초 타이머여도, 파일이 1ms 만에 읽혀도 마찬가지예요.
3. 지금 코드가 파일 끝까지 실행된 **다음에야** "나중" 목록이 준비된 순서대로 실행돼요.

### ▶ 직접 해 보기 — `cpu-io.js`

실행하기 전에 네 줄이 몇 ms에 찍힐지 먼저 적어 보세요. 타이머 기다림은 I/O 기다림 대신이고, `while`은 CPU 작업이에요. `log()`는 시작부터 몇 ms 지났는지 앞에 붙여 출력하는 함수예요. `Date.now()`는 지금 시각을 ms 숫자로 돌려줘요.

```javascript
const start = Date.now();

function log(message) {
  console.log(`${Date.now() - start}ms  ${message}`);
}

log("1. 1초 타이머 예약");
setTimeout(() => {
  log("4. 타이머 콜백");
}, 1000);

log("2. 반복문 계산 시작");
const endTime = Date.now() + 500;
while (Date.now() < endTime) {
  // 계산하는 동안 실행 스레드를 계속 씁니다.
}
log("3. 반복문 계산 끝");
```

```text
0ms  1. 1초 타이머 예약
2ms  2. 반복문 계산 시작
502ms  3. 반복문 계산 끝
1004ms  4. 타이머 콜백
```

1초 기다림과 0.5초 계산이 겹쳐서 전체가 1초에 끝났어요. 타이머를 예약한 뒤 실행 스레드는 바로 계산으로 넘어갔고, 기다림은 그동안 따로 흘렀어요.

**바꿔 보기**
- `Date.now() + 500`을 `Date.now() + 2000`으로 → `2001ms  3. 반복문 계산 끝`, `2001ms  4. 타이머 콜백`. 1초로 예약했는데 2초에 실행됐어요. 시간이 됐어도 계산이 끝날 때까지 콜백이 끼어들지 못해요. 확인하면 500으로 되돌려요.

## 2단계: `readFileSync()` — 결과를 반환값으로 받고, 다 읽을 때까지 다음 줄은 기다린다

🧭 이제 진짜 I/O인 파일 읽기예요. Node.js에 기본으로 들어 있는 `node:fs` 모듈을 써서 패키지 설치는 필요 없어요.

`require("node:fs")`는 파일 시스템 기능을 가져와요. 파이썬의 `import`와 같아요. `fs.readFileSync(경로, "utf8")`는 파일을 **동기식**으로 읽어요. 파일을 다 읽어서 내용을 **반환값**으로 돌려줘야 다음 줄로 넘어가요. 그동안 실행 스레드는 다른 JavaScript를 실행하지 못하니까 **동기·블로킹**이에요. 파이썬의 `open("students.txt").read()`도 이렇게 동작해요.

`"./students.txt"`의 `./`는 **터미널의 현재 폴더**예요. 파일이 있는 폴더가 아니에요. 그래서 다른 폴더에서 `node`를 실행하면 파일을 못 찾아요. `"utf8"`은 읽은 내용을 글자로 바꾸는 방식이에요. 빼면 글자가 아니라 숫자 바이트 묶음(Buffer)이 와요.

`students.txt`처럼 작은 파일은 1ms도 안 걸려서 멈춘 느낌이 없어요. 여기서는 속도가 아니라 **순서**를 봐요.

### ▶ 직접 해 보기 — `read-sync.js` (강의 코드)

```javascript
const fs = require("node:fs");

console.log("1. 파일 읽기 전");

const content = fs.readFileSync(
  "./students.txt",
  "utf8"
);

console.log("2. 파일 내용");
console.log(content);

console.log("3. 파일 읽기 후");
```

```text
1. 파일 읽기 전
2. 파일 내용
한코딩
이학생
박학생
3. 파일 읽기 후
```

적은 순서 그대로예요. "나중" 목록에 들어갈 줄이 하나도 없기 때문이에요.

**바꿔 보기** (하나씩 하고 되돌려요)
- `console.log("1. 파일 읽기 전");` 바로 아래에 이 세 줄을 넣기 → 어디에 찍힐지 먼저 적어 보고 실행해요.
  ```javascript
  setTimeout(() => {
    console.log("0초 타이머 콜백");
  }, 0);
  ```
  → `0초 타이머 콜백`은 `3. 파일 읽기 후` **다음**, 맨 마지막에 찍혀요. 0초여도 콜백이라 "나중" 목록이에요.
- `"utf8"` 줄을 지우기 → 내용 자리에 `<Buffer ed 95 9c ec bd 94 eb 94 a9 0a …>`가 찍혀요. 글자로 바꾸지 않은 바이트예요.
- 경로를 `"./missing.txt"`로 → `1. 파일 읽기 전`만 찍히고 프로그램이 오류로 끝나요. 오류 문장은 `Error: ENOENT: no such file or directory, open './missing.txt'`예요. `ENOENT`는 "그런 파일이나 폴더가 없다"는 뜻이에요. 오류를 받아 줄 코드가 없어서 `3.`까지 가지 못했어요.
- `cd ..`로 한 폴더 올라가서 `node _async연습장/read-sync.js` → 같은 `ENOENT` 오류 (`open './students.txt'`). `./`는 터미널의 현재 폴더예요. `cd _async연습장`으로 돌아와요.

## 3단계: `readFile()` + 콜백 — 읽기를 요청만 하고 다음 줄로 간다

🧭 2단계와 같은 파일을 비동기로 읽어요. 01회차 `setTimeout`의 콜백과 같은 모양이에요.

`fs.readFile(경로, "utf8", 콜백)`은 파일 읽기를 **요청만 하고 바로 돌아와요**. 실제 읽기는 Node.js가 JavaScript 실행 스레드 밖에서 해요. 다 읽으면 넘겨준 콜백 함수를 "나중" 목록에 넣고, 지금 코드가 끝난 뒤 실행해요. 결과는 반환값이 아니라 **콜백의 매개변수**로 와요. 그래서 **비동기·논블로킹**이에요.

콜백의 매개변수는 `(error, content)` 순서예요. Node.js의 콜백 함수들은 **첫 번째 자리에 오류**를 넘겨요. 성공하면 `error`는 `null`이고 `content`에 내용이 와요. 실패하면 `error`에 오류 정보가 와요. 그래서 콜백 첫 줄에서 `if (error)`로 먼저 확인하고 `return`으로 끝내요. 2단계처럼 프로그램이 오류로 끝나지 않고, 오류를 받아서 직접 처리할 수 있어요.

논블로킹이라고 파일 읽기가 더 빨라지지는 않아요. 차이는 **기다리는 동안 실행 스레드를 붙잡아 두지 않는다**는 것뿐이에요.

### ▶ 직접 해 보기 — `read-async.js` (강의 코드)

```javascript
const fs = require("node:fs");

console.log("1. 파일 읽기 전");

fs.readFile("./students.txt", "utf8", (error, content) => {
  if (error) {
    console.log("파일 읽기 실패:", error.message);
    return;
  }

  console.log("2. 파일 내용");
  console.log(content);
});

console.log("3. 파일 읽기 요청 후");
```

```text
1. 파일 읽기 전
3. 파일 읽기 요청 후
2. 파일 내용
한코딩
이학생
박학생
```

`3.`이 `2.`보다 먼저예요. 콜백 안의 `2.`는 "나중" 목록이라서 파일 끝의 `3.`까지 실행된 뒤에 찍혔어요.

### ▶ 직접 해 보기 — `read-wait.js`

파일은 금방 읽히는데, 콜백은 언제 실행될까요? 요청한 다음 1초 동안 계산해 봐요.

```javascript
const fs = require("node:fs");

const start = Date.now();

function log(message) {
  console.log(`${Date.now() - start}ms  ${message}`);
}

log("1. 파일 읽기 요청");
fs.readFile("./students.txt", "utf8", (error, content) => {
  log("4. 콜백 실행 (파일 내용 도착)");
});
log("2. 요청 바로 다음 줄");

const endTime = Date.now() + 1000;
while (Date.now() < endTime) {
  // 1초 동안 계산합니다.
}
log("3. 1초 계산 끝");
```

```text
0ms  1. 파일 읽기 요청
2ms  2. 요청 바로 다음 줄
1002ms  3. 1초 계산 끝
1002ms  4. 콜백 실행 (파일 내용 도착)
```

파일은 몇 ms 만에 다 읽혔어요 (아래 바꿔 보기에서 확인해요). 그래도 콜백은 1002ms에 실행됐어요. 결과가 준비돼도 지금 실행 중인 계산을 끊고 들어오지 못해요.

**바꿔 보기** (하나씩 하고 되돌려요)
- `read-wait.js`에서 `const endTime`부터 `}`까지 네 줄을 지우기 → `1ms  3. 1초 계산 끝`, `1ms  4. 콜백 실행 …`. 파일 읽기는 1ms면 끝나요. 그래도 순서는 여전히 `3` 다음 `4`예요.
- `read-async.js`의 경로를 `"./missing.txt"`로 → `1.`, `3.` 다음에 `파일 읽기 실패: ENOENT: no such file or directory, open './missing.txt'`. 프로그램은 오류 없이 끝나요.
- `read-async.js`의 `(error, content)`를 `(content, error)`로 → `파일 읽기 실패: undefined`. 이름만 바꿨지 순서는 그대로라서, `error`라는 이름에 파일 내용(글자)이 들어갔어요. 글자에는 `.message`가 없어서 `undefined`예요.
- 새 파일에 아래 두 줄을 쓰고 실행 → `받은 값: undefined`. `readFile()`은 결과를 반환하지 않아서, 결과는 콜백 안에서만 쓸 수 있어요.
  ```javascript
  const fs = require("node:fs");
  const content = fs.readFile("./students.txt", "utf8", (error, content) => {});
  console.log("받은 값:", content);
  ```

## 4단계: `node:fs/promises` + `await` — 기다리는 건 그 함수 안뿐이다

🧭 02회차의 `async/await`로 파일을 읽어요. 04회차 React의 `await fetch()`도 같은 방식이에요.

`require("node:fs/promises")`의 `readFile()`은 이름은 같지만 콜백을 받지 않고 **Promise를 돌려줘요**. 그래서 `await`로 결과를 받고, 실패는 `try/catch`로 받아요. 3단계의 콜백 버전과 하는 일은 같고, 쓰는 모양만 달라요.

여기서 헷갈리기 쉬운 게 `await`예요. `await`는 **그 `async` 함수 안의 다음 줄**을 결과가 올 때까지 미뤄요. 그 사이 실행 스레드는 함수 밖으로 나와서 `main()`을 부른 다음 줄부터 계속 실행해요. 그래서 `await` 다음 줄은 1단계 규칙의 "나중" 목록에 들어가요. `readFileSync()`처럼 실행 스레드를 붙잡고 기다리는 게 아니에요.

### ▶ 직접 해 보기 — `read-promise.js` (강의 코드)

```javascript
const fs = require("node:fs/promises");

async function main() {
  console.log("1. 파일 읽기 시작");

  try {
    const content = await fs.readFile(
      "./students.txt",
      "utf8"
    );

    console.log("3. 파일 내용");
    console.log(content);
  } catch (error) {
    console.log("파일 읽기 실패:", error.message);
  }
}

main();

console.log("2. main 함수 밖의 작업");
```

```text
1. 파일 읽기 시작
2. main 함수 밖의 작업
3. 파일 내용
한코딩
이학생
박학생
```

`main()`을 부르면 `1.`은 바로 찍혀요. `await`에서 `main`이 멈추고 밖으로 나와 `2.`가 찍혀요. 파일 끝까지 간 뒤에 `await` 다음 줄인 `3.`이 실행돼요.

### ▶ 직접 해 보기 — `read-await.js`

`await` 다음 줄도 지금 코드가 끝나야 실행되는지 시간으로 확인해요.

```javascript
const fs = require("node:fs/promises");

const start = Date.now();

function log(message) {
  console.log(`${Date.now() - start}ms  ${message}`);
}

async function loadStudents() {
  log("A. loadStudents 시작");

  const content = await fs.readFile("./students.txt", "utf8");

  log("D. await 다음 줄 (파일 내용 도착)");
}

loadStudents();
log("B. loadStudents() 다음 줄");

const endTime = Date.now() + 1000;
while (Date.now() < endTime) {
  // 1초 동안 계산합니다.
}
log("C. 1초 계산 끝");
```

```text
0ms  A. loadStudents 시작
1ms  B. loadStudents() 다음 줄
1001ms  C. 1초 계산 끝
1001ms  D. await 다음 줄 (파일 내용 도착)
```

3단계 `read-wait.js`와 같은 결과예요. 콜백으로 받든 `await`로 받든, 결과를 받아 이어지는 코드는 지금 실행 중인 코드가 끝난 뒤에 실행돼요.

**바꿔 보기** (하나씩 하고 되돌려요)
- `read-promise.js`에서 `await`만 지우기 → `1.`, `3. 파일 내용`, `Promise { <pending> }`, `2.` 순서. `await`가 없으면 기다리지 않고 바로 다음 줄로 가요. `content`에는 파일 내용이 아니라 아직 끝나지 않은 Promise가 들어 있어요.
- `read-promise.js` 첫 줄을 `require("node:fs")`로, `await fs.readFile(`을 `fs.readFileSync(`로 → `1.`, `3. 파일 내용`, 내용, `2.` 순서. `async` 함수 안이어도 `readFileSync()`는 실행 스레드를 붙잡고 다 읽을 때까지 기다려요. 7단계에서 서버로 다시 확인해요.
- 경로를 `"./missing.txt"`로 → `1.`, `2.` 다음에 `파일 읽기 실패: ENOENT: no such file or directory, open './missing.txt'`. 실패한 `await`는 `catch`로 가요.
- 위 상태에서 `try {`, `} catch … }` 부분을 지워 `try/catch` 없이 실행 → `1.`, `2.` 다음에 `[Error: ENOENT: no such file or directory, open './missing.txt'] { … }`가 찍히고 프로그램이 오류로 끝나요.

## 5단계: 비교용 서버 — `/fast`, `/slow-blocking`, `/slow-nonblocking`

🧭 Node과정 03회차의 Express 서버와 같은 모양이에요. 이번에는 응답 속도가 다른 주소 세 개를 만들어요.

서버는 여러 요청을 받아요. 그런데 요청마다 실행되는 함수(핸들러)도 결국 같은 JavaScript 실행 스레드에서 실행돼요. 그러면 한 요청의 핸들러가 실행 스레드를 오래 붙잡을 때 다른 요청은 어떻게 될까요? 이걸 보려고 세 주소를 만들어요.

`/fast`는 바로 응답해요. `/slow-blocking`은 `while`로 3초 동안 계산하고 응답해요. CPU 작업을 흉내 낸 거예요. `/slow-nonblocking`은 `setTimeout`으로 3초 뒤에 응답해요. DB나 파일을 기다리는 I/O 작업 대신 타이머를 쓴 거예요. 응답(`res.send`)을 타이머 콜백 안에서 보내서, 핸들러 함수 자체는 타이머를 예약하고 바로 끝나요.

`while`로 시간을 끄는 코드는 학습용이에요. 실제로 응답을 늦춰야 하면 타이머처럼 실행 스레드를 붙잡지 않는 방식을 써요.

### ▶ 직접 해 보기 — `server.js` (강의 코드)

```javascript
const express = require("express");

const app = express();
const PORT = 3001;

app.get("/fast", (req, res) => {
  console.log("빠른 요청 처리");

  res.send("빠른 응답입니다.");
});

app.get("/slow-blocking", (req, res) => {
  console.log("블로킹 작업 시작");

  const endTime = Date.now() + 3000;

  while (Date.now() < endTime) {
    // 실행 스레드를 점유하는 학습용 반복입니다.
  }

  console.log("블로킹 작업 종료");

  res.send("블로킹 작업이 끝났습니다.");
});

app.get("/slow-nonblocking", (req, res) => {
  console.log("논블로킹 대기 시작");

  setTimeout(() => {
    console.log("논블로킹 대기 종료");

    res.send("기다림이 끝났습니다.");
  }, 3000);
});

app.listen(PORT, () => {
  console.log(`서버 실행 중: http://localhost:${PORT}`);
});
```

```bash
node server.js
```

```text
서버 실행 중: http://localhost:3001
```

서버는 끝나지 않고 켜져 있어요. 브라우저에서 `http://localhost:3001/fast`를 열면 `빠른 응답입니다.`가 보이고, 서버 터미널에 `빠른 요청 처리`가 찍혀요. 코드를 고치면 `Ctrl + C`로 끄고 다시 `node server.js`를 해요.

터미널로도 확인할 수 있어요. VS Code 터미널 오른쪽 위 **+**로 새 터미널을 하나 더 열어요 (서버 터미널은 그대로 둬요). `curl`은 주소로 요청을 보내고 받은 응답을 출력하는 명령이에요. `-s`는 진행 표시를 숨기고, `-w "  (%{time_total}초)\n"`은 응답 뒤에 걸린 시간을 붙여 줘요.

```bash
curl -s -w "  (%{time_total}초)\n" http://localhost:3001/fast
```

```text
빠른 응답입니다.  (0.000738초)
```

**바꿔 보기**
- 서버가 켜진 채로 새 터미널에서 `node server.js`를 한 번 더 → `서버 실행 중: http://localhost:3001`이 찍히고 바로 명령 줄로 돌아와요. 3001번을 이미 앞 서버가 쓰고 있어서 두 번째 서버는 켜지지 못하고 끝난 거예요. Express 5는 이 오류를 `app.listen`의 함수에 넘기는데 강의 코드가 오류를 출력하지 않아서 문장이 안 보여요.

## 6단계: 느린 요청 중에 `/fast` 보내기 — 블로킹과 논블로킹의 차이

🧭 1단계 `cpu-io.js`에서 본 차이를 서버 요청으로 확인해요.

실험은 두 번이에요. 느린 요청을 보내고, **그 응답이 오기 전에** `/fast`를 보내요. `/fast`가 바로 응답하는지 봐요. 느린 요청이 끝난 뒤에 `/fast`를 보내면 차이가 안 보여요.

`/slow-blocking`이면 `/fast`도 기다려요. `/slow-blocking`의 `while`이 실행 스레드를 쓰는 동안 `/fast` 요청이 서버에 도착해도, 그 핸들러를 실행할 수 없어요. 3초 계산이 끝나고 `res.send`까지 간 다음에야 `/fast` 핸들러가 실행돼요. 빠른 요청도 느린 계산 때문에 늦어진 거예요.

`/slow-nonblocking`이면 `/fast`가 바로 응답해요. 핸들러는 타이머만 예약하고 끝났으니, 3초를 기다리는 동안 실행 스레드는 비어 있어요. 그 사이 들어온 `/fast`를 바로 처리해요.

느린 응답 자체는 둘 다 약 3초예요. 논블로킹이 빨라지는 게 아니에요. 차이는 **기다리는 3초 동안 다른 요청을 처리할 수 있느냐**예요.

### ▶ 직접 해 보기 — 브라우저 탭 두 개 (강의 방법)

1. 탭 1에서 `http://localhost:3001/slow-blocking`을 열어요.
2. 로딩이 도는 동안 **바로** 탭 2에서 `http://localhost:3001/fast`를 열어요.
3. 탭 2도 탭 1이 끝날 때까지 로딩이 돌다가 거의 같이 끝나요. 서버 터미널에는 `블로킹 작업 시작` → (약 3초) `블로킹 작업 종료` → `빠른 요청 처리` 순서로 찍혀요.
4. 탭 1을 `http://localhost:3001/slow-nonblocking`으로 바꿔 같은 실험 → 탭 2는 바로 `빠른 응답입니다.`가 보여요. 서버 터미널은 `논블로킹 대기 시작` → `빠른 요청 처리` → `논블로킹 대기 종료` 순서예요.

결과가 이상하면 개발자 도구 **Network** 탭에서 **Disable cache**(캐시 사용 중지)를 켜고 다시 해요.

### ▶ 직접 해 보기 — curl 두 개를 겹쳐 보내기

타이밍을 정확히 맞추려면 터미널이 편해요. 서버는 켜 둔 채, 두 번째 터미널에 한 줄로 붙여 넣어요. `&`는 앞 명령을 뒤에서 실행시키고 바로 다음 명령으로 넘어가게 해요. `sleep 1`은 1초 쉬기, `wait`는 뒤에서 돌던 명령이 끝날 때까지 기다리기예요. 그래서 느린 요청을 보내고 1초 뒤에 `/fast`를 보내요.

```bash
curl -s -w "  (%{time_total}초)\n" http://localhost:3001/slow-blocking & sleep 1; curl -s -w "  (%{time_total}초)\n" http://localhost:3001/fast; wait
```

```text
[1] 65672
블로킹 작업이 끝났습니다.  (3.000838초)
[1]  + done       curl -s -w "  (%{time_total}초)\n" http://localhost:3001/slow-blocking
빠른 응답입니다.  (1.993875초)
```

`[1] 65672`와 `[1]  + done …`은 zsh가 뒤에서 돌린 명령의 시작과 끝을 알려 주는 줄이에요 (숫자는 매번 달라요). `/fast`는 1초 뒤에 보냈는데 응답까지 **1.99초**가 걸렸어요. 블로킹 계산이 끝나는 3초 시점까지 기다린 거예요. 서버 로그에 시각을 붙여 찍어 보니 `블로킹 작업 종료`와 `빠른 요청 처리`가 같은 ms에 찍혔어요.

`/slow-blocking`을 `/slow-nonblocking`으로 바꿔서 다시 보내요.

```bash
curl -s -w "  (%{time_total}초)\n" http://localhost:3001/slow-nonblocking & sleep 1; curl -s -w "  (%{time_total}초)\n" http://localhost:3001/fast; wait
```

```text
[1] 65894
빠른 응답입니다.  (0.000756초)
기다림이 끝났습니다.  (3.003614초)
[1]  + done       curl -s -w "  (%{time_total}초)\n" http://localhost:3001/slow-nonblocking
```

이번에는 `/fast`가 0.0008초 만에 먼저 왔고, 느린 응답은 그대로 3초예요. 서버 터미널은 `논블로킹 대기 시작` → (1초 뒤) `빠른 요청 처리` → (3초 시점) `논블로킹 대기 종료`예요.

**바꿔 보기** — 느린 요청 두 개를 동시에 보내기 (`sleep 1;`을 빼고 같은 주소 두 번)
- `/slow-nonblocking` 두 개 → 둘 다 `(3.003580초)`, `(3.003832초)`. 두 타이머가 같이 기다려서 3초에 같이 끝나요.
- `/slow-blocking` 두 개 → `(3.000323초)`, `(6.000408초)`. 두 번째 요청은 첫 번째 계산 3초가 끝난 뒤에야 자기 계산 3초를 시작해요.
  ```bash
  curl -s -w "  (%{time_total}초)\n" http://localhost:3001/slow-blocking & curl -s -w "  (%{time_total}초)\n" http://localhost:3001/slow-blocking; wait
  ```

## 7단계: `async`를 붙여도 그대로다 — 그리고 콜백 안의 긴 계산

🧭 02회차에서 `async` 함수는 Promise를 돌려준다고 했어요. 그럼 `/slow-blocking` 핸들러에 `async`를 붙이면 논블로킹이 될까요?

안 돼요. `async`는 함수가 **Promise를 돌려주게** 하고, 안에서 `await`를 쓸 수 있게 해 줄 뿐이에요. 함수 안의 코드를 다른 스레드로 보내지 않아요. `while` 계산은 여전히 같은 실행 스레드에서 3초 동안 실행돼요. 4단계 바꿔 보기에서 `async function main` 안의 `readFileSync()`가 블로킹이었던 것과 같은 이유예요.

같은 이유로, 비동기로 기다렸다고 그 뒤의 코드가 저절로 가벼워지지도 않아요. `fs.readFile()`로 기다리는 동안은 다른 일을 할 수 있지만, 결과를 받은 **콜백 안에서** 오래 계산하면 그 계산은 실행 스레드를 붙잡아요. 기다리는 단계와 계산하는 단계를 나눠서 봐요. 오래 걸리는 계산을 다른 스레드로 보내는 방법도 있지만, 강의는 원인과 `async`의 한계까지만 다뤄요.

### ▶ 직접 해 보기 — `server.js`에 `async` 붙이기

`/slow-blocking` 줄만 이렇게 바꾸고, 서버를 `Ctrl + C`로 껐다가 다시 켜요.

```javascript
app.get("/slow-blocking", async (req, res) => {
```

6단계의 첫 번째 curl 명령을 다시 보내요.

```text
[1] 66305
블로킹 작업이 끝났습니다.  (3.003540초)
[1]  + done       curl -s -w "  (%{time_total}초)\n" http://localhost:3001/slow-blocking
빠른 응답입니다.  (1.992329초)
```

`async`가 없을 때와 똑같이 `/fast`가 1.99초를 기다렸어요. 서버 로그도 `블로킹 작업 시작` → `블로킹 작업 종료` → `빠른 요청 처리` 순서 그대로예요. 확인하면 `async `를 지우고 서버를 다시 켜요.

### ▶ 직접 해 보기 — `callback-busy.js`

파일을 비동기로 읽고, 콜백 안에서 1초 동안 계산해요. 100ms 타이머는 언제 실행될까요?

```javascript
const fs = require("node:fs");

const start = Date.now();

function log(message) {
  console.log(`${Date.now() - start}ms  ${message}`);
}

fs.readFile("./students.txt", "utf8", (error, content) => {
  log("2. 파일 콜백 시작");

  const endTime = Date.now() + 1000;
  while (Date.now() < endTime) {
    // 콜백 안에서 1초 동안 계산합니다.
  }

  log("3. 파일 콜백 끝");
});

setTimeout(() => {
  log("4. 100ms 타이머 콜백");
}, 100);

log("1. 파일 읽기와 타이머 예약 끝");
```

```text
0ms  1. 파일 읽기와 타이머 예약 끝
2ms  2. 파일 콜백 시작
1002ms  3. 파일 콜백 끝
1002ms  4. 100ms 타이머 콜백
```

파일 읽기를 기다리는 동안은 논블로킹이었어요. 그런데 2ms에 콜백이 시작되고 1초 계산을 하는 동안, 100ms 타이머는 시간이 됐는데도 실행되지 못하고 1002ms까지 밀렸어요.

**바꿔 보기**
- 콜백 안의 `Date.now() + 1000`을 `Date.now() + 50`으로 → `51ms  3. 파일 콜백 끝`, `102ms  4. 100ms 타이머 콜백`. 계산이 짧으면 타이머가 제시간에 실행돼요. 되돌려요.

## 마무리: `/slow-blocking` 중에 보낸 `/fast`가 기다리기까지

6단계 첫 번째 curl 명령에서 일어난 일을 처음부터 따라가요.

1. `node server.js`가 위에서부터 실행돼요. Express를 가져오고 세 주소의 핸들러를 등록한 뒤, `app.listen`이 3001번에서 요청을 기다리기 시작해요. 실행 스레드는 할 일이 없어서 비어 있어요.
2. 0초: 첫 번째 curl이 `/slow-blocking`을 보내요. 실행 스레드가 그 핸들러를 실행해 `블로킹 작업 시작`을 찍고 `while`에 들어가요.
3. 1초: 두 번째 curl이 `/fast`를 보내요. 요청은 서버에 도착했지만, 실행 스레드가 아직 `while`을 돌고 있어서 `/fast` 핸들러를 실행할 수 없어요.
4. 3초: `while`이 끝나요. `블로킹 작업 종료`를 찍고 `res.send`로 첫 번째 응답을 보내요. 핸들러가 끝나서 실행 스레드가 비어요.
5. 같은 3초: 그제야 기다리던 `/fast` 핸들러가 실행돼 `빠른 요청 처리`를 찍고 응답해요. curl은 1초에 보내서 3초에 받았으니 1.99초가 찍혀요.
6. `/slow-nonblocking`이었다면 2단계에서 핸들러가 타이머만 예약하고 바로 끝나요. 그래서 3단계의 `/fast`가 1초에 바로 처리되고, 3초에 타이머 콜백이 `논블로킹 대기 종료`를 찍고 응답해요.
7. 핸들러에 `async`를 붙여도 2~5번은 그대로예요. 실행 스레드를 붙잡는 건 `while`이에요.
