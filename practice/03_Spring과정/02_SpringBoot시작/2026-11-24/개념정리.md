## 들어가며

**🧭 맥락 — 지금 어디쯤**

01에서는 `Student` 클래스와 `List<Student>`를 만들고 콘솔에 출력했어요. 그 프로그램은 `main`을 실행하면 출력하고 바로 끝났어요.

Node 03에서는 Express로 서버를 만들었어요. `node server.js`로 켜면 서버는 끝나지 않고 3000번 포트에서 요청을 기다렸죠. `app.get("/hello", (req, res) => res.send("..."))`처럼 **주소마다 실행할 함수**를 정해 두면, 그 주소로 요청이 올 때 함수가 실행되고 `res.send`로 보낸 글자가 브라우저에 보였어요.

02에서는 같은 일을 Java로 해요. 도구는 **Spring Boot**예요. 할 일은 Node 03과 같아요.

- 서버를 켜고 8080번 포트에서 요청을 기다리게 한다
- `/hello` 요청이 오면 인사 문장을 돌려준다
- `/school` 경로를 하나 더 만든다
- 콘솔 출력과 브라우저 응답이 어디로 가는지 구분한다
- 포트를 설정 파일에서 바꿔 본다
- 마지막으로 `/hi`에서 글자 대신 HTML 화면을 돌려주는 방법을 미리 본다 (03의 준비)

파이썬 웹 도구 Flask를 써 봤다면 `@app.route("/hello")` 아래에 함수를 쓰던 모양과 비슷해요. Spring에서는 `@GetMapping("/hello")` 아래에 메서드를 써요.

오늘 만드는 `_spring-practice` 프로젝트는 06까지 계속 써요. 03에서 학생 목록 화면, 04에서 등록 폼, 05에서 데이터베이스, 06에서 JSON API를 이 프로젝트에 더해요. 오늘 Thymeleaf를 미리 넣어 두는 것도 03에서 쓰기 때문이에요.

팀 프로젝트(실시간 채팅)는 Node.js라서 Spring은 직접 쓰지 않아요. 다만 "요청 방식 + 주소 → 실행할 함수"를 정하는 생각은 팀 프로젝트의 Express 라우트와 같아요.

## 1단계: Spring Boot 프로젝트는 무엇으로 이루어져 있나

🧭 01의 `_java-practice`는 IntelliJ가 직접 컴파일하는 단순한 Java 프로젝트였어요. 이번에는 Gradle 프로젝트예요. 서버를 만들려면 남이 만든 코드를 많이 가져와야 하기 때문이에요.

**Spring**은 Java로 웹 서버를 만들 때 쓰는 기능 모음(프레임워크)이에요. 요청을 받고, 주소에 맞는 메서드를 찾아 실행하고, 결과를 응답으로 보내는 일을 Spring이 해 줘요. Node 과정의 Express와 같은 자리에 있어요.

**Spring Boot**는 Spring을 바로 쓸 수 있게 설정을 자동으로 해 주는 도구예요. Spring만 쓰면 웹 서버 프로그램을 따로 설치하고 설정 파일을 많이 써야 했어요. Spring Boot는 **Tomcat**(요청을 받아 응답을 보내는 웹 서버 프로그램)을 프로젝트 안에 넣어 두고, 기본 설정도 알아서 해요. 그래서 `main`만 실행하면 서버가 켜져요.

**의존성**은 프로젝트가 가져다 쓰는 외부 코드(라이브러리)예요. **Gradle**은 의존성을 인터넷에서 내려받고, 코드를 컴파일하고, 실행까지 해 주는 도구예요. 무엇을 내려받을지는 `build.gradle` 파일에 적어요. Node의 `package.json`과 `npm install`, 파이썬의 `requirements.txt`와 `pip install`이 하는 일과 비슷해요.

`build.gradle`의 `dependencies` 안에 두 줄이 있어요. Initializr에서 고른 의존성 두 개예요.

- `spring-boot-starter-webmvc`: **Spring Web**을 고르면 생기는 줄이에요. 요청을 받고 응답하는 기능과 Tomcat이 들어 있어요. 강의 원문이나 인터넷 예제에는 `spring-boot-starter-web`으로 나오는데, Spring Boot 3까지 쓰던 이름이에요. 4.x에서 이름이 바뀌었어요.
- `spring-boot-starter-thymeleaf`: **Thymeleaf**는 서버에서 HTML을 만드는 도구예요. 7단계에서 잠깐 쓰고, 03에서 본격적으로 써요.

`testImplementation`으로 시작하는 줄은 테스트 코드용이라 지금은 쓰지 않아요. 의존성 줄에 버전 번호가 없는 것도 볼 수 있어요. 맨 위 `plugins`의 `org.springframework.boot` 버전(4.1.3)에 맞는 버전을 Spring Boot가 골라 주기 때문이에요. `toolchain`의 `JavaLanguageVersion.of(21)`은 "JDK 21로 컴파일하라"는 설정이에요.

폴더도 하는 일이 정해져 있어요. Java 코드는 `src/main/java`, 설정 파일과 화면 파일은 `src/main/resources`에 둬요. `resources` 안의 `static`에는 CSS·이미지를, `templates`에는 Thymeleaf HTML을 둬요. `src/test`는 테스트 코드 자리예요. `build/`와 `.gradle/`은 Gradle이 만드는 폴더라 직접 고치지 않아요. IntelliJ에서는 `com/example/springpractice` 폴더 세 개가 `com.example.springpractice` 한 줄로 보여요.

### ▶ 직접 해 보기 — `build.gradle` 열어 보기

IntelliJ 왼쪽 프로젝트 창에서 `build.gradle`을 열어요. Initializr가 만든 내용이 이래요 (고치지 않아요).

```groovy
plugins {
	id 'java'
	id 'org.springframework.boot' version '4.1.3'
	id 'io.spring.dependency-management' version '1.1.7'
}

group = 'com.example'
version = '0.0.1-SNAPSHOT'

java {
	toolchain {
		languageVersion = JavaLanguageVersion.of(21)
	}
}

repositories {
	mavenCentral()
}

dependencies {
	implementation 'org.springframework.boot:spring-boot-starter-thymeleaf'
	implementation 'org.springframework.boot:spring-boot-starter-webmvc'
	testImplementation 'org.springframework.boot:spring-boot-starter-thymeleaf-test'
	testImplementation 'org.springframework.boot:spring-boot-starter-webmvc-test'
	testRuntimeOnly 'org.junit.platform:junit-platform-launcher'
}

tasks.named('test') {
	useJUnitPlatform()
}
```

`repositories`의 `mavenCentral()`은 의존성을 내려받는 곳이에요. npm 패키지를 npm 저장소에서 받던 것과 같아요.

## 2단계: 실행 클래스를 실행하면 서버가 켜진다

🧭 01에서는 `main`이 끝나면 프로그램도 끝났어요. 서버는 끝나면 안 돼요. 요청을 계속 기다려야 하니까요. Node에서 `app.listen(3000)`이 그 역할이었어요.

Initializr가 만든 `SpringPracticeApplication.java`가 **실행 클래스**예요. 이름은 Name 칸(`_spring-practice`)에서 기호를 빼고 `Application`을 붙여서 정해져요. 수업에서는 Name이 `kdt`라서 `KdtApplication`이었어요.

```java
@SpringBootApplication
public class SpringPracticeApplication {

	public static void main(String[] args) {
		SpringApplication.run(SpringPracticeApplication.class, args);
	}

}
```

클래스 위의 `@SpringBootApplication`은 **어노테이션**이에요. 어노테이션은 `@`로 시작하는 표시로, 클래스나 메서드에 정보를 붙여요. 01에서 `toString()` 위에 붙인 `@Override`와 같은 종류예요. 어노테이션은 코드 동작을 직접 바꾸지 않아요. Spring이 실행될 때 이 표시를 읽고, 표시에 맞는 일을 해요. 모양은 파이썬의 데코레이터(`@`)와 비슷하지만, 데코레이터처럼 함수를 감싸는 코드가 아니라 붙여 두는 정보예요.

`@SpringBootApplication`이 붙으면 Spring은 두 가지를 해요. 첫째, Spring Web·Thymeleaf 같은 의존성에 맞는 설정을 자동으로 해요. 둘째, **이 클래스가 있는 패키지와 그 아래 패키지**를 뒤져서 Spring이 관리할 클래스(예: 3단계의 컨트롤러)를 찾아요. 이 "아래 패키지만 찾는다"는 규칙이 3단계에서 중요해요.

`main` 안의 `SpringApplication.run(...)`이 Spring을 시작해요. Spring Web이 있으니 Tomcat도 같이 켜고, 기본 포트 **8080**에서 요청을 기다려요. 그래서 `main`이 실행돼도 프로그램이 끝나지 않아요.

서버가 켜진 뒤 브라우저로 `http://localhost:8080/`을 열면 **404**가 나와요. `/` 주소를 맡은 코드가 아직 없어서예요. 404는 "서버는 요청을 받았는데, 그 주소를 맡은 곳이 없다"는 뜻이에요. 서버가 꺼져 있으면 404가 아니라 아예 **연결할 수 없다**는 화면이 나와요. 이 둘을 구분할 줄 알아야 오류를 빨리 찾아요.

## 3단계: 컨트롤러로 `/hello`에 응답한다

🧭 Node 03의 `app.get("/hello", (req, res) => res.send("안녕하세요"))`를 Spring으로 옮기는 단계예요.

**컨트롤러**는 요청을 받아 실행할 메서드를 모아 둔 클래스예요. 클래스 위에 `@RestController`를 붙이면 Spring이 이 클래스를 컨트롤러로 알아봐요. 그리고 이 클래스의 메서드가 돌려준 값을 **응답 본문**(브라우저가 받아서 보여 주는 내용)으로 그대로 보내요.

메서드 위의 `@GetMapping("/hello")`는 "**GET** 방식으로 `/hello` 요청이 오면 이 메서드를 실행한다"는 표시예요. 브라우저 주소창에 주소를 치고 Enter를 누르는 건 GET 요청이에요. Node의 `app.get("/hello", 함수)`와 같은 일을 어노테이션으로 해요.

`hello()` 메서드는 `String`을 돌려줘요. Spring이 그 문자열을 받아 응답 본문에 넣어 보내요. Node에서는 `res.send("...")`를 직접 불렀지만, Spring에서는 `return`만 하면 돼요. 응답을 보내는 일은 Spring이 해요.

요청 하나가 들어오면 이런 순서로 일이 일어나요.

1. 브라우저가 `GET /hello` 요청을 보내요.
2. Tomcat이 요청을 받아 Spring에 넘겨요.
3. Spring이 `@GetMapping("/hello")`가 붙은 메서드를 찾아요.
4. `hello()`가 실행되고 문자열을 돌려줘요.
5. `@RestController`라서 Spring이 그 문자열을 응답 본문으로 보내요.
6. 브라우저가 글자를 보여 줘요.

컨트롤러는 **실행 클래스 패키지 아래**에 만들어요. 2단계에서 본 것처럼 Spring은 `com.example.springpractice`와 그 아래 패키지만 뒤지기 때문이에요. 그래서 `com.example.springpractice.controller` 패키지를 만들고 그 안에 둬요. 다른 곳에 두면 Spring이 클래스를 못 찾고, 주소를 맡은 곳이 없으니 404가 나요. 컴파일 오류가 아니라서 서버는 멀쩡히 켜져요. 그래서 더 찾기 어려워요.

주소는 글자 하나까지 맞아야 해요. `/Hello`처럼 대문자가 섞이거나 `/hello/`처럼 끝에 `/`를 더 붙이면 다른 주소로 보고 404를 내요.

### ▶ 직접 해 보기 — `HelloController.java`

`com.example.springpractice` 우클릭 → **New → Package** → `controller` 입력 (이름 칸에 `com.example.springpractice.`가 미리 들어 있으면 그 뒤에 써요). 생긴 `controller` 우클릭 → **New → Java Class** → `HelloController`. 내용을 전부 바꿔요.

```java
package com.example.springpractice.controller;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {

    @GetMapping("/hello")
    public String hello() {
        return "안녕하세요, 한코딩 서버입니다!";
    }

}
```

■ → ▶ 하고 브라우저로 `http://localhost:8080/hello`를 열면 이 글자가 보여요. 수업 코드는 `"안녕하세요 hello입니다."`였어요. 내 `return` 문장이 그대로 보이면 정상이에요.

```text
안녕하세요, 한코딩 서버입니다!
```

터미널에서 `curl -i http://localhost:8080/hello`로 보면 응답의 머리 부분(헤더)도 보여요 (`Date` 줄은 뺐어요). `200`은 성공, `text/plain`은 "그냥 글자"라는 뜻이에요.

```text
HTTP/1.1 200
Content-Type: text/plain;charset=UTF-8
Content-Length: 43

안녕하세요, 한코딩 서버입니다!
```

**바꿔 보기** — 하나씩 바꾸고 ■ → ▶ 한 뒤 `/hello`를 열어 봐요. 확인하면 되돌려요.
- `@RestController` 줄 앞에 `//`를 붙여 주석으로 → 2단계의 Whitelabel 404. Spring이 이 클래스를 컨트롤러로 알아보지 못해요.
- 첫 줄을 wiki 강의 코드처럼 `package com.hancoding.student.controller;`로 → IntelliJ가 그 줄에 빨간 밑줄을 그을 수 있지만, 서버는 오류 없이 켜져요. 그런데 `/hello`는 404예요. 클래스가 `com.example.springpractice` 아래가 아닌 다른 패키지에 들어가서 Spring이 찾지 못했어요. wiki 코드를 복사할 때 `package` 줄을 꼭 고치는 이유예요.
- 주소창에 `http://localhost:8080/Hello`나 `http://localhost:8080/hello/` → 둘 다 404.

## 4단계: 주소는 메서드 이름이 아니라 `@GetMapping`이 정한다

🧭 Node에서 `app.get`을 여러 번 써서 주소를 늘렸던 것처럼, 컨트롤러 안에 메서드를 더 써서 주소를 늘려요.

한 컨트롤러 안에 요청을 맡는 메서드를 여러 개 둘 수 있어요. `/school` 요청을 맡는 `school()` 메서드를 `HelloController`에 더해요.

여기서 헷갈리기 쉬운 게 있어요. 주소 `/school`은 메서드 이름 `school`에서 나온 게 아니에요. **`@GetMapping("/school")`에 쓴 글자**가 주소예요. 메서드 이름을 `showSchool()`로 바꿔도 주소는 그대로 `/school`이에요. 메서드 이름은 Java 코드 안에서 구분하려고 붙인 이름일 뿐이에요.

반대로 **같은 GET 주소를 두 메서드에 붙이면** 안 돼요. `/hello` 요청이 왔을 때 둘 중 어느 메서드를 실행할지 정할 수 없으니까요. Spring은 서버를 켜는 단계에서 이걸 발견하고 시작을 멈춰요. 오류 문장의 `Ambiguous mapping`이 "한 주소에 메서드가 둘"이라는 뜻이에요. 문장 안에 겹친 두 메서드 이름(`HelloController#school()`, `HelloController#hello()`)이 나오니까 그걸 보고 고쳐요.

### ▶ 직접 해 보기 — `/school` 더하기

`HelloController.java`를 이렇게 바꿔요 (강의 최종 `HelloController`와 같고, `package` 줄만 우리 것이에요).

```java
package com.example.springpractice.controller;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {

    @GetMapping("/hello")
    public String hello() {
        return "안녕하세요, 한코딩 서버입니다!";
    }

    @GetMapping("/school")
    public String school() {
        return "한코딩 스쿨입니다.";
    }
}
```

■ → ▶ 하고 두 주소를 열어요.

```text
http://localhost:8080/hello   →  안녕하세요, 한코딩 서버입니다!
http://localhost:8080/school  →  한코딩 스쿨입니다.
```

**바꿔 보기**
- `public String school()`을 `public String showSchool()`로 → ■ → ▶ 해도 `/school`에서 `한코딩 스쿨입니다.`가 그대로 나와요. 되돌려요.
- `@GetMapping("/school")`을 `@GetMapping("/hello")`로 → ▶ 하면 서버가 켜지다가 멈추고 Run 창에 이 문장이 나와요 (앞부분은 길어서 줄였어요). 되돌려요.
```text
Caused by: java.lang.IllegalStateException: Ambiguous mapping. Cannot map 'helloController' method 
com.example.springpractice.controller.HelloController#school()
to {GET [/hello]}: There is already 'helloController' bean method
com.example.springpractice.controller.HelloController#hello() mapped.
```

## 5단계: 콘솔 출력과 브라우저 응답은 다른 곳으로 간다

🧭 01 3단계에서 "`return`은 값을 돌려줄 뿐 출력하지 않는다"를 봤어요. 서버에서는 이 구분이 더 중요해져요. 돌려준 값이 브라우저로 가기 때문이에요.

`System.out.println(...)`은 01처럼 **IntelliJ의 Run 창**(서버 콘솔)에 찍혀요. 브라우저에는 보이지 않아요. 메서드가 `return`한 값은 **브라우저**로 가요. Run 창에는 찍히지 않아요. Node에서 `console.log`는 터미널에, `res.send`는 브라우저에 갔던 것과 같아요. 파이썬 Flask라면 `print`는 터미널, 함수가 `return`한 글자는 브라우저예요.

그래서 서버 코드에서 `println`은 "요청이 정말 들어왔나", "값이 뭐였나"를 개발자가 확인하는 데 써요. 사용자에게 보여 줄 내용은 `return`으로 보내요. 요청이 올 때마다 메서드가 실행되니까, 새로고침할 때마다 Run 창에 한 줄씩 늘어나요.

`return`을 빼먹으면 어떻게 될까요? `hello()`는 `String`을 돌려준다고 약속했어요. 01 3단계에서 본 것처럼 약속한 값을 돌려주지 않으면 컴파일 오류가 나고, 서버는 켜지지도 않아요.

### ▶ 직접 해 보기 — `println` 넣기

`hello()` 메서드만 이렇게 바꿔요.

```java
    @GetMapping("/hello")
    public String hello() {
        System.out.println("GET /hello 요청이 들어왔습니다.");

        return "안녕하세요, 한코딩 서버입니다!";
    }
```

■ → ▶ 하고 `/hello`를 두 번 새로고침, `/school`을 한 번 열어요. 브라우저에는 지금까지와 같은 글자만 보여요. Run 창의 맨 아래에는 이 두 줄이 생겨요. `/school`에는 `println`이 없어서 아무 줄도 생기지 않아요.

```text
GET /hello 요청이 들어왔습니다.
GET /hello 요청이 들어왔습니다.
```

첫 요청 때 바로 위에 `Initializing Spring DispatcherServlet 'dispatcherServlet'` 같은 줄도 보여요. Spring이 첫 요청을 받을 때 한 번 준비하면서 찍는 줄이라 신경 쓰지 않아도 돼요.

**바꿔 보기**
- `return "안녕하세요, 한코딩 서버입니다!";` 앞에 `//`를 붙여 주석으로 → ▶ 하면 서버가 켜지지 않고 빌드 창에 `missing return statement`가 나와요. 되돌려요.

## 6단계: 포트는 `application.properties`에서 정한다

🧭 Node에서는 `app.listen(3000)`처럼 포트를 코드에 썼어요. Spring Boot는 포트 같은 설정을 코드 밖의 설정 파일에 써요.

`src/main/resources/application.properties`는 **설정 파일**이에요. `키=값`을 한 줄에 하나씩 적어요. Initializr가 `spring.application.name=_spring-practice` 한 줄을 미리 넣어 뒀어요. 프로젝트 이름이라 지우지 않고, 그 아래에 줄을 더해요.

`server.port`는 서버가 쓸 포트 번호예요. 8080은 원래 기본값이라 `server.port=8080`을 적어도 달라지는 건 없어요. "이 서버는 8080을 쓴다"를 눈에 보이게 적어 둔 거예요. `8081`로 바꾸고 다시 켜면 서버는 8081에서 기다리고, 주소도 `http://localhost:8081/hello`가 돼요.

정리하면 **포트는 `application.properties`, 주소(경로)는 `@GetMapping`**에서 정해요. 05에서는 이 파일에 데이터베이스 설정도 적어요.

설정 파일의 실수는 두 종류예요. 키 이름을 틀리면(`server.prot`) Spring은 모르는 키로 보고 **오류 없이 무시**해요. 그래서 포트는 기본값 8080 그대로예요. 오류가 안 나니 "바꿨는데 왜 안 바뀌지?"가 돼요. 값을 틀리면(숫자 자리에 글자) 서버가 켜지지 않고 어느 줄이 문제인지 알려 줘요.

### ▶ 직접 해 보기 — `application.properties`

파일을 이렇게 바꿔요.

```properties
spring.application.name=_spring-practice
server.port=8080
```

■ → ▶ 하면 2단계와 같은 `Tomcat started on port 8080`이 나와요. 이제 `8080`을 `8081`로 바꾸고 ■ → ▶ 해요.

```text
o.s.boot.tomcat.TomcatWebServer          : Tomcat started on port 8081 (http) with context path '/'
```

`http://localhost:8081/hello`는 인사 문장이 나오고, `http://localhost:8080/hello`는 연결할 수 없다는 화면이 나와요. 확인했으면 **`8080`으로 되돌리고 ■ → ▶** 해요. 03부터는 계속 8080을 써요.

**바꿔 보기**
- `server.port=8081`을 `server.prot=8081`로 (철자 틀리기) → 오류 없이 켜지고 `Tomcat started on port 8080`. 틀린 줄은 무시돼요.
- `server.port=808l`(숫자 1 대신 영어 소문자 l) → 서버가 켜지지 않고 이 문장이 나와요. `2:13`은 2번째 줄 13번째 글자라는 뜻이에요.
```text
Failed to bind properties under 'server.port' to java.lang.Integer:

    Property: server.port
    Value: "808l"
    Origin: class path resource [application.properties] - 2:13
    Reason: failed to convert java.lang.String to java.lang.Integer (caused by java.lang.NumberFormatException: For input string: "808l")
```

## 7단계: 미리 보기 — `@Controller`는 돌려준 문자열로 HTML 파일을 찾는다

🧭 수업에서는 `@RestController`와 비교하려고 `HiController`와 `Hi.html`을 만들었어요. 03의 학생 목록 화면이 이 방식이라 미리 한 번 봐 둬요.

`@RestController` 대신 **`@Controller`**를 붙이면 `return`한 문자열의 뜻이 달라져요. 글자를 그대로 보내지 않고, 그 문자열을 **화면 파일(템플릿) 이름**으로 써요. `return "Hi";`면 Thymeleaf가 `src/main/resources/templates/Hi.html`을 찾아서, 그 HTML을 응답으로 보내요. 1단계에서 Thymeleaf를 미리 넣어 둔 이유가 이거예요. 반환값에는 `.html`을 붙이지 않아요.

| 같은 `return "Hi";` | 브라우저가 받는 것 |
|---|---|
| `@RestController` | `Hi` 두 글자 |
| `@Controller` | `templates/Hi.html` 파일의 HTML |

wiki 강의 정리 표에는 `@Controller`도 "메서드 반환값을 응답 본문으로 처리"라고 적혀 있는데, 이건 틀린 설명이에요. 위 표가 맞아요.

템플릿 이름은 **대소문자까지** 파일 이름과 맞춰요. 이 Mac은 파일 이름의 대소문자를 구분하지 않아서 `return "hi";`도 화면이 나와요. 그런데 프로젝트를 실행 파일 하나(jar)로 묶어 실행하면 대소문자를 구분해서 500 오류가 나요. 직접 확인해 봤어요. 지금 맞춰 두면 나중에 서버에 올릴 때 문제가 없어요.

템플릿을 못 찾으면 **500 오류**(서버 안에서 문제가 생김)가 나요. 404가 아니에요. 주소를 맡은 메서드는 찾았고 실행도 됐는데, 그 뒤에 화면 파일을 못 찾았기 때문이에요. 브라우저에는 Whitelabel 화면에 `status=500`이 보이고, 진짜 이유는 Run 창에 나와요.

### ▶ 직접 해 보기 — `HiController.java`, `Hi.html`

`controller` 우클릭 → **New → Java Class** → `HiController`.

```java
package com.example.springpractice.controller;

import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;

@Controller
public class HiController {

    @GetMapping("/hi")
    public String hi() {
        return "Hi";
    }
}
```

`resources/templates` 우클릭 → **New → HTML File** → `Hi` 입력 (`.html`은 IntelliJ가 붙여요). 내용을 전부 바꿔요.

```html
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <title>구분할래요</title>
</head>
<body>
<h1>안녕하세요 Hi입니다 여기는 HTML입니다.</h1>
</body>
</html>
```

■ → ▶ 하고 `http://localhost:8080/hi`를 열면 탭 제목이 "구분할래요"이고, 큰 제목 글씨로 "안녕하세요 Hi입니다 여기는 HTML입니다."가 보여요. 페이지 소스 보기(`Cmd + Option + U`)를 하면 `Hi.html` 내용이 그대로 와 있어요. `curl -i http://localhost:8080/hi`로 보면 `Content-Type`이 3단계의 `text/plain`이 아니라 `text/html`이에요.

```text
HTTP/1.1 200
Content-Type: text/html;charset=UTF-8
```

**바꿔 보기** — 하나씩 바꾸고 ■ → ▶, `/hi`를 열어 봐요. 확인하면 되돌려요.
- `@Controller`를 `@RestController`로 (import 줄도 `org.springframework.web.bind.annotation.RestController`로. IntelliJ에서 `Option + Enter`) → 화면에 `Hi` 두 글자만 보여요.
- `return "Hi";`를 `return "Hii";`로 → Whitelabel 화면에 `(type=Internal Server Error, status=500)`. Run 창에는 이 문장이 나와요.
```text
Error resolving template [Hii], template might not exist or might not be accessible by any of the configured Template Resolvers
```
- `return "Hi";`를 `return "hi";`로 → 이 Mac에서 ▶로 실행하면 화면이 그대로 나와요. 위에서 말한 것처럼 jar로 묶으면 `Error resolving template [hi]`가 나요. 파일 이름과 똑같이 `"Hi"`로 되돌려요.

## 마무리: `/hello` 요청 하나가 처리되는 순서

오늘 만든 것을 처음부터 따라가 볼게요.

1. ▶를 누르면 Gradle이 `build.gradle`에 적힌 의존성을 준비하고 코드를 컴파일해요. 컴파일 오류가 있으면 여기서 멈춰요 (5단계 `missing return statement`).
2. JVM이 `SpringPracticeApplication`의 `main`을 실행하고, `SpringApplication.run(...)`이 Spring을 시작해요.
3. Spring이 `application.properties`를 읽어요. `server.port=8080`이에요 (6단계).
4. `@SpringBootApplication` 때문에 Spring이 `com.example.springpractice`와 그 아래 패키지를 뒤져서 `HelloController`(`@RestController`)와 `HiController`(`@Controller`)를 찾아요. 각 메서드의 `@GetMapping`을 읽고 "`/hello` → `hello()`, `/school` → `school()`, `/hi` → `hi()`" 목록을 만들어요. 같은 주소가 두 번 나오면 여기서 멈춰요 (4단계 `Ambiguous mapping`).
5. Tomcat이 8080에서 켜지고 `Started SpringPracticeApplication`이 찍혀요. 서버는 요청을 기다려요 (2단계).
6. 브라우저가 `GET /hello`를 보내면 Spring이 목록에서 `hello()`를 찾아 실행해요. `println`은 Run 창에 찍혀요 (5단계).
7. `hello()`가 문자열을 돌려주면, `@RestController`라서 그 글자가 그대로 응답으로 가요 (3단계). `/hi`였다면 `@Controller`라서 `templates/Hi.html`을 찾아 HTML을 보내요 (7단계).
8. 목록에 없는 주소(`/`)는 404, 서버가 꺼져 있으면 연결할 수 없음이에요 (2단계).
9. ■를 누르면 서버가 꺼져요. 코드를 고쳤으면 ▶로 다시 켜야 반영돼요.

## 다음 회차와 연결

03에서는 7단계의 `@Controller` 방식으로 **학생 목록 화면**을 만들어요. 01의 `Student` 클래스를 이 프로젝트의 `model` 패키지로 옮기고, 컨트롤러가 학생 목록을 **`Model`**에 담아 넘기면 Thymeleaf가 `templates/students.html`에 데이터를 채워 HTML을 만들어요. 오늘 `Hi.html`은 글자가 고정된 HTML이었는데, 03에서는 `th:text`, `th:each`로 데이터에 따라 바뀌는 화면을 만들어요.

## 오류가 날 때 찾아보기

| 오류 문장 · 증상 | 먼저 볼 곳 |
|---|---|
| `Cannot find a Java installation on your machine … matching: {languageVersion=17 …}` | `build.gradle`의 `JavaLanguageVersion.of(21)`, Gradle JVM이 21인지 (1단계) |
| 브라우저 "사이트에 연결할 수 없음", curl `Couldn't connect to server` | 서버가 켜져 있는지, 주소의 포트 번호 (2·6단계) |
| `Web server failed to start. Port 8080 was already in use.` | 다른 서버(다른 프로젝트, 터미널의 `bootRun`)가 켜져 있는지 (2단계) |
| Whitelabel `type=Not Found, status=404` | `@RestController`/`@Controller`가 붙었는지, `package` 줄이 `com.example.springpractice…`인지, 주소 철자·대소문자·끝의 `/`, 재시작했는지 (3단계) |
| `Ambiguous mapping. Cannot map … There is already … mapped.` | 같은 GET 주소를 두 메서드에 붙였는지 (4단계) |
| 고친 응답이 안 보이고 예전 글자가 나옴 | 저장 후 ■ → ▶ 했는지 (시작하기) |
| `missing return statement` | `String` 메서드에 `return`이 있는지 (5단계) |
| `println`이 브라우저에 안 보임 | 정상이에요. Run 창에서 봐요 (5단계) |
| 포트를 바꿨는데 그대로 8080 | `server.port` 철자 (6단계) |
| `Failed to bind properties under 'server.port'` | `application.properties`의 그 줄 값, `Origin`의 줄:글자 (6단계) |
| HTML 대신 `Hi` 같은 글자만 보임 | `@Controller`가 아니라 `@RestController`로 되어 있음 (7단계) |
| Whitelabel `status=500` + `Error resolving template [이름]` | `templates/`의 파일 이름과 `return` 문자열 (대소문자 포함, `.html` 없이) (7단계) |
