## 들어가며

**🧭 맥락 — 지금 어디쯤**

Spring 06에서 React와 Spring을 이미 한 번 이었어요. Spring이 `@RestController`로 학생 목록을 JSON으로 주고, `_react연습장`이 `fetch("http://localhost:8080/api/students")`로 받아 목록을 그렸죠. 그때는 React(5173)와 Spring(8080)의 주소가 달라서 Spring에 `@CrossOrigin`을 붙였어요.

SSR-CSR 과정 02~03에서는 반대쪽을 봤어요. JSP가 서버에서 학생 목록을 넣은 HTML을 완성해서 보냈어요(SSR, 서버에서 화면을 만드는 방식). 03에서는 Network의 Response를 열어 학생 이름이 HTML 안에 이미 들어 있는 걸 확인했고, 검색하면 `/students?keyword=한` 새 문서를 통째로 받는 것도 봤어요.

오늘은 **같은 학생 데이터, 같은 검색 규칙**으로 화면을 브라우저에서 만들어요(CSR, 브라우저에서 화면을 만드는 방식). Spring은 JSON만 주고, React가 그걸 받아 표를 그려요. JSP 화면과 나란히 놓고 "화면을 어디서 만드느냐" 하나만 비교하려는 거예요.

Spring 06과 달라지는 점도 있어요.
- `@CrossOrigin` 대신 **Vite 프록시**로 연결해요 (2단계).
- 검색어 state를 두 개로 나눠요 (3단계).
- `useEffect`가 처음 한 번이 아니라, 검색 조건이 바뀔 때마다 다시 조회해요 (4단계).
- 폼의 기본 제출을 막아요 (5단계).
- 로딩·오류·빈 결과·목록 네 가지를 나눠 보여 줘요 (6단계).

마지막 7단계에서 Network로 JSP와 React가 주고받는 것을 나란히 비교해요.

## 1단계: Spring에 JSON API 추가 — 같은 Service, 다른 응답

**🧭 맥락**: 02의 `StudentPageController` 옆에 JSON용 Controller를 하나 더 둬요. Spring 06의 `@RestController`와 같은 구성이에요.

React는 HTML이 아니라 **데이터**가 필요해요. 표는 React가 직접 그리니까 학생 목록만 받으면 돼요. 그런데 02의 `/students`는 JSP로 만든 HTML 문서를 돌려줘요. 그래서 학생 목록을 **JSON**(자바스크립트 객체 모양으로 쓴 글자 데이터)으로 주는 주소 `/api/students`를 따로 만들어요.

새 Controller에는 `@RestController`를 붙여요. `@Controller` 메서드가 `"students"`를 돌려주면 Spring은 그걸 뷰 이름으로 보고 `students.jsp`로 HTML을 만들어요. `@RestController` 메서드가 돌려준 값은 **그대로 응답 본문**이 돼요. `List<Student>`를 돌려주면 Spring이 학생마다 getter(`getId()`, `getName()` …)를 읽어 `{"id":1,"name":"한코딩",…}` 모양의 JSON 배열로 바꿔요.

검색 로직은 새로 쓰지 않아요. JSP용 Controller가 쓰던 `StudentService`를 생성자로 받아서 `findStudents(keyword)`를 그대로 불러요. 두 Controller가 같은 Service를 쓰니까 데이터와 검색 규칙이 똑같아요.

`@RequestParam(name = "keyword", defaultValue = "")`는 주소의 `?keyword=…` 값을 받아요. 없으면 빈 문자열이 되고, Service는 빈 검색어면 학생 전체를 돌려줘요.

주의할 점이 두 가지 있어요. 첫째, 검색 결과가 없으면 `[]`(빈 배열)가 와요. 이건 **실패가 아니에요.** 요청은 정상으로 처리됐고(상태 코드 200), 조건에 맞는 학생이 없을 뿐이에요. 6단계에서 화면도 둘을 다르게 보여 줘요. 둘째, JSP용 Controller는 `keyword.trim()`으로 앞뒤 공백을 지우고 넘기지만, 이 API Controller는 받은 값을 그대로 넘겨요. 그래서 React 쪽에서 `trim()`한 뒤 보내요 (5단계).

### ▶ 직접 해 보기 — `StudentApiController.java`

IntelliJ에서 `src/main/java/com/example/renderingdemo` 폴더를 우클릭 → **New → Java Class** → `StudentApiController`. 내용을 전부 바꿔요. 강의 코드의 패키지는 `com.hancoding.renderingdemo`라서 내 프로젝트 패키지로 맞췄어요. `Student.java`, `StudentService.java`, `StudentPageController.java`, `students.jsp`는 건드리지 않아요.

```java
package com.example.renderingdemo;

import java.util.List;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class StudentApiController {

    private final StudentService studentService;

    public StudentApiController(StudentService studentService) {
        this.studentService = studentService;
    }

    @GetMapping("/api/students")
    public List<Student> students(
            @RequestParam(name = "keyword", defaultValue = "")
            String keyword) {

        return studentService.findStudents(keyword);
    }
}
```

Spring을 ■로 멈추고 ▶로 다시 실행한 뒤, 브라우저에서 주소 세 개를 열어요.

`http://localhost:8080/api/students`
```text

```
`http://localhost:8080/api/students?keyword=한`
```text
[{"id":1,"name":"한코딩","email":"han@example.com","className":"풀스택 1반"}]
```
`http://localhost:8080/api/students?keyword=없는학생`


강의 자료의 JSON은 이름·이메일·반이 조금 달라요(이리액트, 풀스택 A반 …). 02에서 만든 데이터가 그대로 나오면 맞아요. `http://localhost:8080/students`(JSP 화면)도 그대로 열려요.

**바꿔 보기**
- `http://localhost:8080/api/students?keyword=%20한`(`%20`은 공백)을 열면 `[]`예요. JSP 화면 `http://localhost:8080/students?keyword=%20한`은 한코딩이 나와요. JSP Controller만 `trim()`하기 때문이에요.
- `@RestController`를 `@Controller`로, import 줄을 `import org.springframework.stereotype.Controller;`로 바꾸고 Spring을 다시 실행해요. `/api/students`를 열면 `Whitelabel Error Page`와 `(type=Not Found, status=404)`가 나와요. `@Controller`는 돌려준 값을 응답 본문으로 쓰지 않고 JSP를 찾는데, 이 주소에 맞는 JSP가 없어서예요. 확인하고 되돌린 뒤 다시 실행해요.

## 2단계: React 프로젝트 만들고 Vite 프록시로 연결하기

**🧭 맥락**: Spring 06에서는 React가 8080에 직접 요청해서 `@CrossOrigin`이 필요했어요. 오늘은 Vite가 중간에서 요청을 넘겨 줘서 Spring을 고치지 않아요.

브라우저는 페이지를 연 **출처**(프로토콜 + 주소 + 포트, 예: `http://localhost:5173`)와 다른 출처에서 온 응답을 JavaScript가 읽지 못하게 막아요. 서버가 "이 출처는 읽어도 된다"고 허락하는 규칙이 **CORS**이고, Spring 06의 `@CrossOrigin`이 그 허락이었어요.

오늘은 다른 방법을 써요. React 코드는 `fetch("/api/students")`처럼 주소 앞부분 없이(상대 주소로) 요청해요. 그러면 브라우저는 페이지와 같은 출처인 `http://localhost:5173/api/students`, 즉 Vite 개발 서버로 보내요. Vite는 `vite.config.js`의 **프록시**(받은 요청을 다른 서버로 넘겨 주는 기능) 설정을 보고 `/api`로 시작하는 요청을 `http://localhost:8080`(Spring)으로 넘겨요. Spring의 응답도 Vite를 거쳐 브라우저로 돌아와요. 브라우저는 5173에만 요청한 거라 출처가 같고, Spring에 CORS 설정이 필요 없어요.

이 프록시는 `npm run dev`로 띄운 **개발 서버에만** 있어요. 나중에 배포할 때는 API를 잇는 방법을 따로 정해야 해요.

설정 항목은 세 가지예요.
- `port: 5173`: Vite가 쓸 포트예요.
- `strictPort: true`: 5173이 이미 쓰이고 있으면 다른 포트로 넘어가지 않고 실행을 멈춰요. 주소가 5174로 바뀌어 헷갈리는 일을 막아요.
- `proxy`의 `"/api"`: `/api`로 시작하는 요청을 `target`(8080)으로 넘겨요. `changeOrigin: true`는 넘기는 요청의 `Host` 헤더를 8080 기준으로 바꾸는 옵션이에요.

## 3단계: 화면에 필요한 state 정하기 — 입력 중인 검색어와 적용된 검색어

**🧭 맥락**: JSP에서는 검색어가 주소(`?keyword=한`)에 있었고, 서버가 그걸 읽어 입력창 `value`에 다시 써 줬어요. React 화면에서는 이런 값을 **state**(값이 바뀌면 React가 화면을 다시 그리는 변수)로 들고 있어요.

이 화면의 state는 다섯 개예요.
- `keyword`: 입력창에 지금 쳐 있는 글자. 처음 `""`.
- `searchKeyword`: 실제로 검색에 쓴 검색어. 처음 `""`.
- `students`: 서버에서 받은 학생 목록. 처음 `[]`.
- `loading`: 요청 중인지. 처음 `true`.
- `error`: 실패 안내 문구. 처음 `""`.

검색어를 왜 둘로 나눌까요? 입력창에 글자를 칠 때마다 `onChange`가 실행돼요. 여기서 검색 조건까지 바꾸면 `한`, `한코`, `한코딩`처럼 글자마다 서버에 요청이 가요. 그래서 입력할 때는 `keyword`만 바꾸고, 검색 버튼을 눌렀을 때만 값을 `searchKeyword`로 옮겨요. 4단계의 `useEffect`는 `searchKeyword`만 지켜보니까, 버튼을 눌렀을 때만 요청이 가요.

`loading`이 `true`로 시작하는 데도 이유가 있어요. 이 화면은 나타나자마자 학생 목록을 조회해요. 처음 그려지는 순간이 이미 "불러오는 중"이에요. 버튼을 눌러야 요청하던 비동기 04는 `false`로 시작했어요.

### ▶ 직접 해 보기 — 강의 최종 코드 넣기

여기서 강의 코드를 한 번에 넣어요. 4~6단계는 이 코드를 부분별로 봐요.

**① `src/App.jsx`** — 내용을 전부 바꿔요.

```jsx
import { useEffect, useState } from "react";
import "./App.css";

function App() {
  const [keyword, setKeyword] = useState("");
  const [searchKeyword, setSearchKeyword] = useState("");
  const [students, setStudents] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState("");

  useEffect(() => {
    let ignore = false;

    async function loadStudents() {
      setLoading(true);
      setError("");

      try {
        const params = new URLSearchParams({
          keyword: searchKeyword,
        });

        const response = await fetch(
          `/api/students?${params.toString()}`
        );

        if (!response.ok) {
          throw new Error(
            `학생 목록을 가져오지 못했습니다. (${response.status})`
          );
        }

        const data = await response.json();

        if (!ignore) {
          setStudents(data);
        }
      } catch (error) {
        if (!ignore) {
          setError(error.message);
        }
      } finally {
        if (!ignore) {
          setLoading(false);
        }
      }
    }

    loadStudents();

    return () => {
      ignore = true;
    };
  }, [searchKeyword]);

  function handleSearch(event) {
    event.preventDefault();

    const trimmedKeyword = keyword.trim();

    setKeyword(trimmedKeyword);
    setSearchKeyword(trimmedKeyword);
  }

  function handleShowAll() {
    setKeyword("");
    setSearchKeyword("");
  }

  return (
    <main className="container">
      <header className="page-header">
        <p className="label">Spring Boot API + React</p>
        <h1>학생 목록</h1>
        <p>이름의 일부를 입력하여 학생을 검색하세요.</p>
      </header>

      <form
        className="search-form"
        onSubmit={handleSearch}
      >
        <label htmlFor="keyword">학생 이름</label>

        <div className="search-controls">
          <input
            id="keyword"
            type="text"
            name="keyword"
            placeholder="예: 한"
            value={keyword}
            onChange={(event) => {
              setKeyword(event.target.value);
            }}
          />

          <button type="submit" disabled={loading}>
            검색
          </button>

          <button
            type="button"
            className="secondary-button"
            onClick={handleShowAll}
            disabled={loading}
          >
            전체 보기
          </button>
        </div>
      </form>

      {searchKeyword !== "" && (
        <p className="search-summary">
          검색어: <strong>{searchKeyword}</strong>
        </p>
      )}

      <section aria-live="polite">
        {loading && (
          <p className="status-message">
            학생 목록을 불러오는 중입니다.
          </p>
        )}

        {!loading && error !== "" && (
          <p className="error-message" role="alert">
            {error}
          </p>
        )}

        {!loading &&
          error === "" &&
          students.length === 0 && (
            <p className="empty-message">
              검색 결과가 없습니다.
            </p>
          )}

        {!loading &&
          error === "" &&
          students.length > 0 && (
            <div className="table-wrapper">
              <table>
                <thead>
                  <tr>
```

## 4단계: `useEffect`로 서버 데이터 가져오기

**🧭 맥락**: Node 04와 Spring 06에서는 `useEffect(…, [])`로 처음 한 번만 목록을 받았어요. 오늘은 의존성 배열이 `[searchKeyword]`라서 검색 조건이 바뀔 때마다 다시 받아요.

서버에서 데이터를 가져오는 일은 화면을 그리는 계산과 떼어 놔야 해요. 컴포넌트 본문에서 바로 `fetch`하면 다시 그릴 때마다 요청이 나가고, 받은 결과로 state를 바꾸면 또 다시 그려서 끝없이 반복돼요. 그래서 **`useEffect`**(화면을 그린 뒤 바깥 시스템과 화면을 맞추는 코드를 넣는 Hook)에 넣어요. 두 번째 인자 **의존성 배열** `[searchKeyword]`는 "처음 나타났을 때, 그리고 `searchKeyword`가 바뀌었을 때만 실행"하라는 뜻이에요. `keyword`만 바뀌면 실행하지 않아요.

Effect 안의 `loadStudents()`는 위에서부터 이렇게 움직여요.

1. `setLoading(true)`, `setError("")`: 안내를 "불러오는 중"으로 바꾸고 이전 오류를 지워요.
2. `new URLSearchParams({ keyword: searchKeyword })`: 검색어를 주소 뒤에 붙일 글자(쿼리 문자열)로 바꿔요. 한글·공백·`&`도 주소에 맞게 바꿔 줘요. `한`은 `keyword=%ED%95%9C`, 빈 검색어는 `keyword=`가 돼요.
3. `` fetch(`/api/students?${params.toString()}`) ``: 2단계의 프록시를 타도록 상대 주소로 요청해요.
4. `if (!response.ok) throw …`: `fetch`는 서버가 404·500 같은 실패 상태 코드로 답해도 오류를 던지지 않아요. 응답이 오기만 하면 성공으로 끝나요. 그래서 `response.ok`(상태 코드가 200~299면 `true`)를 직접 검사하고, 아니면 `throw`로 `catch`에 보내요. 문구 끝의 `(${response.status})`로 상태 코드도 보여 줘요.
5. `await response.json()` → `setStudents(data)`: 받은 JSON을 배열로 바꿔 저장해요.
6. `catch (error)` → `setError(error.message)`: 4번에서 던진 오류, 연결 실패, JSON이 아닌 응답이 모두 여기로 와요. 여기 `error`는 catch 안에서만 쓰는 오류 객체예요. state `error`와 이름만 같아요.
7. `finally` → `setLoading(false)`: 성공이든 실패든 로딩을 끝내요.

남은 건 `ignore`예요. Effect가 돌려주는 함수 `return () => { ignore = true; };`를 **정리 함수**라고 해요. React는 `searchKeyword`가 바뀌어 Effect를 다시 실행하기 직전, 그리고 컴포넌트가 화면에서 사라질 때 이전 Effect의 정리 함수를 불러요. 그러면 이전 요청의 `ignore`가 `true`가 되고, 그 요청이 늦게 도착해도 `if (!ignore)`에 막혀 state를 바꾸지 못해요. 이미 다른 검색으로 바뀐 화면을 옛 결과가 덮어쓰지 않게 하는 거예요. 요청 자체를 취소하지는 않아요. 도착한 결과를 쓸지 말지만 정해요.

개발 중에는 이게 실제로 일어나요. `main.jsx`의 `<StrictMode>`(개발할 때만 켜지는, 실수를 찾아 주는 모드)는 처음 화면을 띄울 때 Effect를 실행 → 정리 → 다시 실행해요. 그래서 처음 접속하면 요청이 **두 번** 보이고, 첫 번째 결과는 `ignore` 때문에 버려져요. 사용자가 검색할 때는 한 번만 나가요.

같은 검색어로 다시 검색하면 요청이 없어요. `searchKeyword`가 이미 `"한"`이면 `setSearchKeyword("한")`을 해도 값이 바뀌지 않아서 Effect가 다시 실행되지 않아요. 이 화면은 "검색 조건이 바뀔 때 조회"하는 구성이라 정상이에요.

## 5단계: 폼 기본 제출 막기 — `preventDefault()`

**🧭 맥락**: 03에서 JSP 검색은 폼 기본 제출로 `GET /students?keyword=한` 새 문서를 받았어요. React 08(할 일 앱)에서 처음 쓴 `preventDefault()`를 여기서 다시 써요.

`<form>`이 제출되면 브라우저가 알아서 하는 일이 있어요. 이걸 **기본 동작**이라고 해요. 이 폼에는 `action`이 없어서 지금 주소로, `method`가 없어서 GET으로 제출해요. 입력창 `name="keyword"`의 값이 주소에 붙어 `http://localhost:5173/?keyword=한`으로 **새 문서를 요청**해요. JSP는 이 동작 덕분에 JavaScript 없이 검색할 수 있었어요.

React 화면에서는 이게 문제예요. 새 문서를 받으면 페이지가 처음부터 다시 시작해서 React state가 전부 처음 값으로 돌아가요. 그래서 `handleSearch`의 첫 줄에서 `event.preventDefault()`로 기본 동작을 막아요. React를 쓴다고 폼의 기본 동작이 저절로 없어지지는 않아요.

막은 다음에는 state만 바꿔요. `keyword.trim()`으로 앞뒤 공백을 지우고, 정리한 값을 `keyword`(입력창에도 정리된 값이 보이게)와 `searchKeyword`(검색 조건) 둘 다에 넣어요. `searchKeyword`가 바뀌었으니 4단계의 Effect가 요청을 보내요.

**전체 보기** 버튼은 `type="button"`이에요. 폼 안의 `<button>`은 `type`을 안 쓰면 제출 버튼이 돼요. 그러면 클릭 한 번에 `onClick`(전체 보기)과 폼 제출(검색)이 둘 다 일어나요. JSP의 전체 보기는 `<a href>` 링크라서 새 문서를 받았지만, React는 `handleShowAll()`로 두 검색어 state를 `""`로 비우기만 해요.

## 6단계: 로딩·오류·빈 결과·목록 나눠 보여 주기

**🧭 맥락**: 비동기 04에서 느린 API를 기다리는 화면을 만들었어요. CSR은 화면이 먼저 뜨고 데이터가 나중에 와서, 기다리는 동안과 실패했을 때를 꼭 보여 줘야 해요.

JSP는 서버가 학생 목록을 다 넣은 HTML을 보내서, 화면이 나타나는 순간 목록도 있었어요. React 화면은 빈 틀이 먼저 뜨고 JSON을 받은 다음에 표가 생겨요. 그 사이에 무슨 일이 있는지 사용자에게 알려 줘야 해요.

`<section aria-live="polite">` 안에 네 덩어리가 있고, 조건이 서로 겹치지 않아서 항상 하나만 보여요.
- `loading`이면 → "학생 목록을 불러오는 중입니다."
- 로딩이 끝났고 `error`가 있으면 → 오류 문구 (`role="alert"`)
- 로딩이 끝났고 오류가 없고 `students.length === 0`이면 → "검색 결과가 없습니다."
- 로딩이 끝났고 오류가 없고 학생이 있으면 → 표

`{조건 && (…)}`는 조건이 참일 때만 뒤의 JSX를 그려요(**조건부 렌더링**). 조건마다 `!loading && error === ""`를 반복해서, 오류가 났는데 "검색 결과가 없습니다."까지 같이 뜨는 일을 막아요. 빈 결과와 실패를 나누는 게 핵심이에요. 빈 결과는 "찾아봤는데 없다"이고, 실패는 "찾아보지 못했다"라서 사용자가 할 일이 달라요.

그 밖에 `disabled={loading}`으로 요청 중에는 두 버튼을 막아요. `button:disabled` 스타일 때문에 흐려지고 마우스 커서가 기다림 모양이 돼요. `searchKeyword`가 있으면 표 위에 "검색어: 한"을 보여 줘요. `aria-live="polite"`는 이 영역 내용이 바뀌면 화면 낭독기가 읽어 주게 하는 속성이에요.

브라우저가 연결된 곳은 Vite라서, Spring이 꺼져도 브라우저는 Vite에게서 응답을 받아요. Vite가 Spring에 넘기지 못해서 502(Bad Gateway, 중간 서버가 뒤쪽 서버에 닿지 못했다는 뜻)로 답한 거예요. wiki에는 `(500)`으로 적혀 있는데, 이 Mac의 Vite 8.3.8에서는 502가 나왔어요. Vite 버전에 따라 숫자가 다를 수 있어요. 비동기 04처럼 서버에 직접 요청할 때는 서버가 꺼지면 `fetch` 자체가 실패했어요.

**바꿔 보기** (하나씩 바꾸고 되돌려요)
- `if (!response.ok) { … }` 블록을 지우고, Spring을 끈 채 다른 검색어로 검색해요 → `Failed to execute 'json' on 'Response': Unexpected end of JSON input`. 502 응답은 본문이 비어 있는데 `json()`으로 읽으려다 실패한 거예요. 사용자는 영어 문장만 보고 원인을 알 수 없어요.
- `vite.config.js`에서 `proxy: { … },` 부분을 지우고 저장한 뒤 새로고침해요 → `Unexpected token '<', "<!doctype "... is not valid JSON`. 프록시가 없으면 Vite가 `/api/students`에 자기 `index.html`을 200으로 줘요. `response.ok`는 통과했지만 HTML을 JSON으로 읽다가 실패했어요.

## 7단계: Network로 JSP SSR과 React CSR 비교하기

**🧭 맥락**: 03에서 JSP 화면의 Network를 봤어요. React 화면을 같은 방법으로 열면, 화면은 똑같아 보여도 브라우저가 받은 것은 전혀 달라요.

React 화면을 새로고침하면 처음 받는 HTML(Type `document`)에는 학생 이름이 없어요. 표가 들어갈 빈 `<div id="root"></div>`와 JavaScript 파일 연결뿐이에요. 그다음 브라우저가 JavaScript 파일들을 받아 실행하고, React가 `/api/students?keyword=`로 JSON을 요청하고, 받은 데이터로 `<div id="root">` 안에 표를 만들어요. 그래서 학생 이름은 Response에는 없고 Elements(지금 화면의 HTML)에만 있어요. 검색할 때는 새 문서 없이 API 요청 하나만 생겨요.

JSP는 반대였어요. 처음 받은 HTML에 이미 학생 이름이 있었고, 검색하면 결과가 들어간 HTML 문서를 통째로 새로 받았어요.

그렇다고 "CSR이면 서버 요청이 없다"는 건 아니에요. React 화면도 검색할 때마다 Spring에 요청해요. 줄어든 건 **문서 HTML을 다시 만들고 페이지를 옮기는 과정**이에요. 또 03 6단계처럼 JSP에도 JavaScript를 붙이면 일부만 바꿀 수 있어서, 이 비교를 모든 SSR·CSR의 특징으로 넓히지 않아요.

대신 잃은 것도 있어요. 검색어가 주소에 없어서 새로고침하거나 주소를 복사해 보내면 검색 조건이 사라져요. JavaScript가 없으면 목록이 아예 안 나와요. CSR이라서 꼭 그런 건 아니에요. CSR에서도 검색어를 주소에 저장할 수 있지만, 저절로 되지 않고 따로 만들어야 해요. 이번 예제는 그걸 만들지 않았어요.

### ▶ 직접 해 보기

`http://localhost:5173`에서 개발자 도구 → Network → 새로고침.

1. Type `document` 요청(`localhost`) → **Response**. 이 Mac에서 나온 내용이에요. 위쪽 `<script>` 몇 줄은 Vite 개발 서버가 넣은 거예요. 학생 이름은 한 글자도 없어요.
   ```html
   <!doctype html>
   <html lang="en">
     <head>
       <script type="module">import { injectIntoGlobalHook } from "/@react-refresh";
   injectIntoGlobalHook(window);
   window.$RefreshReg$ = () => {};
   window.$RefreshSig$ = () => (type) => type;</script>

       <script type="module" src="/@vite/client"></script>

       <meta charset="UTF-8" />
       <link rel="icon" type="image/svg+xml" href="/favicon.svg" />
       <meta name="viewport" content="width=device-width, initial-scale=1.0" />
       <title>rendering-react</title>
     </head>
     <body>
       <div id="root"></div>
       <script type="module" src="/src/main.jsx"></script>
     </body>
   </html>
   ```
2. 그 아래 Type `script` 요청들: `client`, `main.jsx`, `@react-refresh`, `react.js?v=…`, `react-dom_client.js?v=…`, `App.jsx`, `App.css` … 개발 서버는 CSS도 JavaScript 모듈로 보내서 `App.css`도 Type이 `script`예요.
3. **Fetch/XHR** 필터 → `students?keyword=`가 두 개(StrictMode)예요. Response는 학생 네 명 JSON이고, Headers의 `Content-Type`은 `application/json;charset=UTF-8`이에요.
4. 지우기 버튼(동그라미에 사선)으로 목록을 비우고 `한`을 검색해요. 필터를 **All**로 바꿔도 `students?keyword=%ED%95%9C` **하나만** 있어요. Request URL은 `http://localhost:5173/api/students?keyword=%ED%95%9C`예요. 프록시를 썼어도 5173으로 보이는 게 정상이에요. 8080으로 넘기는 일은 Vite가 안에서 해요.
5. 다른 탭에서 `http://localhost:8080/students`를 열고 같은 `한`을 검색해요. Type `document` 요청 `students?keyword=%ED%95%9C`가 생기고, Response에 `한코딩`이 든 `<tr>`가 있어요 (03에서 본 것).

**바꿔 보기**
- React 화면에서 `한`을 검색한 뒤 새로고침 → 네 명, 빈 입력창으로 돌아가요. 주소에 검색어가 없어서예요. JSP 화면은 새로고침해도 주소의 `?keyword=한` 덕분에 결과가 그대로예요.
- 개발자 도구 안을 클릭 → `Cmd + Shift + P` → `Disable JavaScript` → 새로고침 → React 화면은 아무것도 없는 하얀 화면이에요. 초기 HTML의 `<div id="root">`가 비어 있으니까요. 같은 상태에서 JSP 화면은 목록과 검색이 그대로 동작해요 (03 5단계). 끝나면 `Enable JavaScript`로 되돌려요.

다 봤으면 정상 상태로 되돌려요. 속도는 No throttling, JavaScript는 켜기, 바꿔 본 코드는 강의 코드로 되돌리기, 서버는 Vite `Ctrl + C`와 Spring ■로 끄기예요.

## 마무리: CSR에서 `한`을 검색하면 일어나는 일

1. 입력창에 `한`을 치면 `onChange`가 `setKeyword("한")`을 해요. React가 입력창을 다시 그려요. 요청은 없어요.
2. **검색**을 누르면 폼의 `submit` 이벤트가 생기고 `handleSearch`가 실행돼요.
3. `event.preventDefault()`가 새 문서 요청(`/?keyword=한`)을 막아요. 주소와 문서는 그대로예요.
4. `"한".trim()`한 값으로 `setKeyword("한")`, `setSearchKeyword("한")`을 해요.
5. React가 다시 그려요. 표 위에 "검색어: 한"이 생겨요. `searchKeyword`가 `""`에서 `"한"`으로 바뀌었으니 React가 이전 Effect의 정리 함수(`ignore = true`)를 부르고 Effect를 새로 실행해요.
6. `setLoading(true)` → "학생 목록을 불러오는 중입니다."가 보이고 두 버튼이 막혀요.
7. `URLSearchParams`가 `keyword=%ED%95%9C`를 만들고, `fetch("/api/students?keyword=%ED%95%9C")`가 브라우저에서 5173(Vite)으로 가요.
8. Vite 프록시가 같은 요청을 `http://localhost:8080/api/students?keyword=%ED%95%9C`로 넘겨요.
9. Spring의 `StudentApiController`가 `keyword`로 `"한"`을 받아 `StudentService.findStudents("한")`을 불러요. JSP 때와 같은 메서드예요.
10. 돌려받은 `List<Student>`(한코딩 한 명)를 Spring이 JSON `[{"id":1,"name":"한코딩",…}]`으로 바꿔 응답하고(`application/json`), Vite가 그대로 브라우저에 전해요.
11. `response.ok`가 `true` → `response.json()` → `ignore`가 `false`라서 `setStudents(data)`.
12. `finally`에서 `setLoading(false)`. React가 다시 그리면서 네 조건 중 "학생이 있음"이 맞아 표에 한코딩 한 줄을 그려요. 주소창은 `http://localhost:5173/` 그대로예요.

03의 JSP 검색은 이랬어요. 폼 기본 제출 → `GET /students?keyword=한` 새 문서 요청 → `StudentPageController` → 같은 `StudentService` → `Model`에 담기 → `students.jsp`가 결과와 검색어를 넣은 **HTML 전체**를 만듦 → 브라우저가 이전 문서를 버리고 새 문서를 표시. 조회 로직(9번)은 같고, 그 앞뒤가 달라요. JSP는 서버가 HTML을 만들고 브라우저는 문서를 바꿔요. React는 서버가 JSON만 주고, 브라우저의 React가 지금 문서 안의 표만 고쳐요.
