# 개념 정리 — SSR-CSR과정 03. SSR의 요청 흐름과 화면 갱신 확인하기

> 날짜: 2026-11-24 · wiki: [03_SSR요청흐름](../../../../wiki/08_SSR-CSR과정/03_SSR요청흐름.md)
> 단계별 설명문으로 쓰고, 단계 끝마다 직접 해 보는 예시를 둔다. 쉬운 말, 비유 없이. 응답 내용은 이 Mac에서 curl로 미리 확인했다 (브라우저 화면은 그 결과를 바탕으로 설명).

## 들어가며

**🧭 맥락 — 지금 어디쯤**

01회차에서 SSR과 CSR을 말로 배웠어요. SSR은 서버가 데이터를 넣은 HTML을 만들어 보내는 방식이고, CSR은 서버가 데이터만 보내고 브라우저의 JavaScript가 화면을 만드는 방식이에요. 02회차에서는 Spring Boot와 JSP로 학생 목록·검색 화면(`rendering-demo`)을 직접 만들었어요.

그런데 화면만 봐서는 이 페이지가 정말 SSR인지 알 수 없어요. React로 만든 CSR 화면도 똑같이 학생 네 명을 보여 줄 수 있거든요. 차이는 화면 뒤에서 브라우저와 서버가 **무엇을 주고받았는지**에 있어요.

03회차는 새 코드를 쓰지 않아요. 02에서 만든 페이지를 켜 두고, 크롬 개발자 도구로 오가는 요청과 응답을 직접 봐요. 확인할 것은 세 가지예요.
- 서버가 보낸 HTML 안에 학생 이름이 이미 들어 있나?
- 검색하면 어떤 요청이 가고, 무엇이 돌아오나?
- JavaScript를 꺼도 페이지가 동작하나?

과정 안에서는 01 배경 → 02 JSP로 만들기 → **03 주고받는 것 보기(오늘)** → 04 React로 같은 화면 만들기 순서예요. 오늘 본 Network 화면이 04에서 비교 기준이 돼요. 04의 React 화면을 같은 방법으로 열어 보면, 오늘과 무엇이 다른지가 곧 SSR과 CSR의 차이예요.

## 🛠 시작하기

1. IntelliJ에서 `practice/08_SSR-CSR과정/rendering-demo` 프로젝트를 열어요.
2. `RenderingDemoApplication`의 `main` 줄 왼쪽 초록 **▶** → **Run**. Run 창에 `Tomcat started on port 8080 (http) with context path '/'`와 `Started RenderingDemoApplication in … seconds`가 나오면 서버가 켜진 거예요.
3. 크롬 주소창에 `http://localhost:8080/students` → 학생 네 명(한코딩, 김자바, 이스프링, 박리액트)이 보여요.
4. 개발자 도구를 열어요. 페이지 빈 곳 오른쪽 클릭 → **검사**, 또는 `Cmd + Option + I`. 위쪽 탭 줄에서 **Network**를 눌러요.

개발자 도구가 한국어로 나오면 이름이 이렇게 바뀌어 있어요: Network → 네트워크, Elements → 요소, Console → 콘솔, Headers → 헤더, Payload → 페이로드, Response → 응답, Preserve log → 로그 보존.

**터미널로 볼 때**: curl은 주소로 요청을 보내고, 받은 응답을 글자 그대로 보여 주는 프로그램이에요. Mac에 기본으로 있어요. 서버를 켠 채로 터미널에서 쳐요.

```bash
curl -i http://localhost:8080/students
```

`-i`는 응답 본문 앞에 응답 헤더도 같이 보여 달라는 옵션이에요. 맨 위가 `HTTP/1.1 200`이고 아래로 HTML이 쭉 나오면 돼요. 이 글의 터미널 출력은 모두 이렇게 미리 받아 본 거예요. `JSESSIONID` 값과 `Date`는 칠 때마다 달라요.

이 글은 학생 데이터를 Java 목록으로 둔 02 버전 기준이에요. 02를 MyBatis + DB 버전으로 만들었다면 이름·이메일·반이 DB 값으로 보이고, 요청과 응답의 흐름은 같아요.

## 1단계: Network 탭에서 문서 요청 찾기

브라우저는 페이지 하나를 보여 줄 때 파일 하나만 받지 않아요. 먼저 HTML 문서를 받고, 그 HTML을 읽다가 `<link rel="stylesheet" href="/css/students.css">` 같은 줄을 만나면 CSS 파일을 또 받아요. 브라우저가 서버에 "이 주소의 내용을 주세요"라고 보내는 것을 **요청**, 서버가 돌려보내는 것을 **응답**이라고 해요. **Network 탭**은 이 요청과 응답을 한 줄씩 기록해 보여 주는 개발자 도구 화면이에요.

Network는 **열려 있는 동안 생긴 요청만** 기록해요. 페이지를 먼저 열고 개발자 도구를 나중에 열었다면 목록이 비어 있어요. 그래서 Network를 연 다음 새로고침을 해요.

새로고침하면 이런 줄이 보여요.
- `students`: HTML 문서예요. Type 칸이 `document`예요.
- `students.css`: 화면을 꾸미는 CSS예요. Type 칸이 `stylesheet`예요.
- `favicon.ico`: 브라우저 탭에 작은 아이콘을 띄우려고 브라우저가 알아서 보내는 요청이에요. 이 프로젝트에는 아이콘 파일이 없어서 Status가 빨간 `404`(그 주소에 아무것도 없음)로 보일 수 있어요. 학생 목록과는 상관없어요.

오늘 볼 것은 `students` 하나예요. 이렇게 **브라우저가 화면에 띄울 HTML 문서를 받아 오는 요청**을 문서 요청이라고 하고, 개발자 도구에서는 줄여서 **Doc**이라고 해요. 필터 줄의 `Doc`를 누르면 문서 요청만 남아요.

자주 하는 실수는 두 가지예요. 새로고침을 안 해서 빈 목록을 보고 "요청이 없다"고 생각하는 것, 그리고 빨간 `favicon.ico`를 보고 페이지가 실패했다고 생각하는 것이에요.

### ▶ 직접 해 보기

브라우저에서:
1. Network 탭을 연 채로 `Cmd + R`(새로고침)을 눌러요.
2. Name 칸에 `students`, `students.css`가 보이고 Status 칸은 둘 다 `200`이에요. `favicon.ico`가 보이면 `404`예요.
3. 필터 줄에서 `Doc`를 누르면 `students`만 남아요. 다시 `All`을 눌러 전체를 봐요.

터미널에서 (브라우저가 보낸 세 요청을 하나씩 보내 봐요):

```bash
for p in /students /css/students.css /favicon.ico; do
  curl -s -o /dev/null -w "%{http_code} %{content_type}  $p\n" "http://localhost:8080$p"
done
```

```text
200 text/html;charset=UTF-8  /students
200 text/css;charset=UTF-8  /css/students.css
404 application/json;charset=UTF-8  /favicon.ico
```

`-s`는 진행 표시를 숨기고, `-o /dev/null`은 본문을 버리고, `-w`는 상태 코드와 응답 형식만 찍으라는 옵션이에요.

**바꿔 보기**
- Network를 연 채로 주소를 `http://localhost:8080/student`(끝의 `s` 빼기)로 바꿔 Enter → 화면에 `Whitelabel Error Page`가 뜨고, Doc 요청 `student`의 Status가 `404`예요. 그 주소를 맡은 Controller 메서드가 없다는 뜻이에요. 주소를 되돌려요.
- 개발자 도구를 닫았다가 다시 열어요. Network가 비어 있어요. 새로고침해야 다시 쌓여요.

## 2단계: Headers — 어디로, 어떤 방식으로 보냈고, 무엇이 왔나

요청과 응답에는 본문 말고도 짧은 정보 줄이 붙어 다녀요. 이걸 **헤더**라고 해요. **요청 헤더**는 브라우저가 보낸 정보(주소, 받고 싶은 형식, 쿠키)이고, **응답 헤더**는 서버가 응답에 붙인 정보(처리 결과, 본문 형식, 본문 길이)예요.

`students`를 클릭하고 **Headers** 탭을 열어요. 맨 위 **General** 부분에 세 줄이 있어요.
- **Request URL** `http://localhost:8080/students`: 요청한 주소예요.
- **Request Method** `GET`: 요청 방식이에요. GET은 "가져오기"예요. 주소창에 치거나, 새로고침하거나, 링크를 누르면 GET이에요. 02의 Controller가 `@GetMapping("/students")`라서 이 요청을 받아요.
- **Status Code** `200`: **상태 코드**는 서버가 처리한 결과 번호예요. `200` 정상, `404` 그 주소가 없음, `405` 그 방식은 안 받음, `500` 서버 코드 오류예요. 화면에는 `200 OK`처럼 뒤에 글자가 붙어 보일 수 있어요.

그 아래 **Response Headers**에서 **Content-Type**을 찾아요. 값은 `text/html;charset=UTF-8`이에요. Content-Type은 응답 본문의 형식이에요. `text/html`은 HTML 문서라는 뜻이고, `charset=UTF-8`은 한글을 UTF-8 방식으로 적었다는 뜻이에요. 02에서 JSP 첫 줄에 쓴 `contentType="text/html; charset=UTF-8"`에서 온 값이에요.

Content-Type이 중요한 이유는 이걸로 응답이 무엇인지 구분하기 때문이에요. `text/html`은 HTML 문서, `application/json`은 JSON 데이터, `text/css`는 CSS 파일이에요. 이번 페이지는 학생 데이터를 쓰지만 JSON으로 보내지 않았어요. 학생 정보는 HTML 안에 글자로 들어 있어요. "학생 데이터니까 JSON이겠지"라고 짐작하지 말고 이 줄을 봐요. 04의 React 화면에서는 같은 학생 데이터가 `application/json`으로 와요.

응답 헤더에 `Set-Cookie: JSESSIONID=…`가 보일 때도 있어요. **쿠키**는 서버가 브라우저에 "저장해 두라"고 보내는 작은 값이고, 브라우저는 다음 요청부터 그 값을 요청 헤더 `Cookie`에 실어 보내요. `JSESSIONID`는 Spring Boot 안의 서버 프로그램(Tomcat)이 브라우저마다 붙이는 번호예요. JSP는 따로 설정하지 않으면 이 번호를 자동으로 만들어서, 쿠키가 없는 첫 요청의 응답에 `Set-Cookie`가 붙어요. 이미 쿠키를 가진 브라우저에서 새로고침하면 `Set-Cookie`는 없고, 대신 **Request Headers**에 `Cookie: JSESSIONID=…`가 보여요. 서버를 껐다 켠 뒤 첫 요청에는 새 번호로 다시 붙어요. 오늘 주제와 직접 관계는 없지만, curl과 브라우저의 응답이 조금 다르게 보이는 이유라서 알아 둬요.

### ▶ 직접 해 보기

브라우저에서:
1. `Doc` 필터 → `students` 클릭 → **Headers**.
2. General: Request URL `http://localhost:8080/students`, Request Method `GET`, Status Code `200`.
3. Response Headers: Content-Type `text/html;charset=UTF-8` (헤더 이름이 소문자 `content-type`으로 보일 수도 있어요).
4. Request Headers: `Accept: text/html,…`(HTML을 받고 싶다는 표시)와 `Cookie: JSESSIONID=…`.

터미널에서:

```bash
curl -s -v -o /dev/null http://localhost:8080/students 2>&1 | grep "^[<>]"
```

```text
> GET /students HTTP/1.1
> Host: localhost:8080
> User-Agent: curl/8.7.1
> Accept: */*
> 
< HTTP/1.1 200 
< Set-Cookie: JSESSIONID=8407D09958675442CE478F7291235847; Path=/; HttpOnly
< Content-Type: text/html;charset=UTF-8
< Content-Language: ko-KR
< Content-Length: 4155
< Date: Tue, 24 Nov 2026 06:30:19 GMT
< 
```

`-v`는 주고받는 과정을 자세히 보여 주는 옵션이고, `2>&1 | grep "^[<>]"`는 그중 헤더 줄만 남겨요. `>` 줄이 curl이 보낸 요청 헤더, `<` 줄이 서버가 보낸 응답 헤더예요. 첫 줄 `GET /students`가 Request Method와 주소, `HTTP/1.1 200`이 Status Code예요.

curl은 쿠키를 기억하지 않아서 칠 때마다 "첫 방문"이에요. 그래서 `Set-Cookie`가 매번 붙어요. 브라우저처럼 쿠키를 저장했다가 다시 보내 봐요.

```bash
curl -s -c /tmp/ssr-cookie.txt -o /dev/null http://localhost:8080/students
curl -s -i -b /tmp/ssr-cookie.txt http://localhost:8080/students | head -5
```

```text
HTTP/1.1 200 
Content-Type: text/html;charset=UTF-8
Content-Language: ko-KR
Content-Length: 4023
Date: Tue, 24 Nov 2026 06:30:19 GMT
```

`-c`는 받은 쿠키를 파일에 저장, `-b`는 그 쿠키를 같이 보내라는 옵션이에요. `Set-Cookie` 줄이 사라졌어요. 본문 길이(`Content-Length`)가 4155에서 4023으로 줄어든 이유는 3단계에서 봐요.

**바꿔 보기**
- `curl -s -i -X POST http://localhost:8080/students`(`-X POST`는 요청 방식을 POST로 바꾸는 옵션) → `HTTP/1.1 405`와 `Allow: GET`이 나와요. 이 주소는 GET만 받는다는 뜻이에요. IntelliJ Run 창에는 `Request method 'POST' is not supported`가 찍혀요.
- 1단계의 `favicon.ico`를 `curl -i http://localhost:8080/favicon.ico`로 받아 봐요. `404`인데 Content-Type이 `application/json`이고 본문이 `{"timestamp":…,"status":404,"error":"Not Found","path":"/favicon.ico"}`예요. 실패 응답에도 형식이 있고, 그것도 Content-Type으로 구분해요.

## 3단계: Response에서 학생 이름 찾기 — 페이지 소스, Elements와 비교

Headers로 "HTML이 왔다"까지 알았어요. 이제 그 HTML 안에 **학생 이름이 이미 들어 있었는지** 봐요. 이게 SSR인지 판단하는 핵심이에요.

`students` 요청의 **Response** 탭은 서버가 보낸 본문을 그대로 보여 줘요. 여기서 `한코딩`을 찾으면 첫 결과는 `<title>학생 목록 | 한코딩</title>`(02에서 제목에 넣은 이름)이고, 다음 결과가 표 안의 학생 이름이에요. 실제 응답의 첫 학생 줄은 이래요 (앞쪽 공백만 줄였어요).

```html
<tr>
    <td>
        1
    </td>
    <td>
        한코딩
    </td>
    <td>
        han@example.com
    </td>
    <td>
        풀스택 1반
    </td>
</tr>
```

강의 자료의 예시에는 `풀스택 A반`이라고 나오는데, 이 프로젝트 데이터는 `풀스택 1반`·`풀스택 2반`이에요. 이런 `<tr>`가 학생 수만큼 네 개 있어요.

02의 JSP에 썼던 `<c:forEach>`, `<c:out>`, `<c:url>`, `<c:if>`, `${…}`는 응답 어디에도 없어요. JSP는 **서버에서 실행되고, 실행 결과인 HTML 글자만** 브라우저로 가기 때문이에요. `<c:forEach>`는 학생 수만큼 `<tr>`를 찍었고, `<c:out value="${student.name}" />`은 `한코딩`이 됐어요. `<c:if test="${not empty keyword}">`의 "검색어:" 줄은 검색어가 없어서 아무것도 찍지 않았어요. JSP 태그가 있던 자리에는 빈 줄만 남아요. 응답 맨 위에 빈 줄 세 개가 있는 것도 `<%@ page … %>`, `<%@ taglib … %>` 줄이 처리되고 남은 자리예요.

`<c:url>`이 만든 주소도 볼 만해요. 쿠키가 없는 첫 요청의 응답에서는 `href="/css/students.css;jsessionid=…"`처럼 주소 뒤에 세션 번호가 붙어 있어요. 브라우저가 쿠키를 저장할지 서버가 아직 모르니, 쿠키 대신 주소로도 번호를 전할 수 있게 붙인 거예요. 다음 요청부터 브라우저가 쿠키를 보내면 붙지 않아요. 2단계에서 본 4155 → 4023바이트가 이 세 군데 글자만큼의 차이예요. 오류가 아니에요. 이 첫 화면에서 바로 검색하면 폼의 `action`에도 번호가 붙어 있어서 주소창이 `/students;jsessionid=…?keyword=…`처럼 보여요. 이것도 정상이고, 그다음 화면부터는 붙지 않아요.

HTML을 보는 곳은 세 군데가 있어요.
- **Network → Response**: 요청 하나에 서버가 보낸 본문 그대로예요.
- **페이지 소스 보기**(`Cmd + Option + U`, 또는 페이지 빈 곳 오른쪽 클릭 → 페이지 소스 보기): 새 탭에 이 페이지의 HTML 원문이 열려요. 이번 페이지는 Response와 내용이 같아서 학생 이름이 보여요.
- **Elements**: 브라우저가 HTML을 읽어서 만든 **DOM**을 지금 상태 그대로 보여 줘요. DOM은 브라우저 메모리 안에 있는 문서 구조(태그들의 나무 모양)예요. JavaScript가 DOM을 바꾸면 Elements도 바로 바뀌어요. Response와 페이지 소스는 바뀌지 않아요.

그래서 **Elements에 이름이 있다는 것만으로는 SSR이라고 할 수 없어요.** CSR은 처음 받은 HTML에 이름이 없고, JavaScript가 실행된 뒤에 DOM에 넣어요. 그래도 Elements에는 이름이 보여요. "처음 받은 응답에 있었나"는 Response(또는 페이지 소스)로 봐요.

### ▶ 직접 해 보기

브라우저에서:
1. `Doc` → `students` → **Response** → 본문을 한 번 클릭하고 `Cmd + F` → `한코딩`. 첫 결과(`<title>`)에서 다음 결과로 넘겨 `<td>` 안의 이름을 찾아요. `김자바`, `이스프링`, `박리액트`도 찾아요.
2. 같은 검색창에 `c:`를 쳐요. 결과가 0개예요.
3. `Cmd + Option + U` → 새 탭의 소스에서 `Cmd + F` → `한코딩`. Response와 같아요.
4. 개발자 도구 **Elements** 탭 → `<tbody>` 왼쪽 삼각형을 눌러 펼치면 `<tr>` 네 개가 있어요. 맨 위 빈 줄 세 개는 보이지 않아요. Elements는 받은 글자가 아니라 브라우저가 만든 구조를 보여 주기 때문이에요.
5. **Console** 탭에 아래 코드를 붙여 넣고 Enter. 처음 붙여 넣으면 경고와 함께 막힐 수 있어요. 안내대로 `allow pasting`을 치고 Enter한 다음 다시 붙여 넣어요.

```javascript
document.querySelector("tbody").insertAdjacentHTML(
  "beforeend",
  "<tr><td>5</td><td>콘솔학생</td><td>console@example.com</td><td>풀스택 3반</td></tr>"
);
```

Console에 `undefined`가 찍히는 건 정상이에요(돌려주는 값이 없는 코드라서). 화면 표에 다섯 번째 줄 `콘솔학생`이 생겨요. Elements에도 `<tr>`가 다섯 개예요. 그런데 Response에서 `콘솔학생`을 찾으면 없어요. 페이지 소스 탭을 새로고침해도 없어요. JavaScript가 DOM만 바꿨고, 서버의 응답은 그대로이기 때문이에요. CSR 화면이 바로 이런 상태예요. 새로고침하면 `콘솔학생`은 사라져요.

터미널에서:

```bash

curl -s http://localhost:8080/students | grep -c "<c:"
curl -s http://localhost:8080/students | grep -n "jsessionid"
```


`grep -n`은 찾은 줄을 줄 번호와 함께, `grep -c`는 찾은 줄 수만 보여 줘요. 이름은 있고, JSP 태그는 0개, `;jsessionid`는 curl이 매번 첫 방문이라 세 군데 다 붙어 있어요.

**바꿔 보기**
- Elements에서 `한코딩` 글자를 더블클릭 → `바꾼이름`으로 고치고 Enter → 화면이 바로 바뀌어요. Response에는 여전히 `한코딩`이에요. 새로고침하면 원래대로 돌아와요.

## 4단계: 검색하면 새 문서 요청이 간다

지금까지는 첫 화면이었어요. 이제 검색을 봐요. 실제 응답 HTML 속 검색 폼은 이래요.

```html
<form class="search-form" action="/students" method="get">
    <input id="keyword" type="text" name="keyword" placeholder="예: 한" value="">
    <button type="submit">검색</button>
```

(줄바꿈을 줄였어요.) 폼에는 브라우저가 기본으로 하는 동작이 있어요. 검색 버튼을 누르거나 입력칸에서 Enter를 치면, 브라우저가 `action` 주소로 `method` 방식의 요청을 보내요. `method="get"`이면 입력칸의 `name`과 값을 주소 뒤에 `?keyword=한`처럼 붙여요. 주소에서 `?` 뒤의 `이름=값` 부분을 **쿼리 스트링**이라고 하고, 그 안의 `keyword=한` 하나하나를 **쿼리 파라미터**라고 해요. 02의 Controller는 `@RequestParam(name = "keyword")`로 이 값을 받아요.

주소에는 영어·숫자와 일부 기호만 그대로 쓸 수 있어요. 그래서 브라우저가 한글을 `%`와 16진수 글자로 바꿔 보내요. 이걸 **URL 인코딩**이라고 해요. `한`은 `%ED%95%9C`, `자바`는 `%EC%9E%90%EB%B0%94`가 돼요. 공백은 `+`가 돼요. Spring이 받을 때 다시 `한`으로 되돌려요. 주소창에는 `한`으로 보여도 Network의 Request URL에는 `%ED%95%9C`로 보일 수 있어요. 같은 요청이에요.

중요한 점은 이 요청이 **새 문서 요청**이라는 거예요. 브라우저는 지금 문서를 떠나서 `/students?keyword=%ED%95%9C`라는 새 문서를 받아 다시 그려요. 그런데 Network는 기본 설정에서 새 문서로 넘어갈 때 기록을 지워요. 검색 전후를 이어서 보려면 **Preserve log**(이동해도 기록 유지)에 체크해요. 그다음 지우기 버튼(Network 왼쪽 위, 동그라미에 사선이 그어진 모양)으로 지금까지의 기록을 비우면 검색 요청만 깔끔하게 남아요.

### ▶ 직접 해 보기

브라우저에서 (`http://localhost:8080/students` 전체 목록에서 시작):
1. **Preserve log** 체크 → 지우기 버튼.
2. 검색창에 `한` → **검색**.
3. `Doc` 필터에 새 줄 `students?keyword=…`가 생겨요. 클릭 → **Headers**: Request URL `http://localhost:8080/students?keyword=%ED%95%9C`, Request Method `GET`, Status Code `200`, Content-Type `text/html;charset=UTF-8`.
4. **Payload** 탭 → **Query String Parameters**에 `keyword: 한`. 옆의 `view URL-encoded`(또는 `view source`)를 누르면 `keyword=%ED%95%9C`로 바뀌어 보여요. 검색 전 `students` 요청에는 Payload 탭이 없어요. 보낸 쿼리 파라미터가 없기 때문이에요.
5. **Response**: 학생 줄은 `한코딩` 하나뿐이고 `김자바`·`이스프링`·`박리액트`는 없어요. 위쪽에는 `<html lang="ko">`, `<head>`, `<title>`, CSS `<link>`, `<form>`이 모두 있어요. 목록만 온 게 아니라 **페이지 전체가 새로** 왔어요.

터미널에서:

```bash
curl -s "http://localhost:8080/students?keyword=%ED%95%9C" | grep -nE "<html|<head>|<title>|stylesheet|<form|value=|<strong>|<tbody>|한코딩|김자바|이스프링|박리액트"
```

```text
5:<html lang="ko">
6:<head>
11:    <title>학생 목록 | 한코딩</title>
14:    <link rel="stylesheet" href="/css/students.css;jsessionid=A4D924D92C1708E8B1EFE16272DDEDBC">
26:        <form class="search-form"
38:                    value="한"
50:                <strong>한</strong>
68:                    <tbody>
76:                                    한코딩
```

페이지의 뼈대가 모두 있고, 학생 이름은 76줄의 `한코딩` 하나예요(11줄은 제목). 38줄 `value="한"`과 50줄 "검색어: 한"은 6단계에서 다시 봐요.

한글을 그대로 쓰고 인코딩은 curl에 맡길 수도 있어요. `-G`는 값을 주소 뒤 `?`에 붙이라는 옵션, `--data-urlencode`는 그 값을 URL 인코딩하라는 옵션이에요.

```bash
curl -s -G --data-urlencode "keyword=자바" http://localhost:8080/students | grep -nE "value=|<strong>|한코딩|김자바|이스프링|박리액트"
```

```text
11:    <title>학생 목록 | 한코딩</title>
38:                    value="자바"
50:                <strong>자바</strong>
76:                                    김자바
```

**바꿔 보기**
- 주소창에 직접 `localhost:8080/students?keyword=스프링`을 치고 Enter → 검색 버튼을 누른 것과 같은 결과(이스프링)예요. 폼은 이 주소를 만들어 주는 일만 했어요.
- `없는학생`으로 검색 → Status는 `200`이고 화면에 "검색 결과가 없습니다."가 나와요. 결과가 없는 것도 정상 응답이에요.
- 입력칸에 `  한  `(앞뒤 공백)을 넣고 검색 → Request URL에는 `keyword=++%ED%95%9C++`처럼 공백이 `+`로 가지만, 응답의 입력칸은 `value="한"`이에요. Controller의 `keyword.trim()`이 공백을 지웠어요.
- 터미널에서 `curl -i "http://localhost:8080/students?keyword=한"` → `HTTP/1.1 400`(잘못된 요청)이고, IntelliJ Run 창에 `Invalid character found in the request target`이 찍혀요. 브라우저는 알아서 인코딩하지만 curl은 한글을 그대로 보내서 서버가 거절해요.

## 5단계: JavaScript를 꺼도 동작한다

3·4단계에서 학생 목록도, 검색 결과도 서버가 만든 HTML 안에 들어 있었어요. 검색도 폼의 기본 동작(주소를 만들어 새 문서 요청)으로 했고, `fetch`도 React도 쓰지 않았어요. 실제로 응답 HTML에는 `<script>` 태그가 하나도 없어요. 브라우저의 JavaScript가 할 일이 없으니, 꺼도 똑같이 동작해야 해요. 직접 꺼서 확인해요.

크롬 개발자 도구에는 **명령 메뉴**가 있어요. 개발자 도구 기능을 이름으로 찾아 실행하는 입력창이에요. 개발자 도구 안을 한 번 클릭한 상태에서 `Cmd + Shift + P`를 누르면 열려요. 여기서 `Disable JavaScript`를 고르면, 개발자 도구가 열려 있는 **이 탭에서만** JavaScript가 꺼져요. 꺼져 있는 동안 Sources 탭 이름 옆에 노란 경고 표시가 생겨요. 실습이 끝나면 꼭 `Enable JavaScript`로 다시 켜요. 6단계는 JavaScript가 켜져 있어야 해요.

하나 구분할 게 있어요. 이건 **이번 페이지의 목록과 검색** 이야기예요. SSR 페이지라도 메뉴 열기, 차트, 자동완성처럼 JavaScript를 쓰는 기능이 있을 수 있고, 그런 기능은 꺼지면 동작하지 않아요. 반대로 04에서 만들 React 화면은 처음 받은 HTML에 `<div id="root"></div>`만 있어서, JavaScript를 끄면 목록을 그릴 방법이 없어요.

### ▶ 직접 해 보기

브라우저에서:
1. 개발자 도구 안을 클릭 → `Cmd + Shift + P` → `Disable JavaScript` 입력 → 나온 항목에서 Enter. (한국어 화면이면 `JavaScript`만 쳐서 "사용 중지"가 들어간 항목을 골라요.)
2. `http://localhost:8080/students` 새로고침 → 학생 네 명이 보여요.
3. `한` 검색 → 한코딩 한 명. 주소에 `?keyword=한`이 붙고 Network `Doc`에 새 요청이 생겨요.
4. `없는학생` 검색 → "검색 결과가 없습니다."
5. **전체 보기** 링크 → 다시 네 명.
6. `Cmd + Shift + P` → `Enable JavaScript` → 새로고침.

터미널에서: curl은 JavaScript를 실행하지 못하는 프로그램이에요. 그런데도 1~4단계에서 학생 이름과 검색 결과를 다 받았어요. 그 자체가 "JavaScript 없이 동작한다"는 증거예요.

```bash
curl -s http://localhost:8080/students | grep -c "<script"
```

```text
0
```

**바꿔 보기**
- JavaScript를 끈 채로 2단계 Headers와 3단계 Response를 다시 봐요. 켰을 때와 똑같아요. 서버는 브라우저의 JavaScript가 켜졌는지 모르고, 같은 HTML을 보내요.

## 6단계: 문서 전체 교체와 부분 갱신 — 입력값과 스크롤은 어떻게 되나

검색 전후 화면은 제목과 검색창 디자인이 같아서 목록만 바뀐 것처럼 보여요. 내 컴퓨터의 서버는 빨라서 깜빡임도 거의 안 보일 수 있어요. 하지만 4단계에서 본 것처럼 브라우저는 **문서를 통째로 새로** 받았어요. 문서가 바뀌면 이전 문서에 있던 것, 즉 입력칸 요소, 스크롤 위치, JavaScript 변수도 같이 사라져요. 깜빡임이 있었나로 판단하지 말고 Doc 요청과 Response로 판단해요.

그런데 검색 후에도 입력칸에 `한`이 남아 있어요. 이전 입력칸이 남은 게 아니에요. **서버가 새 HTML의 입력칸에 다시 써 줬기** 때문이에요. 02의 Controller가 `model.addAttribute("keyword", searchKeyword);`로 검색어를 넘기고, JSP가 `value="<c:out value='${keyword}' />"`로 출력해서, 응답 HTML에 `value="한"`이 들어 있었어요(4단계 curl의 38줄). 문서를 새로 받아도 서버가 필요한 값을 다시 출력하면 일부 상태를 이어 갈 수 있어요. 반대로 서버에 보내지 않은 값은 새 문서에 남지 않아요.

CSS는 새 문서마다 다시 요청될 수 있지만, 브라우저가 전에 받아 둔 것을 쓰기도 해요. 이렇게 받아 둔 파일을 **캐시**라고 해요. curl로 확인해 보니 서버는 CSS에 `Last-Modified`(마지막 수정 시각)를 붙여 보내고, 그 시각을 다시 보내면 본문 없이 `304`(바뀌지 않았으니 갖고 있는 것을 쓰라는 뜻)로 답했어요. 그래서 Network에서 `students.css`가 Status `304`이거나 Size 칸에 `(memory cache)`, `(disk cache)`로 보일 수 있어요. 문서를 새로 받는다고 모든 파일을 다시 내려받는 건 아니에요.

다른 방법도 있어요. 기존 문서는 그대로 두고, JavaScript가 데이터만 받아서 화면의 일부만 바꾸는 **부분 갱신**이에요. 폼의 기본 제출을 막고(`event.preventDefault()`), `fetch`로 페이지를 떠나지 않은 채 요청하고, 받은 결과로 목록 부분만 바꿔요. 문서가 그대로라 입력칸, 스크롤, JavaScript 변수가 다 남아요. 대신 로딩 중 표시와 실패 처리를 JavaScript가 직접 맡아야 해요. 04의 React 화면이 이 방식이에요. 부분 갱신이 CSR만의 기능은 아니에요. JSP 페이지에도 JavaScript를 붙여 부분 갱신을 할 수 있어요. 아래 B가 그 예예요.

### ▶ 직접 해 보기

**A. 문서가 바뀌면 사라지는 것** (`http://localhost:8080/students` 전체 목록에서 시작)
1. Console에 붙여 넣고 Enter.

```javascript
document.querySelector("#keyword").style.background = "yellow";
window.memo = "검색 전에 남긴 값";
```

입력칸이 노래지고 Console에 `'검색 전에 남긴 값'`이 찍혀요.

2. `한` 검색 → 입력칸 값은 `한`인데 배경은 다시 흰색이에요. Console에 `window.memo`를 치면 `undefined`예요. 새 문서의 새 입력칸이고, JavaScript 변수도 처음부터 다시 시작했어요.
3. 입력칸에 `김`을 쓰기만 하고(검색 안 함) **전체 보기**를 눌러요. 입력칸이 비어 있어요. 서버에 보낸 적 없는 값은 새 문서에 없어요.

**B. 부분 갱신 맛보기** (새로고침해서 전체 목록에서 시작. "검색 결과가 없습니다." 화면에서 시작하면 표가 없어서 안 돼요)
1. A의 1번 코드를 다시 붙여 넣어 입력칸을 노랗게 해요.
2. 아래 코드를 Console에 붙여 넣고 Enter.

```javascript
document.querySelector("form").addEventListener("submit", async (event) => {
  event.preventDefault(); // 기본 제출(새 문서 요청)을 막아요
  const keyword = document.querySelector("#keyword").value;
  const response = await fetch("/students?keyword=" + encodeURIComponent(keyword));
  const html = await response.text();
  const newPage = new DOMParser().parseFromString(html, "text/html");
  const newBody = newPage.querySelector("tbody");
  document.querySelector("tbody").innerHTML =
    newBody ? newBody.innerHTML : "<tr><td colspan='4'>검색 결과가 없습니다.</td></tr>";
});
```

`addEventListener("submit", …)`는 폼이 제출될 때 이 함수를 실행하라는 뜻이에요. `event.preventDefault()`가 새 문서 요청을 막아요. `fetch`는 페이지를 떠나지 않고 요청을 보내고, `encodeURIComponent`는 한글을 `%ED%95%9C`로 인코딩해요. `DOMParser`는 받은 HTML 글자를 문서 구조로 바꿔서 그 안의 `<tbody>`를 찾을 수 있게 해요. 마지막 줄이 지금 표의 본문만 새 본문으로 바꿔요.

3. Network 지우기 버튼 → `한` 검색. 이렇게 보여요.
   - 표에는 한코딩 한 줄만 남아요.
   - 주소창은 `/students` 그대로예요(`?keyword=` 없음).
   - 입력칸은 노란색 그대로이고, `window.memo`도 그대로예요.
   - Network `Doc` 필터에는 새 요청이 없어요. `Fetch/XHR` 필터에 `students?keyword=…`가 있고 Type은 `fetch`예요.
   - 그 요청의 Response는 4단계와 같은 페이지 전체 HTML이에요. 서버는 똑같이 답했고, JavaScript가 그중 표 본문만 꺼내 바꿨어요.
4. `없는학생` → 안내 한 줄, `자바` → 김자바, 빈칸으로 검색 → 네 명. 모두 주소와 노란색이 그대로예요. (이 코드는 미리 같은 서버 응답으로 돌려서 이 결과를 확인했어요.)
5. 새로고침하면 붙여 넣은 코드가 사라지고 원래 방식(새 문서 요청)으로 돌아와요.

**바꿔 보기**
- **스크롤 위치**: `Cmd + +`를 여러 번 눌러 페이지가 스크롤될 만큼 확대해요. 입력칸을 클릭해 `한`을 쓰고, 화면을 조금 내린 뒤 Console에서 `window.scrollY`(지금 스크롤 위치) → 0보다 큰 숫자. 입력칸을 다시 클릭하고 Enter로 검색한 뒤 `window.scrollY` → `0`이에요. 새 문서는 맨 위부터 시작해요. B 코드를 붙인 상태에서 같은 걸 하면 숫자가 그대로예요. 끝나면 `Cmd + 0`으로 확대를 되돌려요.

## 마무리: `한`을 검색했을 때 일어나는 일

1. 입력칸에 `한`을 쓰고 **검색** 버튼(또는 Enter)을 눌러요.
2. 브라우저가 폼을 읽어요. `action="/students"`, `method="get"`, 입력칸 `name="keyword"`라서 주소 `/students?keyword=한`을 만들고, 한글을 `%ED%95%9C`로 인코딩해요.
3. 브라우저가 지금 문서를 떠나며 새 문서 요청 `GET /students?keyword=%ED%95%9C`를 보내요. 요청 헤더에는 쿠키 `JSESSIONID`도 실려요. (Network `Doc`, Payload `keyword: 한`)
4. Spring이 주소 `/students`를 보고 `StudentPageController`의 `students` 메서드를 불러요. `@RequestParam`이 `%ED%95%9C`를 되돌린 `한`을 `keyword`에 넣어 주고, `trim()`이 앞뒤 공백을 지워요.
5. `StudentService.findStudents("한")`가 네 명 중 이름에 `한`이 들어간 학생(한코딩)만 골라 돌려줘요. (DB 버전이면 이 일을 SQL의 `LIKE`가 해요.)
6. Controller가 Model에 `students`(한코딩 한 명)와 `keyword`(`한`)를 담고 `"students"`를 돌려줘요. Spring이 `/WEB-INF/views/students.jsp`를 찾아요.
7. 서버에서 JSP가 실행돼요. `<c:forEach>`가 `<tr>`를 한 번 찍고, `<c:out>`이 이름·이메일·반을 찍고, 입력칸에 `value="한"`을, `<c:if>`가 "검색어: 한" 줄을 찍어요. JSP 태그는 사라지고 HTML 글자만 남아요.
8. 서버가 응답해요. Status `200`, Content-Type `text/html;charset=UTF-8`, 본문은 `<!DOCTYPE html>`부터 `</html>`까지 페이지 전체예요.
9. 브라우저가 이전 문서를 버리고, 새 HTML을 읽어 DOM을 처음부터 만들어요. `<link>`를 보고 CSS를 요청하는데, 받아 둔 게 있으면 캐시를 써요.
10. 새 화면을 그려요. 주소창은 `?keyword=한`, 입력칸은 서버가 써 준 `한`, 표에는 한코딩 한 줄이에요. 스크롤은 맨 위이고, 이전 문서의 JavaScript 변수는 없어요.

이 모든 과정에 브라우저 JavaScript는 한 번도 쓰이지 않았어요. 그래서 5단계에서 꺼도 똑같이 동작했어요.

## 다음 회차와 연결

04회차에서는 같은 `StudentService`로 학생 목록을 **JSON**으로 응답하는 `/api/students`를 Spring에 추가하고, Vite React 프로젝트(`rendering-react`, 5173번 포트)에서 그 API를 `fetch`로 불러 화면을 만들어요. 그 화면을 오늘과 같은 방법으로 열어 보면 이런 차이가 보여요.

- 처음 받은 문서(Doc)의 Response에 학생 이름이 없어요. `<div id="root"></div>`만 있어요. 이름은 JavaScript가 실행된 뒤 Elements에만 보여요. 3단계에서 Response와 Elements를 구분한 게 여기서 쓰여요.
- 검색해도 Doc 요청이 생기지 않고, `Fetch/XHR`에 `api/students?keyword=…`가 생겨요. Content-Type은 `application/json`이에요. 6단계 B와 같은 흐름(`preventDefault` → `fetch` → 일부만 바꾸기)인데, 응답이 HTML 대신 JSON이고 화면을 바꾸는 일은 React state가 해요.
- 주소창이 그대로라 검색어가 주소에 남지 않아요(04 예제는 검색어를 URL에 저장하지 않아요). 새로고침하면 전체 목록으로 돌아가요.

04에서 API를 추가한 뒤 `curl -i "http://localhost:8080/api/students?keyword=%ED%95%9C"`를 치면 이렇게 와요 (04 코드를 넣은 프로젝트로 미리 확인했어요). 같은 한코딩 정보가 이번에는 `<html>`도 `<tr>`도 없이 데이터만 와요. 이 데이터를 화면으로 만드는 일이 서버에서 브라우저로 넘어간 게 CSR이에요.

```text
HTTP/1.1 200 
Content-Type: application/json;charset=UTF-8
Transfer-Encoding: chunked
Date: Tue, 24 Nov 2026 06:25:59 GMT

[{"id":1,"name":"한코딩","email":"han@example.com","className":"풀스택 1반"}]
```

## 오류가 날 때 찾아보기

| 오류 문장 · 증상 | 먼저 볼 곳 |
|---|---|
| 브라우저 "사이트에 연결할 수 없음" / curl `Failed to connect to localhost port 8080` | 서버가 안 켜짐 → IntelliJ Run 창에 `Tomcat started on port 8080`이 있는지 (시작하기) |
| Network 목록이 비어 있음 | 개발자 도구를 연 뒤 새로고침 (1단계) |
| `favicon.ico`가 빨간 `404` | 아이콘 파일이 없어서, 정상. 볼 것은 `students` (1단계) |
| `Whitelabel Error Page`, Status `404` | 주소 오타 (`/student` 등) (1단계) |
| `405` / Run 창 `Request method 'POST' is not supported` | 이 주소는 GET만 받음 (2단계) |
| 학생 데이터인데 Content-Type이 JSON이 아님 | 정상. 이번엔 데이터가 HTML 안에 있음 (2단계) |
| curl에만 매번 `Set-Cookie`, 링크에 `;jsessionid=…` | 쿠키 없는 첫 방문 표시, 정상 (2·3단계) |
| 주소창이 `/students;jsessionid=…?keyword=…` | 첫 방문 화면에서 바로 검색함, 정상. 다음 검색부터 안 붙음 (3단계) |
| Console에 붙여 넣기가 막힘 | `allow pasting` 입력 후 Enter, 다시 붙여 넣기 (3단계) |
| Elements에서 바꾼 내용이 Response에 없음, 새로고침하면 원래대로 | 정상. Elements는 지금 DOM, Response는 서버가 보낸 본문 (3단계) |
| 검색하니 이전 요청이 Network에서 사라짐 | Preserve log 체크 (4단계) |
| 이전 문서의 Response가 안 보임 (`Failed to load response data` 같은 문장) | 문서를 떠나면서 이전 본문을 버린 것. 다시 새로고침하거나 curl로 보기 (4단계) |
| curl `HTTP/1.1 400`, Run 창 `Invalid character found in the request target` | 한글을 그대로 보냄 → `%ED%95%9C` 또는 `-G --data-urlencode` (4단계) |
| 검색 결과가 없는데 Status `200` | 정상. "결과 없음"도 정상 응답 (4단계) |
| `Cmd + Shift + P`를 눌러도 명령 메뉴가 안 열림 | 개발자 도구 안을 먼저 클릭 (5단계) |
| Sources 탭 옆 노란 경고, 페이지 JavaScript가 안 움직임 | `Enable JavaScript` → 새로고침 (5단계) |
| `Uncaught (in promise) TypeError: Cannot set properties of null (setting 'innerHTML')` | 표가 없는 "결과 없음" 화면에서 B 코드를 붙임 → 전체 목록에서 다시 (6단계) |
| 검색 한 번에 `fetch` 요청이 두 줄 | B 코드를 두 번 붙여 함수가 두 번 붙음 → 새로고침 후 한 번만 (6단계) |
