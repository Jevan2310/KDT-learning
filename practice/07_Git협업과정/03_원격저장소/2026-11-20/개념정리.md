# 개념 정리 — Git협업과정 03. 원격 저장소

> 날짜: 2026-11-20 · wiki: [03_원격저장소](../../../../wiki/07_Git협업과정/03_원격저장소.md)
> 단계별 설명문으로 쓰고, 단계 끝마다 터미널에 직접 쳐 보는 명령을 둔다. 쉬운 말, 비유 없이. 출력은 이 Mac의 Git 2.50.1에서 로컬 폴더를 원격 저장소처럼 써서 미리 확인했다 (GitHub 주소 부분만 다르다).

## 들어가며

02회차에서 만든 버전은 내 컴퓨터의 `.git` 안에만 있어요. 노트북을 잃어버리면 기록도 같이 사라지고, 다른 사람은 내 기록을 볼 수 없어요.

03회차에서는 이 기록을 GitHub에 올리고(`push`), GitHub에 있는 새 기록을 받아 오고(`pull`), GitHub의 저장소를 통째로 내 컴퓨터에 복제해요(`clone`). `KDT학습`을 마칠 때마다 Claude가 한 `git push origin main`이 이 회차 내용이에요.

팀 프로젝트에서는 모두가 같은 GitHub 저장소에 올리고 받아요. 그래서 "받고 나서 올린다"는 순서가 중요해지고, 이 순서를 어기면 생기는 일은 05회차에서 직접 만들어 봐요.

## 🛠 시작하기 — GitHub에 연습용 저장소 만들기

이 단계는 GitHub 웹에서 직접 해요.

1. github.com에 로그인 → 오른쪽 위 **+** → **New repository**
2. Repository name: `git-practice-remote`
3. Public / Private: 원하는 대로 (비공개여도 실습에 지장 없어요)
4. **README, .gitignore, license는 모두 추가하지 않아요.** 빈 저장소로 만들어야 해요 (이유는 3단계)
5. **Create repository**
6. 다음 화면 위쪽의 **HTTPS** 주소를 복사해요. `https://github.com/<내 아이디>/git-practice-remote.git` 모양이에요. 아래 명령의 `<저장소 주소>` 자리에 이 주소를 넣어요.

로그인은 따로 안 해도 될 거예요. 이 Mac은 `KDT-learning`을 올리면서 GitHub 로그인 정보가 macOS 키체인에 저장되어 있을 거예요. 같은 계정의 새 저장소에도 그 정보가 쓰여요. 로그인 창이 뜨거나 오류가 나면 맨 아래 표를 보세요.

## 1단계: 원격 저장소란

**원격 저장소**는 인터넷이나 네트워크에 있는 저장소예요. GitHub, GitLab, Bitbucket 같은 곳에 만들어요. 여러 사람이 함께 쓰려고 두는 저장소예요.

구조는 내 컴퓨터의 `.git`과 같아요. 버전 기록과 브랜치가 들어 있어요. 다른 점은 위치뿐이에요. 그리고 두 저장소는 **저절로 맞춰지지 않아요.** 내 컴퓨터에서 커밋해도 GitHub는 모르고, GitHub에 새 커밋이 생겨도 내 컴퓨터는 몰라요. 내가 `push`해야 올라가고, `pull`해야 내려와요.

```text
[내 컴퓨터]  Working Directory → Staging Area → Local Repository
                                                    │  ▲
                                               push │  │ pull
                                                    ▼  │
[GitHub]                                      Remote Repository
```

## 2단계: `git remote` — 원격 저장소 주소에 별칭 붙이기

GitHub 주소는 길어서 매번 치기 어려워요. 그래서 내 저장소에 주소를 **별칭**으로 등록해 두고, 그 뒤로는 별칭으로 불러요.

| 명령 | 하는 일 |
|---|---|
| `git remote add [별칭] [주소]` | 원격 저장소를 별칭으로 등록. 여러 개 등록할 수 있다 |
| `git remote -v` | 등록된 원격 저장소 목록 보기 |
| `git remote rename [기존] [새 별칭]` | 별칭 바꾸기 |
| `git remote rm [별칭]` | 등록 지우기 (GitHub의 저장소는 그대로) |

별칭은 아무 이름이나 돼요. 첫 번째 원격 저장소를 보통 `origin`이라고 짓는 건 관례예요. `KDT학습`도 `origin`으로 등록되어 있어요 (01회차 6단계의 `remote.origin.url`).

`remote add`는 저장소마다 한 번만 해요. 등록 정보는 그 저장소의 `.git/config`에 저장돼요.

### ▶ 직접 해 보기 — 로컬 저장소를 만들고 GitHub 주소 등록하기

강의 예제 순서예요. 버전이 하나 있는 저장소를 만들고 주소를 등록해요.

```bash
mkdir -p ~/git-practice/remote-test
cd ~/git-practice/remote-test
git init
echo "# Remote Test" > README.md
git add README.md
git commit -m "첫 번째 커밋"
git remote -v
```

마지막 `git remote -v`는 아무것도 안 나와요. 아직 등록한 원격 저장소가 없어요.

```bash
git remote add origin <저장소 주소>
git remote -v
```

```text
origin	https://github.com/<내 아이디>/git-practice-remote.git (fetch)
origin	https://github.com/<내 아이디>/git-practice-remote.git (push)
```

같은 주소가 두 줄 나오는 게 정상이에요. `(fetch)`는 받아 올 때, `(push)`는 올릴 때 쓰는 주소예요.

**바꿔 보기**
- `git remote add origin <저장소 주소>`를 한 번 더 쳐요. `error: remote origin already exists.`가 나와요. 이미 있는 별칭이에요.
- `git remote rename origin github` → `git remote -v`로 별칭이 바뀐 걸 봐요. 이 상태에서 `git push origin main`을 치면 `fatal: 'origin' does not appear to be a git repository`가 나와요. 그런 별칭이 없어서예요. 확인했으면 `git remote rename github origin`으로 되돌려요.

## 3단계: `git push` — 내 커밋을 GitHub에 올리기

`git push [별칭] [브랜치]`는 내 컴퓨터의 그 브랜치에 있는 커밋 중 GitHub에 없는 것을 올려요. `git push origin main`은 "내 `main`의 커밋을 `origin`의 `main`으로 올린다"는 뜻이에요. 파일을 올리는 게 아니라 **커밋을** 올려요. 그래서 커밋하지 않은 변경은 올라가지 않아요.

시작하기에서 README 없이 빈 저장소를 만든 이유가 여기 있어요. GitHub에서 README를 추가하면 GitHub 쪽에 커밋이 하나 먼저 생겨요. 그러면 GitHub에는 내 컴퓨터에 없는 커밋이 있어서 push가 거부돼요. 이 상황은 05회차에서 일부러 만들어 봐요.

**`git push -f`(강제 push)는 쓰지 않아요.** GitHub의 기록과 내 기록이 달라도 내 기록으로 덮어써서, 다른 사람이 올린 커밋이 사라져요. 강의도 "매우 위험, 사용 금지"라고 해요.

### ▶ 직접 해 보기

```bash
git push origin main
```

```text
Enumerating objects: 3, done.
Counting objects: 100% (3/3), done.
Writing objects: 100% (3/3), 238 bytes | 238.00 KiB/s, done.
Total 3 (delta 0), reused 0 (delta 0), pack-reused 0 (from 0)
To https://github.com/<내 아이디>/git-practice-remote.git
 * [new branch]      main -> main
```

위의 네 줄은 보내는 양이에요(숫자는 달라요). 중요한 건 마지막 줄이에요. `* [new branch] main -> main`은 GitHub에 `main` 브랜치가 새로 생겼다는 뜻이에요. 브라우저에서 저장소 화면을 새로고침하면 `README.md`와 "첫 번째 커밋"이 보여요.

push 뒤 `git status`를 치면 `nothing to commit, working tree clean`만 나와요. `KDT학습`처럼 "GitHub보다 앞서 있다/같다"(`ahead`, `up to date`)는 안 나와요. 강의 방식(`git push origin main`)은 별칭과 브랜치를 매번 적어서, Git이 이 브랜치의 짝을 기억하지 않기 때문이에요. GitHub의 빈 저장소 화면에 나오는 `git push -u origin main`처럼 `-u`를 붙이면 짝을 기억해서, 그 뒤로는 `git push`만 쳐도 되고 `git status`에도 비교가 나와요.

**바꿔 보기**
- 파일을 하나 더 만들어 커밋하고(`echo "두 번째" > second.txt` → `git add second.txt` → `git commit -m "두 번째 파일"`) 다시 `git push origin main`을 쳐요. 마지막 줄이 `abc1234..def5678  main -> main`처럼 나와요. 새 커밋만 올라갔다는 뜻이에요. GitHub 화면의 커밋 수가 2로 바뀌어요.
- 아무것도 안 바꾸고 `git push origin main`을 한 번 더 쳐요. `Everything up-to-date`가 나와요.

## 4단계: `git clone` — GitHub 저장소를 통째로 복제하기

`git clone [주소] [폴더]`는 GitHub의 저장소를 내 컴퓨터에 그대로 복제해요. 파일만 받는 게 아니라 `.git`까지, 즉 **모든 버전 기록**이 같이 와요. 그래서 이미 저장소이고, `git init`이 필요 없어요. 받아 온 주소도 자동으로 `origin`으로 등록돼서 `git remote add`도 필요 없어요. 그래도 `git remote -v`로 확인은 해요.

폴더 이름을 생략하면 저장소 이름으로 새 폴더를 만들어요. `.`을 쓰면 지금 폴더에 바로 받는데, 이때 지금 폴더는 **비어 있어야** 해요.

`clone`은 처음 한 번 저장소 전체를 가져올 때 쓰고, 그 뒤로 새 커밋만 받을 때는 `pull`을 써요 (5단계).

### ▶ 직접 해 보기 — 다른 컴퓨터에서 받는 것처럼 복제하기

같은 Mac이지만 다른 폴더에 복제하면, 다른 컴퓨터(또는 팀원)에서 받는 것과 똑같이 동작해요.

```bash
cd ~/git-practice
git clone <저장소 주소> clone-test
cd clone-test
git remote -v
git log --oneline
```

```text
Cloning into 'clone-test'...
origin	https://github.com/<내 아이디>/git-practice-remote.git (fetch)
origin	https://github.com/<내 아이디>/git-practice-remote.git (push)
e198b1c 첫 번째 커밋
```

`remote add`를 안 했는데 `origin`이 있고, 버전 기록도 같이 왔어요. 실제로는 `Cloning into …` 아래에 받는 양을 알려 주는 `remote: …` 줄이 몇 개 더 나와요. 버전 번호는 매번 다르고, 3단계 바꿔 보기를 했으면 커밋이 두 개 보여요.

**바꿔 보기**
- 파일이 있는 폴더에서 `git clone <저장소 주소> .`을 쳐 봐요. `fatal: destination path '.' already exists and is not an empty directory.`가 나와요. `.`으로 받을 때는 빈 폴더여야 해요.

## 5단계: `git pull` — GitHub의 새 커밋 받아 오기

`git pull [별칭] [브랜치]`는 GitHub에 있는데 내 컴퓨터에 없는 커밋을 받아 와서 내 브랜치에 합쳐요. 팀원이 올린 커밋을 내 컴퓨터에 반영할 때 써요.

그래서 강의는 작업 순서를 이렇게 정해요.

1. **pull 먼저** — 그사이 다른 사람이 올린 걸 받아 둔다
2. 작업한다
3. 커밋한다
4. push한다

순서를 지키면 내 커밋이 항상 GitHub의 최신 기록 위에 쌓여서 push가 바로 돼요. pull을 안 하고 작업했는데 그사이 GitHub에 새 커밋이 생겼으면, push가 거부되거나 충돌이 나요. 이건 05회차에서 직접 해 봐요.

### ▶ 직접 해 보기 — `clone-test`에서 올리고 `remote-test`에서 받기

`clone-test`를 "다른 사람"으로 써요. 여기서 커밋해서 올려요.

```bash
cd ~/git-practice/clone-test
echo "다른 컴퓨터에서 추가" > from-clone.txt
git add from-clone.txt
git commit -m "clone에서 파일 추가"
git push origin main
```

이제 처음 폴더 `remote-test`로 돌아가요. 이 폴더는 방금 올라간 커밋을 아직 몰라요.

```bash
cd ~/git-practice/remote-test
ls
git pull origin main
ls
```

```text
README.md
From https://github.com/<내 아이디>/git-practice-remote
 * branch            main       -> FETCH_HEAD
   e198b1c..7069b34  main       -> origin/main
Updating e198b1c..7069b34
Fast-forward
 from-clone.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 from-clone.txt
README.md	from-clone.txt
```

pull 전에는 `README.md`만 있다가, pull 뒤에 `from-clone.txt`가 생겼어요. (앞에서 바꿔 보기를 했으면 `second.txt`도 보이고, 번호도 달라요.) `Fast-forward`는 내 쪽에 새 커밋이 없어서 받아 온 커밋을 그대로 이어 붙였다는 뜻이에요 (04회차에서 자세히).

**바꿔 보기**
- `git log --oneline`을 `remote-test`와 `clone-test`에서 각각 쳐요. 두 폴더의 기록이 똑같아졌어요.
- 바로 `git pull origin main`을 한 번 더 쳐요. `Already up to date.`가 나와요. 받을 게 없어요.

## 6단계: 프로젝트를 시작하는 두 가지 방법

지금까지 두 방법을 다 해 봤어요.

**내 컴퓨터에서 처음 시작할 때** (`remote-test`): `git init` → 파일 작성·커밋 → `git remote add origin 주소` → `git push origin main`. GitHub에는 빈 저장소를 먼저 만들어 둬요.

**GitHub에 이미 있는 프로젝트를 이어서 할 때** (`clone-test`): `git clone 주소` → 파일 작성·커밋 → `git push origin main`. `init`과 `remote add`가 없어요.

팀 프로젝트에서는 한 명이 첫 번째 방법으로 저장소를 만들어 올리고, 나머지는 두 번째 방법으로 시작해요. 06회차에서 이 과정을 Organization과 Fork로 해요.

## 7단계: 올리면 안 되는 파일 — `.gitignore`

GitHub에 올라간 건 다른 사람이 볼 수 있어요. 공개 저장소면 누구나 봐요. 그래서 **비밀번호, API 키 같은 민감한 정보는 커밋하지 않아요.** 보통 이런 값은 `.env` 같은 파일에 따로 두고, 그 파일을 Git이 아예 무시하게 해요.

`.gitignore`는 저장소 맨 위 폴더에 두는 글자 파일이에요. 한 줄에 하나씩, Git이 무시할 파일·폴더 이름을 적어요. 여기 적힌 파일은 `git status`에도 안 나오고 `git add .`에도 안 들어가요. Mac의 `.DS_Store`도 여기에 적어요.

조심할 게 두 가지 있어요. 첫째, **이미 커밋한 파일은 `.gitignore`에 적어도 계속 기록돼요.** 그래서 처음부터 적어 둬요. 둘째, 비밀번호를 실수로 커밋했다가 다음 커밋에서 지워도 **이전 버전에는 남아 있어요.** 이미 올렸다면 그 비밀번호나 키를 즉시 바꾸는 수밖에 없어요. 강의가 "실수로 올린 경우 즉시 비밀번호 변경"이라고 한 이유예요.

### ▶ 직접 해 보기

```bash
cd ~/git-practice/remote-test
echo "SECRET=abc" > .env
touch .DS_Store
git status -s
```

```text
?? .DS_Store
?? .env
```

`touch`는 빈 파일을 만드는 명령이에요. 둘 다 Untracked로 보여요. 이대로 `git add .`을 하면 같이 올라가요. `.gitignore`를 만들어요.

```bash
printf ".env\n.DS_Store\n" > .gitignore
git status -s
```

```text
?? .gitignore
```

`.env`와 `.DS_Store`가 목록에서 사라지고 `.gitignore`만 남았어요. `.gitignore`는 팀원도 같은 규칙을 써야 하니 커밋해서 올려요.

```bash
git add .gitignore
git commit -m ".gitignore 추가"
git push origin main
```

GitHub 화면에는 `.gitignore`만 보이고 `.env`는 없어요.

**바꿔 보기**
- 이미 커밋한 파일을 무시해 봐요: `echo "v1" > config.txt` → `git add config.txt` → `git commit -m "config 추가"` → `echo "config.txt" >> .gitignore` → `echo "v2" >> config.txt` → `git status -s`. `config.txt`가 여전히 ` M`(Modified)으로 나와요. `.gitignore`는 아직 기록되지 않은 파일에만 효과가 있어요.

## 마무리: `git push origin main` 한 번에 일어나는 일

1. `origin`이라는 별칭으로 `.git/config`에서 GitHub 주소를 찾는다.
2. 키체인에 저장된 로그인 정보로 GitHub에 접속한다.
3. 내 `main`의 커밋과 GitHub `main`의 커밋을 비교해, GitHub에 없는 커밋만 고른다.
4. 그 커밋들을 보낸다. 커밋하지 않은 변경, `.gitignore`로 무시한 파일은 가지 않는다.
5. GitHub의 `main`이 내 마지막 커밋을 가리키도록 옮긴다 (`main -> main`).
6. GitHub에 내가 없는 커밋이 있으면 5번을 하지 않고 거부한다 → 먼저 `pull` (05회차).

## 다음 회차와 연결

04회차는 다시 내 컴퓨터 안의 이야기예요. 하나의 저장소 안에서 작업 줄기(브랜치)를 나눠서, `main`을 건드리지 않고 새 기능을 만들고 합쳐요. `remote-test`를 그대로 써도 돼요. 브랜치를 GitHub에 올리는 건 06회차에서 `git push origin 브랜치이름`으로 해요.

## 오류가 날 때 찾아보기

| 오류 문장 · 증상 | 먼저 볼 곳 |
|---|---|
| `error: remote origin already exists.` | 이미 등록함 → `git remote -v`로 주소 확인 (2단계) |
| `fatal: 'origin' does not appear to be a git repository` | 그 별칭이 없음 → `git remote -v`로 이름 확인, `remote add` (2단계) |
| `error: src refspec main does not match any` | 아직 커밋이 없음 → `add`·`commit` 먼저 (3단계) |
| `remote: Repository not found.` | 주소 오타이거나 저장소를 아직 안 만듦 (시작하기, 2단계) |
| `remote: Support for password authentication was removed …` / `Authentication failed` | GitHub는 계정 비밀번호로 push를 받지 않음 → 비밀번호 대신 토큰을 넣거나 `gh auth login` 후 `gh auth setup-git` (시작하기) |
| `! [rejected] main -> main (fetch first)` | GitHub에 내가 없는 커밋이 있음 → `git pull origin main` 먼저 (5단계, 05회차) |
| push했는데 GitHub에 파일이 없음 | 커밋을 안 했거나 다른 브랜치를 올림 → `git status`, `git log` (3단계) |
| `fatal: destination path '.' already exists and is not an empty directory.` | `.`으로 clone할 때 폴더가 비어 있지 않음 (4단계) |
| `git status`에 `ahead`·`up to date`가 안 나옴 | `-u` 없이 push해서 정상. 비교하려면 `git push -u origin main` 한 번 (3단계) |
| `.gitignore`에 적었는데 계속 `M`으로 나옴 | 이미 커밋한 파일 (7단계) |
