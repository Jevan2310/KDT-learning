# 개념 정리 — Git협업과정 05. 원격 저장소와 충돌

> 날짜: 2026-11-20 · wiki: [05_원격충돌-fetch](../../../../wiki/07_Git협업과정/05_원격충돌-fetch.md)
> 단계별 설명문으로 쓰고, 단계 끝마다 터미널에 직접 쳐 보는 명령을 둔다. 쉬운 말, 비유 없이. 명령과 출력은 이 Mac의 Git 2.50.1(zsh)에서 로컬 폴더를 원격 저장소처럼 써서 미리 확인했다 (GitHub 주소 부분만 다르다). 버전 번호(7글자)는 매번 다르다.

## 들어가며

03회차에서는 한 번에 한쪽만 커밋했어요. `clone-test`에서 올리고, `remote-test`에서 받기만 했어요. 팀 프로젝트는 이렇게 차례대로 돌아가지 않아요. 내가 작업하는 동안 팀원도 커밋해서 GitHub에 올려요.

그러면 두 가지 일이 생겨요.
- push하려는데 GitHub에 내가 모르는 커밋이 있어서 **push가 거부돼요.**
- 받아 와서 합치려는데 팀원과 내가 **같은 부분을 다르게** 고쳐서 **충돌**이 나요.

05회차에서는 이 두 가지를 일부러 만들고 해결해요. pull은 GitHub에서 받아 온 커밋을 merge하는 거라서, 04회차의 Fast-forward와 병합 커밋, vim 화면이 그대로 다시 나와요.

---

## 🛠 시작하기

03회차의 `remote-test`·`clone-test` 폴더와 GitHub `git-practice-remote` 저장소를 다시 써요. `remote-test`는 "나", `clone-test`는 "팀원"이에요. 03회차를 아직 안 했으면 03회차의 시작하기와 2~5단계를 먼저 해요.

먼저 두 폴더를 GitHub와 똑같이 맞춰요.

```bash
cd ~/git-practice/remote-test
git status -s
git pull origin main
cd ~/git-practice/clone-test
git pull origin main
```

`git status -s`는 아무것도 안 나와야 해요. 03회차 바꿔 보기에서 남은 변경(` M config.txt` 등)이 보이면 `git add .` → `git commit -m "03 정리"` → `git push origin main`으로 정리하고 시작해요.

`clone-test`의 pull은 03회차 7단계에서 `remote-test`가 올린 `.gitignore 추가` 커밋을 받아 와요. `Fast-forward`나 `Already up to date.`가 나오면 돼요.

아래 출력은 03회차 기본 흐름만 한 상태 기준이에요. 바꿔 보기까지 했으면 커밋이 더 보여요.

## 1단계: 로컬 main과 원격 main은 따로 움직인다

원격 저장소도 로컬처럼 브랜치를 가져요. GitHub의 `git-practice-remote`에도 `main`이 있고, 내 컴퓨터의 `remote-test`에도 `main`이 있어요. 이름은 같지만 **서로 다른 브랜치**예요. 한쪽에 커밋이 생겨도 다른 쪽은 그대로예요. push·pull을 해야만 맞춰져요.

내 컴퓨터는 GitHub의 `main`이 어디까지 와 있는지를 `origin/main`이라는 이름으로 기억해요. "`origin`(별칭)의 `main`"이라는 뜻이에요. 이 기억은 **GitHub와 주고받을 때만**(push, pull, fetch) 바뀌어요. 그사이 팀원이 올린 커밋은 `origin/main`에 반영되지 않아요.

### ▶ 직접 해 보기

```bash
cd ~/git-practice/remote-test
git log --oneline --all
```

```text
a625589 (HEAD -> main, origin/main) .gitignore 추가
8d5d81b clone에서 파일 추가
cfe44b8 첫 번째 커밋
```

`HEAD -> main`(내 `main`)과 `origin/main`(기억하는 GitHub `main`)이 같은 커밋에 있어요. 둘이 같다는 뜻이에요.

이제 팀원(`clone-test`)이 커밋해서 올려요.

```bash
cd ~/git-practice/clone-test
echo "팀원이 만든 파일" > team.txt
git add team.txt
git commit -m "팀원 파일 추가"
git push origin main
```

```text
[main 2f238ae] 팀원 파일 추가
 1 file changed, 1 insertion(+)
 create mode 100644 team.txt
To https://github.com/<내 아이디>/git-practice-remote.git
   a625589..2f238ae  main -> main
```

(`To …` 위에 보내는 양을 알려 주는 줄이 몇 개 더 나와요.) GitHub의 `main`은 이제 `2f238ae`예요. `remote-test`에서 다시 봐요.

```bash
cd ~/git-practice/remote-test
git log --oneline --all
```

```text
a625589 (HEAD -> main, origin/main) .gitignore 추가
8d5d81b clone에서 파일 추가
cfe44b8 첫 번째 커밋
```

그대로예요. `remote-test`는 GitHub에 새 커밋이 생긴 걸 몰라요.

**바꿔 보기**
- 브라우저에서 GitHub 저장소 화면을 새로고침해요. `team.txt`가 보여요. GitHub와 `remote-test`가 달라졌어요.
- `git branch -a`를 쳐요. `* main` 아래에 `remotes/origin/main`이 보여요. `-a`는 `origin/main` 같은 원격 쪽 브랜치까지 모두 보여 주는 옵션이에요.

## 2단계: push는 앞으로 옮기기(Fast-forward)만 한다

push는 내 커밋을 올려서 GitHub의 `main`을 **앞으로 옮기는** 일이에요. 04회차의 Fast-forward와 같아요. GitHub는 push를 받으면서 병합 커밋을 만들어 주지 않아요.

그래서 GitHub에 **내가 없는 커밋**이 있으면 push가 거부돼요. GitHub `main`의 마지막 커밋(팀원 커밋)이 내 기록에 없어서, 내 커밋을 그 뒤에 이어 붙일 수 없기 때문이에요. 이걸 무시하고 내 기록으로 덮어쓰는 게 03회차에서 금지한 `push -f`예요. 팀원 커밋이 사라져요.

### ▶ 직접 해 보기

```bash
echo "내가 만든 파일" > mine.txt
git add mine.txt
git commit -m "내 파일 추가"
git push origin main
```

```text
[main bf1848d] 내 파일 추가
 1 file changed, 1 insertion(+)
 create mode 100644 mine.txt
To https://github.com/<내 아이디>/git-practice-remote.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/<내 아이디>/git-practice-remote.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.
```

`! [rejected]`는 거부됐다는 뜻이에요. `(fetch first)`는 "원격 커밋부터 받아 와라", hint 첫 줄은 "원격에 내 컴퓨터에 없는 작업이 있다"는 뜻이에요.

서로 다른 파일(`team.txt`, `mine.txt`)을 만들었는데도 거부됐어요. 파일이 겹쳐서가 아니라 **커밋 기록이 갈라져서** 거부된 거예요. 지금 기록은 이래요.

```text
GitHub main       … a625589 ─ 2f238ae (팀원 파일 추가)
remote-test main  … a625589 ─ bf1848d (내 파일 추가)
```

**바꿔 보기**
- `git log --oneline --all`을 쳐요. 맨 위 `bf1848d (HEAD -> main)` 아래에 `a625589 (origin/main)`이 있어요. 거부된 push는 아무것도 받아 오지 않아서, `origin/main`은 여전히 팀원 커밋을 몰라요.

## 3단계: pull은 받아 와서 합친다

pull은 두 가지를 차례로 해요.

1. **받아 오기(fetch)**: GitHub에서 내가 없는 커밋을 받아 와서 `origin/main`을 옮긴다.
2. **합치기(merge)**: `origin/main`을 내 `main`에 merge한다. 04회차의 `git merge`와 같다.

지금은 양쪽에 새 커밋이 있어서 2번에서 병합 커밋이 생겨야 해요. 그런데 Mac에서는 그 전에 멈춰요. 갈라진 기록을 합치는 방법이 merge 말고도 있어서(rebase), Git이 어느 쪽을 쓸지 정해 달라고 하는 거예요. 강의(Windows)는 Git 설치 화면에서 Merge를 골라서 이미 정해져 있어요. Mac은 한 번 직접 정해요.

### ▶ 직접 해 보기

```bash
git pull origin main
```

```text
From https://github.com/<내 아이디>/git-practice-remote
 * branch            main       -> FETCH_HEAD
   a625589..2f238ae  main       -> origin/main
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
hint:
hint: You can replace "git config" with "git config --global" to set a default
hint: preference for all repositories. You can also pass --rebase, --no-rebase,
hint: or --ff-only on the command line to override the configured default per
hint: invocation.
fatal: Need to specify how to reconcile divergent branches.
```

위 세 줄을 보면 받아 오기(1번)는 끝났어요. `origin/main`이 `2f238ae`로 옮겨졌어요. 합치기(2번)에서 멈춘 거예요.

hint 중 `pull.rebase false  # merge`가 강의 방식이에요. 01회차에서 본 `--global`로 이 컴퓨터 전체에 한 번 정해 둬요. 설정을 바꾸기 싫으면 갈라질 때마다 `git pull --no-rebase origin main`을 쳐도 돼요 (강의 주석의 방법).

```bash
git config --global pull.rebase false
git config --global pull.rebase
```

```text
false
```

다시 pull해요.

```bash
git pull origin main
```

vim 화면이 열려요. 첫 줄에 `Merge branch 'main' of https://github.com/…`이 이미 적혀 있어요. 04회차처럼 `Esc` → `:wq` → Enter로 나와요.

```text
From https://github.com/<내 아이디>/git-practice-remote
 * branch            main       -> FETCH_HEAD
Merge made by the 'ort' strategy.
 team.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 team.txt
```

내 `main`에 팀원 커밋이 들어왔어요. 다시 push해요.

```bash
git push origin main
git log --oneline --graph --all
```

```text
To https://github.com/<내 아이디>/git-practice-remote.git
   2f238ae..26b2fb7  main -> main
*   26b2fb7 (HEAD -> main, origin/main) Merge branch 'main' of https://github.com/<내 아이디>/git-practice-remote
|\
| * 2f238ae 팀원 파일 추가
* | bf1848d 내 파일 추가
|/
* a625589 .gitignore 추가
* 8d5d81b clone에서 파일 추가
* cfe44b8 첫 번째 커밋
```

병합 커밋 `26b2fb7`은 GitHub의 마지막 커밋 `2f238ae` 뒤에 이어지는 커밋이에요. 그래서 이번에는 앞으로 옮기기로 올라갔어요.

마지막으로 팀원(`clone-test`)도 받아 둬요.

```bash
cd ~/git-practice/clone-test
git pull origin main
cd ~/git-practice/remote-test
```

```text
…
Updating 2f238ae..26b2fb7
Fast-forward
```

`clone-test`에는 새 커밋이 없어서 Fast-forward예요.

**바꿔 보기**
- `git pull origin main`을 바로 한 번 더 쳐요. `Already up to date.`가 나와요. 받을 게 없어요.
- `clone-test`에서 `git log --oneline --all -1`을 쳐요. `26b2fb7 (HEAD -> main, origin/main, origin/HEAD)`로 `remote-test`와 같은 커밋이에요. `origin/HEAD`는 GitHub 저장소의 기본 브랜치(`main`)를 가리키는 표시예요. clone으로 받으면 생기고, 신경 쓰지 않아도 돼요.

## 4단계: 같은 부분을 다르게 고치면 충돌한다

2·3단계에서는 서로 다른 파일을 만들어서 pull이 알아서 합쳤어요. 같은 파일이라도 서로 다른 부분을 고쳤으면 알아서 합쳐요.

**같은 파일의 같은 부분을 양쪽이 다르게 고쳤을 때**는 Git이 어느 쪽을 남길지 정할 수 없어요. 이게 **충돌(conflict)**이에요. Git은 합치기를 멈추고, 그 파일에 양쪽 내용을 모두 적어 둔 뒤 사람에게 맡겨요.

push 거부와 충돌은 달라요. push 거부는 "먼저 받아라"는 뜻이고, 받으면 풀려요. 충돌은 받아서 합치다가 부딪힌 거라 사람이 고쳐야 해요.

강의 예제는 내 컴퓨터와 GitHub 웹 화면에서 **같은 이름의 파일**을 서로 다른 내용으로 만들어요.

### ▶ 직접 해 보기 — 강의 기초 예제 2~4

먼저 내 컴퓨터에서 만들어요.

```bash
echo "로컬에서 수정" > file.txt
git add file.txt
git commit -m "로컬에서 파일 추가"
```

이번에는 팀원 대신 GitHub 웹 화면에서 커밋해요.

1. 브라우저에서 `git-practice-remote` 저장소 화면을 열어요.
2. 파일 목록 위의 **Add file** → **Create new file**
3. 파일 이름 칸에 `file.txt`, 내용 칸에 `GitHub에서 수정`
4. 오른쪽 위 **Commit changes...** → 메시지 칸에 `GitHub에서 파일 추가` → **Commit changes**

(GitHub 화면 대신 `clone-test`에서 `echo "GitHub에서 수정" > file.txt` → add → commit → push를 해도 결과는 같아요.)

push부터 해 봐요.

```bash
git push origin main
```

```text
 ! [rejected]        main -> main (fetch first)
```

2단계와 같은 거부예요 (아래 error·hint 줄도 같아요). 받아 와요.

```bash
git pull origin main
```

```text
From https://github.com/<내 아이디>/git-practice-remote
 * branch            main       -> FETCH_HEAD
   26b2fb7..f12f2cd  main       -> origin/main
Auto-merging file.txt
CONFLICT (add/add): Merge conflict in file.txt
Automatic merge failed; fix conflicts and then commit the result.
```

- `Auto-merging file.txt`: `file.txt`를 자동으로 합치려고 했다.
- `CONFLICT (add/add)`: 양쪽에서 같은 이름의 파일을 새로 만들어서(add) 충돌했다.
- `Automatic merge failed; …`: 자동 합치기에 실패했으니, 충돌을 고치고 커밋하라는 뜻이다.

vim은 열리지 않아요. 병합 커밋을 만들기 전에 멈췄기 때문이에요. 지금은 **병합하는 중**인 상태예요.

```bash
git status -s
```

```text
AA file.txt
```

`AA`는 양쪽 다 추가(Added)했다는 표시예요.

**바꿔 보기** (5단계로 가기 전에)
- `git merge --abort`를 쳐요. 병합을 그만두고 pull 전으로 돌아가요. `git status -s`는 아무것도 안 나오고, `cat file.txt`는 `로컬에서 수정`이에요. 다시 `git pull origin main`을 치면 같은 충돌이 나요. 이 상태로 5단계로 가요.
- 충돌 중에 `git pull origin main`을 또 쳐요. `error: Pulling is not possible because you have unmerged files.`가 나와요. 지금 충돌을 해결하거나 그만둬야 다음 pull을 할 수 있어요.

## 5단계: 충돌 해결하기 — 고치고, add, commit

충돌한 파일을 열면 Git이 양쪽 내용을 표시해 둔 게 보여요.

```text
<<<<<<< HEAD
로컬에서 수정          ← 내 쪽 (지금 브랜치, HEAD)
=======
GitHub에서 수정        ← 받아 온 쪽 (GitHub)
>>>>>>> f12f2cd…      ← 받아 온 커밋 번호
```

해결 순서는 이래요.

1. 파일을 열어 남길 내용으로 고친다. 한쪽만 남겨도, 둘 다 남겨도, 새로 써도 된다.
2. `<<<<<<<`, `=======`, `>>>>>>>` 세 줄을 **모두 지운다.** 안 지우면 이 글자가 그대로 코드에 남는다.
3. `git add 파일` — "이 파일은 해결했다"는 표시다.
4. `git commit` — 병합 커밋을 만든다. `-m`을 주면 vim이 안 열린다.
5. `git push origin main`

`add`를 하지 않고 커밋하면 `error: Committing is not possible because you have unmerged files.`로 막혀요. 해결 표시를 안 한 파일이 남았다는 뜻이에요.

충돌은 **커밋끼리** 부딪힐 때 나요. 커밋하지 않은 수정이 있는 파일을 pull이 바꾸려고 하면, 충돌 전에 pull이 아예 멈춰요 (`error: Your local changes to the following files would be overwritten by merge:`). 04회차 5단계에서 브랜치 이동이 막힌 것과 같은 이유예요. 먼저 커밋하고 pull해요.

### ▶ 직접 해 보기 — 강의 기초 예제 5~7

```bash
git status
cat file.txt
```

```text
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both added:      file.txt

no changes added to commit (use "git add" and/or "git commit -a")
<<<<<<< HEAD
로컬에서 수정
=======
GitHub에서 수정
>>>>>>> f12f2cd8274df64950f3cb1fdeef58a225ebd9cf
```

`Unmerged paths` 아래의 `both added`가 충돌한 파일이에요. 파일이 여러 개면 여기서 찾아요. 강의처럼 파일 전체를 새 내용으로 바꿔서 해결해요.

```bash
echo "충돌 해결: 두 내용 합치기" > file.txt
git add file.txt
git status
```

```text
On branch main
All conflicts fixed but you are still merging.
  (use "git commit" to conclude merge)

Changes to be committed:
	modified:   file.txt
```

"충돌은 다 고쳤지만 아직 병합 중"이라는 뜻이에요. 커밋해서 끝내고 올려요.

```bash
git commit -m "충돌 해결"
git push origin main
git log --oneline --graph --all -4
```

```text
[main 9627efe] 충돌 해결
To https://github.com/<내 아이디>/git-practice-remote.git
   f12f2cd..9627efe  main -> main
*   9627efe (HEAD -> main, origin/main) 충돌 해결
|\
| * f12f2cd GitHub에서 파일 추가
* | 70b5f65 로컬에서 파일 추가
|/
*   26b2fb7 Merge branch 'main' of https://github.com/<내 아이디>/git-practice-remote
|\
```

`-4`는 최근 커밋 4개만 보는 옵션이에요. "충돌 해결" 커밋이 양쪽 줄기를 합친 병합 커밋이에요. GitHub에서 `file.txt`를 열면 `충돌 해결: 두 내용 합치기`가 보여요.

**바꿔 보기**
- **같은 줄을 고쳐서 VS Code로 풀기**: 팀원이 먼저 고쳐서 올려요. `cd ~/git-practice/clone-test` → `git pull origin main` → `echo "팀원이 고친 내용" > file.txt` → `git add file.txt` → `git commit -m "팀원이 file 수정"` → `git push origin main`. 그다음 `cd ~/git-practice/remote-test` → `echo "내가 고친 내용" > file.txt` → `git add file.txt` → `git commit -m "내가 file 수정"` → `git pull origin main`. 이번에는 `CONFLICT (content)`가 나오고, `git status`에는 `both modified`가 보여요. 이미 있던 파일의 내용끼리 부딪혔다는 뜻이에요. `open -a "Visual Studio Code" .`로 지금 폴더를 VS Code로 열고 `file.txt`를 누르면, 표시 위에 **Accept Current Change**(내 쪽) / **Accept Incoming Change**(받아 온 쪽) / **Accept Both Changes**(둘 다)가 보여요. 하나 골라 저장하고 `git add file.txt` → `git commit -m "충돌 해결"` → `git push origin main`.
- **다른 줄을 고치면 충돌이 안 나요**: `remote-test`에서 `printf "제목\n본문\n끝\n" > page.txt` → add → commit → push. `clone-test`에서 `git pull origin main` → `printf "새 제목\n본문\n끝\n" > page.txt`(1번째 줄만 바꿈) → add → commit → push. `remote-test`에서 `printf "제목\n본문\n새 끝\n" > page.txt`(3번째 줄만 바꿈) → add → commit → `git pull origin main`. `Auto-merging page.txt` 뒤에 vim이 열리고(`:wq`) `Merge made by the 'ort' strategy.`가 나와요. `cat page.txt`는 `새 제목` / `본문` / `새 끝`이에요. 끝나면 `git push origin main`. 단, 바로 붙은 두 줄(1번째와 2번째)을 나눠 고치면 Git은 같은 부분으로 보고 충돌을 내요.

## 6단계: fetch — 받아 오기만 하고 합치지는 않기

push 거부 메시지의 `(fetch first)`가 `git fetch` 명령이에요. 3단계에서 본 pull의 1번(받아 오기)만 따로 하는 명령이에요.

- `git fetch origin` — GitHub의 새 커밋을 받아서 `origin/main`만 옮긴다. 내 `main`과 폴더의 파일은 그대로다.
- `git merge origin/main` — 받아 온 것을 내 `main`에 합친다.

`git pull origin main`은 이 두 명령을 한 번에 하는 거예요. 평소에는 pull 한 번으로 충분해요. 팀원이 무엇을 올렸는지 **먼저 보고** 합치고 싶을 때 fetch를 따로 써요.

### ▶ 직접 해 보기

팀원이 하나 더 올려요.

```bash
cd ~/git-practice/clone-test
git pull origin main
echo "fetch 연습" > fetch.txt
git add fetch.txt
git commit -m "fetch 연습 파일 추가"
git push origin main
```

`remote-test`에서는 받아 오기만 해요.

```bash
cd ~/git-practice/remote-test
git fetch origin
ls fetch.txt
git log --oneline --graph --all -3
```

```text
From https://github.com/<내 아이디>/git-practice-remote
   9627efe..9e01afc  main       -> origin/main
ls: fetch.txt: No such file or directory
* 9e01afc (origin/main, origin/HEAD) fetch 연습 파일 추가
*   9627efe (HEAD -> main) 충돌 해결
|\
| * f12f2cd GitHub에서 파일 추가
```

`origin/main`은 팀원 커밋까지 왔는데, `HEAD -> main`은 그대로고 `fetch.txt`도 아직 없어요. (`origin/HEAD`는 3단계 바꿔 보기에서 본 표시예요. fetch할 때 `remote-test`에도 생겨요.) 이제 합쳐요.

```bash
git merge origin/main
```

```text
Updating 9627efe..9e01afc
Fast-forward
 fetch.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 fetch.txt
```

내 쪽에 새 커밋이 없어서 Fast-forward예요.

**바꿔 보기**
- 바로 `git fetch origin`을 한 번 더 쳐요. 아무것도 안 나와요. 받을 게 없어요.
- **받아 오기만 하고 합치지 않은 채 push하기**: `clone-test`에서 하나 더 올리고(`git pull origin main` → 파일 만들기 → add → commit → push), `remote-test`에서 `git fetch origin` → 다른 파일 하나 커밋 → `git push origin main`. 이번에는 `(fetch first)`가 아니라 `! [rejected]        main -> main (non-fast-forward)`가 나와요. 받아 오기는 했지만 아직 합치지 않았다는 뜻이에요. `git merge origin/main`(vim `:wq`) → `git push origin main`으로 올라가요. 이때 병합 커밋 메시지는 `Merge remote-tracking branch 'origin/main'`이에요.

---

## 마무리: `git pull origin main`을 쳤을 때 일어나는 일

1. `origin` 주소로 GitHub에 접속해 내가 없는 커밋을 받아 오고, `origin/main`을 옮긴다 (fetch).
2. 받아 온 게 없으면 `Already up to date.`로 끝난다.
3. 내 쪽에 새 커밋이 없으면 앞으로 옮기기만 한다 (`Fast-forward`).
4. 양쪽에 새 커밋이 있으면 병합 커밋을 만든다 (vim이 열림). 합치는 방법을 안 정했으면 여기서 멈춘다 (`Need to specify …`).
5. 같은 파일의 같은 부분(바로 붙은 줄 포함)을 양쪽이 다르게 고쳤으면 `CONFLICT`로 멈춘다 → 파일을 고치고 `add` → `commit`.
6. 이제 내 기록이 GitHub의 기록을 포함하니 push가 된다.

충돌을 줄이는 기본은 03회차의 순서예요. **작업 전에 pull, 커밋했으면 push.** 받지 않고 오래 쌓아 둘수록 갈라진 부분이 커져서 충돌이 잦아져요.

| 오류 문장 · 증상 | 먼저 볼 곳 |
|---|---|
| `! [rejected] main -> main (fetch first)` | GitHub에 내가 없는 커밋이 있음 → `git pull origin main` 먼저 (2단계) |
| `! [rejected] main -> main (non-fast-forward)` | 받아 오기만 하고 안 합침, 또는 충돌 해결 전 → `git merge origin/main`이나 pull, 해결 후 push (5·6단계) |
| `fatal: Need to specify how to reconcile divergent branches.` | pull 방식을 안 정함 → `git config --global pull.rebase false` 또는 `git pull --no-rebase origin main` (3단계) |
| pull 뒤 vim 화면 | 병합 커밋 메시지 → `Esc` → `:wq` → Enter (3단계) |
| `CONFLICT (add/add)` / `CONFLICT (content)` | 같은 파일의 같은 부분을 양쪽이 다르게 고침 → 파일 고치기 (4·5단계) |
| `error: Committing is not possible because you have unmerged files.` | 충돌 파일을 `add` 안 함 (5단계) |
| `error: Pulling is not possible because you have unmerged files.` | 충돌 해결 중 → 해결해서 커밋하거나 `git merge --abort` (4단계) |
| `All conflicts fixed but you are still merging.` | `git commit`으로 끝내기 (5단계) |
| 커밋한 파일에 `<<<<<<<`·`=======`·`>>>>>>>`가 남음 | 표시 줄을 안 지움 → 지우고 다시 add·commit·push (5단계) |
| 충돌을 그만두고 pull 전으로 돌아가고 싶음 | `git merge --abort` (4단계) |
| `error: Your local changes to the following files would be overwritten by merge:` | 커밋 안 한 수정이 받아 올 파일과 겹침 → 먼저 커밋하고 pull (5단계) |
| fetch했는데 파일이 안 바뀜 | 정상. 합치려면 `git merge origin/main` (6단계) |
| `git status`에 뒤처졌다(`behind`)는 말이 없음 | `-u` 없이 push해서 정상 (03회차 3단계) |
