# 개념 정리 — 데이터베이스과정 03. 필요한 데이터 조회하기

> 날짜: 2026-11-24 · wiki: [03_데이터조회](../../../../wiki/06_데이터베이스과정/03_데이터조회.md)
> 단계별 설명문으로 쓰고, 단계 끝마다 직접 해 보는 예시를 둔다. 쉬운 말, 비유 없이. 02 노트대로 학생 다섯 명을 넣은 MySQL 8.4.13에서 이 노트의 SQL(바꿔 보기 포함)을 터미널 `mysql`로 모두 실행해 출력과 오류 문장을 확인했다.

## 들어가며

**🧭 맥락 — 지금 어디쯤**

02에서 `students` 테이블에 학생 다섯 명을 넣고 `SELECT * FROM students;`로 확인했어요. 이 문장은 "전부 다 보여 줘"예요. 학생이 다섯 명일 때는 괜찮지만, 학생이 만 명이면 전부 보는 건 쓸모가 없어요. 실제 서비스에서는 "이메일이 이것인 학생 한 명", "이름에 '김'이 들어간 학생", "최근 등록한 학생 3명"처럼 필요한 것만 가져와요.

파이썬이라면 학생 리스트를 `for`로 돌면서 `if`로 골라내고, `sorted()`로 정렬하고, `[:3]`으로 잘랐을 거예요. SQL에서는 이 일을 MySQL에 한 문장으로 맡겨요. "어느 테이블에서(`FROM`), 어떤 조건의 행만(`WHERE`), 어떤 열만(`SELECT`), 어떤 순서로(`ORDER BY`), 몇 개까지(`LIMIT`)". MySQL이 골라서 결과만 돌려줘요.

여기서 배우는 `WHERE`는 04의 수정·삭제(`UPDATE`, `DELETE`)에서 "어느 학생을 바꿀지" 정할 때 그대로 써요. 06에서는 Spring이 이 `SELECT` 문장을 MyBatis로 실행해서 학생 목록 API를 만들어요. 03은 데이터를 바꾸지 않아요. 조회만 해요.

## 🛠 시작하기

1. MySQL이 켜져 있는지 `brew services list`로 확인하고, DBeaver에서 새 SQL 스크립트를 열어요.
2. 맨 위에 `USE school;`을 실행하고, 내 데이터부터 확인해요.

```sql
USE school;

SELECT * FROM students ORDER BY id ASC;
```
```text
+----+--------------+--------------------+-----------------+
| id | name         | email              | registered_date |
+----+--------------+--------------------+-----------------+
|  1 | 한코딩       | han@example.com    | 2026-11-16      |
|  2 | 김자바       | java@example.com   | 2026-11-17      |
|  3 | 이리액트     | react@example.com  | 2026-11-18      |
|  4 | 박스프링     | spring@example.com | NULL            |
|  6 | 정데이터     | data@example.com   | 2026-11-20      |
+----+--------------+--------------------+-----------------+
5 rows in set (0.00 sec)
```

이 노트의 결과는 이 다섯 명 기준이에요. 내 `id`가 다르면(02에서 같은 `INSERT`를 여러 번 실행한 경우 등) `id`로 조건을 거는 결과만 번호가 달라요. 이름·이메일·등록일 조건의 결과는 같아요. 학생이 다섯 명이 아니면 02를 다시 확인해요.

이 노트의 출력은 터미널 `mysql`에서 얻은 것이에요. DBeaver 결과 영역에도 같은 행과 열이 표로 보여요. 결과가 없을 때 터미널은 `Empty set`, DBeaver는 열 이름만 있는 빈 표를 보여 줘요.

## 1단계: 필요한 열만 고르기 — `SELECT … FROM …`

`SELECT`는 조회하는 SQL이에요. 두 부분으로 읽어요. `FROM students`는 "어느 테이블에서", `SELECT` 바로 뒤는 "어떤 열을"이에요. `*`는 모든 열이에요. 이름과 이메일만 필요하면 `*` 대신 열 이름을 쉼표로 이어서 써요.

결과의 열은 **내가 쓴 순서대로** 나와요. `SELECT email, name`으로 쓰면 이메일이 먼저 나와요. 그렇다고 테이블의 열 순서가 바뀌지는 않아요. `SELECT`는 결과를 보여 줄 뿐, 저장된 구조와 데이터는 그대로예요. 03의 어떤 문장도 데이터를 바꾸지 않아요.

필요한 열만 고르는 이유가 있어요. 06에서 Spring API가 학생 목록을 보낼 때, 화면에 필요 없는 열까지 다 가져오면 쓸데없는 데이터가 오가요. 나중에 비밀번호 같은 열이 생기면 실수로 밖에 보낼 수도 있어요.

### ▶ 직접 해 보기
```sql
SELECT name, email
FROM students;

SELECT name, registered_date
FROM students;
```
```text
mysql> SELECT name, email
    -> FROM students;
+--------------+--------------------+
| name         | email              |
+--------------+--------------------+
| 한코딩       | han@example.com    |
| 김자바       | java@example.com   |
| 이리액트     | react@example.com  |
| 박스프링     | spring@example.com |
| 정데이터     | data@example.com   |
+--------------+--------------------+
5 rows in set (0.00 sec)
```
두 번째 문장은 `name`과 `registered_date` 두 열에 다섯 행이에요. 박스프링의 등록일 칸은 `NULL`이에요.

**바꿔 보기**
- `SELECT email, name FROM students;` → `email` 열이 왼쪽에 나와요. 행은 그대로 5개예요.
- 열 이름 오타 `SELECT nme, email FROM students;` →
  ```text
  ERROR 1054 (42S22): Unknown column 'nme' in 'field list'
  ```
- 테이블 이름 오타 `SELECT * FROM studens;` →
  ```text
  ERROR 1146 (42S02): Table 'school.studens' doesn't exist
  ```
- 마지막 열 뒤에 쉼표 `SELECT name, email, FROM students;` →
  ```text
  ERROR 1064 (42000): ... for the right syntax to use near 'FROM students' at line 1
  ```
- 쉼표 빼기 `SELECT name email FROM students;` → **오류가 안 나요.** 대신 열이 하나뿐이고, 머리줄은 `email`인데 내용은 이름이에요. MySQL이 `name email`을 "`name` 열에 `email`이라는 이름을 붙여 보여 줘"로 읽었어요. 오류가 없어도 결과의 열 이름과 내용이 맞는지 봐야 해요.
  ```text
  +--------------+
  | email        |
  +--------------+
  | 한코딩       |
  | 김자바       |
  ...
  ```
- 새 편집기에서 `USE school;` 없이 `SELECT * FROM students;` →
  ```text
  ERROR 1046 (3D000): No database selected
  ```

## 2단계: 조건에 맞는 행만 — `WHERE`

1단계는 열(세로)을 골랐어요. `WHERE`는 **행**(가로)을 골라요. `FROM` 뒤에 `WHERE 조건`을 쓰면, MySQL이 행을 하나씩 보면서 조건이 참인 행만 결과에 넣어요. 파이썬의 `[s for s in students if s["name"] == "한코딩"]`과 같은 일이에요.

SQL 조건의 `=`는 **같은지 비교**예요. 파이썬이나 JavaScript에서 `=`는 값을 넣는 대입이었고 비교는 `==`, `===`였죠. SQL의 `WHERE name = '한코딩'`은 이름을 바꾸는 게 아니라 "이름이 '한코딩'과 같은가?"를 묻는 거예요. SQL에는 `==`가 없어요.

값을 쓰는 규칙은 02와 같아요. 문자열과 날짜는 작은따옴표, 숫자는 따옴표 없이. 따옴표를 빼면 MySQL은 그 글자를 열 이름으로 읽어요.

조건에 맞는 행이 없으면 오류가 아니라 **빈 결과**가 나와요. 결과가 비었다고 문법이 틀린 건 아니에요. 먼저 그런 데이터가 정말 있는지 전체 조회로 확인해요.

### ▶ 직접 해 보기
```sql
SELECT *
FROM students
WHERE name = '한코딩';

SELECT *
FROM students
WHERE email = 'react@example.com';

SELECT *
FROM students
WHERE id = 1;
```
```text
mysql> SELECT *
    -> FROM students
    -> WHERE name = '한코딩';
+----+-----------+-----------------+-----------------+
| id | name      | email           | registered_date |
+----+-----------+-----------------+-----------------+
|  1 | 한코딩    | han@example.com | 2026-11-16      |
+----+-----------+-----------------+-----------------+
1 row in set (0.00 sec)
```
`WHERE email = 'react@example.com'`은 3번 이리액트 한 명, `WHERE id = 1`은 한코딩 한 명이 나와요. `WHERE email = 'java@example.com'`으로 바꾸면 김자바가 나와요.

**바꿔 보기**
- `WHERE id = 5` → `Empty set`. 02에서 중복 오류가 5번을 써 버려서 5번 학생이 없어요. 오류가 아니라 결과가 없는 거예요.
- 따옴표 빼기 `WHERE name = 한코딩` → 열 이름으로 읽었어요. 이번에는 `'where clause'`(WHERE 부분)라고 알려 줘요.
  ```text
  ERROR 1054 (42S22): Unknown column '한코딩' in 'where clause'
  ```
- `WHERE name == '한코딩'` →
  ```text
  ERROR 1064 (42000): ... for the right syntax to use near '== '한코딩'' at line 3
  ```
- 끝에 공백 하나 `WHERE name = '한코딩 '` → `Empty set`. 공백도 글자라서 다른 값이에요.
- 대문자로 `WHERE email = 'JAVA@example.com'` → 김자바가 나와요. 02 6단계처럼 이 데이터베이스는 글자 비교에서 대문자와 소문자를 같게 봐요.

## 3단계: 범위로 찾기 — 비교 연산자

`=` 말고도 비교 연산자가 있어요. `<>`(다르다), `>`(크다), `>=`(크거나 같다), `<`(작다), `<=`(작거나 같다)예요. 파이썬의 `!=`에 해당하는 게 `<>`예요. MySQL은 `!=`도 받아 줘요.

숫자뿐 아니라 날짜도 비교할 수 있어요. 날짜는 이전 날짜가 작고 이후 날짜가 커요. `registered_date >= '2026-11-18'`은 "11월 18일이거나 그 뒤에 등록한 학생"이에요.

여기서 중요한 게 `NULL`이에요. 박스프링은 등록일이 `NULL`이라서, `>= '2026-11-18'`에도 `< '2026-11-18'`에도 나오지 않아요. `NULL`은 "모르는 값"이라, MySQL은 모르는 값이 어떤 날짜보다 큰지 작은지 판단하지 않아요. 조건이 참이 아니니 결과에서 빠져요. 그래서 "날짜로 나눴는데 학생 한 명이 사라졌다"면 `NULL`부터 의심해요. `NULL`인 행을 찾는 법은 8단계에서 봐요.

### ▶ 직접 해 보기
```sql
SELECT *
FROM students
WHERE name <> '한코딩';

SELECT *
FROM students
WHERE registered_date >= '2026-11-18';

SELECT name, registered_date
FROM students
WHERE registered_date < '2026-11-18';
```
첫 문장은 한코딩을 뺀 4명(김자바, 이리액트, 박스프링, 정데이터)이에요. 이름을 비교했으니 등록일이 `NULL`인 박스프링도 들어 있어요.
```text
mysql> SELECT *
    -> FROM students
    -> WHERE registered_date >= '2026-11-18';
+----+--------------+-------------------+-----------------+
| id | name         | email             | registered_date |
+----+--------------+-------------------+-----------------+
|  3 | 이리액트     | react@example.com | 2026-11-18      |
|  6 | 정데이터     | data@example.com  | 2026-11-20      |
+----+--------------+-------------------+-----------------+
2 rows in set (0.00 sec)

mysql> SELECT name, registered_date
    -> FROM students
    -> WHERE registered_date < '2026-11-18';
+-----------+-----------------+
| name      | registered_date |
+-----------+-----------------+
| 한코딩    | 2026-11-16      |
| 김자바    | 2026-11-17      |
+-----------+-----------------+
2 rows in set (0.00 sec)
```
`>=` 2명 + `<` 2명 = 4명이에요. 다섯 번째 박스프링은 어느 쪽에도 없어요. `WHERE id >= 3`은 이리액트(3)·박스프링(4)·정데이터(6) 세 명이에요.

**바꿔 보기**
- `<>`를 `!=`로 → 결과가 똑같이 4명이에요.
- 날짜의 따옴표 빼기 `WHERE registered_date >= 2026-11-18` → **오류 없이 4명**이 나와요. 끝에 `1 warning`이 붙어요. `SHOW WARNINGS;`로 보면 따옴표 없는 `2026-11-18`을 빼기로 계산한 `1997`을 날짜로 바꾸지 못했다고 해요. 조건이 엉뚱하게 처리돼서 11-16, 11-17 학생까지 나왔어요. 결과 끝의 `warning`을 그냥 넘기지 않아요.
  ```text
  4 rows in set, 1 warning (0.00 sec)

  mysql> SHOW WARNINGS;
  +---------+------+--------------------------------------------------------------------+
  | Level   | Code | Message                                                            |
  +---------+------+--------------------------------------------------------------------+
  | Warning | 1292 | Incorrect date value: '1997' for column 'registered_date' at row 1 |
  +---------+------+--------------------------------------------------------------------+
  ```

## 4단계: 조건 여러 개 — `AND`, `OR`, 괄호

조건을 두 개 이상 쓰려면 `AND`나 `OR`로 이어요. `AND`는 **둘 다** 참인 행, `OR`는 **하나라도** 참인 행이에요. 파이썬의 `and`, `or`와 같아요. 날짜 범위(17일부터 18일까지)는 `AND`로, "한코딩 또는 김자바"는 `OR`로 써요.

둘을 섞을 때 조심해요. **`AND`가 `OR`보다 먼저 계산돼요.** 파이썬도 `and`가 `or`보다 먼저예요. 그래서 `name = '한코딩' OR name = '김자바' AND registered_date >= '2026-11-17'`이라고 쓰면, MySQL은 `김자바 AND 날짜`를 먼저 묶어요. 결과는 "한코딩이거나, (김자바이면서 17일 이후)"가 돼요. 의도는 "(한코딩 또는 김자바) 중에서 17일 이후"였다면 **괄호로 먼저 묶어야** 해요.

### ▶ 직접 해 보기
```sql
SELECT *
FROM students
WHERE registered_date >= '2026-11-17'
  AND registered_date <= '2026-11-18';

SELECT *
FROM students
WHERE name = '한코딩'
   OR name = '김자바';

SELECT *
FROM students
WHERE (name = '한코딩' OR name = '김자바')
  AND registered_date >= '2026-11-17';
```
첫 문장(`AND`)은 17일 김자바와 18일 이리액트 두 명이에요.
```text
mysql> SELECT *
    -> FROM students
    -> WHERE (name = '한코딩' OR name = '김자바')
    ->   AND registered_date >= '2026-11-17';
+----+-----------+------------------+-----------------+
| id | name      | email            | registered_date |
+----+-----------+------------------+-----------------+
|  2 | 김자바    | java@example.com | 2026-11-17      |
+----+-----------+------------------+-----------------+
1 row in set (0.00 sec)
```
두 번째 문장(`OR`)은 한코딩·김자바 두 명이에요. 세 번째는 그중 17일 이후인 김자바만 남았어요. 강의 실습의 `WHERE name = '이리액트' OR name = '정데이터'`도 해 봐요. 두 명이 나와요.

**바꿔 보기**: 세 번째 문장의 괄호를 지워요. 오류는 없지만 등록일이 16일인 한코딩이 다시 들어와요. `AND`가 먼저 묶였기 때문이에요. 괄호를 되살려요.
```text
mysql> SELECT *
    -> FROM students
    -> WHERE name = '한코딩' OR name = '김자바'
    ->   AND registered_date >= '2026-11-17';
+----+-----------+------------------+-----------------+
| id | name      | email            | registered_date |
+----+-----------+------------------+-----------------+
|  1 | 한코딩    | han@example.com  | 2026-11-16      |
|  2 | 김자바    | java@example.com | 2026-11-17      |
+----+-----------+------------------+-----------------+
2 rows in set (0.00 sec)
```

## 5단계: 이름 일부로 찾기 — `LIKE`

`=`는 값 **전체**가 같아야 해요. 검색창처럼 "이름에 '리액트'가 들어간 학생"을 찾으려면 `LIKE`를 써요. `LIKE`는 글자의 **모양(패턴)**을 비교해요.

패턴 안의 `%`는 "여기에 아무 글자나 0개 이상 와도 된다"는 자리예요. `'김%'`는 김으로 시작(뒤에 뭐가 와도 됨), `'%코딩'`은 코딩으로 끝남, `'%리액트%'`는 앞뒤에 뭐가 와도 되니 리액트가 들어 있음이에요. 파이썬으로 치면 `startswith("김")`, `endswith("코딩")`, `"리액트" in name`이에요.

`%`가 없으면 `LIKE`도 `=`처럼 전체가 같아야 해요. 반대로 `=` 뒤에 `%`를 써도 `%`는 그냥 글자로 비교돼서 패턴 역할을 하지 않아요.

### ▶ 직접 해 보기
```sql
SELECT *
FROM students
WHERE name LIKE '김%';

SELECT *
FROM students
WHERE name LIKE '%코딩';

SELECT *
FROM students
WHERE name LIKE '%리액트%';

SELECT *
FROM students
WHERE name LIKE '%데이터%';
```
```text
mysql> SELECT *
    -> FROM students
    -> WHERE name LIKE '김%';
+----+-----------+------------------+-----------------+
| id | name      | email            | registered_date |
+----+-----------+------------------+-----------------+
|  2 | 김자바    | java@example.com | 2026-11-17      |
+----+-----------+------------------+-----------------+
1 row in set (0.00 sec)
```
나머지는 차례로 한코딩, 이리액트, 정데이터가 한 명씩 나와요.

**바꿔 보기**: 넷 다 오류 없이 `Empty set`이에요. 이름 전체가 그 글자와 같은 학생이 없기 때문이에요.
- `WHERE name = '김'` → 이름 전체가 `김`인 학생을 찾아요.
- `WHERE name LIKE '김'` → `%`가 없으면 `=`와 같아요.
- `WHERE name = '김%'` → `=`에서는 `%`도 그냥 글자예요.
- `WHERE name LIKE '리액트'` → 이름이 정확히 `리액트`인 학생을 찾아요. 들어 있는지 보려면 `'%리액트%'`예요.

---

## 6단계: 순서 정하기 — `ORDER BY`

`ORDER BY`를 쓰지 않으면 결과의 **순서는 정해져 있지 않아요.** 지금은 번호 순으로 나오는 것처럼 보여도, MySQL이 약속한 게 아니에요. 데이터가 많아지거나 조건이 바뀌면 순서가 달라질 수 있어요. 순서가 중요하면 꼭 `ORDER BY`를 써요.

`ORDER BY 열 ASC`는 작은 값부터(오름차순), `DESC`는 큰 값부터(내림차순)예요. 날짜는 이전 날짜가 작아요. 한글은 가나다 순이에요. `ASC`는 생략해도 되지만 처음에는 적어 둬요.

정렬 기준을 쉼표로 여러 개 쓰면 **앞의 기준부터** 적용하고, 앞의 값이 같을 때만 다음 기준을 써요. `ORDER BY registered_date DESC, id DESC`는 "등록일이 늦은 학생부터, 등록일이 같으면 번호가 큰 학생부터"예요. 지금은 등록일이 겹치는 학생이 없지만, 겹치면 두 번째 기준이 순서를 정해요.

`NULL`은 정렬에서 어디로 갈까요? MySQL에서 `NULL`은 가장 작은 값처럼 다뤄져요. `ASC`면 맨 앞, `DESC`면 맨 뒤예요. 강의 예제에 `WHERE registered_date IS NOT NULL`이 붙은 건 등록일이 없는 학생을 빼고 정렬하려는 거예요.

정렬도 결과의 순서만 바꿔요. 저장된 데이터는 그대로예요.

### ▶ 직접 해 보기
```sql
SELECT *
FROM students
ORDER BY id DESC;

SELECT *
FROM students
WHERE registered_date IS NOT NULL
ORDER BY registered_date DESC, id DESC;

SELECT *
FROM students
ORDER BY name ASC, id ASC;
```
첫 문장은 6, 4, 3, 2, 1번 순서로 다섯 명이에요. `DESC`를 `ASC`로 바꾸면 1번부터 나와요.
```text
mysql> SELECT *
    -> FROM students
    -> WHERE registered_date IS NOT NULL
    -> ORDER BY registered_date DESC, id DESC;
+----+--------------+-------------------+-----------------+
| id | name         | email             | registered_date |
+----+--------------+-------------------+-----------------+
|  6 | 정데이터     | data@example.com  | 2026-11-20      |
|  3 | 이리액트     | react@example.com | 2026-11-18      |
|  2 | 김자바       | java@example.com  | 2026-11-17      |
|  1 | 한코딩       | han@example.com   | 2026-11-16      |
+----+--------------+-------------------+-----------------+
4 rows in set (0.00 sec)

mysql> SELECT *
    -> FROM students
    -> ORDER BY name ASC, id ASC;
+----+--------------+--------------------+-----------------+
| id | name         | email              | registered_date |
+----+--------------+--------------------+-----------------+
|  2 | 김자바       | java@example.com   | 2026-11-17      |
|  4 | 박스프링     | spring@example.com | NULL            |
|  3 | 이리액트     | react@example.com  | 2026-11-18      |
|  6 | 정데이터     | data@example.com   | 2026-11-20      |
|  1 | 한코딩       | han@example.com    | 2026-11-16      |
+----+--------------+--------------------+-----------------+
5 rows in set (0.00 sec)
```
마지막 결과는 김·박·이·정·한, 가나다 순이에요.

**바꿔 보기**
- 두 번째 문장에서 `WHERE registered_date IS NOT NULL` 줄을 지우기 → 박스프링이 `NULL`과 함께 **맨 뒤**에 붙어 5명이 나와요. `DESC`를 `ASC`로 바꾸면 박스프링이 **맨 앞**으로 가요.
- `ORDER BY`를 `FROM` 앞에 쓰기 `SELECT * ORDER BY id DESC FROM students;` → SQL은 부분마다 쓰는 자리가 정해져 있어요.
  ```text
  ERROR 1064 (42000): ... for the right syntax to use near 'FROM students' at line 1
  ```
- `ORDER BY`를 `WHERE` 앞에 쓰기 → 이번에는 `near` 뒤가 `WHERE …`예요.
  ```text
  ERROR 1064 (42000): ... for the right syntax to use near 'WHERE registered_date IS NOT NULL' at line 4
  ```

## 7단계: 몇 개만 가져오기 — `LIMIT`

`LIMIT n`은 결과를 **최대** n개까지만 돌려줘요. 데이터가 n개보다 적으면 있는 만큼만 나와요. 파이썬의 `[:3]`과 같아요.

`LIMIT`은 정렬과 같이 써야 의미가 있어요. `ORDER BY id DESC LIMIT 3`은 "번호가 큰 학생 3명"이지만, `LIMIT 3`만 쓰면 "아무 학생 3명"이에요. 6단계처럼 정렬 없는 결과의 순서는 정해져 있지 않으니까요.

그리고 기준을 맞게 골라야 해요. "최근 등록한 학생 3명"을 구하려고 `ORDER BY id DESC LIMIT 3`을 쓰면 틀려요. 번호가 크다고 등록일이 늦은 게 아니에요. 지금 데이터에서도 4번 박스프링은 등록일이 없어요. 최근 등록이면 `registered_date`로 정렬해요.

### ▶ 직접 해 보기
```sql
SELECT *
FROM students
ORDER BY id DESC
LIMIT 3;

SELECT name, email
FROM students
ORDER BY id ASC
LIMIT 2;
```
```text
mysql> SELECT *
    -> FROM students
    -> ORDER BY id DESC
    -> LIMIT 3;
+----+--------------+--------------------+-----------------+
| id | name         | email              | registered_date |
+----+--------------+--------------------+-----------------+
|  6 | 정데이터     | data@example.com   | 2026-11-20      |
|  4 | 박스프링     | spring@example.com | NULL            |
|  3 | 이리액트     | react@example.com  | 2026-11-18      |
+----+--------------+--------------------+-----------------+
3 rows in set (0.00 sec)
```
두 번째 문장은 `한코딩 | han@example.com`, `김자바 | java@example.com` 두 줄이에요. `SELECT`에 `id`가 없는데도 `id`로 정렬했어요. 결과에 보여 주지 않는 열로도 정렬할 수 있어요.

**바꿔 보기**
- `ORDER BY id DESC`를 `ORDER BY registered_date DESC`로 (`LIMIT 3` 그대로) → 정데이터, 이리액트, 김자바예요. 번호 기준(정데이터, 박스프링, 이리액트)과 다른 세 명이에요. "최근 등록 3명"은 이쪽이에요.
- `LIMIT 3`을 `LIMIT 10`으로 → 학생이 5명뿐이라 5명만 나와요. 오류가 아니에요.
- `ORDER BY` 줄을 지우고 `LIMIT 3`만 → 지금은 1·2·3번이 나왔지만, 이 순서는 보장되지 않아요.
- `LIMIT`을 `ORDER BY` 앞에 쓰기 →
  ```text
  ERROR 1064 (42000): ... for the right syntax to use near 'ORDER BY id DESC' at line 4
  ```

## 8단계: 값이 없는 행 찾기 — `IS NULL`

등록일이 없는 학생을 찾고 싶어요. `WHERE registered_date = NULL`이라고 쓰고 싶어지는데, 이러면 **오류도 없이 빈 결과**가 나와요.

3단계에서 본 것과 같은 이유예요. `NULL`은 "모르는 값"이라 `=`로 비교하면 결과가 참도 거짓도 아닌 `NULL`(모름)이 돼요. 심지어 `NULL = NULL`도 `NULL`이에요. `WHERE`는 참인 행만 남기니까, `= NULL` 조건으로는 어떤 행도 남지 않아요.

그래서 "값이 없는 상태인가?"를 묻는 전용 문법 `IS NULL`을 써요. 반대는 `IS NOT NULL`(값이 있는가)이에요. 파이썬에서 `None`을 `== None` 대신 `is None`으로 확인하는 것과 모양이 같아요.

### ▶ 직접 해 보기
```sql
SELECT *
FROM students
WHERE registered_date = NULL;

SELECT *
FROM students
WHERE registered_date IS NULL;

SELECT NULL = NULL, NULL IS NULL;
```
```text
mysql> SELECT *
    -> FROM students
    -> WHERE registered_date = NULL;
Empty set (0.00 sec)

mysql> SELECT *
    -> FROM students
    -> WHERE registered_date IS NULL;
+----+--------------+--------------------+-----------------+
| id | name         | email              | registered_date |
+----+--------------+--------------------+-----------------+
|  4 | 박스프링     | spring@example.com | NULL            |
+----+--------------+--------------------+-----------------+
1 row in set (0.00 sec)

mysql> SELECT NULL = NULL, NULL IS NULL;
+-------------+--------------+
| NULL = NULL | NULL IS NULL |
+-------------+--------------+
|        NULL |            1 |
+-------------+--------------+
1 row in set (0.00 sec)
```
`= NULL`은 비교 결과가 `NULL`(모름)이고, `IS NULL`은 `1`(참)이에요. `WHERE registered_date IS NOT NULL`은 박스프링을 뺀 4명이에요. 강의 실습의 `SELECT name, email FROM students WHERE registered_date IS NULL;`은 `박스프링 | spring@example.com` 한 줄이에요.

**바꿔 보기**
- `= NULL`을 `<> NULL`로 → 이것도 `Empty set`이에요. "NULL이 아닌 학생"을 찾으려면 `IS NOT NULL`이에요.
- `IS NULL`을 `IS 'NULL'`로 → `IS` 뒤에는 따옴표 없는 `NULL`만 와요.
  ```text
  ERROR 1064 (42000): ... for the right syntax to use near ''NULL'' at line 3
  ```

## 9단계: 배운 것 합치기

이제 한 문장에 다 써 봐요. 강의 조건은 이래요. 등록일이 2026-11-17 이후 · 이름에 `자바` 또는 `리액트` 포함 · 등록일 늦은 순, 같으면 번호 큰 순 · 최대 두 명 · 이름·이메일·등록일만.

쓰는 순서는 항상 `SELECT → FROM → WHERE → ORDER BY → LIMIT`이에요. 6·7단계 바꿔 보기처럼 이 순서를 바꾸면 `1064` 오류가 나요. 이름 조건 두 개는 `OR`인데 날짜 조건과 `AND`로 이어지니, 4단계대로 괄호로 묶어요.

한 번에 쓰기 어려우면 한 줄씩 붙이면서 실행해요. 줄을 붙일 때마다 결과가 어떻게 줄어드는지 보면, 어느 조건이 어떤 학생을 뺐는지 알 수 있어요.

### ▶ 직접 해 보기 — 한 줄씩 붙이기
①을 실행한 뒤, ②~④의 줄을 하나씩 붙여 가며 매번 다시 실행해요. 다 붙이고 ⑤의 `LIMIT 2`까지 붙이면 맨 아래 완성 문장이 돼요.
```sql
-- ① 필요한 열만
SELECT name, email, registered_date
FROM students;
-- 5명

-- ② + 날짜 조건: WHERE registered_date >= '2026-11-17'
-- 3명 (김자바, 이리액트, 정데이터) — 한코딩(16일)과 박스프링(NULL)이 빠짐

-- ③ + 이름 조건: AND ( name LIKE '%자바%' OR name LIKE '%리액트%' )
-- 2명 (김자바, 이리액트) — 정데이터가 빠짐

-- ④ + 정렬: ORDER BY registered_date DESC, id DESC
-- 2명, 이리액트가 위로

-- ⑤ + 개수 제한: LIMIT 2 → 완성
SELECT name, email, registered_date
FROM students
WHERE registered_date >= '2026-11-17'
  AND (
      name LIKE '%자바%'
      OR name LIKE '%리액트%'
  )
ORDER BY registered_date DESC, id DESC
LIMIT 2;
```
```text
+--------------+-------------------+-----------------+
| name         | email             | registered_date |
+--------------+-------------------+-----------------+
| 이리액트     | react@example.com | 2026-11-18      |
| 김자바       | java@example.com  | 2026-11-17      |
+--------------+-------------------+-----------------+
2 rows in set (0.00 sec)
```
②~④의 주석에 적은 사람 수와 순서도 실제로 실행해서 확인한 결과예요.

**바꿔 보기**
- `LIMIT 2`를 `LIMIT 1`로 → 이리액트 한 명만 나와요. 정렬한 뒤 위에서부터 자르기 때문이에요.
- 날짜를 `'2026-11-18'`로 → 김자바(17일)가 빠지고 이리액트 한 명이에요. `LIMIT 2`여도 조건에 맞는 학생이 한 명이면 한 명만 나와요.

## 마무리: MySQL이 조회 문장을 처리하는 순서

9단계의 완성 문장을 MySQL은 쓴 순서와 다르게 처리해요. 이 순서를 알면 "왜 이 학생이 빠졌지?"를 따라갈 수 있어요.

1. `FROM students` — `students` 테이블의 다섯 행을 대상으로 잡아요.
2. `WHERE registered_date >= '2026-11-17' AND (…)` — 행을 하나씩 보며 조건이 참인 행만 남겨요. 한코딩은 날짜가 16일이라, 박스프링은 날짜가 `NULL`이라(비교 결과가 참이 아님), 정데이터는 이름 조건에 안 맞아서 빠져요. 김자바, 이리액트가 남아요.
3. `SELECT name, email, registered_date` — 남은 행에서 보여 줄 열을 골라요.
4. `ORDER BY registered_date DESC, id DESC` — 등록일이 늦은 이리액트를 위로 올려요. 날짜가 같은 학생이 있었다면 `id`가 큰 쪽이 위로 가요. `WHERE`로 남긴 행에는 `id`도 아직 들어 있어서, `SELECT`에 없어도 `id`로 정렬할 수 있어요.
5. `LIMIT 2` — 위에서부터 최대 두 명을 잘라서 돌려줘요.
6. DBeaver(또는 터미널 `mysql`)가 돌려받은 두 행을 표로 보여 줘요. 테이블의 데이터는 처음 그대로예요.

## 다음 회차와 연결

04에서는 데이터를 바꿔요. `UPDATE students SET … WHERE …`로 고치고, `DELETE FROM students WHERE …`로 지워요. 이때 `WHERE`가 오늘 배운 것과 똑같이 "어느 행을 바꿀지"를 정해요. 그래서 04의 규칙은 "바꾸기 전에 같은 `WHERE`로 `SELECT`부터 해서 대상을 확인한다"예요. 오늘 본 것처럼 따옴표 하나, 괄호 하나로 조건이 달라지면, 04에서는 엉뚱한 학생이 고쳐지거나 지워져요. `WHERE`를 빼면 모든 행이 바뀌어요.

06에서는 Spring이 `SELECT * FROM students ORDER BY id` 같은 문장을 MyBatis로 실행하고, 결과 행을 Java `Student` 객체 목록으로 바꿔서 JSON으로 보내요.

| 결과 열 이름과 내용이 안 맞고 열이 하나 모자람 | `SELECT`의 열 사이 쉼표 (1단계) |
| 날짜 조건인데 범위 밖 학생까지 나오고 `1 warning` | 날짜의 작은따옴표, `SHOW WARNINGS;` (3단계) |

| 정렬하면 `NULL`인 학생이 맨 앞/맨 뒤에 붙음 | `ASC`는 맨 앞, `DESC`는 맨 뒤. 빼려면 `IS NOT NULL` (6단계) |
| 실행할 때마다 순서가 다르거나 `LIMIT` 결과가 기대와 다름 | `ORDER BY`와 정렬 기준이 맞는지 (`id` ≠ 등록일) (6·7단계) |
| `id`로 찾았는데 결과가 없음 | 내 데이터의 실제 번호, 02에서 건너뛴 번호 (🛠, 2단계) |
