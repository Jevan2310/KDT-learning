# 개념 정리 — 데이터베이스과정 04. 데이터 수정·삭제와 트랜잭션

> 날짜: 2026-11-24 · wiki: [04_수정삭제-트랜잭션](../../../../wiki/06_데이터베이스과정/04_수정삭제-트랜잭션.md)
> 단계별 설명문으로 쓰고, 단계 끝마다 직접 해 보는 예시를 둔다. 쉬운 말, 비유 없이. SQL과 출력·오류 문장은 MySQL 8.4.13에 01~03회차와 같은 `school` DB를 만들어 놓고 터미널 `mysql`로 미리 실행해 확인했다 (DBeaver 화면은 설명만 했다).

## 들어가며

**🧭 맥락 — 지금 어디쯤**

01에서 MySQL을 켜고 `school` 데이터베이스를 만들었어요. 02에서 `students` 테이블을 만들고 `INSERT`로 학생 다섯 명을 넣었고, 03에서는 `SELECT`로 조회만 했어요. 03까지는 이미 저장된 데이터를 한 번도 바꾸지 않았어요.

04에서 처음으로 저장된 데이터를 **고치고(`UPDATE`) 지워요(`DELETE`)**. 조회는 조건을 틀려도 결과만 이상하게 나올 뿐 데이터는 그대로예요. 수정·삭제는 달라요. 조건을 잘못 쓰면 다른 학생의 데이터가 바뀌거나 사라져요. 그래서 이번 회차는 두 가지를 함께 배워요. 하나는 **바꾸기 전에 같은 조건으로 먼저 조회하는 습관**이고, 다른 하나는 실행한 변경을 확정하기 전에 취소할 수 있게 해 주는 **트랜잭션**이에요.

파이썬으로 학생 리스트를 고친다면 `for`문으로 돌면서 `if`로 대상을 고르고 값을 바꿨을 거예요. `UPDATE`는 이 일을 DB 안에서 한 문장으로 해요. `WHERE`가 `if` 자리예요. 다른 점은 파이썬 리스트는 프로그램을 끄면 사라지지만, DB의 변경은 한번 확정되면 계속 남는다는 거예요.

오늘 쓰는 문장은 뒤에서 다시 나와요. 05에서는 `UPDATE`로 학생마다 반 번호를 넣고, 06에서는 Spring API의 수정(PUT)·삭제(DELETE) 요청이 오늘과 같은 `UPDATE`·`DELETE`를 실행해요.

03을 마친 지금 `students` 테이블은 이래요 (02의 오류 실습까지 한 경우).

| id | name | email | registered_date |
|---|---|---|---|
| 1 | 한코딩 | han@example.com | 2026-11-16 |
| 2 | 김자바 | java@example.com | 2026-11-17 |
| 3 | 이리액트 | react@example.com | 2026-11-18 |
| 4 | 박스프링 | spring@example.com | NULL |
| 6 | 정데이터 | data@example.com | 2026-11-20 |

5번이 없는 건 02에서 일부러 넣어 본 중복 이메일(`최노드`)이 번호 5를 쓰고 실패했기 때문이에요. 번호는 사람마다 다를 수 있어요. 그래서 오늘은 번호가 아니라 이메일로 대상을 찾아요 (1단계).

## 🛠 시작하기 — DBeaver SQL 편집기 준비

1. MySQL이 켜져 있는지 확인해요. 터미널에서 `brew services list` → `mysql@8.4`가 `started`. 아니면 `brew services start mysql@8.4` (01 개념정리 🛠).
2. DBeaver에서 왼쪽 `localhost` 연결을 마우스 오른쪽으로 누르고 **SQL 편집기 → 새 SQL 스크립트**를 열어요.
3. 맨 위에 `USE school;`을 쓰고 실행한 뒤 `SELECT DATABASE();`가 `school`인지 봐요.
4. 이 노트의 SQL은 **한 문장씩** 선택해서 `Cmd + Enter`로 실행해요. 여러 문장을 한꺼번에 선택해서 실행하지 않아요. 특히 6·7단계의 트랜잭션은 중간 결과를 보면서 한 줄씩 가야 해요.
5. DBeaver 위쪽 도구 모음의 커밋 모드는 처음 상태(자동 커밋) 그대로 둬요. 트랜잭션은 SQL 문장으로만 다뤄요 (6단계).
6. **오늘은 처음부터 끝까지 같은 SQL 편집기 탭 하나**에서 해요. 탭을 바꾸면 다른 연결이 될 수 있어서 트랜잭션이 이어지지 않아요.
7. 연습한 SQL을 남기고 싶으면 **File → Save As**로 이 날짜 폴더(`practice/06_데이터베이스과정/04_수정삭제-트랜잭션/2026-11-24/`)에 `연습.sql`로 저장해요. 파일 저장은 DB 변경과는 상관없어요 (6단계).

이 노트의 출력은 터미널 `mysql`에서 얻은 것이에요. DBeaver에서는 같은 값이 결과 영역 표로 보여요. `UPDATE`·`DELETE`·`INSERT`는 표 대신 바뀐 행 수가 보여요. 터미널의 `Query OK, 1 row affected`가 "1개 행이 바뀌었다"는 뜻이에요. 오류는 MySQL이 보내는 문장이라 DBeaver에서도 같은 오류 번호와 영어 문장이 나와요.

## 1단계: 바꾸기 전에 지금 데이터를 보고, 대상은 이메일로 찾는다

🧭 03의 `SELECT`가 04의 첫 단계예요. 수정·삭제는 항상 조회로 시작해요.

수정하거나 지우기 전에 해야 할 일은 "지금 무엇이 들어 있는지" 보는 거예요. 머릿속으로 기억하는 데이터와 실제 데이터는 다를 수 있어요. 02에서 오류를 몇 번 냈는지, 다른 연습을 했는지에 따라 번호도 이름도 달라져요.

그다음 대상을 무엇으로 찾을지 정해요. 이름은 같은 학생이 또 있을 수 있어서 대상이 여러 명이 될 수 있어요. 번호(`id`)는 겹치지 않지만, 위에서 본 것처럼 사람마다 다를 수 있어요. 이메일은 02에서 `UNIQUE`를 걸어 두어서 같은 값이 두 번 저장될 수 없어요. 그래서 `WHERE email = '...'`은 많아야 한 행만 찾아요. 강의가 이메일로 대상을 찾는 이유예요.

### ▶ 직접 해 보기 — 지금 데이터 보기
```sql
SELECT *
FROM students
ORDER BY id ASC;
```
```text
+----+--------------+--------------------+-----------------+
| id | name         | email              | registered_date |
+----+--------------+--------------------+-----------------+
|  1 | 한코딩       | han@example.com    | 2026-11-16      |
|  2 | 김자바       | java@example.com   | 2026-11-17      |
|  3 | 이리액트     | react@example.com  | 2026-11-18      |
|  4 | 박스프링     | spring@example.com | NULL            |
|  6 | 정데이터     | data@example.com   | 2026-11-20      |
+----+--------------+--------------------+-----------------+
5 rows in set (0.00 sec)
```
**바꿔 보기**: `ORDER BY id ASC` 줄을 `WHERE id = 5`로 바꾸면 `Empty set`이 나와요. 오류가 아니라 5번 행이 없는 거예요. 번호로 대상을 찾으면 이렇게 사람마다 결과가 달라질 수 있어요.

## 2단계: `UPDATE`로 한 열을 고친다

🧭 02의 `INSERT`는 새 행을 더했어요. `UPDATE`는 이미 있는 행의 값을 바꿔요. 행 수는 그대로예요.

`UPDATE`는 세 부분으로 되어 있어요. `UPDATE students`는 어느 테이블을 고칠지, `SET email = '...'`은 어느 열을 어떤 값으로 바꿀지, `WHERE email = '...'`은 어느 행을 바꿀지예요. 같은 문장에 `=`가 두 번 나오는데 뜻이 달라요. `SET` 뒤의 `=`는 "이 값으로 바꿔라"이고, `WHERE` 뒤의 `=`는 03에서 배운 대로 "같은지 비교해라"예요.

순서는 조회 → 수정 → 다시 조회예요. 수정 전에 같은 조건으로 조회해서 한코딩 한 명만 나오는지 확인해요. 수정한 뒤 확인할 때는 조심할 점이 있어요. 조건으로 쓴 값(이메일)을 바꿨기 때문에, 예전 이메일로 조회하면 아무것도 안 나와요. 바뀐 이메일로 조회해야 해요.

터미널에는 `Rows matched: 1  Changed: 1`이 나와요. `matched`는 `WHERE`에 맞은 행 수, `Changed`는 실제로 값이 바뀐 행 수예요. 이미 같은 값이면 맞기는 해도 바뀌지 않아서 두 숫자가 달라질 수 있어요 (3단계 바꿔 보기).

자동 커밋 상태라서 이 `UPDATE`는 실행하는 순간 확정돼요. 나중에 `ROLLBACK`을 해도 되돌아오지 않아요 (6단계).

### ▶ 직접 해 보기 — 한코딩의 이메일 바꾸기
세 문장을 하나씩 실행해요.
```sql
SELECT *
FROM students
WHERE email = 'han@example.com';

UPDATE students
SET email = 'hancoding@example.com'
WHERE email = 'han@example.com';

SELECT *
FROM students
WHERE email = 'hancoding@example.com';
```
```text
+----+-----------+-----------------+-----------------+
| id | name      | email           | registered_date |
+----+-----------+-----------------+-----------------+
|  1 | 한코딩    | han@example.com | 2026-11-16      |
+----+-----------+-----------------+-----------------+
1 row in set (0.00 sec)

Query OK, 1 row affected (0.00 sec)
Rows matched: 1  Changed: 1  Warnings: 0

+----+-----------+-----------------------+-----------------+
| id | name      | email                 | registered_date |
+----+-----------+-----------------------+-----------------+
|  1 | 한코딩    | hancoding@example.com | 2026-11-16      |
+----+-----------+-----------------------+-----------------+
1 row in set (0.00 sec)
```
**바꿔 보기**
- 마지막 조회를 예전 이메일 `'han@example.com'`으로 → `Empty set`. 학생이 사라진 게 아니라 조건이 바뀐 값과 안 맞는 거예요.
- 가운데 `UPDATE`를 한 번 더 실행 → 오류 없이 `Query OK, 0 rows affected` / `Rows matched: 0  Changed: 0`. `han@example.com`인 행이 이제 없어서예요. **오류가 안 나도 0행이면 아무것도 안 바뀐 거예요.**
- `SET email`을 `SET emial`로 오타 → `ERROR 1054 (42S22): Unknown column 'emial' in 'field list'`. 아무것도 안 바뀌어요.

## 3단계: 여러 열을 함께 고치고, `NULL`로 되돌린다

🧭 02에서 `INSERT`의 열 목록을 쉼표로 이었던 것처럼, `SET`에서도 바꿀 열을 쉼표로 이어요.

박스프링 학생의 이름과 등록일을 한 번에 바꿔요. `SET name = '박스프링부트', registered_date = '2026-11-19'`처럼 쓰면 두 열이 함께 바뀌어요. 이번에는 이메일을 안 바꾸니까 수정 전 조회와 수정 후 조회를 같은 조건(`email = 'spring@example.com'`)으로 해요.

등록일을 다시 "모름"으로 돌리고 싶으면 `NULL`을 넣어요. 02에서 본 대로 `NULL`에는 따옴표를 붙이지 않아요. `'NULL'`은 N·U·L·L 네 글자라서 날짜 열에 넣을 수 없어요.

### ▶ 직접 해 보기 — 박스프링 수정하고 등록일 비우기
```sql
UPDATE students
SET name = '박스프링부트',
    registered_date = '2026-11-19'
WHERE email = 'spring@example.com';

SELECT *
FROM students
WHERE email = 'spring@example.com';

UPDATE students
SET registered_date = NULL
WHERE email = 'spring@example.com';

SELECT *
FROM students
WHERE email = 'spring@example.com';
```
```text
Query OK, 1 row affected (0.00 sec)
Rows matched: 1  Changed: 1  Warnings: 0

+----+--------------------+--------------------+-----------------+
| id | name               | email              | registered_date |
+----+--------------------+--------------------+-----------------+
|  4 | 박스프링부트       | spring@example.com | 2026-11-19      |
+----+--------------------+--------------------+-----------------+

Query OK, 1 row affected (0.00 sec)
Rows matched: 1  Changed: 1  Warnings: 0

+----+--------------------+--------------------+-----------------+
| id | name               | email              | registered_date |
+----+--------------------+--------------------+-----------------+
|  4 | 박스프링부트       | spring@example.com | NULL            |
+----+--------------------+--------------------+-----------------+
```
**바꿔 보기**
- `SET registered_date = NULL`을 `SET registered_date = 'NULL'`로 → `ERROR 1292 (22007): Incorrect date value: 'NULL' for column 'registered_date' at row 1`
- 첫 `UPDATE`에서 `'박스프링부트',` 뒤의 쉼표를 지우기 → `ERROR 1064 (42000): You have an error in your SQL syntax; ... near 'registered_date = '2026-11-19'`. `near` 뒤가 문제가 시작된 곳이에요.
- `NULL`로 바꾸는 `UPDATE`를 한 번 더 실행 → `Rows matched: 1  Changed: 0`. 이미 `NULL`이라 바뀐 게 없어요.
- `SET name = NULL`로 → `ERROR 1048 (23000): Column 'name' cannot be null`. 02에서 `name`에 건 `NOT NULL`이 수정 때도 지켜져요.

## 4단계: `WHERE`가 없거나 넓으면 여러 행이 바뀐다

🧭 2·3단계는 `WHERE`가 정확히 한 행을 골랐어요. 이번 단계는 그렇지 않을 때 무슨 일이 생기는지 봐요.

`UPDATE students SET name = '한코딩';`처럼 `WHERE`를 빼면 조건이 없으니 **모든 행**이 대상이 돼요. 다섯 명 모두 이름이 한코딩이 되고, 자동 커밋이라 바로 확정돼요. 파이썬으로 치면 `for`문 안의 `if`를 지운 것과 같아요. `DELETE FROM students;`도 같아서 모든 학생이 지워져요. 강의는 이 두 문장을 "실행하지 않는 설명용"으로 보여 줬어요. 여기서도 실행하지 않아요. 안전하게 직접 보는 방법은 7단계에 있어요.

`WHERE`가 있다고 한 명만 바뀌는 것도 아니에요. `WHERE registered_date IS NULL`은 등록일이 비어 있는 학생 **모두**를 골라요. 지금은 박스프링부트 한 명뿐이지만, 데이터가 늘면 여러 명이 될 수 있어요. 그래서 확인 순서는 늘 같아요. 같은 조건으로 `SELECT` → 나온 행과 **개수** 확인 → `UPDATE`/`DELETE` → 다시 `SELECT`.

MySQL에는 이런 실수를 막는 **안전 수정 모드**(`sql_safe_updates`)가 있어요. 켜면 `WHERE`가 없거나, `WHERE`에 키 열(기본키·`UNIQUE` 열)을 쓰지 않은 `UPDATE`·`DELETE`를 거부해요. MySQL의 기본값은 꺼짐(0)이에요. MySQL Workbench라는 다른 도구는 이 모드를 켜고 시작하지만, DBeaver는 MySQL 기본값을 그대로 써요. 아래 예시의 첫 줄 `SELECT @@sql_safe_updates;`로 내 편집기가 0인지 직접 확인해요. 0이면 DBeaver에서 `WHERE` 없는 문장이 그대로 실행돼요. DBeaver가 `WHERE` 없는 `UPDATE`·`DELETE`를 실행하기 전에 확인 창을 띄우기도 하는데, 설정에 따라 다르니 그 창을 믿지 말고 1단계의 확인 순서를 지켜요.

### ▶ 직접 해 보기 — 아무것도 안 바뀌는 `WHERE` 없는 `UPDATE`
`registered_date`를 자기 자신의 값으로 바꾸는 문장이에요. `WHERE`가 없어서 모든 행이 대상이 되지만, 값이 그대로라서 실제로 바뀌는 건 없어요. `WHERE`가 없으면 몇 행이 대상이 되는지만 안전하게 볼 수 있어요.
```sql
SELECT @@sql_safe_updates;

UPDATE students
SET registered_date = registered_date;
```
```text
+--------------------+
| @@sql_safe_updates |
+--------------------+
|                  0 |
+--------------------+

Query OK, 0 rows affected (0.00 sec)
Rows matched: 5  Changed: 0  Warnings: 0
```
`Rows matched: 5` — 조건이 없으니 다섯 명 전부 대상이 됐어요.

**바꿔 보기**: 안전 수정 모드를 켜고 같은 문장을 다시 실행한 뒤, 꼭 끄고 넘어가요.
```sql
SET SQL_SAFE_UPDATES = 1;

UPDATE students
SET registered_date = registered_date;

SET SQL_SAFE_UPDATES = 0;
```
```text
ERROR 1175 (HY000): You are using safe update mode and you tried to update a table without a WHERE that uses a KEY column.
```
확인할 때 안전 모드에서 강의의 `WHERE registered_date IS NULL` 문장도 같은 1175로 막혔어요. `registered_date`가 키 열이 아니기 때문이에요. 반대로 `WHERE email = 'spring@example.com'`은 `email`이 `UNIQUE` 열이라 통과했어요. 이 설정은 지금 편집기의 연결에만 적용돼요.

## 5단계: `DELETE`로 행을 지운다

🧭 `UPDATE`가 행의 값을 바꿨다면, `DELETE`는 행 자체를 없애요.

`DELETE FROM students WHERE ...;`는 조건에 맞는 행을 지워요. `SELECT`처럼 `*`이나 열 이름을 쓰지 않아요. 행을 통째로 지우니까 고를 열이 없어요. `DELETE`는 행만 지우고 **테이블 구조는 남겨요.** 모든 행을 지워도 `students` 테이블과 열 정의는 그대로예요.

강의는 기존 학생을 지우지 않아요. 05·06에서 계속 쓰기 때문이에요. 대신 지울 학생을 하나 새로 넣고 그 학생을 지워요. 지운 뒤 같은 조건으로 조회해서 `Empty set`이 나오면 지워진 거예요.

삭제연습 학생은 7번을 받아요. 지워도 7번은 다시 쓰이지 않아서, 다음에 추가하는 학생은 8번부터예요. 06에서 API로 학생을 추가하면 8번이 나오는 이유예요.

### ▶ 직접 해 보기 — 지울 학생을 넣고 지우기
```sql
INSERT INTO students (name, email, registered_date)
VALUES ('삭제연습', 'delete-practice@example.com', '2026-11-21');

SELECT *
FROM students
WHERE email = 'delete-practice@example.com';

DELETE FROM students
WHERE email = 'delete-practice@example.com';

SELECT *
FROM students
WHERE email = 'delete-practice@example.com';

DESCRIBE students;
```
```text

+----+--------------+-----------------------------+-----------------+
| id | name         | email                       | registered_date |
+----+--------------+-----------------------------+-----------------+
|  7 | 삭제연습     | delete-practice@example.com | 2026-11-21      |
+----+--------------+-----------------------------+-----------------+

Query OK, 1 row affected (0.01 sec)

Empty set (0.00 sec)

+-----------------+--------------+------+-----+---------+----------------+
| Field           | Type         | Null | Key | Default | Extra          |
+-----------------+--------------+------+-----+---------+----------------+
| id              | int          | NO   | PRI | NULL    | auto_increment |
| name            | varchar(50)  | NO   |     | NULL    |                |
| email           | varchar(100) | NO   | UNI | NULL    |                |
| registered_date | date         | YES  |     | NULL    |                |
+-----------------+--------------+------+-----+---------+----------------+
```
행은 지워졌지만 `DESCRIBE`로 보면 테이블 구조는 그대로예요.

**바꿔 보기**
- `DELETE`를 한 번 더 실행 → `Query OK, 0 rows affected`. 지울 행이 없어도 오류는 안 나요. 06에서 이 "0행"을 보고 404를 돌려줘요.
- `DELETE FROM`을 `DELETE * FROM`으로 → `ERROR 1064 (42000): You have an error in your SQL syntax; ... near '* FROM students ...`
- `FROM`을 빼고 `DELETE students`로 → `ERROR 1064 (42000): You have an error in your SQL syntax; ... near 'WHERE email = 'delete-practice@example.com''`

`SELECT`에 익숙해서 `*`를 넣거나 `FROM`을 빠뜨리기 쉬워요. 1064는 문법 오류이고, `near` 뒤에 MySQL이 이해하지 못한 곳부터 보여 줘요.

## 6단계: 트랜잭션 — 확정하기 전에는 취소할 수 있다

🧭 2~5단계의 변경은 실행하자마자 확정됐어요. 이번 단계부터는 "실행했지만 아직 확정하지 않은" 상태를 만들어요.

**트랜잭션**은 함께 확정하거나 함께 취소할 작업 묶음이에요. 강의의 예처럼 학생이 반을 옮기면 "기존 반 학생 수 -1"과 "새 반 학생 수 +1"이 둘 다 반영되거나 둘 다 반영되지 않아야 해요. 하나만 반영되면 숫자가 안 맞아요. 이런 작업을 하나로 묶어요. **`COMMIT`**은 묶음 안의 변경을 확정하고, **`ROLLBACK`**은 아직 확정하지 않은 변경을 취소해요.

그런데 왜 2단계의 이메일 변경은 취소할 수 없을까요? MySQL은 **자동 커밋**이 켜져 있어서, 트랜잭션을 따로 시작하지 않으면 성공한 변경문 하나하나가 실행 즉시 확정돼요. `SELECT @@autocommit;`이 `1`이면 켜진 상태예요. 확정된 변경은 `ROLLBACK`으로 되돌릴 수 없어요.

그래서 취소할 가능성이 있는 작업은 **`START TRANSACTION;`**으로 시작해요. 그 뒤의 변경은 `COMMIT`이나 `ROLLBACK`을 만날 때까지 확정되지 않아요. 둘 중 하나를 실행하면 트랜잭션이 끝나고, 다시 원래대로 문장마다 자동 확정돼요.

트랜잭션 안에서 `UPDATE`한 뒤 같은 편집기에서 조회하면 바뀐 이름이 보여요. 그렇다고 확정된 건 아니에요. 지금 연결이 **자기가 바꾼 내용**을 보는 것뿐이에요. 확인할 때 터미널 연결을 두 개 열어 봤어요. 한쪽에서 `START TRANSACTION` 뒤 `김자바수정`으로 바꾼 상태에서 다른 쪽이 조회하니 `김자바`가 나왔어요. 트랜잭션은 연결 하나에 속해요. 그래서 시작부터 끝까지 같은 편집기 탭에서 해야 해요. DBeaver 도구 모음에도 커밋·롤백 버튼이 있지만, SQL 문장과 버튼을 섞으면 어느 쪽이 무엇을 확정했는지 헷갈려서 오늘은 SQL로만 해요.

`COMMIT`은 DBeaver에서 SQL 파일을 저장하는 것과도 달라요. 파일 저장은 SQL **글자**를 파일에 남기는 것이고, `COMMIT`은 DB의 **데이터 변경**을 확정하는 거예요.

### ▶ 직접 해 보기 — 트랜잭션 ①: 고친 이름을 `ROLLBACK`으로 취소
```sql
SELECT @@autocommit;

SELECT name, email
FROM students
WHERE email = 'java@example.com';

START TRANSACTION;

UPDATE students
SET name = '김자바수정'
WHERE email = 'java@example.com';

SELECT name, email
FROM students
WHERE email = 'java@example.com';

ROLLBACK;

SELECT name, email
FROM students
WHERE email = 'java@example.com';
```
```text
+--------------+
| @@autocommit |
+--------------+
|            1 |
+--------------+

+-----------+------------------+
| name      | email            |
+-----------+------------------+
| 김자바    | java@example.com |
+-----------+------------------+

Query OK, 0 rows affected (0.00 sec)

Query OK, 1 row affected (0.00 sec)
Rows matched: 1  Changed: 1  Warnings: 0

+-----------------+------------------+
| name            | email            |
+-----------------+------------------+
| 김자바수정      | java@example.com |
+-----------------+------------------+

Query OK, 0 rows affected (0.00 sec)

+-----------+------------------+
| name      | email            |
+-----------+------------------+
| 김자바    | java@example.com |
+-----------+------------------+
```
트랜잭션 안에서는 `김자바수정`이 보였지만, `ROLLBACK` 뒤에는 `김자바`로 돌아왔어요.

### ▶ 직접 해 보기 — 트랜잭션 ②: 고친 이름을 `COMMIT`으로 확정
```sql
START TRANSACTION;

UPDATE students
SET name = '김자바개발자'
WHERE email = 'java@example.com';

SELECT name, email
FROM students
WHERE email = 'java@example.com';

COMMIT;

SELECT name, email
FROM students
WHERE email = 'java@example.com';
```
```text
Query OK, 0 rows affected (0.00 sec)

Query OK, 1 row affected (0.00 sec)
Rows matched: 1  Changed: 1  Warnings: 0

+--------------------+------------------+
| name               | email            |
+--------------------+------------------+
| 김자바개발자       | java@example.com |
+--------------------+------------------+

Query OK, 0 rows affected (0.00 sec)

+--------------------+------------------+
| name               | email            |
+--------------------+------------------+
| 김자바개발자       | java@example.com |
+--------------------+------------------+
```
**바꿔 보기**
- 지금 바로 `ROLLBACK;`을 실행하고 조회 → 그대로 `김자바개발자`. `COMMIT`으로 확정한 변경은 되돌릴 수 없어요.
- `START TRANSACTION;` 없이 `UPDATE students SET name = '김자바수정' WHERE email = 'java@example.com';` → `ROLLBACK;` → 조회하면 `김자바수정`이 그대로 남아 있어요. 자동 커밋이라 `UPDATE`가 끝나자마자 확정됐기 때문이에요. 이 실수가 가장 흔해요. 되돌리기: `UPDATE students SET name = '김자바개발자' WHERE email = 'java@example.com';`

## 7단계: 지운 행도 돌아온다 — `ROLLBACK`은 확정 안 된 변경 전체를 취소한다

🧭 6단계는 `UPDATE` 하나를 취소했어요. 이번에는 `DELETE`를 취소하고, 여러 변경을 한 번에 취소해요.

`DELETE`도 트랜잭션 안에서는 확정 전이라 `ROLLBACK`으로 되살릴 수 있어요. 삭제한 뒤 같은 트랜잭션에서 조회하면 `Empty set`이지만, `ROLLBACK` 뒤에는 원래 번호(3번) 그대로 돌아와요.

`ROLLBACK`은 마지막 한 문장만 취소하는 게 아니에요. `START TRANSACTION` 뒤에 실행한 **모든** 변경을 취소해요. 정데이터의 이름을 바꾸고 이리액트를 지운 다음 `ROLLBACK`하면 둘 다 원래대로 돌아와요.

예외가 있어요. `CREATE TABLE`, `DROP TABLE`, `ALTER TABLE` 같은 **구조 변경 문장**은 MySQL에서 실행 전에 그때까지의 트랜잭션을 자동으로 확정해 버려요. 그래서 트랜잭션 도중에 구조를 바꾸면, 그 앞의 변경은 `ROLLBACK`해도 돌아오지 않아요. 05에서 `ALTER TABLE`을 쓸 때 트랜잭션과 섞지 않는 이유예요.

### ▶ 직접 해 보기 — 트랜잭션 ③: 지운 학생을 `ROLLBACK`으로 되살리기
```sql
START TRANSACTION;

SELECT *
FROM students
WHERE email = 'react@example.com';

DELETE FROM students
WHERE email = 'react@example.com';

SELECT *
FROM students
WHERE email = 'react@example.com';

ROLLBACK;

SELECT *
FROM students
WHERE email = 'react@example.com';
```
```text
Query OK, 0 rows affected (0.00 sec)

+----+--------------+-------------------+-----------------+
| id | name         | email             | registered_date |
+----+--------------+-------------------+-----------------+
|  3 | 이리액트     | react@example.com | 2026-11-18      |
+----+--------------+-------------------+-----------------+

Query OK, 1 row affected (0.01 sec)

Empty set (0.00 sec)

Query OK, 0 rows affected (0.00 sec)

+----+--------------+-------------------+-----------------+
| id | name         | email             | registered_date |
+----+--------------+-------------------+-----------------+
|  3 | 이리액트     | react@example.com | 2026-11-18      |
+----+--------------+-------------------+-----------------+
```

### ▶ 직접 해 보기 — 변경 두 개를 한 번에 취소
```sql
START TRANSACTION;

UPDATE students
SET name = '정데이터수정'
WHERE email = 'data@example.com';

DELETE FROM students
WHERE email = 'react@example.com';

SELECT id, name, email
FROM students
ORDER BY id ASC;

ROLLBACK;

SELECT id, name, email
FROM students
ORDER BY id ASC;
```

```text
+----+--------------------+-----------------------+
|  1 | 한코딩             | hancoding@example.com |

+----+--------------------+-----------------------+
| id | name               | email                 |
+----+--------------------+-----------------------+
|  1 | 한코딩             | hancoding@example.com |
|  2 | 김자바개발자       | java@example.com      |

```
**바꿔 보기**
- 4단계의 `WHERE` 없는 `UPDATE`를 트랜잭션 안에서 직접 보기. `START TRANSACTION;` → `UPDATE students SET name = '한코딩';` → `SELECT id, name, email FROM students ORDER BY id ASC;` → `ROLLBACK;` 순서로 실행해요. 결과는 `Rows matched: 5  Changed: 4`(한코딩은 이미 한코딩이라 4명만 바뀜)이고, 조회하면 다섯 명 모두 이름이 `한코딩`이에요. `ROLLBACK` 뒤에 다시 조회하면 원래 이름으로 돌아와요. **`START TRANSACTION;`을 먼저 실행했는지 꼭 확인하고** 해요.
- 트랜잭션 중간에 구조 변경 넣기. `START TRANSACTION;` → `UPDATE students SET name = '정데이터수정' WHERE email = 'data@example.com';` → `CREATE TABLE ddl_test (id INT);` → `ROLLBACK;` → 조회하면 `정데이터수정`이 그대로예요. `CREATE TABLE`이 앞의 `UPDATE`를 확정해 버렸어요. 되돌리기: `UPDATE students SET name = '정데이터' WHERE email = 'data@example.com';` 그리고 `DROP TABLE ddl_test;`

## 마무리: 04회차를 처음부터 끝까지

1. `USE school;` → 전체 조회로 지금 데이터를 봐요. 대상은 `UNIQUE`인 이메일로 찾아요.
2. 한코딩의 이메일을 `hancoding@example.com`으로 바꿔요. 자동 커밋이라 바로 확정돼요. 확인 조회는 바뀐 이메일로 해요.
3. 박스프링의 이름·등록일을 함께 바꾼 뒤 등록일을 `NULL`(따옴표 없이)로 되돌려요.
4. `WHERE`가 없으면 모든 행이, `WHERE`가 넓으면 여러 행이 대상이 된다는 걸 확인해요. 변경 전에는 같은 조건으로 조회해서 개수까지 봐요.
5. 삭제연습 학생을 넣고(7번) 지워요. 테이블 구조는 남아요.
6. 트랜잭션 ①: `START TRANSACTION` → 김자바수정 → `ROLLBACK` → 김자바로 돌아와요.
7. 트랜잭션 ②: `START TRANSACTION` → 김자바개발자 → `COMMIT` → 확정. 이후 `ROLLBACK`해도 그대로예요.
8. 트랜잭션 ③: `START TRANSACTION` → 이리액트 삭제 → `ROLLBACK` → 3번 그대로 돌아와요.

끝나면 데이터가 이렇게 돼요. 05는 이 상태에서 시작해요.
```sql
SELECT *
FROM students
ORDER BY id ASC;
```

## 다음 회차와 연결

05에서는 반 정보를 `classes` 테이블로 따로 만들고, `ALTER TABLE`로 `students`에 `class_id` 열을 더해요. `ALTER TABLE`은 7단계에서 본 구조 변경 문장이라 트랜잭션 밖에서 한 번씩 실행해요. 그다음 오늘 배운 `UPDATE ... WHERE email = ... OR email = ...`로 학생을 반에 배정해요. 조건에 세 명이 걸리니 `Rows matched: 3`이 나와요.

06에서는 Spring API가 오늘의 `UPDATE`·`DELETE`를 실행해요. 5단계에서 본 "0 rows affected"를 Java 코드가 숫자 `0`으로 받아서, 대상이 없으면 404를 돌려줘요. API의 변경은 요청마다 바로 확정돼서, DBeaver에서 `ROLLBACK`해도 취소되지 않아요. 6단계에서 본 "트랜잭션은 연결 하나에 속한다"가 그 이유예요.

## 오류가 날 때 찾아보기

| 오류 문장 · 증상 | 먼저 볼 곳 |
|---|---|
| `UPDATE`했는데 확인 조회가 `Empty set` | 조건으로 쓴 값을 바꿨는지 → 바뀐 값으로 조회 (2단계) |
| `Query OK, 0 rows affected` / `Rows matched: 0` | `WHERE`에 맞는 행이 없음. 오타·이미 바꾼 값인지 (2·5단계) |
| `Rows matched: 1  Changed: 0` | 이미 같은 값이라 바뀐 게 없음 (3단계) |
| `ERROR 1054 ... Unknown column 'emial' in 'field list'` | 열 이름 철자, `DESCRIBE students;` (2단계) |
| `ERROR 1292 ... Incorrect date value: 'NULL'` | `NULL`에 따옴표를 붙임 (3단계) |
| `ERROR 1064 ... near 'registered_date = ...'` | `SET`의 열 사이 쉼표 (3단계) |
| `ERROR 1064 ... near '* FROM ...'` / `near 'WHERE ...'` | `DELETE FROM 테이블 WHERE` 모양인지 (5단계) |
| `ERROR 1048 ... Column 'name' cannot be null` | `NOT NULL` 열에 `NULL`을 넣음 (3단계) |
| `ERROR 1062 ... Duplicate entry ... for key 'students.email'` | 다른 학생이 이미 쓰는 이메일로 바꿈 (02의 `UNIQUE`) |
| `ERROR 1175 ... safe update mode` | 안전 수정 모드가 켜짐 → `WHERE`에 키 열, 또는 `SET SQL_SAFE_UPDATES = 0;` (4단계) |
| 모든 학생 이름이 같아짐 | `WHERE`가 빠짐. 트랜잭션 안이면 `ROLLBACK`, 아니면 하나씩 `UPDATE`로 되돌리기 (4·7단계) |
| `ROLLBACK`했는데 안 돌아옴 | `START TRANSACTION;`을 먼저 했는지, 이미 `COMMIT`했는지, 중간에 구조 변경이 있었는지 (6·7단계) |
| 다른 탭·다른 프로그램에서 바뀐 값이 안 보임 | 아직 `COMMIT` 전. 트랜잭션은 그 연결에만 보임 (6단계) |
