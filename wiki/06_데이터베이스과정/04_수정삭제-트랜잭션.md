# 04. 데이터 수정·삭제와 트랜잭션 — `UPDATE`·`DELETE`·`COMMIT`·`ROLLBACK`

> 과정: 데이터베이스과정 · [노션 원문](https://app.notion.com/p/41a848f71c9b80c6ba5afcc85d8392fb) · 최종 갱신일: 2026-11-27

## 한눈에 보기
- **`UPDATE 테이블 SET 열 = 값 WHERE 조건;`** 으로 기존 행을 수정하고, **`DELETE FROM 테이블 WHERE 조건;`** 으로 행을 삭제한다. 여러 열은 `SET`에서 쉼표로 구분한다.
- **`WHERE`가 없으면 모든 행**이 바뀌거나 지워진다. `WHERE`가 있어도 여러 행이 해당될 수 있다. → **같은 조건으로 먼저 `SELECT`** 해서 대상과 개수를 확인하고, 변경 후 다시 조회한다.
- **트랜잭션** = 함께 확정하거나 함께 취소할 작업 단위. **`COMMIT`** = 확정, **`ROLLBACK`** = 아직 확정 안 된 변경 **전체** 취소. 커밋한 변경은 되돌릴 수 없다.
- **자동 커밋**이 켜져 있으면 성공한 변경문이 바로 확정된다. 그래서 취소 연습은 **MySQL `START TRANSACTION;`** (H2는 `SET AUTOCOMMIT FALSE;`)으로 시작하고 **같은 편집기**에서 진행했다.
- 트랜잭션 안에서 바뀐 값이 조회돼도 **확정된 것은 아니다.** SQL 파일 저장 ≠ `COMMIT`.

> 💡 보충: 2026-11-23 원문에 **수업 중 추가된 SQL** 세 덩어리가 들어왔다 (4장·5장·9장 끝에 따로 적음). 이 중 5장 끝의 이리액트 삭제 SQL은 트랜잭션 없이 실제로 지우므로, 그대로 실행하면 뒤의 트랜잭션 ③과 [05](05_테이블관계-JOIN.md)의 B반 배정이 대상 없이 끝난다 (5장 끝 보충).

## 학습 목표
- `UPDATE`로 저장된 데이터를 수정한다.
- `DELETE`로 조건에 맞는 데이터를 삭제한다.
- 변경 전에 조회해 대상을 확인하는 습관을 익힌다.
- 자동 커밋과 트랜잭션의 의미를 이해한다.
- `COMMIT`과 `ROLLBACK`으로 변경을 확정하거나 취소한다.

## 핵심 개념

### 1. 실습 준비 — 대상은 이메일로 찾는다
[03](03_데이터조회.md)까지의 학생 다섯 명을 그대로 쓴다. MySQL은 `USE school;`, H2는 실습 DB에 연결하고 `USE`는 생략한다.

```sql
SELECT *
FROM students
ORDER BY id ASC;
```

| 이름 | 이메일 | 등록일 |
|---|---|---|
| 한코딩 | han@example.com | 2026-11-16 |
| 김자바 | java@example.com | 2026-11-17 |
| 이리액트 | react@example.com | 2026-11-18 |
| 박스프링 | spring@example.com | NULL |
| 정데이터 | data@example.com | 2026-11-20 |

- 학생 번호는 사람마다 다를 수 있으므로, 예제는 **중복이 금지된(`UNIQUE`) 이메일로 대상을 찾는다.**
- **코드 블록을 하나씩 실행한다.** 특히 트랜잭션 실습은 중간 결과를 확인하며 진행한다.

### 2. 데이터 수정 — `UPDATE`

```sql
UPDATE 테이블
SET 열 = 변경할_값
WHERE 변경할_행의_조건; -- 반드시... 안 적으면 테이블 전체 데이터를 다 업데이트 해 버림
```

| 문법 | 역할 |
|---|---|
| `UPDATE` | 수정할 테이블 |
| `SET` | 변경할 열과 값 |
| `WHERE` | 수정할 행의 조건 |

**① 수정할 학생 먼저 조회 → ② 수정 → ③ 결과 확인**

```sql
SELECT *
FROM students
WHERE email = 'han@example.com';
```

```sql
UPDATE students
SET email = 'hancoding@example.com'
WHERE email = 'han@example.com';
```

```sql
SELECT *
FROM students
WHERE email = 'hancoding@example.com';
```

- **조건으로 쓴 값(이메일)을 수정했다면, 결과 확인에도 바뀐 값을 써야 한다.**

### 3. 여러 열 함께 수정, `NULL`로 되돌리기
`SET`에서 여러 열은 **쉼표**로 구분한다.

```sql
UPDATE students
SET name = '박스프링부트',
    registered_date = '2026-11-19'
WHERE email = 'spring@example.com';
```

- 이메일은 안 바꿨으므로 같은 조건(`email = 'spring@example.com'`)으로 대상 확인·결과 확인을 한다.

```sql
UPDATE students
SET registered_date = NULL
WHERE email = 'spring@example.com';
```

- 등록일을 다시 미정으로 바꿀 때는 `NULL`을 넣는다. **`NULL`에는 따옴표를 붙이지 않는다.**

### 4. `WHERE`가 없으면 어떻게 될까?
아래는 **실행하지 않고 의미만 보는** 예제다.

```sql
-- 실행하지 않는 설명용 예제
UPDATE students
SET name = '한코딩';
```

- 조건이 없으므로 **모든 학생의 이름이 한코딩으로 바뀐다.**

| 코드 | 변경 범위 |
|---|---|
| `UPDATE ... WHERE ...` | 조건을 만족하는 행 |
| `UPDATE ...` | 테이블의 모든 행 |

**`WHERE`가 있다고 항상 한 명만 바뀌는 것도 아니다**

```sql
-- 여러 명이 변경될 수 있는 설명용 예제
UPDATE students
SET registered_date = '2026-11-20'
WHERE registered_date IS NULL;
```

- 등록일이 없는 학생이 여러 명이면 **모두** 바뀐다. → `WHERE`의 유무뿐 아니라 **그 조건에 몇 명이 해당하는지**도 확인한다.

**변경 전 확인하는 순서**

```text
같은 조건으로 SELECT
          ↓
조회된 대상과 개수 확인
          ↓
UPDATE 실행
          ↓
다시 SELECT로 결과 확인
```

**수업 중 추가된 코드 — 트랜잭션 안에서 확인하며 수정하기**

```sql
-- 1) 롤백 가능하게 트랙잭션 시작
START TRANSACTION;

-- 2) 업데이트할 데이터 확인
select * from students where name = 'KDT';

-- 3) 업데이트문 작성
update students set name = '케이디티' where name = 'KDT';

-- 4_1) 업데이트 후 데이터가 사라진 것을 확인
select * from students where name = 'KDT';

-- 4_2) 업데이트 후 데이터가 수정된 것을 확인
select * from students where name = '케이디티';

-- 5) 전체 데이터 확인
select * from student

-- 6) 데이터에 문제가 있을 시
rollback;

-- 7) 문제 없을시
commit;
```

> 💡 보충: 실행 결과 (MySQL 8.4)
> - 위 "변경 전 확인하는 순서"를 6장의 트랜잭션 안에서 하는 버전이다. 확인 결과가 이상하면 6), 괜찮으면 7) — **둘 중 하나만** 실행한다.
> - `'KDT'`는 강의 데이터(학생 다섯 명)에 없는 이름이다. 그대로 실행하면 조회 결과가 비고 `UPDATE`도 `Rows matched: 0`이다. 수업 DB에 있던 학생 기준이다 ([05](05_테이블관계-JOIN.md) 수업 SQL에서도 `KDT` 학생을 추가한다). 내 데이터에 있는 이름으로 바꿔 실행한다.
> - 5)의 `select * from student`는 테이블 이름 오타(`students`)라 `ERROR 1146 (42S02): Table 'school.student' doesn't exist`가 난다. 끝에 세미콜론도 없다. 이 오류가 나도 트랜잭션은 이어져서, 뒤의 `rollback;`으로 수정이 취소됐다.

### 5. 데이터 삭제 — `DELETE`

```sql
DELETE FROM 테이블
WHERE 삭제할_행의_조건;
```

기존 학생은 이후 실습에서 쓰므로 **삭제 전용 학생**을 추가해서 지운다.

```sql
INSERT INTO students (name, email, registered_date)
VALUES ('삭제연습', 'delete-practice@example.com', '2026-11-21');
```

```sql
SELECT *
FROM students
WHERE email = 'delete-practice@example.com';
```

```sql
DELETE FROM students
WHERE email = 'delete-practice@example.com';
```

```sql
SELECT *
FROM students
WHERE email = 'delete-practice@example.com';
```

- 마지막 조회 결과가 비어 있으면 삭제된 것이다.
- **`DELETE`는 행을 삭제한다. 테이블 구조는 남아 있다.**

```sql
-- 실행하지 않는 설명용 예제
DELETE FROM students;
```

- 조건이 없으므로 **테이블의 모든 행을 삭제**한다. 실행하지 않는다.

**수업 중 추가된 코드 — 삭제 전후를 조회·개수로 확인하기**

```sql
-- 1. 삭제할 데이터 선택
select * from students where name = '이리액트'

-- 2. 삭제할 대상 데이터의 갯수 확인
select count(*) from students where name = '이리액트'

-- 3. 삭제 전 데이터 갯수 확인 
select count(*) from students

-- 4. 데이터 삭제
delete from students where name = '이리액트'

-- 5. 삭제한 데이터가 검색되는 않는 것을 확인
select * from students where name = '이리액트'

-- 6. 전체 데이터에 영향이 없는지 확인
select * from students

-- 7. 전체 데이터에 영향이 없는지 확인
select count(*) from students
```

> 💡 보충: 실행 결과 (MySQL 8.4, 한 문장씩 실행)
> - 2번 `count(*)` 1, 3번 5 → 4번 삭제 → 5번 결과 없음 → 7번 4. 삭제 대상 개수(1)만큼 전체 개수가 줄었는지 보는 순서다.
> - **트랜잭션 없이 실행하므로 이리액트가 바로 확정 삭제된다** (자동 커밋). 그러면 실습 정리의 트랜잭션 ③(이리액트 삭제 → `ROLLBACK`으로 복구)은 `0 rows affected`로 지울 대상이 없고, 복구 확인 조회도 비어 있다. [05](05_테이블관계-JOIN.md)의 "이리액트는 B반" `UPDATE`도 `Rows matched: 0`이 되어 B반 학생이 0명이 된다. 강의 흐름대로 이어 가려면 이 블록은 읽기만 하거나, 위의 `삭제연습` 학생처럼 연습용 학생으로 바꿔 실행한다.
> - 문장 끝에 세미콜론(`;`)이 없다. 한 문장씩 선택해 실행해야 한다. 블록 전체를 mysql 명령줄에 붙여 넣었더니 문장이 이어 붙어 `ERROR 1064 (42000)`(문법 오류)가 났다.
> - 대상을 `name`으로 찾는다. 이름은 `UNIQUE`가 아니어서 같은 이름이 여럿이면 모두 지워진다 → 2번처럼 개수를 먼저 확인하는 이유다. 강의 본문은 중복이 없는 이메일로 찾는다 (1장).

### 6. 실행한 변경을 취소할 수 있을까? — 트랜잭션
변경을 취소하려면 **아직 확정되지 않은 트랜잭션 안에서 작업했어야** 한다.

**트랜잭션** = 하나의 작업 단위로 묶어 **확정하거나 취소**하는 데이터베이스 작업.

```text
기존 반의 학생 수 감소
          +
새 반의 학생 수 증가
```

- 반을 옮길 때 둘 중 하나만 반영되면 정보가 맞지 않는다. 하나의 트랜잭션으로 묶으면 **모두 확정하거나 모두 취소**할 수 있다.
- 이번에는 학생 정보 수정·삭제를 취소해 보며 원리를 익힌다.

| 명령 | 역할 |
|---|---|
| `COMMIT` | 현재 트랜잭션의 변경 **확정** |
| `ROLLBACK` | 현재 트랜잭션의 **미확정** 변경 취소 |

```text
트랜잭션 시작
      ↓
데이터 변경
      ↓
결과 확인
   ┌──┴──┐
COMMIT  ROLLBACK
확정     취소
```

- **`COMMIT`으로 확정한 변경을 나중에 `ROLLBACK`으로 되돌릴 수는 없다.**

### 7. 자동 커밋
자동 커밋이 켜져 있으면, 따로 트랜잭션을 시작하지 않은 상태에서 **성공한 변경문이 자동으로 확정**된다.

```text
UPDATE 실행 → 자동 확정
DELETE 실행 → 자동 확정
```

- 그래서 앞(2절)에서 이미 확정된 이메일 변경은 지금 `ROLLBACK`으로 취소할 수 없다.
- DBeaver는 **자동 커밋 / 수동 커밋** 모드를 제공한다. 수동 커밋에서는 직접 확정하거나 취소한다. ([DBeaver 트랜잭션 모드 안내](https://dbeaver.com/docs/dbeaver/Auto-and-Manual-Commit-Modes/))

**이번 실습의 진행 방식** — 도구의 커밋 버튼과 SQL 명령을 섞으면 헷갈리므로 **SQL로 트랜잭션을 제어**한다.
- 앞의 수정·삭제를 수동 커밋으로 했다면 결과를 확인하고 **먼저 확정**한다.
- 아래의 DB별 시작 명령을 실행한다.
- 시작부터 끝까지 **같은 연결·같은 SQL 편집기**에서 진행한다.
- 트랜잭션 도중 **연결을 바꾸거나 커밋 모드를 바꾸지 않는다.**
- MySQL은 테이블이 트랜잭션을 지원하는 기본 엔진 **InnoDB**를 쓴다는 전제다.

| DB | 트랜잭션 시작 | 끝낸 뒤 |
|---|---|---|
| MySQL | `START TRANSACTION;` | `COMMIT`/`ROLLBACK` 후 원래 자동 커밋 방식으로 돌아감 |
| H2 | `SET AUTOCOMMIT FALSE;` (자동 커밋 끄기) | 실습을 마치면 `SET AUTOCOMMIT TRUE;` |

- **자신이 쓰는 DB의 명령 하나만** 실행한다. ([H2 명령 안내](https://h2database.github.io/html/commands.html#set_autocommit))

### 8. 트랜잭션 안에서 보이는 값은 확정된 것이 아니다
트랜잭션 안에서 `UPDATE` 후 같은 편집기로 조회하면 **바뀐 값이 보인다.**

- **조회 결과에 보인다고 변경이 확정된 것은 아니다.** 같은 트랜잭션에서 **자신이 변경한 내용**을 보고 있는 상태다.

| 동작 | 의미 |
|---|---|
| SQL 파일 저장 | 작성한 SQL **문장을 파일로** 저장 |
| `COMMIT` | 실행한 **데이터 변경을 DB에 확정** |

### 9. `ROLLBACK`의 범위
`ROLLBACK`은 **현재 트랜잭션에서 아직 확정하지 않은 변경 전체**를 취소한다. 마지막 SQL 한 줄만 취소하는 기능이 아니다.

```text
트랜잭션 시작
      ↓
A 학생 이름 수정
      ↓
B 학생 삭제
      ↓
ROLLBACK
      ↓
이름 수정과 삭제가 모두 취소
```

| 작업 | 이번 수업에서의 이해 |
|---|---|
| `INSERT`, `UPDATE`, `DELETE` | 트랜잭션 안에서 확정 전 취소 가능 |
| 이미 커밋된 변경 | `ROLLBACK`으로 취소 불가 |
| `CREATE TABLE`, `DROP TABLE`, `TRUNCATE TABLE` | 데이터 변경과 구분. 같은 방식의 취소를 기대하지 않음 |

- 테이블 생성·삭제 같은 **구조 변경 명령은 DB에 따라 자동 커밋을 일으킬 수 있다.** → **트랜잭션 실습 중에는 테이블 구조를 바꾸는 SQL을 실행하지 않는다.**
- **커밋과 저장 매체는 별개다.** 파일 방식 DB는 커밋한 데이터가 재실행 후에도 남지만, **H2 메모리 DB는 커밋했어도 프로세스가 끝나면 사라진다.** (메모리·파일 모드 비교: [Spring 05](../03_Spring과정/05_H2-JPA저장.md))

**수업 중 추가된 코드 — 삭제 확인을 트랜잭션으로 감싸기**

```sql
start transaction

-- 1. 삭제할 데이터 선택
select * from students where name = '김리액트'

-- 2. 삭제할 대상 데이터의 갯수 확인
select count(*) from students where name = '김리액트'

-- 3. 삭제 전 데이터 갯수 확인 
select count(*) from students

-- 4. 데이터 삭제
delete from students where name = '김리액트'

-- 5. 삭제한 데이터가 검색되는 않는 것을 확인
select * from students where name = '김리액트'

-- 6. 전체 데이터에 영향이 없는지 확인
select * from students

-- 7. 전체 데이터에 영향이 없는지 확인
select count(*) from students

commit
```

> 💡 보충: 5장 끝 수업 SQL을 `start transaction` ~ `commit`으로 감싼 버전이다. 2~7번 확인 결과가 이상하면 `commit` 대신 `rollback`을 실행해 되돌린다. `'김리액트'`는 강의 데이터에 없는 이름이라 그대로 실행하면 `0 rows affected`다 (실행 확인). 세미콜론이 없으므로 한 문장씩 선택해 실행한다.

### 정리

| 문법·개념 | 역할 |
|---|---|
| `UPDATE` | 기존 행의 값 수정 |
| `SET` | 변경할 열과 값 지정 |
| `DELETE FROM` | 행 삭제 |
| `WHERE` | 변경하거나 삭제할 대상 지정 |
| 트랜잭션 | 함께 확정하거나 취소할 작업 단위 |
| 자동 커밋 | 별도 트랜잭션 밖에서 성공한 변경문을 자동 확정 |
| `START TRANSACTION` | MySQL에서 트랜잭션 시작 |
| `SET AUTOCOMMIT FALSE` | H2에서 자동 커밋 끄기 |
| `COMMIT` | 현재 트랜잭션 변경 확정 |
| `ROLLBACK` | 현재 트랜잭션의 미확정 변경 취소 |

## 실습 정리

### 한 일
1. 한코딩 이메일 수정 (자동 커밋으로 바로 확정)
2. 박스프링 이름·등록일 수정 → 등록일을 다시 `NULL`로
3. 삭제 전용 학생 추가 → 삭제
4. 트랜잭션 ① 김자바 이름 수정 → **`ROLLBACK`** (원래대로)
5. 트랜잭션 ② 김자바 이름 수정 → **`COMMIT`** (확정)
6. 트랜잭션 ③ 이리액트 삭제 → **`ROLLBACK`** (복구)

수업 중 추가된 SQL(4·5·9장 끝)은 위 흐름에 넣지 않았다. 특히 5장 끝 SQL은 이리액트를 실제로 지우므로 강의 흐름을 따라갈 때는 실행하지 않는다.

### 트랜잭션 ① — 수정한 내용을 `ROLLBACK`으로 취소

```sql
-- ① 변경 전 값 확인
SELECT name, email
FROM students
WHERE email = 'java@example.com';

-- ② 트랜잭션 시작 (MySQL)
START TRANSACTION;
-- (H2라면 대신) SET AUTOCOMMIT FALSE;

-- ③ 이름 변경
UPDATE students
SET name = '김자바수정'
WHERE email = 'java@example.com';

-- ④ 같은 편집기에서 확인 → 바뀐 이름이 보임 (아직 미확정)
SELECT name, email
FROM students
WHERE email = 'java@example.com';
```

```sql
-- ⑤ 변경 취소
ROLLBACK;
```

```sql
-- ⑥ 다시 확인 → 변경 전 이름(김자바)으로 돌아옴
SELECT name, email
FROM students
WHERE email = 'java@example.com';
```

### 트랜잭션 ② — 수정한 내용을 `COMMIT`으로 확정

```sql
-- ① 트랜잭션 시작 (MySQL)
START TRANSACTION;
-- (H2라면 대신) SET AUTOCOMMIT FALSE;

-- ② 이름 수정
UPDATE students
SET name = '김자바개발자'
WHERE email = 'java@example.com';

-- ③ 결과 확인
SELECT name, email
FROM students
WHERE email = 'java@example.com';

-- ④ 변경 확정
COMMIT;

SELECT name, email
FROM students
WHERE email = 'java@example.com';
```

### 트랜잭션 ③ — 삭제한 학생을 `ROLLBACK`으로 복구

```sql
-- ① 트랜잭션 시작 (MySQL)
START TRANSACTION;
-- (H2라면 대신) SET AUTOCOMMIT FALSE;

-- ② 삭제할 대상 확인
SELECT *
FROM students
WHERE email = 'react@example.com';

-- ③ 학생 삭제
DELETE FROM students
WHERE email = 'react@example.com';

-- ④ 삭제 결과 확인 → 현재 트랜잭션에서는 결과 없음
SELECT *
FROM students
WHERE email = 'react@example.com';

-- ⑤ 삭제 취소
ROLLBACK;

-- ⑥ 복구 확인 → 이리액트가 다시 조회됨
SELECT *
FROM students
WHERE email = 'react@example.com';
```

**H2 실습 종료 설정** — 모든 변경을 `COMMIT` 또는 `ROLLBACK`으로 마친 뒤 자동 커밋을 다시 켠다.

```sql
SET AUTOCOMMIT TRUE;
```

- MySQL의 `START TRANSACTION`은 그 트랜잭션만 시작하는 명령이다. 원래 자동 커밋이 켜져 있었다면, 트랜잭션이 끝난 뒤 다시 문장마다 자동 확정된다.

> 💡 보충: 이 회차를 마친 뒤의 데이터다. [05](05_테이블관계-JOIN.md)에서 이어서 쓴다.
>
> | 이름 | 이메일 | 등록일 |
> |---|---|---|
> | 한코딩 | hancoding@example.com | 2026-11-16 |
> | 김자바개발자 | java@example.com | 2026-11-17 |
> | 이리액트 | react@example.com | 2026-11-18 |
> | 박스프링부트 | spring@example.com | NULL |
> | 정데이터 | data@example.com | 2026-11-20 |

## 헷갈리기 쉬운 점
- **`WHERE` 없는 `UPDATE`·`DELETE`는 모든 행에 적용된다.** 설명용 예제는 실행하지 않는다.
- **`WHERE`가 있어도 여러 행이 바뀔 수 있다.** 같은 조건의 `SELECT`로 대상 **개수**까지 확인한다.
- **조건으로 쓴 값을 바꿨으면 확인 조회도 바뀐 값으로 한다** (`han@…` → `hancoding@…`).
- **`DELETE`는 행만 지운다.** 테이블 구조는 남는다.
- **자동 커밋 상태에서 실행한 변경은 이미 확정됐다.** 나중에 `ROLLBACK`해도 안 돌아온다.
- **트랜잭션 안에서 바뀐 값이 보인다고 확정된 게 아니다.** `COMMIT`해야 확정이다.
- **`COMMIT` 후에는 `ROLLBACK`으로 되돌릴 수 없다.**
- **`ROLLBACK`은 마지막 한 줄이 아니라 미확정 변경 전체를 취소한다.**
- **SQL 파일 저장 ≠ `COMMIT`.**
- **트랜잭션은 같은 연결·같은 편집기에서 시작하고 끝낸다.** 도중에 연결·커밋 모드를 바꾸지 않는다. DBeaver의 커밋 버튼과 SQL 명령을 섞지 않는다.
- **MySQL은 `START TRANSACTION;`, H2는 `SET AUTOCOMMIT FALSE;`** — 내 DB의 것 하나만. H2는 끝나면 `SET AUTOCOMMIT TRUE;`.
- **트랜잭션 중에는 `CREATE`·`DROP`·`TRUNCATE` 같은 구조 변경을 하지 않는다.** 자동 커밋을 일으킬 수 있다.
- **커밋 ≠ 영구 보관.** H2 메모리 DB는 커밋해도 프로세스가 끝나면 사라진다 (메모리·파일 모드 비교: [Spring 05](../03_Spring과정/05_H2-JPA저장.md)).

> 💡 보충: 수업 추가 SQL에서 헷갈리기 쉬운 점
> - **`START TRANSACTION` 없이 실행한 `DELETE`는 바로 확정된다.** 확인용 조회를 아무리 잘 넣어도 되돌릴 수 없다 → 확인 후 되돌릴 여지를 남기려면 9장 끝 버전처럼 트랜잭션으로 감싼다.
> - **테이블 이름 오타(`student`)는 `ERROR 1146`.** 오류가 나도 트랜잭션은 끝나지 않는다. `ROLLBACK`/`COMMIT`으로 직접 끝낸다.
> - **세미콜론 없는 SQL은 한 문장씩 선택해 실행한다.** 한꺼번에 실행하면 문장이 이어 붙어 문법 오류.

## 확인 문제

<details><summary>Q. `UPDATE`문의 `UPDATE`, `SET`, `WHERE`는 각각 무엇을 정하는가?</summary>

`UPDATE` = 수정할 테이블, `SET` = 변경할 열과 값 (여러 열은 쉼표), `WHERE` = 수정할 행의 조건.
</details>

<details><summary>Q. 수정·삭제 전에 같은 조건으로 `SELECT`하는 이유는? 안전한 변경 순서는?</summary>

조건에 걸리는 **대상과 개수**를 미리 확인하기 위해서다. 순서: 같은 조건으로 `SELECT` → 대상·개수 확인 → `UPDATE`(`DELETE`) 실행 → 다시 `SELECT`로 결과 확인.
</details>

<details><summary>Q. `WHERE email = 'han@example.com'`으로 이메일을 `hancoding@example.com`으로 바꿨다. 결과는 어떤 조건으로 확인하는가?</summary>

**바뀐 값**인 `WHERE email = 'hancoding@example.com'`으로 조회한다. 원래 값으로 조회하면 결과가 없다.
</details>

<details><summary>Q. `WHERE` 없이 `UPDATE students SET name = '한코딩';`이나 `DELETE FROM students;`를 실행하면? `WHERE`가 있으면 항상 한 명만 바뀌는가?</summary>

**모든 학생**의 이름이 바뀌거나 모든 행이 삭제된다. `WHERE`가 있어도 조건에 해당하는 행이 여러 개면 **모두** 바뀐다 (예: `WHERE registered_date IS NULL`).
</details>

<details><summary>Q. `DELETE`로 모든 행을 지우면 테이블도 사라지는가?</summary>

아니다. `DELETE`는 **행만** 삭제하고 테이블 구조는 남는다.
</details>

<details><summary>Q. 트랜잭션이란 무엇이고, 왜 필요한가?</summary>

하나의 작업 단위로 묶어 **모두 확정하거나 모두 취소**하는 DB 작업이다. 예: 반 이동에서 "기존 반 학생 수 감소 + 새 반 학생 수 증가" 중 하나만 반영되면 정보가 맞지 않으므로 함께 묶는다.
</details>

<details><summary>Q. `COMMIT`과 `ROLLBACK`의 차이는? `COMMIT`한 변경을 `ROLLBACK`으로 되돌릴 수 있는가?</summary>

`COMMIT` = 현재 트랜잭션의 변경 확정, `ROLLBACK` = 현재 트랜잭션의 미확정 변경 취소. **커밋한 변경은 `ROLLBACK`으로 되돌릴 수 없다.**
</details>

<details><summary>Q. 자동 커밋이 켜진 상태에서 실행한 이메일 변경을 나중에 `ROLLBACK`으로 취소할 수 있는가?</summary>

없다. 자동 커밋에서는 성공한 변경문이 **바로 확정**된다. 취소하려면 확정 전, 트랜잭션 안에서 작업했어야 한다.
</details>

<details><summary>Q. MySQL과 H2에서 트랜잭션 실습을 시작하는 명령은? H2는 끝날 때 무엇을 하는가?</summary>

MySQL `START TRANSACTION;`, H2 `SET AUTOCOMMIT FALSE;` (내 DB의 것 하나만). H2는 모두 `COMMIT`/`ROLLBACK`한 뒤 `SET AUTOCOMMIT TRUE;`로 자동 커밋을 다시 켠다.
</details>

<details><summary>Q. 트랜잭션 안에서 `UPDATE`한 뒤 조회했더니 바뀐 이름이 보였다. 확정된 것인가?</summary>

아니다. 같은 트랜잭션에서 **자신이 변경한 내용**을 보는 것일 뿐이다. `COMMIT`해야 확정되고, `ROLLBACK`하면 원래대로 돌아온다.
</details>

<details><summary>Q. 트랜잭션 안에서 A 학생 수정, B 학생 삭제를 한 뒤 `ROLLBACK`하면?</summary>

**수정과 삭제가 모두 취소**된다. `ROLLBACK`은 마지막 한 줄이 아니라 현재 트랜잭션의 미확정 변경 **전체**를 취소한다.
</details>

<details><summary>Q. SQL 편집기에서 파일을 저장하면 DB 변경이 확정되는가?</summary>

아니다. 파일 저장은 **SQL 문장**을 파일로 저장하는 것이고, DB 변경 확정은 **`COMMIT`** 이다.
</details>

<details><summary>Q. 트랜잭션 실습 중에 `CREATE TABLE`·`DROP TABLE`을 실행하지 않는 이유는?</summary>

테이블 구조 변경 명령은 DB에 따라 **자동 커밋을 일으킬 수 있어서**, 데이터 변경과 같은 방식의 취소를 기대할 수 없다.
</details>

<details><summary>Q. 커밋했으면 데이터는 항상 영구히 남는가?</summary>

아니다. **커밋과 저장 매체는 별개**다. 파일 방식 DB는 재실행 후에도 남지만, H2 **메모리** DB는 커밋했어도 프로세스가 끝나면 사라진다.
</details>

<details><summary>Q. (수업 추가 SQL) 5장 끝의 이리액트 삭제 SQL을 그대로 실행한 뒤 트랜잭션 ③(이리액트 삭제 → `ROLLBACK`)을 하면 어떻게 되는가?</summary>

수업 SQL은 `START TRANSACTION` 없이 `delete`를 실행해서 자동 커밋으로 이미 확정됐다. 트랜잭션 ③의 `DELETE`는 지울 대상이 없어 `0 rows affected`이고, `ROLLBACK` 뒤에도 이리액트는 돌아오지 않는다 (커밋된 변경은 `ROLLBACK`으로 취소 불가). 확인하며 지우려면 9장 끝 버전처럼 `start transaction` ~ `commit`/`rollback`으로 감싼다.
</details>

- [ ] 트랜잭션 안에서 삭제한 학생을 복구했다.
