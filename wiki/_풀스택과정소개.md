# 풀스택 과정 소개 — 무엇을 배우고 무엇을 만들 수 있나

> 오리엔테이션 (2026-10-30) · [노션 원문: 풀스택 과정 소개](https://app.notion.com/p/408848f71c9b803c9104e4c7430e4b92) · [노션 원문: 우리가 만들 수 있는 것들](https://app.notion.com/p/408848f71c9b80f69c51dbad9fec28a2) · 최종 갱신일: 2026-11-19

과정 전체를 안내하는 파일이다. 회차가 아니라서 연습 진도·실력점검에는 넣지 않는다.

## 한눈에 보기
- 풀스택 개발은 **화면(프론트엔드) – 서버(백엔드) – 데이터베이스 – 배포**를 연결하는 일이다. 이 과정에서는 React로 화면을, Node.js와 Spring으로 서버를, MySQL로 데이터를 다룬다.
- 전체 흐름: **이론 학습(1개월) → 기본 프로젝트 → 심화 프로젝트 → 실무 통합 프로젝트**. 배운 내용을 프로젝트에 적용하며 구현 범위와 협업 경험을 넓힌다.
- 수업은 **핵심 개념 설명 → 강사의 구현 시연 → 직접 변형 실습 → 오류 해결과 정리** 순서다. **모든 내용을 첫 설명에서 이해할 필요는 없다.** 듣고, 실행하고, 바꿔 보기를 반복한다.
- 만들 수 있는 결과물은 웹사이트부터 스토어에 출시하는 Android·iOS 앱까지. 중요한 것은 서비스의 종류보다 **왜 만들었고 어떻게 검증하고 개선했는지 설명할 수 있는 경험**이다.
- 개발 기록(GitHub·블로그) 준비는 [GitHub-블로그-기록](00_개발환경/GitHub-블로그-기록.md).

## 과정에서 연습할 것
코드를 실행하는 경험에서 출발해 각 시스템의 연결을 이해하고, 이후 AI를 활용해 기획부터 출시까지 경험을 쌓는다.

- 사용자가 조작할 수 있는 화면 만들기 (프론트엔드)
- 서버에 데이터를 요청하고 결과 표시하기 (백엔드)
- 데이터를 저장·조회·수정·삭제하기 (CRUD)
- AI를 이용하여 코드를 만들고 테스트
- 만든 서비스를 테스트하고 배포하기 (WEB / Android / iOS)

### 풀스택 개발은 무엇을 연결하는 일일까
일정 관리 앱에서 일정을 등록하는 상황을 생각해 본다.

```text
제목과 시작일, 종료일 등 입력 → 추가하기 버튼 클릭 → 서버에 요청
→ 입력값 검사 → DB 저장 → 화면에 결과 표시
```

| 구성 요소 | 하는 일 | 과정에서 만날 기술 |
|---|---|---|
| 프론트엔드 | 사용자가 보고 조작하는 화면 | React (HTML, CSS) |
| 백엔드 | 요청 처리, 검증, 서비스 로직 실행 | Node.js / Spring |
| 데이터베이스 | 서비스에 필요한 데이터 저장·조회 | MySQL / D1 등 |
| 배포 | 이용자들이 사용할 수 있는 공간 | AWS / Cloudflare 등 |

- **Node.js와 Spring은 서버를 구현하는 서로 다른 선택지**다. 같은 기능을 구현하면서 공통 원리와 구현 방식의 차이를 살펴본다.

> 💡 보충: D1은 Cloudflare가 제공하는 SQLite 기반 데이터베이스다.

## 수업 방식

### 진행
- 수업 시간은 **매시 정시부터 50분까지, 이후 10분은 휴식**.
- 설명을 들은 뒤 직접 실행하고 수정하는 시간을 갖는다.
- 실습은 **필수 과제**와 **추가 도전 과제**로 나누어 안내한다.
- 막힌 부분은 기록해 두고 실습 시간에 질문한다.

### 질문하는 법
아래 내용을 함께 알리면 상황을 더 빨리 파악할 수 있다. 모든 항목을 몰라도 질문해도 된다.

| 함께 알릴 것 | 내용 |
|---|---|
| 하려던 것 | 어떤 기능을 구현하려 했나? |
| 실제 결과 | 무엇이 예상과 달랐나? |
| 오류 내용 | 어떤 메시지가 나왔나? |
| 시도한 방법 | 어디까지 확인했나? |

- 진도(어느 부분을 진행할 때 생긴 오류인지)와 오류 화면, 이해가 안 된 내용을 과정 커뮤니티 채널에 올린다.
- 질문 예시: "(사진 첨부와 함께) 이미지에 보이는 것처럼 Cannot read field "name" because "board" is null 이라는 오류가 발생합니다."
- 화면 캡처: Windows `Win + Shift + S`.
- **공유하기 전에 비밀번호, API 키, 개인정보가 들어 있지 않은지 확인한다.**

> 💡 보충: macOS 화면 캡처는 `⌘ + ⇧ + 4`(영역 선택) 또는 `⌘ + ⇧ + 5`(캡처 도구).

### AI 활용
AI를 선생님처럼, 조교처럼 활용해 이해가 안 되는 내용은 바로 질문해도 된다. 다만 AI가 알려 준 정보로 문제만 해결하지 말고 **어떻게 해결했는지 과정을 학습**한다.
- 오류가 발생한 부분의 이미지를 첨부한다.
- AI의 답변을 토대로 어느 부분에서 문제가 생겼는지 파악한다.
- 코드를 그대로 붙여 넣지 말고 직접 수정하며 학습한다.

### 학습 약속
- 다른 사람과의 격차나 학습 속도를 비교하기보다, 어제보다 오늘 더 성장했는지 확인한다.
- 다양한 연령대·학과·직업군에서 온 사람들이 함께한다. 질문과 실수를 서로 존중한다.
- 함께 해결하더라도 직접 실행하고 확인하는 과정에 참여한다.
- 모르는 부분을 숨기지 않고, 도움받을 수 있도록 공유한다.

## 만들 수 있는 결과물
**웹사이트, Android 앱, iOS 앱까지** — 앞으로 배우는 기술은 **누군가가 실제로 사용하는 서비스를 만드는 데 연결**된다. 강의에서는 실제로 운영 중인 웹사이트·앱 사례를 보며 만들 결과물을 생각했다.

| 결과물 | 강의에서 말한 비용·조건 |
|---|---|
| 웹사이트 | — |
| Android 앱 | 25달러 |
| iOS 앱 | 매년 129,000원, 맥북 |

> 💡 보충: Android 25달러는 Google Play 개발자 계정 등록비(한 번만 낸다), iOS 129,000원은 Apple Developer Program 연회비다. iOS 앱은 빌드·제출에 Xcode가 필요해서 Mac이 있어야 한다.

### 1. 지식과 경험을 전달하는 웹 서비스
예: 이론·영상·연습문제 같은 학습 콘텐츠를 제공하는 강의 사이트. 웹사이트를 운영하면 화면을 만드는 것 외에도 이런 질문을 만난다.
- 원하는 콘텐츠를 쉽게 찾을 수 있을까?
- 콘텐츠를 어떤 순서로 보여 줘야 이해하기 쉬울까?
- 새 콘텐츠를 편하게 추가하고 수정할 수 있을까?
- 휴대폰에서도 불편 없이 볼 수 있을까?

**내가 가진 지식이나 경험도 웹 서비스의 출발점이 될 수 있다.**

### 2. 내가 필요한 기능을 만드는 생활 서비스
예: 일정 관리처럼 내가 매일 쓰는 기능을 한곳에 모은 서비스. 개발자가 직접 사용자가 되면 구현할 때는 보이지 않던 불편을 발견한다.
- 자주 쓰는 기능에 접근하기 쉬운가?
- 같은 내용을 반복해서 입력하고 있지는 않은가?
- 작은 화면에서도 내용을 알아보기 쉬운가?
- 다시 사용하고 싶을 만큼 편리한가?

**내가 반복해서 겪는 불편은 좋은 서비스 아이디어가 될 수 있다.**

### 3. 스토어에 출시하고 운영하는 모바일 앱
서비스는 코드가 완성된 뒤에도 계속 손볼 일이 생긴다.
- 사용자가 앱을 발견할 수 있도록 소개 페이지 만들기
- 기능이 잘 전달되도록 스크린샷과 설명 준비하기
- 스토어 심사와 배포 과정 진행하기
- 사용자 의견과 오류를 확인하고 업데이트하기
- 서비스를 알리고, 사용자가 계속 이용할 이유 찾기

**출시는 개발 경험을 실제 운영 경험으로 넓히는 출발점이다.**

### 4. 흥미를 끄는 앱
실용적인 앱 말고도, 사용자의 흥미를 이용해 끌어들이고 수익을 낼 수 있는 앱도 있다. **사용자를 끌어들일 수 있는 앱이 진정으로 좋은 포트폴리오**라고 볼 수 있다.

### 기획부터 사용자에게 전달하기까지

```text
문제 발견 → 기획 → 구현 → 테스트 → 출시 → 홍보 → 피드백 → 개선
```

기능을 구현하는 능력과 함께, 그 기능이 **누구에게 왜 필요한지**도 생각한다.

| 단계 | 스스로 던져 볼 질문 |
|---|---|
| 문제 발견 | 누가 어떤 불편을 겪고 있을까? |
| 기획 | 가장 먼저 해결할 문제 한 가지는 무엇일까? |
| 구현 | 그 문제를 해결하는 최소 기능은 무엇일까? |
| 출시 | 다른 사람이 직접 사용할 수 있는가? |
| 홍보·마케팅 | 필요한 사람에게 어떻게 알릴까? |
| 개선 | 사용자가 어디서 막혔고, 무엇을 바꿨는가? |

- 처음부터 큰 서비스를 만들 필요는 없다. 주변의 몇 명이라도 직접 사용해 보고 의견을 줄 수 있는 작은 서비스부터 시작할 수 있다.

### 포트폴리오에 담을 수 있는 이야기
사용자에게 서비스를 제공하고 개선해 보면, 포트폴리오에서 설명할 구체적인 근거가 생긴다.

| 구현 경험 | 운영을 통해 더할 수 있는 이야기 |
|---|---|
| 로그인 기능을 만들었습니다. | 가입 과정에서 발견한 불편을 이렇게 개선했습니다. |
| 게시판을 만들었습니다. | 사용자의 목적에 맞춰 작성·검색 흐름을 바꿨습니다. |
| 서버를 배포했습니다. | 운영 중 발생한 오류를 발견하고 해결했습니다. |
| 앱을 출시했습니다. | 사용자의 의견을 받아 기능을 업데이트했습니다. |

- 커뮤니티나 게시판도 실제 문제를 해결하고 운영한다면 좋은 프로젝트가 될 수 있다.
- **중요한 것은 서비스의 종류보다, 왜 만들었고 어떻게 검증하고 개선했는지 설명할 수 있는 경험이다.**
- 출시와 수익화는 도전할 수 있는 목표다. 수익이 없더라도 사용자를 만나고 문제를 해결한 과정은 프로젝트에 담을 수 있다.

### 나라면 무엇을 만들까
- 내가 자주 겪는 불편은 무엇인가?
- 주변에서 같은 불편을 겪는 사람은 누구인가?
- 그 사람에게 가장 먼저 제공할 기능 한 가지는 무엇인가?

**"누가 사용할 것인가?"를 떠올리며 이번 과정의 프로젝트를 생각한다.**
