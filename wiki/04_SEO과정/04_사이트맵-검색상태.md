# 04. 사이트맵 제출과 검색 상태 확인하기 — sitemap.xml · URL 검사 · 수집 요청

> 과정: SEO과정 · [노션 원문](https://app.notion.com/p/41a848f71c9b809d9219e0fafe06d747) · 최종 갱신일: 2026-11-18

## 한눈에 보기
- 소유권 확인([03_사이트등록-소유확인](03_사이트등록-소유확인.md)) 다음 흐름: **사이트맵 제출 → 주요 페이지 검사·수집 요청 → 수집·색인 상태 확인 → 문제 수정과 콘텐츠 개선.** **요청 접수 ≠ 검색 노출.**
- **사이트맵(`sitemap.xml`)** 은 검색엔진에 알려주고 싶은 **공개 페이지 주소 목록**이다. `<urlset>` 안에 페이지마다 `<url><loc>전체 주소</loc></url>`를 쓴다. `localhost`·없는 페이지·로그인 페이지·관리자 화면·`noindex` 페이지·`#위치`는 넣지 않는다.
- 사이트맵은 **배포**해야 읽힌다. Vite React는 `public/sitemap.xml`, Spring Boot는 `src/main/resources/static/sitemap.xml`. 배포 후 `https://내주소/sitemap.xml`에서 XML이 보이는지 확인한다.
- 제출은 파일 업로드가 아니라 **사이트맵 주소를 알려주는 것**이다. 구글: Search Console **Sitemaps**, 네이버: **요청 → 사이트맵 제출**. 처리 "성공"도 모든 페이지 색인을 뜻하지 않는다.
- 특정 페이지는 구글 **URL 검사**(저장된 색인 정보 / **실제 URL 테스트** / 색인 생성 요청), 네이버 **요청 → 웹 페이지 수집**으로 확인·요청한다. 반복 요청해도 즉시 처리되지 않는다. 검색에 안 나오면 **상태를 먼저 확인하고 원인에 맞게 고친다.**

## 학습 목표
- 사이트맵의 역할을 이해한다.
- 간단한 사이트맵을 작성하고 배포할 수 있다.
- 구글과 네이버에 사이트맵을 제출할 수 있다.
- 주요 페이지의 수집과 색인 상태를 확인할 수 있다.

## 핵심 개념

### 1. 사이트 등록 다음에는?
이번에는 검색엔진에 **어떤 페이지가 있는지 알려주고, 검색에 반영되는 과정을 확인**한다.

```text
사이트 소유권 확인
        ↓
사이트맵 제출
        ↓
주요 페이지 검사·수집 요청
        ↓
수집·색인 상태 확인
        ↓
문제 수정과 콘텐츠 개선
```

**요청이 접수되었다는 것과 검색에 노출되었다는 것은 서로 다르다.**

### 2. 사이트맵이란?
**검색엔진에 알려주고 싶은 페이지 주소를 모아 둔 파일**이다. 보통 `sitemap.xml`이라는 이름을 쓴다.

| 페이지 | 주소 예시 |
|---|---|
| 메인 페이지 | `/` |
| 강의 목록 | `/courses` |
| 서비스 소개 | `/about` |

- 검색엔진은 페이지 안의 **링크를 따라가며** 다른 페이지를 발견할 수 있다. 사이트맵은 이런 주소를 **추가로** 알려준다 ([01_SEO-검색엔진](01_SEO-검색엔진.md) 4장).
- **사이트맵 제출은 페이지 발견을 돕는 방법일 뿐, 모든 주소의 수집·색인을 보장하지 않는다.** 👉 [Google 사이트맵 안내](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap?hl=ko)

**XML이란?** 정해진 태그로 데이터를 표현하는 형식이다. 이번에는 문법 전체가 아니라 **정해진 구조 안에 페이지 주소를 넣는다**고 이해하면 된다.

> 💡 보충: XML도 HTML처럼 `<태그>내용</태그>` 모양이지만, 태그 이름이 정해진 목록이 아니라 용도(여기서는 사이트맵 규칙)에 따라 정해진다. 서버가 데이터를 주고받을 때 쓴 JSON([03_서버-데이터보내기](../02_Node과정/03_서버-데이터보내기.md) 8장)과 같은 "데이터 형식"의 한 종류다.

### 3. 사이트맵 작성하기
메인 페이지 하나만 넣은 사이트맵이다. **예시 주소는 실제 배포한 사이트 주소로 바꾼다.**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://my-service.example.com/</loc>
  </url>
</urlset>
```

| 요소 | 의미 |
|---|---|
| `urlset` | 페이지 주소 목록을 감싸는 요소 |
| `url` | 페이지 하나에 대한 정보 |
| `loc` | 해당 페이지의 **전체 주소** |

페이지가 더 있으면 `<url>` 묶음을 추가한다.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://my-service.example.com/</loc>
  </url>

  <url>
    <loc>https://my-service.example.com/courses</loc>
  </url>

  <url>
    <loc>https://my-service.example.com/about</loc>
  </url>
</urlset>
```

**실제로 존재하고, 공개 검색에 포함하고 싶은 페이지 주소만 넣는다.** 넣지 않는 것:
- `localhost` 주소
- 존재하지 않는 페이지
- 로그인해야 볼 수 있는 개인정보 페이지
- 관리자 화면
- `noindex`를 설정한 페이지 ([02_검색친화-페이지](02_검색친화-페이지.md) 6장)
- `#learning`처럼 같은 페이지 안의 위치를 가리키는 주소 (별도 페이지가 아님)

**이미 사이트맵이 있다면?** 프레임워크나 서비스가 사이트맵을 자동으로 만들어 줄 수도 있다. 이미 있으면 새 파일로 덮어쓰지 말고, 기존 사이트맵의 내용과 제공 방식을 먼저 확인한다.

### 4. 사이트맵 배포하기 — 파일 위치
사이트맵이 내 컴퓨터에만 있으면 검색엔진이 읽을 수 없다. **배포해서 외부에서 접근할 수 있어야** 한다. 아래는 도메인 최상위 경로에서 제공하는 일반적인 구성이다.

| 프로젝트 | 파일 위치 |
|---|---|
| 일반 HTML 사이트 | 메인 `index.html`과 같은 배포 폴더의 `sitemap.xml` |
| Vite React 프로젝트 | `public/sitemap.xml` |
| Spring Boot 프로젝트 | `src/main/resources/static/sitemap.xml` |

Vite 프로젝트:

```text
프로젝트
├─ public
│  └─ sitemap.xml
├─ src
├─ index.html
└─ package.json
```

Spring Boot 프로젝트:

```text
src
└─ main
   └─ resources
      ├─ static
      │  └─ sitemap.xml
      └─ templates
```

파일을 추가한 뒤 **다시 배포**한다.

> 💡 보충: 두 위치 모두 "파일을 주소 그대로 제공하는 폴더"다. Vite의 `public/profile.png`가 `/profile.png`로 열리고([04_React시작](../01_React과정/04_React시작.md)), Spring의 `static/css/students.css`가 `/css/students.css`로 열리는 것([03_Thymeleaf-학생목록](../03_Spring과정/03_Thymeleaf-학생목록.md) 9장)과 같이, 여기 둔 `sitemap.xml`은 `/sitemap.xml`로 열린다.

### 5. 사이트맵 제출 = 주소를 알려주기
사이트맵 제출은 파일을 관리 도구에 **업로드하는 것이 아니라**, **사이트맵이 있는 주소를 검색엔진에 알려주는 과정**이다. 👉 [Google 사이트맵 제출 안내](https://support.google.com/webmasters/answer/7451001?hl=ko)

구글 서치 콘솔 제출 후 상태:

| 상태 | 확인할 내용 |
|---|---|
| 성공 | 사이트맵을 읽고 처리했는지 확인 |
| 가져올 수 없음 | 주소, 외부 접근, 서버 응답 확인 |
| 형식 관련 오류 | XML 구조와 오류 세부정보 확인 |

- **사이트맵 처리 성공 ≠ 사이트맵 안의 모든 페이지가 검색에 등록됨.**
- 구글과 네이버에는 **같은 사이트맵 주소**를 제출할 수 있다.

### 6. 구글 URL 검사 — 특정 페이지 상태 확인
사이트맵이 **여러 페이지의 목록**을 알려준다면, **URL 검사**는 **특정 페이지 하나의 상태**를 확인한다.

| 구분 | 확인하는 내용 |
|---|---|
| 기본 URL 검사 결과 | Google이 **저장하고 있는** 페이지의 색인 정보 |
| 실제 URL 테스트 | **현재 배포된** 페이지의 접근과 색인 가능 여부에 관한 검사 |

- 아직 등록되지 않았으면 세부정보를 펼쳐 **이유**를 본다.
- **실제 URL 테스트가 정상이어도 이미 색인되었다거나 반드시 색인된다는 뜻은 아니다.** 👉 [Google URL 검사 안내](https://support.google.com/webmasters/answer/9012289?hl=ko)
- 새 페이지를 만들었거나 중요한 내용을 고쳤다면 **색인 생성 요청**을 쓸 수 있다. 같은 주소를 반복 요청한다고 즉시 처리되지 않는다.

```text
페이지 배포
    ↓
URL 검사
    ↓
문제가 있다면 수정
    ↓
색인 생성 요청
```

### 7. 네이버 웹 페이지 수집 요청
네이버에서는 주요 페이지를 **요청 → 웹 페이지 수집**으로 요청한다.
- 네이버는 수집 요청을 즉시 처리하지 않으며, **같은 URL을 매일 반복해서 요청할 필요는 없다**고 안내한다. 👉 [네이버 수집 요청 안내](https://searchadvisor.naver.com/guide/request-crawl)
- **수집 요청 접수와 검색 노출 완료를 구분한다.**

### 8. 검색에 나오지 않으면 무엇을 확인할까?
등록 직후 검색에 안 나온다고 바로 오류로 판단하지 않는다. 먼저 확인한다.

| 확인 항목 | 점검 내용 |
|---|---|
| 사이트 접근 | 외부에서 로그인 없이 공개 페이지에 접속할 수 있는가? |
| 페이지 주소 | 실제로 존재하며 정상적인 내용을 제공하는가? |
| 서버 응답 | 정상 페이지가 HTTP `200`으로 응답하는가? |
| 수집 제한 | `robots.txt`가 공개 페이지의 수집을 막고 있지 않은가? |
| 색인 제외 | `noindex`가 잘못 설정되어 있지 않은가? |
| 본문 내용 | 서비스의 목적과 정보를 충분히 제공하는가? |
| 내부 링크 | 메인 페이지에서 중요한 페이지로 이동할 수 있는가? |
| 처리 상태 | 관리 도구에 표시된 사유와 검사 결과는 무엇인가? |

- HTTP **`200`** 은 요청한 페이지를 정상적으로 응답했다는 상태 코드다 ([03_서버-데이터보내기](../02_Node과정/03_서버-데이터보내기.md) 10장). 개발자 도구 **Network**에서 문서 요청을 선택해 확인한다.
- 수집·색인에는 시간이 걸리고, 검색엔진이 모든 페이지를 색인하지도 않는다. **관리 도구에 표시된 이유를 먼저 확인**하고 필요한 부분을 고친다.

**검색 결과에 없다면 무조건 코드를 바꿔야 할까?** 그렇지 않다.

| 상태 | 할 일 |
|---|---|
| 아직 발견·수집하지 못함 | 발견 경로와 처리 상태 확인 |
| 수집 오류 | 서버나 접근 설정 수정 |
| 중복 페이지로 판단 | 같은 내용을 제공하는 다른 주소가 있는지 확인 |
| 내용이 부족 | 실제 사용자에게 필요한 설명과 정보 보완 |

**상태를 먼저 확인하고 원인에 맞게 고치는 것이 중요하다.**

### 9. 등록 후에도 서비스를 관리해야 한다
SEO는 등록 버튼을 누르는 것으로 끝나지 않는다. 운영하면서 꾸준히 본다.
- 새로운 공개 페이지가 사이트맵에 반영되는가?
- 삭제한 페이지 주소가 사이트맵에 남아 있지는 않은가?
- 사이트와 주요 페이지가 정상적으로 열리는가?
- 검색엔진이 보고한 문제가 있는가?
- 사용자에게 필요한 정보가 충분한가?

사이트맵을 직접 작성했다면 **페이지가 바뀔 때 파일도 고쳐야** 한다. 페이지가 많아지면 사이트맵 **자동 생성**을 고려한다.
**검색으로 방문한 사람이 서비스의 용도를 이해하고 실제로 사용할 수 있도록 만드는 것까지가 운영의 일부다.**

### 정리

| 항목 | 역할 |
|---|---|
| 사이트 소유권 확인 | 사이트 관리 권한 확인 |
| 사이트맵 | 검색엔진에 알려줄 공개 페이지 주소 목록 |
| 사이트맵 제출 | 사이트맵이 있는 주소를 검색엔진에 전달 |
| 구글 URL 검사 | 특정 페이지의 색인 정보와 현재 접근 상태 확인 |
| 구글 색인 생성 요청 | 페이지를 다시 수집·처리하도록 요청 |
| 네이버 웹 페이지 수집 | 주요 페이지의 수집 요청 |
| 상태 확인과 개선 | 수집·색인 문제를 파악하고 서비스 보완 |

## 실습 정리

### 실습 1. 사이트맵 작성·배포하고 브라우저에서 확인하기
1. 핵심 개념 3의 XML로 `sitemap.xml`을 만든다. `<loc>`는 **실제 공개 페이지의 전체 주소**로 바꾼다.
2. 프로젝트에 맞는 위치(Vite `public/`, Spring Boot `src/main/resources/static/`)에 두고 다시 배포한다.
3. 배포 주소 뒤에 `/sitemap.xml`을 붙여 연다.

```text
https://my-service.example.com/sitemap.xml
```

- [ ] XML 내용이 표시되는가?
- [ ] `<loc>`에 실제 사이트 주소가 들어 있는가?
- [ ] 메인 페이지 화면이나 오류 화면이 대신 표시되지는 않는가?

- XML을 열면 **"스타일 정보가 없다"는 안내**가 나올 수 있다. XML 내용이 정상적으로 보이면 그 안내는 오류가 아니다.
- 주소가 열리는 것만 보지 말고 **실제 응답 내용이 사이트맵인지** 확인한다. React 배포 설정에 따라 잘못된 주소에서도 메인 화면이 나올 수 있다.

### 실습 2. 구글에 사이트맵 제출하기
👉 [구글 서치 콘솔](https://search.google.com/search-console)
1. 03회차에서 소유권을 확인한 사이트를 선택한다.
2. 왼쪽 메뉴에서 **Sitemaps**를 연다.
3. 사이트맵 주소를 입력한다. **입력란 앞에 사이트 주소가 이미 표시되어 있으면 나머지 경로만** 넣는다.

```text
sitemap.xml
```

전체 주소를 넣는 형태라면 전체 URL을 넣는다. **앞에 표시된 주소와 중복 입력하지 않는다.**

```text
https://my-service.example.com/sitemap.xml
```

4. 제출한 사이트맵 목록에서 처리 상태(성공 / 가져올 수 없음 / 형식 관련 오류)를 확인한다.

### 실습 3. 네이버에 사이트맵 제출하기
👉 [네이버 서치어드바이저](https://searchadvisor.naver.com/)
1. 웹마스터 도구에서 소유확인을 완료한 사이트를 선택한다.
2. **요청 → 사이트맵 제출** 메뉴로 간다.
3. 배포된 사이트맵의 **전체 주소**를 입력하고 제출한다.

```text
https://my-service.example.com/sitemap.xml
```

4. 제출 목록이나 처리 결과에서 등록한 주소를 확인한다. 👉 [네이버 사이트맵 제출 안내](https://help.naver.com/service/30010/contents/17629?lang=ko&osType=PC)

### 실습 4. 구글 URL 검사로 메인 페이지 확인하기
1. 서치 콘솔 상단의 **URL 검사** 입력란에 메인 페이지 주소를 넣는다.

```text
https://my-service.example.com/
```

2. 검사 결과에서 Google이 알고 있는 **색인 상태**를 본다. 아직 등록되지 않았으면 세부정보를 펼쳐 이유를 본다.
3. **실제 URL 테스트**를 실행해 현재 배포된 페이지에 접근할 수 있는지 등을 검사한다.
4. 새 페이지이거나 중요한 내용을 고쳤다면 **색인 생성 요청**을 한다.

### 실습 5. 네이버에서 웹 페이지 수집 요청하기
1. 웹마스터 도구에서 사이트를 선택한다.
2. **요청 → 웹 페이지 수집**으로 간다.
3. 수집을 요청할 페이지 주소를 입력한다. 입력란에 사이트 주소가 이미 표시되어 있으면 **경로만** 넣는다.

```text
/
```

별도 소개 페이지가 실제로 있다면:

```text
/about
```

4. 요청 결과를 확인한다.

## 헷갈리기 쉬운 점
- **요청 접수 ≠ 수집 ≠ 색인 ≠ 검색 노출.** 사이트맵 처리 "성공", 실제 URL 테스트 정상도 색인 보장이 아니다.
- **사이트맵 제출은 업로드가 아니다.** 사이트에 배포된 `sitemap.xml`의 **주소**를 알려주는 것이다. 그래서 먼저 배포해야 한다.
- **`<loc>`에는 전체 주소**(`https://…`)를 쓴다. `localhost`·없는 페이지·로그인/관리자 화면·`noindex` 페이지·`#위치`는 넣지 않는다.
- **이미 자동 생성된 사이트맵이 있으면 덮어쓰지 않는다.** 내용과 제공 방식부터 확인한다.
- **Vite는 `public/`, Spring Boot는 `static/`** 에 둔다 (`templates/` 아님). 주소는 둘 다 `/sitemap.xml`.
- **`/sitemap.xml`이 "열린다"만으로 끝내지 않는다.** React 배포 설정에 따라 메인 화면이 대신 나올 수 있으니 XML 내용인지 본다. "스타일 정보가 없다"는 안내는 오류가 아니다.
- **구글 Sitemaps 입력란 앞에 주소가 표시되어 있으면 `sitemap.xml`만** 입력한다 (중복 입력 주의). 네이버 사이트맵 제출은 전체 주소, 네이버 웹 페이지 수집은 표시된 주소 뒤 경로만.
- **기본 URL 검사 결과 = Google이 저장한 정보, 실제 URL 테스트 = 지금 배포된 페이지 검사.**
- **같은 주소를 반복 요청해도 빨라지지 않는다.** 네이버는 매일 반복 요청할 필요가 없다고 안내한다.
- **검색에 안 나온다고 무조건 코드를 고치지 않는다.** 관리 도구의 사유를 먼저 보고 원인(미발견·수집 오류·중복·내용 부족)에 맞게 고친다.
- **페이지가 바뀌면 사이트맵도 고친다.** 삭제한 주소가 남아 있지 않은지도 본다.

| 페이지 추가 | `<url>` 묶음 추가 | `<loc>https://my-service.example.com/about</loc>` |

| 구글 특정 페이지 상태 | **URL 검사** → 실제 URL 테스트 → 색인 생성 요청 | 메인 페이지 주소 |

## 확인 문제
강의에 별도 "💬 확인하기"는 없어서, 본문의 질문형 제목과 강조된 내용, 실습 확인 항목에서 뽑았다.

<details><summary>Q. (강의 질문) 사이트 등록(소유권 확인) 다음에는 무엇을 하나? 흐름을 말하라.</summary>

사이트맵 제출 → 주요 페이지 검사·수집 요청 → 수집·색인 상태 확인 → 문제 수정과 콘텐츠 개선. 요청 접수와 검색 노출은 다르다.
</details>

<details><summary>Q. (강의 질문) 사이트맵이란? 사이트맵을 제출하면 모든 페이지가 색인되나?</summary>

검색엔진에 알려주고 싶은 페이지 주소를 모아 둔 파일(보통 `sitemap.xml`). 링크로 발견하는 것에 더해 주소를 추가로 알려준다. 발견을 도울 뿐 **모든 주소의 수집·색인을 보장하지 않는다.**
</details>

<details><summary>Q. 사이트맵의 `urlset`, `url`, `loc`는 각각 무엇인가? 페이지를 하나 더 넣으려면?</summary>

`urlset`: 페이지 주소 목록을 감싸는 요소. `url`: 페이지 하나의 정보. `loc`: 그 페이지의 **전체 주소**. 페이지를 추가하려면 `<url><loc>…</loc></url>` 묶음을 하나 더 쓴다.
</details>

<details><summary>Q. 사이트맵에 넣으면 안 되는 주소는?</summary>

`localhost` 주소, 존재하지 않는 페이지, 로그인해야 보는 개인정보 페이지, 관리자 화면, `noindex`를 설정한 페이지, `#learning` 같은 같은 페이지 안의 위치. **실제로 존재하고 공개 검색에 포함하고 싶은 주소만** 넣는다.
</details>

<details><summary>Q. Vite React 프로젝트와 Spring Boot 프로젝트에서 `sitemap.xml`은 어디에 두나? 브라우저에서는 어떤 주소로 확인하나?</summary>

Vite: `public/sitemap.xml`. Spring Boot: `src/main/resources/static/sitemap.xml`. 일반 HTML 사이트: 메인 `index.html`과 같은 배포 폴더. 배포 후 `https://내주소/sitemap.xml`로 확인한다.
</details>

<details><summary>Q. `/sitemap.xml`을 열었더니 "스타일 정보가 없다"는 안내가 나왔다. 또는 메인 화면이 나왔다. 각각 어떻게 판단하나?</summary>

XML 내용이 정상적으로 보인다면 스타일 안내는 오류가 아니다. 메인 화면이나 오류 화면이 나오면 사이트맵이 제대로 배포·제공되지 않은 것이다 (React 배포 설정에 따라 잘못된 주소에서도 메인 화면이 나올 수 있음). `<loc>`에 실제 주소가 들어 있는지도 본다.
</details>

<details><summary>Q. 사이트맵 "제출"은 파일을 업로드하는 것인가?</summary>

아니다. **사이트맵이 있는 주소를 검색엔진에 알려주는 과정**이다. 그래서 사이트맵을 먼저 배포해 외부에서 열 수 있어야 한다. 구글·네이버에 같은 주소를 제출할 수 있다.
</details>

<details><summary>Q. 구글 서치 콘솔 Sitemaps 입력란 앞에 사이트 주소가 이미 표시되어 있다. 무엇을 입력하나? 네이버는?</summary>

구글: 나머지 경로인 `sitemap.xml`만 입력한다 (주소 중복 입력 금지). 전체 주소를 넣는 형태면 전체 URL. 네이버: 요청 → 사이트맵 제출에서 사이트맵의 전체 주소를 넣는다.
</details>

<details><summary>Q. 구글 사이트맵 상태가 "성공", "가져올 수 없음", "형식 관련 오류"일 때 각각 무엇을 확인하나? "성공"이면 모든 페이지가 검색에 등록된 것인가?</summary>

성공: 사이트맵을 읽고 처리했는지. 가져올 수 없음: 주소, 외부 접근, 서버 응답. 형식 관련 오류: XML 구조와 오류 세부정보. "성공"이어도 사이트맵 안의 **모든 페이지가 검색에 등록됐다는 뜻은 아니다.**
</details>

<details><summary>Q. 사이트맵과 URL 검사는 무엇이 다른가? 기본 URL 검사 결과와 실제 URL 테스트의 차이는?</summary>

사이트맵: 여러 페이지 목록을 알려준다. URL 검사: 특정 페이지 하나의 상태를 확인한다. 기본 결과: Google이 **저장하고 있는** 색인 정보. 실제 URL 테스트: **현재 배포된** 페이지의 접근·색인 가능 여부 검사. 테스트가 정상이어도 색인이 보장되지는 않는다.
</details>

<details><summary>Q. 색인 생성 요청(구글)·웹 페이지 수집 요청(네이버)은 언제 하나? 같은 주소를 매일 요청하면 빨라지나?</summary>

새 페이지를 만들었거나 중요한 내용을 고쳤을 때 쓴다 (구글은 URL 검사 → 문제 수정 → 색인 생성 요청 순서). 반복 요청해도 즉시 처리되지 않으며, 네이버는 같은 URL을 매일 요청할 필요가 없다고 안내한다. 요청 접수 ≠ 검색 노출.
</details>

<details><summary>Q. (강의 질문) 검색에 나오지 않으면 무엇을 확인할까? HTTP 200은 어디서 확인하나?</summary>

외부에서 로그인 없이 접속되는지, 페이지가 실제로 있고 정상 내용인지, HTTP `200`으로 응답하는지, `robots.txt`·`noindex`가 잘못 막고 있지 않은지, 본문이 충분한지, 메인에서 중요한 페이지로 링크가 있는지, 관리 도구에 표시된 사유는 무엇인지. `200`은 개발자 도구 **Network**에서 문서 요청을 선택해 확인한다.
</details>

<details><summary>Q. (강의 질문) 검색 결과에 없다면 무조건 코드를 바꿔야 할까?</summary>

아니다. 아직 발견·수집 전이면 발견 경로와 처리 상태를 확인, 수집 오류면 서버·접근 설정 수정, 중복으로 판단됐으면 같은 내용의 다른 주소 확인, 내용이 부족하면 사용자에게 필요한 정보 보완. **상태를 먼저 확인하고 원인에 맞게 고친다.**
</details>

<details><summary>Q. 사이트맵을 직접 작성했을 때, 운영하면서 무엇을 관리해야 하나?</summary>

새 공개 페이지를 사이트맵에 넣고, 삭제한 주소는 뺀다. 사이트·주요 페이지가 잘 열리는지, 검색엔진이 보고한 문제가 없는지, 사용자에게 필요한 정보가 충분한지 꾸준히 본다. 페이지가 많아지면 자동 생성을 고려한다.
</details>
