# 03. 블로킹과 논블로킹 직접 비교하기 — 파일 읽기와 느린 API 서버

> 과정: 비동기과정 · [노션 원문](https://app.notion.com/p/419848f71c9b80d0bb51cce616a77ed1) · 최종 갱신일: 2026-11-18

## 한눈에 보기
- 볼 것은 하나다: **작업이 끝나기를 기다리는 동안, 같은 실행 스레드가 다른 JavaScript 코드를 실행할 수 있는가?**
- **CPU 작업**(반복 계산)은 실행 스레드를 쓰며 일하고, **I/O 작업**(파일·네트워크·DB)은 바깥과 데이터를 주고받느라 **기다리는 시간**이 생긴다.
- `fs.readFileSync()`는 **동기·블로킹**(읽기가 끝나야 다음 줄), `fs.readFile(경로, "utf8", 콜백)`은 **비동기·논블로킹**(요청 후 다음 줄 진행, 결과는 콜백으로). `node:fs/promises` + `await`도 바깥 코드는 계속 진행된다.
- Express 서버(3001)에서 `/slow-blocking`(`while` 3초 점유) 중에는 **`/fast`도 기다리고**, `/slow-nonblocking`(`setTimeout` 3초) 중에는 **`/fast`가 먼저 응답**한다. 느린 응답 자체는 둘 다 약 3초다.
- **핸들러에 `async`만 붙여도 블로킹은 사라지지 않는다.** `async`는 Promise를 반환하게 할 뿐, 계산을 다른 스레드로 보내지 않는다.

## 학습 목표
- 동기식·비동기식 파일 읽기를 비교한다.
- CPU 작업과 I/O 작업을 구분한다.
- 블로킹 코드가 다른 요청을 지연시키는 것을 확인한다.
- `async`만으로 계산이 다른 스레드에서 실행되지 않는다는 점을 이해한다.

## 핵심 개념

### 1. 무엇이 멈추는지 확인하기
> 작업이 완료되는 동안, 같은 실행 스레드가 다른 JavaScript 코드를 실행할 수 있을까?

| 비교 대상 | 확인할 것 |
|---|---|
| 파일 읽기 | 읽기를 요청한 뒤 다음 코드를 진행하는가? |
| 서버 요청 | 느린 작업 중 다른 요청에도 응답할 수 있는가? |

**블로킹이라고 컴퓨터 전체가 멈추는 것은 아니다.** 이번에는 그 Node.js 프로세스의 **기본 JavaScript 실행 스레드**를 중심으로 관찰한다 ([01_실행순서-기다림](01_실행순서-기다림.md) 6장).

### 2. CPU 작업과 I/O 작업

| 구분 | 뜻 | 예시 |
|---|---|---|
| **CPU 작업** | 프로세서가 직접 계산하는 작업. 계산하는 동안 CPU와 실행 스레드를 사용 | 많은 숫자 계산, 큰 데이터의 복잡한 변환, 오래 실행되는 반복문 |
| **I/O 작업** | 프로그램 바깥과 데이터를 주고받는 작업 (Input/Output, 입력·출력) | 파일 읽기·쓰기, 네트워크 통신, 데이터베이스 통신 |

- I/O에서는 작업 완료를 **기다리는 시간**이 생길 수 있다. **이 기다림을 어떤 방식으로 처리하는지**가 중요하다.
- 실제 기능에는 두 종류의 작업이 함께 들어 있을 수 있다.

### 3. 동기식 파일 읽기 — `readFileSync()`
Node.js는 기본 모듈로 파일 읽기 기능을 제공한다 (**패키지 설치 불필요**). `students.txt`(한 줄에 한 명씩 `한코딩`, `이학생`, `박학생`)를 읽는다.

```javascript
const fs = require("node:fs");

console.log("1. 파일 읽기 전");

const content = fs.readFileSync(
  "./students.txt",
  "utf8"
);

console.log("2. 파일 내용");
console.log(content);

console.log("3. 파일 읽기 후");
```

| 코드 | 역할 |
|---|---|
| `node:fs` | 파일 시스템 관련 기본 모듈 |
| `readFileSync()` | 파일을 **동기식**으로 읽기 |
| `./students.txt` | **현재 작업 폴더** 기준 파일 경로 |
| `"utf8"` | 파일 내용을 문자열로 읽을 인코딩 |

```text
1. 파일 읽기 전
2. 파일 내용
한코딩
이학생
박학생
3. 파일 읽기 후
```

- `readFileSync()`가 읽기를 끝내고 **결과를 반환해야** 다음 줄로 진행한다.
- **읽기 호출이 끝날 때까지 그 스레드는 다른 JavaScript 작업을 실행하지 못한다.**
- 파일이 작으면 매우 빨리 끝나 멈춘 느낌이 없을 수 있다. 이번에는 속도보다 **실행 순서**에 집중한다.

### 4. 비동기식 파일 읽기 — `readFile()`

```javascript
const fs = require("node:fs");

console.log("1. 파일 읽기 전");

fs.readFile("./students.txt", "utf8", (error, content) => {
  if (error) {
    console.log("파일 읽기 실패:", error.message);
    return;
  }

  console.log("2. 파일 내용");
  console.log(content);
});

console.log("3. 파일 읽기 요청 후");
```

```text
1. 파일 읽기 전
3. 파일 읽기 요청 후
2. 파일 내용
한코딩
이학생
박학생
```

- 파일 읽기가 끝나기 전에 아래의 `console.log("3. 파일 읽기 요청 후");`를 **먼저 실행**할 수 있다.
- 파일 읽기 결과는 **나중에 콜백으로** 전달된다.

**콜백의 매개변수** — Node.js의 여러 콜백 API는 **첫 번째 인자로 오류**를 전달한다.

| 매개변수 | 의미 |
|---|---|
| `error` | 실패한 경우의 오류 정보 |
| `content` | 성공한 경우의 파일 내용 |

**두 방식 비교**

| 구분 | `readFileSync()` | `readFile()` |
|---|---|---|
| 파일 결과 받기 | 호출의 **반환값** | 나중에 **콜백**으로 받음 |
| 다음 코드 | 읽기가 끝난 뒤 진행 | 읽기 요청 후 진행 가능 |
| 이번 호출의 특징 | **동기·블로킹** | **비동기·논블로킹** |

**논블로킹이라고 파일 읽기 자체가 더 빨라지는 것은 아니다.** 차이는 **기다리는 동안 같은 JavaScript 실행 스레드를 붙잡아 두지 않는다**는 것이다.

### 5. Promise 방식으로 파일 읽기 — `node:fs/promises`
앞에서 배운 `async/await`로도 파일을 읽을 수 있다 ([02_Promise-async-await](02_Promise-async-await.md)).

```javascript
const fs = require("node:fs/promises");

async function main() {
  console.log("1. 파일 읽기 시작");

  try {
    const content = await fs.readFile(
      "./students.txt",
      "utf8"
    );

    console.log("3. 파일 내용");
    console.log(content);
  } catch (error) {
    console.log("파일 읽기 실패:", error.message);
  }
}

main();

console.log("2. main 함수 밖의 작업");
```

```text
1. 파일 읽기 시작
2. main 함수 밖의 작업
3. 파일 내용
한코딩
이학생
박학생
```

- `await`는 **`main` 함수 안의 다음 코드**를 기다리게 한다. 파일 읽기를 기다리는 동안 **바깥 코드는 실행된다.**
- **`await`로 기다리는 것과 `readFileSync()`로 스레드를 블로킹하는 것은 다르다.**

> 💡 보충: `require("node:fs/promises")`의 `fs.readFile()`은 콜백 대신 **Promise를 반환**하는 버전이다. 그래서 `await`로 결과를 받고, 실패는 `try/catch`로 처리한다. 이름은 같아도 4장의 `require("node:fs")` 버전과 쓰는 법이 다르다.

### 6. 서버에서는 어떤 차이가 생길까?
서버는 여러 요청을 받는다. **한 요청의 처리 코드가 JavaScript 실행 스레드를 오래 점유하면 다른 요청의 처리도 늦어질 수 있다.** 비교용 서버에 세 API를 만든다.

| 경로 | 역할 |
|---|---|
| `/fast` | 즉시 짧은 응답 |
| `/slow-blocking` | **반복문**으로 약 3초 동안 실행 스레드 점유 |
| `/slow-nonblocking` | **타이머**를 예약하고 약 3초 뒤 응답 |

타이머는 실제 파일·DB 작업 대신 **기다림이 있는 상황을 단순하게 재현하는 도구**로 쓴다. (서버 코드 전체는 아래 실습 정리)

### 7. 블로킹 요청 중 다른 요청 보내기
첫 번째 탭에서 `/slow-blocking`을 요청하고, 응답이 오기 전에 두 번째 탭에서 `/fast`를 요청한다.

```text
블로킹 작업 시작
    ↓ 약 3초
블로킹 작업 종료
    ↓
빠른 요청 처리
```

- `/slow-blocking`의 반복문이 실행 중이면 **`/fast`의 요청 처리 코드도 실행되지 못한다.**
- **빠른 요청도 느린 계산의 영향을 받았다.** (실제 로그는 요청이 도착한 타이밍에 따라 조금 다를 수 있다.)

### 8. 논블로킹 대기 중 다른 요청 보내기
첫 번째 탭을 `/slow-nonblocking`으로 바꿔 같은 실험을 한다.

```text
논블로킹 대기 시작
    ↓
빠른 요청 처리
    ↓
논블로킹 대기 종료
```

- 타이머를 기다리는 동안 **`/fast`가 먼저 응답**할 수 있다.
- 느린 요청의 응답까지는 **여전히 약 3초**가 걸린다. 차이는 **그 기다림 동안 다른 요청을 처리할 수 있다는 것**이다.

| 구분 | 블로킹 예제 | 논블로킹 예제 |
|---|---|---|
| 느린 응답까지 걸리는 시간 | 약 3초 | 약 3초 |
| 기다리는 방법 | 반복문으로 스레드 점유 | 타이머 예약 후 제어 반환 |
| 그동안 `/fast` 처리 | 반복 종료 후 가능 | 대기 중에도 가능 |

### 9. `async`를 붙이면 해결될까?
`/slow-blocking` 핸들러에 `async`를 붙인다.

```javascript
app.get("/slow-blocking", async (req, res) => {
  console.log("블로킹 작업 시작");

  const endTime = Date.now() + 3000;

  while (Date.now() < endTime) {
    // 여전히 현재 실행 스레드에서 실행됩니다.
  }

  console.log("블로킹 작업 종료");

  res.send("블로킹 작업이 끝났습니다.");
});
```

서버를 재시작하고 두 탭 실험을 반복하면 **여전히 `/fast` 요청 처리가 지연된다.**

- `async`는 함수가 **Promise를 반환**하게 한다. 함수 내부의 계산을 **자동으로 다른 스레드에 보내지는 않는다** ([02_Promise-async-await](02_Promise-async-await.md) 6장).

```text
async 함수
≠ 모든 코드가 논블로킹
≠ 자동으로 별도 스레드 실행
```

- CPU 작업을 별도 스레드나 프로세스로 분리하는 방법도 있지만, 이번에는 **문제의 원인과 `async`의 한계**를 이해하는 데 집중한다.

### 10. 콜백이 실행된 뒤에도 주의해야 한다
비동기 작업을 썼다고 그 이후의 코드까지 자동으로 가벼워지지는 않는다.

```javascript
fs.readFile("./students.txt", "utf8", (error, content) => {
  if (error) {
    console.log(error.message);
    return;
  }

  // 여기에서 아주 오래 걸리는 계산을 하면
  // 그 계산 동안 다른 JavaScript 작업이 지연될 수 있습니다.

  console.log(content);
});
```

파일 읽기를 **기다리는 동안**에는 다른 작업이 가능하지만, **콜백에서 긴 계산**을 하면 그 계산은 JavaScript 실행 스레드를 점유한다. **기다리는 단계와 결과를 계산하는 단계를 나누어 생각한다.**

### 정리

| 개념 | 핵심 |
|---|---|
| CPU 작업 | 계산을 위해 실행 자원 사용 |
| I/O 작업 | 파일·네트워크 등과 데이터 입출력 |
| `readFileSync()` | 파일 읽기가 끝날 때까지 호출 스레드가 기다림 |
| 비동기 `readFile()` | 파일 읽기 결과를 나중에 받고 다른 코드 진행 가능 |
| 블로킹 영향 | 같은 실행 스레드의 다른 작업도 지연 |
| `async` | 무거운 계산을 자동으로 다른 스레드에 보내지 않음 |

## 실습 정리

### 실습 1. 파일 읽기 비교 (`async-basic` 폴더)
[01_실행순서-기다림](01_실행순서-기다림.md)에서 만든 `async-basic` 폴더에 파일을 추가한다.

```text
async-basic
├─ students.txt
├─ read-sync.js
└─ read-async.js
```

`students.txt`:

```text
한코딩
이학생
박학생
```

| 파일 | 코드 | 실행 | 출력 순서 |
|---|---|---|---|
| `read-sync.js` | 3장 `readFileSync()` | `node read-sync.js` | `1 → 2(내용) → 3` |
| `read-async.js` | 4장 `readFile()` + 콜백 | `node read-async.js` | `1 → 3 → 2(내용)` |
| `read-promise.js` (새 파일) | 5장 `node:fs/promises` + `await` | `node read-promise.js` | `1 → 2 → 3(내용)` |

**터미널이 `async-basic` 폴더에 있는지** 확인하고 실행한다 (`./students.txt`는 현재 작업 폴더 기준).

**직접 바꿔보기** — 파일 이름을 잠시 없는 이름으로 바꿔 오류 처리를 확인하고, 확인이 끝나면 되돌린다.

```javascript
fs.readFile("./missing.txt", "utf8", (error, content) => {
  if (error) {
    console.log("파일 읽기 실패:", error.message);
    return;
  }

  console.log(content);
});
```

> 💡 보충: 실행해 보면 `파일 읽기 실패: ENOENT: no such file or directory, open './missing.txt'`가 출력된다. `ENOENT`는 "그런 파일이나 폴더가 없다"는 Node.js의 오류 코드다.

### 실습 2. 비교용 서버 만들기 (`blocking-server` 폴더)
기존 서버와 구분하려고 **새 폴더** `blocking-server`를 만들고 연다 (Express 준비는 [03_서버-데이터보내기](../02_Node과정/03_서버-데이터보내기.md) 실습 1과 같다).

```bash
npm init -y
```

```bash
npm install express
```

**`server.js`**

```javascript
const express = require("express");

const app = express();
const PORT = 3001;

app.get("/fast", (req, res) => {
  console.log("빠른 요청 처리");

  res.send("빠른 응답입니다.");
});

app.get("/slow-blocking", (req, res) => {
  console.log("블로킹 작업 시작");

  const endTime = Date.now() + 3000;

  while (Date.now() < endTime) {
    // 실행 스레드를 점유하는 학습용 반복입니다.
  }

  console.log("블로킹 작업 종료");

  res.send("블로킹 작업이 끝났습니다.");
});

app.get("/slow-nonblocking", (req, res) => {
  console.log("논블로킹 대기 시작");

  setTimeout(() => {
    console.log("논블로킹 대기 종료");

    res.send("기다림이 끝났습니다.");
  }, 3000);
});

app.listen(PORT, () => {
  console.log(`서버 실행 중: http://localhost:${PORT}`);
});
```

```bash
node server.js
```

이번에는 **3001번 포트**를 쓴다.

### 실습 3. 브라우저 탭 두 개로 비교하기

| 실험 | 첫 번째 탭 | 두 번째 탭 | 관찰 결과 (서버 로그) |
|---|---|---|---|
| 블로킹 | `http://localhost:3001/slow-blocking` | `http://localhost:3001/fast` | 블로킹 작업 시작 → (약 3초) 블로킹 작업 종료 → 빠른 요청 처리 |
| 논블로킹 | `http://localhost:3001/slow-nonblocking` | `http://localhost:3001/fast` | 논블로킹 대기 시작 → 빠른 요청 처리 → 논블로킹 대기 종료 |
| `async` 붙인 블로킹 | 9장 코드로 바꾸고 서버 재시작 → `/slow-blocking` | `/fast` | 여전히 `/fast`가 지연됨 |

진행 순서: ① 첫 번째 탭에서 느린 요청 시작 → ② **응답이 오기 전에** 두 번째 탭에서 `/fast` 요청 → ③ 화면과 서버 로그 확인.

- 브라우저 캐시의 영향을 줄이려면 개발자 도구 **Network** 탭에서 **캐시 사용 중지**를 켜고 확인한다.
- 빠른 요청을 너무 늦게 보내면 블로킹 작업이 이미 끝났을 수 있다. 필요하면 **실습 중에만** 대기 시간을 5초로 늘려 비교한다.
- 코드를 고친 뒤에는 서버를 **종료(`Ctrl + C`)하고 다시 실행**한다.

### 실험이 예상과 다를 때 확인하기

| 증상 | 확인할 내용 |
|---|---|
| 파일을 찾지 못함 | 터미널의 현재 폴더와 파일 위치 |
| 서버가 실행되지 않음 | Express 설치 여부, 현재 폴더 |
| 포트 사용 중 오류 | 기존 3001번 서버가 실행 중인지 (💡 Express 5 + 강의 코드에서는 오류 문장 없이 "서버 실행 중"만 찍히고 바로 종료된다 — 2026-11-24 확인) |
| `/fast`가 지연되지 않음 | 느린 작업이 실행 중일 때 요청했는지 |
| 코드 수정 결과가 안 보임 | 서버를 종료하고 다시 실행했는지 |
| 두 방식이 모두 느리게 보임 | 각각 어떤 경로를 요청했는지, 다른 무거운 작업이 있는지 |

## 헷갈리기 쉬운 점
- **블로킹 = 컴퓨터 전체 멈춤이 아니다.** 그 Node.js 프로세스의 JavaScript 실행 스레드가 다른 코드를 못 하는 것이다.
- **`readFileSync()`는 반환값으로, `readFile()`은 콜백으로** 결과를 받는다. `readFile()`의 결과를 다음 줄에서 바로 쓸 수 없다.
- **콜백의 첫 번째 매개변수는 `error`**다 (`(error, content)`). 순서를 바꾸지 않는다.
- **논블로킹이 더 빠른 것은 아니다.** 느린 응답은 둘 다 약 3초. 그동안 다른 일을 할 수 있느냐가 다르다.
- **`await`로 기다리기 ≠ `readFileSync()` 블로킹.** `await`는 그 함수 안만 기다리고 바깥 코드는 진행된다.
- **`async`를 붙여도 `while` 계산은 블로킹이다.** `async`는 Promise 반환일 뿐, 별도 스레드 실행이 아니다.
- **비동기 콜백 안의 긴 계산도 스레드를 점유한다.** 기다리는 단계와 계산하는 단계를 나눠 생각한다.
- **`while`로 3초 점유하는 코드는 학습용**이다. 실제 지연이 필요하면 타이머처럼 스레드를 붙잡지 않는 방식을 쓴다.
- **상대 경로 `./students.txt`는 터미널의 현재 폴더 기준**이다. 다른 폴더에서 실행하면 파일을 못 찾는다.
- **실험 타이밍**: 느린 요청이 끝난 뒤 `/fast`를 보내면 차이가 안 보인다.

| 하고 싶은 것 | 쓰는 것 | 예시 |
|---|---|---|

## 확인 문제
강의에 별도 "💬 확인하기"는 없어서, 본문의 질문형 제목과 "직접 바꿔보기"에서 뽑았다.

<details><summary>Q. 블로킹·논블로킹을 판단할 때 확인할 질문 하나는?</summary>

작업이 완료되는 동안, **같은 실행 스레드가 다른 JavaScript 코드를 실행할 수 있는가?** 컴퓨터 전체가 아니라 그 Node.js 프로세스의 JavaScript 실행 스레드를 본다.
</details>

<details><summary>Q. 다음을 CPU 작업과 I/O 작업으로 나누면? — 반복문 계산, 파일 읽기, 서버 통신, 큰 데이터 변환, DB 통신</summary>

CPU: 반복문 계산, 큰 데이터 변환. I/O: 파일 읽기, 서버 통신, DB 통신. I/O는 바깥과 데이터를 주고받느라 기다리는 시간이 생기고, 그 기다림을 어떻게 처리하는지가 중요하다.
</details>

<details><summary>Q. `read-sync.js`와 `read-async.js`의 출력 순서는 각각? 왜 다른가?</summary>

`read-sync.js`: `1. 파일 읽기 전` → `2. 파일 내용`(+내용) → `3. 파일 읽기 후`. `read-async.js`: `1. 파일 읽기 전` → `3. 파일 읽기 요청 후` → `2. 파일 내용`(+내용). `readFileSync()`는 읽기가 끝나야 다음 줄로 가고(동기·블로킹), `readFile()`은 요청 후 다음 줄을 진행하고 결과는 나중에 콜백으로 받는다(비동기·논블로킹).
</details>

<details><summary>Q. `fs.readFile()` 콜백 `(error, content)`의 두 매개변수는 각각 무엇인가?</summary>

`error`: 실패한 경우의 오류 정보. `content`: 성공한 경우의 파일 내용. Node.js의 여러 콜백 API는 첫 번째 인자로 오류를 전달한다.
</details>

<details><summary>Q. (직접 바꿔보기) 경로를 `./missing.txt`로 바꾸면 무엇이 출력되나?</summary>

`if (error)` 분기로 들어가 `파일 읽기 실패: ENOENT: no such file or directory, open './missing.txt'`가 출력되고 `return`으로 끝난다.
</details>

<details><summary>Q. 논블로킹 방식이면 파일 읽기 자체가 더 빨라지나?</summary>

아니다. 기다리는 동안 같은 JavaScript 실행 스레드를 붙잡아 두지 않는다는 차이다.
</details>

<details><summary>Q. `read-promise.js`의 출력 순서는? `await`로 기다리는 것과 `readFileSync()`의 차이는?</summary>

`1. 파일 읽기 시작` → `2. main 함수 밖의 작업` → `3. 파일 내용`(+내용). `await`는 `main` 안의 다음 코드만 기다리게 하고 바깥 코드는 실행되지만, `readFileSync()`는 읽기가 끝날 때까지 스레드를 블로킹한다.
</details>

<details><summary>Q. (강의 질문) 서버에서는 어떤 차이가 생길까? `/slow-blocking` 요청 중에 `/fast`를 요청하면?</summary>

`/slow-blocking`의 반복문이 실행 스레드를 점유하는 동안 `/fast`의 처리 코드도 실행되지 못한다. 로그: 블로킹 작업 시작 → (약 3초) 블로킹 작업 종료 → 빠른 요청 처리. 빠른 요청도 느린 계산의 영향을 받는다.
</details>

<details><summary>Q. `/slow-nonblocking` 요청 중에 `/fast`를 요청하면? 느린 응답 시간은 줄어드나?</summary>

`/fast`가 먼저 응답한다 (논블로킹 대기 시작 → 빠른 요청 처리 → 논블로킹 대기 종료). 느린 응답은 여전히 약 3초다. 차이는 그 기다림 동안 다른 요청을 처리할 수 있다는 것.
</details>

<details><summary>Q. (강의 질문) `async`를 붙이면 해결될까? `/slow-blocking` 핸들러를 `async (req, res) => {…}`로 바꾸면?</summary>

해결되지 않는다. 여전히 `/fast`가 지연된다. `async`는 함수가 Promise를 반환하게 할 뿐, 내부 계산을 자동으로 다른 스레드에 보내지 않는다. `async 함수 ≠ 모든 코드가 논블로킹 ≠ 자동으로 별도 스레드 실행`.
</details>

<details><summary>Q. `fs.readFile()`로 비동기로 읽었으니, 콜백 안에서 아주 긴 계산을 해도 다른 작업에 영향이 없나?</summary>

영향이 있다. 파일 읽기를 기다리는 동안에는 다른 작업이 가능하지만, 콜백에서 긴 계산을 하면 그 계산이 JavaScript 실행 스레드를 점유해 다른 작업이 지연된다. 기다리는 단계와 계산하는 단계를 나눠 생각한다.
</details>

<details><summary>Q. 블로킹 실험을 했는데 `/fast`가 지연되지 않았다. 무엇을 확인하나?</summary>

느린 작업이 실행 중일 때(응답이 오기 전에) `/fast`를 요청했는지 확인한다. 너무 늦게 보내면 블로킹 작업이 이미 끝났을 수 있다. 필요하면 실습 중에만 대기 시간을 5초로 늘린다. 코드를 바꿨다면 서버를 재시작했는지도 본다.
</details>
