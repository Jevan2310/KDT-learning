# 01. 실행 순서와 기다림 이해하기 — 동기·비동기, 블로킹·논블로킹, `setTimeout()`

> 과정: 비동기과정 · [노션 원문](https://app.notion.com/p/419848f71c9b80d98c48cffd2f2151f6) · 최종 갱신일: 2026-11-18

## 한눈에 보기
- **동기**: 호출한 작업이 끝나고 결과를 받은 뒤 다음 코드로 진행한다. **비동기**: 완료됐을 때 실행할 코드를 연결해 두고 **결과 처리를 나중에** 이어 간다.
- **블로킹·논블로킹은 다른 관점**이다. "호출한 작업이 **실행 스레드를 붙잡아 두는가**?"를 묻는다. 동기·비동기와 같은 뜻으로 외우지 않는다.
- `setTimeout(함수, 밀리초)`는 코드를 멈추는 명령이 아니라 **나중에 실행할 함수(콜백)를 예약**한다. 그래서 `"1. 시작" → "3. 끝" → (나중에) "2. 타이머 실행"` 순서가 된다. **0초 타이머도 즉시 실행되지 않는다.**
- `while`로 실행 스레드를 2초 동안 점유하면, 0초로 예약한 타이머 콜백도 반복이 끝난 뒤에야 실행된다. 이 흐름을 조율하는 구조가 **이벤트 루프**다.
- `await`는 **그 함수 안의 다음 줄만** 기다리게 한다. "`await`가 있다 → 무조건 스레드를 블로킹한다"가 아니다.

## 학습 목표
- 동기·비동기를 구분한다.
- 블로킹·논블로킹을 구분한다.
- `setTimeout()`으로 나중에 실행할 함수를 예약한다.
- 출력 순서를 예상하고 실제 결과를 확인한다.
- 이벤트 루프의 기본 역할을 알아본다.

## 핵심 개념

### 1. 시간이 걸리는 작업들
프로그램에는 바로 끝나는 작업도, 결과가 준비될 때까지 시간이 걸리는 작업도 있다.

| 작업 | 시간이 필요한 이유 |
|---|---|
| 서버에 학생 목록 요청 | 네트워크 통신과 서버 처리 |
| 파일 읽기 | 저장 장치에서 데이터 읽기 |
| 이미지 내려받기 | 네트워크에서 파일 전송 |
| 복잡한 계산 | CPU에서 많은 연산 수행 |

중요한 것은 작업이 빠른지 느린지가 아니라, **작업이 끝나기를 기다리는 동안 다른 코드는 어떻게 실행되는지**다.

### 2. 동기 실행 — 현재 작업이 끝나면 다음으로

```javascript
console.log("1. 시작");

const first = 10;
const second = 20;
const result = first + second;

console.log("2. 계산 결과:", result);
console.log("3. 끝");
```

```text
1. 시작
2. 계산 결과: 30
3. 끝
```

앞의 계산이 끝난 뒤 다음 코드를 실행한다. **호출한 작업이 완료되고 결과를 받은 뒤 이어서 진행하는 방식**을 **동기** 방식이라고 한다.

함수도 마찬가지다. `calculate()`가 실행되고 값을 **반환해야** 다음 줄로 넘어간다.

```javascript
function calculate() {
  console.log("2. 함수 실행");

  return 10 + 20;
}

console.log("1. 시작");

const result = calculate();

console.log("3. 계산 결과:", result);
console.log("4. 끝");
```

```text
1. 시작
2. 함수 실행
3. 계산 결과: 30
4. 끝
```

### 3. 비동기 실행 — `setTimeout()`으로 나중에 처리하기
어떤 작업은 시작한 자리에서 최종 결과를 바로 받지 않고, **완료되었을 때 실행할 코드를 연결해 나중에 처리**한다. 타이머로 이 흐름을 확인한다.

```javascript
setTimeout(실행할함수, 지연시간);
```

| 인자 | 의미 |
|---|---|
| 첫 번째 | 나중에 실행할 함수 |
| 두 번째 | 지연 시간, **밀리초** 단위 (1,000밀리초 = 1초) |

**`setTimeout()`은 현재 코드를 멈춰 두는 명령이 아니다. 일정 시간이 지난 뒤 실행할 함수를 예약한다.**

```javascript
console.log("1. 시작");

setTimeout(() => {
  console.log("2. 타이머 실행");
}, 3000);

console.log("3. 끝");
```

같은 코드를 이름 있는 함수로 쓴 수업 화면 버전:

```javascript
console.log("1. 시작");


function timer() {
    console.log("2. 타이머 실행");
}

setTimeout(timer, 3000);

console.log("3. 끝");
```

실행 결과 (두 코드 모두 같다):

```text
1. 시작
3. 끝
```

약 3초 뒤 추가 출력:

```text
2. 타이머 실행
```

**코드에 적은 숫자(1, 2, 3)가 실제 출력 순서를 정하는 것은 아니다.**

```text
"1. 시작" 출력
    ↓
타이머에 함수 예약
    ↓
"3. 끝" 출력
    ↓
시간이 지나고 실행 가능한 시점에 타이머 함수 실행
```

타이머의 콜백을 기다리는 동안 나머지 코드는 계속 진행했다. 이렇게 **완료 이후의 처리를 나중에 이어 가는 흐름**이 비동기 처리의 예다.

### 4. 콜백 함수
**다른 코드에 전달해 두고, 그 코드가 호출하도록 하는 함수**를 **콜백 함수**라고 한다. 이 예제에서는 타이머가 호출할 함수를 전달한다.

```javascript
setTimeout(() => {
  console.log("타이머 실행");
}, 2000);
```

화살표 함수가 어렵다면 일반 함수로 나눠 쓸 수 있다 ([03_JavaScript](../01_React과정/03_JavaScript.md) 13장 화살표 함수). 이 예제에서는 같은 역할이다.

```javascript
function showMessage() {
  console.log("타이머 실행");
}

setTimeout(showMessage, 2000);
```

**함수를 전달하는 것과 호출하는 것은 다르다.**

| 코드 | 의미 |
|---|---|
| `setTimeout(showMessage, 2000);` | `showMessage` 함수를 **전달** → 타이머가 나중에 호출 |
| `showMessage();` | 함수를 **지금 즉시 호출** |

React에서도 같은 구분을 썼다 ([07_이벤트-state](../01_React과정/07_이벤트-state.md) 1장).

```jsx
<button onClick={handleClick}>클릭</button>
```

**콜백이라고 모두 비동기는 아니다.** `map()`도 함수를 전달받지만 ([06_목록-조건부렌더링](../01_React과정/06_목록-조건부렌더링.md) 2장), 각 항목의 처리를 **그 자리에서 마치고** 새 배열을 반환한다.

```javascript
const numbers = [1, 2, 3];

const doubled = numbers.map((number) => number * 2);

console.log(doubled);
```

```text
[ 2, 4, 6 ]
```

**함수를 전달했다는 사실만으로 비동기라고 판단하지 않는다. 그 함수를 언제 실행하는지 확인해야 한다.**

### 5. 0초 타이머는 즉시 실행될까?

```javascript
console.log("A");

setTimeout(() => {
  console.log("B");
}, 0);

console.log("C");
```

```text
A
C
B
```

- `0`은 **현재 실행 중인 코드를 중단하고 지금 즉시 호출하라는 뜻이 아니다.**
- Node.js의 타이머는 최소 지연 처리 등의 영향을 받고, 실행 시점에는 현재 실행 중인 작업도 영향을 준다.
- 기억할 것: **타이머의 시간이 짧아도 현재 실행 중인 JavaScript를 중간에 끊고 콜백을 실행하지는 않는다.**

### 6. 블로킹과 논블로킹은 다른 관점이다

| 구분 | 살펴보는 질문 |
|---|---|
| 동기·비동기 | 작업의 **완료와 결과 처리가 어떻게 이어지는가?** |
| 블로킹·논블로킹 | 호출한 작업이 **실행 스레드를 기다리게 붙잡는가?** |

**스레드는 코드를 실행하는 일꾼**이라고 생각한다.

- **블로킹**: 호출한 작업이 끝나기를 기다리느라 그 실행 스레드가 **다음 작업을 진행하지 못하는** 상황. 예) Node.js의 동기식 파일 읽기는 읽기가 끝날 때까지 같은 스레드에서 다른 JavaScript 코드를 진행할 수 없다 ([03_블로킹-논블로킹](03_블로킹-논블로킹.md)에서 직접 확인).
- **논블로킹**: 작업 완료를 기다리는 동안 호출한 실행 흐름을 **붙잡아 두지 않는** 방식. 예) 타이머를 예약한 뒤 바로 다음 출력문을 실행할 수 있었다.

```javascript
setTimeout(() => {
  console.log("나중에 실행");
}, 2000);

console.log("지금 진행할 수 있는 작업");
```

**'다른 작업'의 범위를 주의한다.** 블로킹이라고 컴퓨터 전체나 모든 프로그램이 멈추는 것은 아니다. **어떤 스레드나 실행 흐름이 막히는지**를 구분한다. 이 과정에서는 **Node.js의 JavaScript 실행 스레드가 다른 코드를 실행할 수 있는지**를 중심으로 본다.

### 7. 오래 걸리는 계산이 있다면?
타이머는 시간이 지나도 **현재 실행 중인 JavaScript를 중단시키지 못한다.** 일부러 실행 스레드를 오래 점유하는 코드로 확인한다 (`busy.js`).

```javascript
console.log("1. 시작");

setTimeout(() => {
  console.log("2. 타이머 콜백 실행");
}, 0);

const endTime = Date.now() + 2000;

while (Date.now() < endTime) {
  // 실행 순서를 관찰하기 위한 반복입니다.
}

console.log("3. 반복 종료");
```

| 코드 | 의미 |
|---|---|
| `Date.now()` | 현재 시각을 **밀리초 단위 숫자**로 반환 |
| `const endTime = Date.now() + 2000;` | 지금부터 약 2초 뒤의 시각 계산 |
| `while (Date.now() < endTime) { }` | 그 시각이 될 때까지 반복해서 조건 검사 ([03_JavaScript](../01_React과정/03_JavaScript.md) 7장 반복문) |

실행 결과:

```text
1. 시작
```

약 2초 뒤:

```text
3. 반복 종료
2. 타이머 콜백 실행
```

- 타이머는 0으로 예약했지만, **반복문이 끝날 때까지 콜백을 실행하지 못했다.**
- 이 반복문은 쉬면서 기다리는 코드가 아니라 **CPU를 사용하며 실행 스레드를 계속 점유하는 코드**다. 그래서 이벤트 루프가 다른 JavaScript 콜백을 처리하지 못한다.
- **시간을 지연시키는 기능을 만들 때 이 반복문을 쓰지 않는다.** 실행 흐름을 관찰하기 위한 예제다.

| 코드 | 관찰한 동작 |
|---|---|
| `setTimeout()`으로 함수 예약 | 예약 후 다음 코드 진행 |
| 오래 실행하는 `while` | 반복이 끝날 때까지 같은 스레드의 다른 JS 작업 진행 불가 |

### 8. 이벤트 루프의 기본 역할
Node.js는 기본적으로 **하나의 JavaScript 실행 스레드**에서 현재 코드를 실행하고, 그 뒤 준비된 콜백 등을 처리한다. 이 흐름을 조율하는 구조가 **이벤트 루프**다.

```text
현재 JavaScript 코드 실행
        ↓
타이머 등록
        ↓
현재 코드 계속 실행
        ↓
현재 실행이 끝남
        ↓
타이머가 실행 가능한 상태인지 확인
        ↓
콜백 실행
```

실제로는 작업 종류별 처리 단계가 더 있지만, 지금은 두 가지만 기억한다.
- **타이머를 예약했다고 현재 코드가 멈추지는 않는다.**
- **현재 실행 스레드를 오래 점유하면 준비된 콜백도 늦어진다.**

타이머의 지연 시간은 **정확한 실행 시각을 보장하는 값이 아니다.**

### 9. 이미 사용한 `await`와 연결하기
앞서 API를 호출할 때 쓴 코드 ([04_React-서버연결](../02_Node과정/04_React-서버연결.md) 5장):

```javascript
async function loadStudents() {
  const response = await fetch(
    "http://localhost:8080/api/students"
  );

  const students = await response.json();

  console.log(students);
}
```

> 💡 보충: 이 주소(`8080/api/students`)는 Spring Boot 서버의 학생 API 주소다 ([Spring 06_JSON-API-React연결](../03_Spring과정/06_JSON-API-React연결.md)). Node과정에서는 같은 흐름을 `http://localhost:3000/students`로 썼다. 주소만 다르고 `await` 흐름은 같다.

- 이 함수는 응답이 준비될 때까지 **다음 줄의 실행을 잠시 중단**한다.
- 하지만 그동안 **브라우저 전체나 JavaScript 실행 스레드를 붙잡아 두는 것은 아니다.**

```javascript
loadStudents();

console.log("요청 결과를 기다리는 동안 실행");
```

`loadStudents()` 안의 후속 코드는 기다리지만, **바깥 코드는 계속 진행**할 수 있다. 따라서 다음처럼 판단하지 않는다.

```text
await가 있다 → 무조건 스레드를 블로킹한다
```

대신 두 질문을 나눠 생각한다.

```text
어느 함수의 진행이 기다리는가?
그동안 실행 스레드는 다른 일을 할 수 있는가?
```

### 정리

| 개념 | 핵심 |
|---|---|
| 동기 | 호출한 작업의 완료와 결과를 받은 뒤 흐름 진행 |
| 비동기 | 작업 완료 후의 처리를 나중에 이어 감 |
| 블로킹 | 기다림 때문에 해당 실행 스레드가 붙잡힘 |
| 논블로킹 | 작업 완료 대기로 해당 실행 흐름을 붙잡아 두지 않음 |
| 콜백 | 다른 코드에 전달해 호출하도록 하는 함수 |
| `setTimeout()` | 나중에 실행할 함수를 예약 |
| 이벤트 루프 | 현재 실행 이후 준비된 비동기 콜백 등의 처리를 조율 |

### 준비 — `async-basic` 폴더
기존 서버·React 프로젝트와 구분하려고 **새 폴더**를 쓴다. Node.js 기본 기능만 쓰므로 **패키지 설치가 필요 없다.**

```text
async-basic
└─ order.js
```

`order.js`에 작성하고 실행해 Node.js가 동작하는지 확인한다.

```javascript
console.log("Node.js 실행 확인");
```

```bash
node order.js
```

파일을 수정한 뒤에는 **저장하고 명령을 다시 실행**한다 ([01_백엔드-Node](../02_Node과정/01_백엔드-Node.md) 실습 1).

### 실습 순서

| 단계 | 파일 | 코드 | 확인할 것 |
|---|---|---|---|
| 1 | `order.js` | 2장 동기 실행 (계산, `calculate()`) | 적힌 순서대로 출력 |
| 2 | `order.js` | 3장 `setTimeout(…, 3000)` | `1 → 3`, 약 3초 뒤 `2` |
| 3 | `order.js` | 5장 0초 타이머 | `A → C → B` |
| 4 | `busy.js` (새 파일) | 7장 `while` 2초 점유 | 약 2초 뒤 `3. 반복 종료` 다음에 `2. 타이머 콜백 실행` |

`busy.js` 실행:

```bash
node busy.js
```

### 직접 바꿔보기 (강의의 ✍️ 항목)
- **동기 실행**: `calculate()` 함수 안과 밖에 출력문을 추가하고, 실행 전에 순서를 적어 본 뒤 실제 결과와 비교한다.
- **0초 타이머**: 지연 시간을 `1000`으로 바꾸고 마지막에 `console.log("D")`를 추가한 뒤, 타이머 콜백이 어디에 출력되는지 확인한다.

> 💡 보충: 두 번째 항목을 실행해 보면 `A → C → D`가 먼저 나오고 약 1초 뒤 `B`가 나온다. 타이머 콜백은 **현재 코드가 모두 끝난 뒤**에 실행된다.

## 헷갈리기 쉬운 점
- **동기·비동기 ≠ 블로킹·논블로킹.** 앞은 "결과 처리가 어떻게 이어지나", 뒤는 "실행 스레드가 붙잡히나"를 묻는다.
- **`setTimeout()`은 멈춤이 아니라 예약**이다. 예약하고 바로 다음 줄로 간다.
- **코드에 붙인 번호가 출력 순서가 아니다.** 실제 순서는 실행해 보고 확인한다.
- **0초 타이머도 즉시 실행되지 않는다.** 현재 실행 중인 코드가 끝난 뒤 실행된다.
- **지연 시간은 정확한 실행 시각이 아니다.** 스레드가 바쁘면 더 늦어진다 (`busy.js`).
- **함수를 넘기는 것(`showMessage`)과 호출하는 것(`showMessage()`)은 다르다.** 콜백으로 넘길 때는 괄호 없이 이름만 쓴다.
- **콜백 = 비동기가 아니다.** `map()`의 콜백은 그 자리에서 바로 실행된다. 언제 실행되는지를 본다.
- **`while`로 시간 지연을 만들지 않는다.** 스레드를 점유해 다른 콜백을 모두 늦춘다 (관찰용 예제일 뿐).
- **블로킹이라고 컴퓨터 전체가 멈추는 것은 아니다.** 어떤 스레드·실행 흐름이 막히는지를 구분한다.
- **`await` = 블로킹이 아니다.** 그 함수 안의 다음 줄만 기다리고, 바깥 코드와 실행 스레드는 계속 일할 수 있다.

## 확인 문제
강의에 별도 "💬 확인하기"는 없어서, 본문의 질문형 제목과 "직접 바꿔보기"에서 뽑았다.

<details><summary>Q. 동기 방식과 비동기 방식을 한 문장씩으로 설명하면?</summary>

동기: 호출한 작업이 완료되고 결과를 받은 뒤 다음 코드로 진행한다. 비동기: 완료됐을 때 실행할 코드를 연결해 두고, 결과 처리를 나중에 이어 간다.
</details>

<details><summary>Q. 다음 코드의 출력 순서는? `console.log("1. 시작"); setTimeout(() => console.log("2. 타이머 실행"), 3000); console.log("3. 끝");`</summary>

`1. 시작` → `3. 끝` → (약 3초 뒤) `2. 타이머 실행`. `setTimeout()`은 코드를 멈추지 않고 함수를 **예약**만 한다.
</details>

<details><summary>Q. (강의 질문) 콜백 함수는 무엇인가? `setTimeout(showMessage, 2000)`과 `showMessage()`의 차이는?</summary>

다른 코드에 전달해 두고 그 코드가 호출하도록 하는 함수다. `setTimeout(showMessage, 2000)`은 함수를 **전달**해 타이머가 나중에 호출하게 하고, `showMessage()`는 지금 즉시 **호출**한다.
</details>

<details><summary>Q. `numbers.map((number) => number * 2)`도 함수를 전달한다. 그러면 비동기인가?</summary>

아니다. `map()`은 각 항목의 처리를 그 자리에서 마치고 새 배열을 반환한다. 함수를 전달했다는 사실만으로 비동기라고 판단하지 않고, **그 함수를 언제 실행하는지**를 본다.
</details>

<details><summary>Q. (강의 질문) 0초 타이머는 즉시 실행될까? `A`, `setTimeout(B, 0)`, `C`의 출력 순서는?</summary>

즉시 실행되지 않는다. `A → C → B`. 타이머 시간이 짧아도 현재 실행 중인 JavaScript를 중간에 끊고 콜백을 실행하지는 않는다.
</details>

<details><summary>Q. (직접 바꿔보기) 0초 타이머 예제에서 지연을 `1000`으로 바꾸고 마지막에 `console.log("D")`를 추가하면?</summary>

`A → C → D`, 약 1초 뒤 `B`. 타이머 콜백은 현재 코드가 모두 끝난 뒤에 실행된다.
</details>

<details><summary>Q. 동기·비동기와 블로킹·논블로킹은 각각 무엇을 묻는 구분인가?</summary>

동기·비동기: 작업의 완료와 결과 처리가 어떻게 이어지는가. 블로킹·논블로킹: 호출한 작업이 실행 스레드를 기다리게 붙잡는가. 같은 뜻이 아니다.
</details>

<details><summary>Q. "블로킹이 일어나면 컴퓨터 전체가 멈춘다"는 맞는 말인가?</summary>

아니다. 어떤 스레드나 실행 흐름이 막히는지를 구분해야 한다. 이 과정에서는 Node.js의 JavaScript 실행 스레드가 다른 코드를 실행할 수 있는지를 본다.
</details>

<details><summary>Q. (강의 질문) 오래 걸리는 계산이 있다면? `busy.js`에서 0초 타이머가 `3. 반복 종료`보다 늦게 나오는 이유는?</summary>

`while` 반복문이 CPU를 쓰며 실행 스레드를 2초 동안 계속 점유해서, 이벤트 루프가 타이머 콜백을 실행할 수 없었다. 타이머는 현재 실행 중인 JavaScript를 중단시키지 못한다. 출력: `1. 시작` → (약 2초 뒤) `3. 반복 종료` → `2. 타이머 콜백 실행`.
</details>

<details><summary>Q. `Date.now()`는 무엇을 반환하나? 시간 지연 기능을 `while (Date.now() < endTime)`으로 만들어도 되나?</summary>

현재 시각을 밀리초 단위 숫자로 반환한다. 시간 지연용으로 쓰지 않는다. 실행 스레드를 점유해 다른 콜백을 모두 늦추므로, 실행 흐름 관찰용 예제일 뿐이다.
</details>

<details><summary>Q. 이벤트 루프의 기본 역할과, 지금 기억할 두 가지는?</summary>

현재 JavaScript 실행이 끝난 뒤 준비된 콜백 등의 처리를 조율한다. ① 타이머를 예약했다고 현재 코드가 멈추지는 않는다. ② 현재 실행 스레드를 오래 점유하면 준비된 콜백도 늦어진다.
</details>

<details><summary>Q. "`await`가 있으니 스레드를 블로킹한다"는 판단은 맞나? 대신 무엇을 물어야 하나?</summary>

맞지 않다. `await`는 그 함수 안의 다음 줄만 기다리게 하고, 바깥 코드와 실행 스레드는 계속 진행할 수 있다. "어느 함수의 진행이 기다리는가?"와 "그동안 실행 스레드는 다른 일을 할 수 있는가?"를 나눠 묻는다.
</details>
