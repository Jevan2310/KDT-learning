# 01. 서버에서 화면을 만들던 웹과 CSR이 확산된 배경 — SSR·CSR·부분 갱신·SPA 구분

> 과정: SSR-CSR과정 · [노션 원문](https://app.notion.com/p/420848f71c9b80ccb79ac71059b43099) · 최종 갱신일: 2026-11-24

## 한눈에 보기
- 이번 과정의 질문: **학생 데이터를 반영한 화면 구조를 서버에서 만들까, 브라우저에서 만들까?**
- **SSR**(Server-Side Rendering) = 서버(Spring + JSP·Thymeleaf)가 **데이터를 넣은 HTML**을 만들어 응답한다. 링크·검색 폼 제출마다 **새 문서**를 요청하는 구성이 흔하다.
- 웹이 문서 읽기를 넘어 상호작용이 많아지자, 동작마다 새 문서를 받으면 흐름이 끊긴다 → JavaScript로 **필요한 데이터(JSON)만 요청해 일부만 바꾸는 부분 갱신**이 쓰였다.
- **CSR**(Client-Side Rendering) = 브라우저의 **JavaScript(React)가 데이터로 화면 구조를 구성**한다. **서버는 여전히 필요하다** — Spring이 데이터 조회·검색·검사·권한·변경을 맡고, 달라지는 것은 **HTML을 구성하는 위치와 응답 형태(HTML ↔ JSON)** 다.
- CSR은 장점(문서 유지 갱신, state로 상호작용 관리, 화면·API 역할 분리)과 고려 사항(초기 빈 화면, 브라우저 부담, 검색엔진, 늘어나는 상태)이 함께 있다. **어느 쪽이 항상 우월하지 않다.** 부분 갱신·SPA·CSR은 **서로 다른 기준**의 말이다.

수업 그림 (강의 맨 위): 제목 "SSR과 CSR — 학생 목록 HTML은 어디에서 만들어질까?". 왼쪽 **SSR · 서버에서 HTML 생성**: Spring 서버가 JSP·Thymeleaf로 **학생 목록 HTML**을 만들어 **HTML 응답** → 브라우저에 학생 목록(한코딩, 김자바)이 표시된다. 오른쪽 **CSR · 브라우저에서 화면 구성** (초기 HTML·JavaScript 로드 후): Spring 서버가 **JSON 데이터**를 **API 응답** → 브라우저에서 **React 실행**(데이터로 화면 구성) → 학생 목록. 아래: "SSR과 CSR 모두 서버와 통신할 수 있습니다. React도 SSR이 가능합니다. 이 그림은 React CSR 예제입니다."

## 학습 목표
- 브라우저와 서버의 요청·응답 흐름을 이해한다.
- SSR과 CSR에서 화면을 구성하는 위치를 구분한다.
- 웹의 상호작용이 늘어나면서 CSR이 활용된 이유를 설명한다.
- 부분 갱신 · SPA(Single Page Application) · CSR의 차이를 이해한다.
- CSR의 장점과 추가로 고려할 점을 구분한다.

## 핵심 개념

### 1. 웹사이트에 접속하면 — 요청과 응답
주소창에 주소를 입력하면 브라우저가 서버에 **요청**하고, 서버가 처리해서 **응답**한다.

```text
브라우저
“학생 목록 페이지를 주세요.”
        ↓ 요청
서버
        ↓ 응답
브라우저가 내용을 해석하고 화면 표시
```

- 서버가 보내는 것은 **화면을 촬영한 이미지가 아니다.** HTML·CSS·JavaScript·데이터 등을 받은 **브라우저가 처리해서** 화면에 표시한다.
- 처음 HTML을 받은 뒤 CSS·JavaScript·이미지 등을 **추가로 요청**할 수도 있다. 👉 [MDN 클라이언트·서버 개요](https://developer.mozilla.org/en-US/docs/Learn_web_development/Extensions/Server-side/First_steps/Client-Server_overview)

| 구성 요소 | 역할 |
|---|---|
| HTML | 문서의 내용과 구조 |
| CSS | 색상·크기·배치 등 표현 |
| JavaScript | 사용자 동작 처리와 화면 변경 |
| 서버 | 요청 처리와 데이터 제공 |

### 2. SSR — 서버에서 HTML을 만드는 방식
**SSR**(Server-Side Rendering) = 서버가 **데이터를 반영한 HTML을 만들어** 브라우저에 응답하는 방식.

```text
① 브라우저가 학생 목록 요청
              ↓
② 서버가 학생 데이터 조회
              ↓
③ 서버가 학생 목록 HTML 생성
              ↓
④ 브라우저가 HTML을 받아 표시
```

서버가 응답한 HTML에는 학생 이름이 들어 있다.

```html
<h1>학생 목록</h1>

<ul>
  <li th:text="${name}"></li>
  <li>김자바 — 풀스택 A반</li>
  <li>이리액트 — 풀스택 B반</li>
</ul>
```

> 💡 보충: 첫 번째 `<li th:text="${name}"></li>`는 **서버에서 처리되기 전의 Thymeleaf 템플릿** 모양이다. 아래 흐름처럼 `model.addAttribute("name", "한코딩")`으로 값을 넣었다면, 브라우저가 실제로 받는 응답에는 `th:text`가 남지 않고 `<li>한코딩</li>`처럼 **값이 들어간 결과**가 온다 ([03_Thymeleaf-학생목록](../03_Spring과정/03_Thymeleaf-학생목록.md) 10장).

**Spring에서는?** 이번 수업은 JSP와 Thymeleaf를 쓴다.

```text
Spring Controller
        ↓
학생 데이터를 Model에 담기 -- model.addAttribute("name" , "한코딩");
        ↓
JSP 또는 Thymeleaf에서 HTML 생성
        ↓
브라우저에 HTML 응답
```

- **JSP나 Thymeleaf의 템플릿 코드를 브라우저가 실행하는 것이 아니다.** 서버에서 처리한 결과인 HTML을 브라우저가 받는다.
- SSR에서도 **최종적으로 화면을 그리는 것은 브라우저**다. "서버에서 렌더링한다" = **데이터가 반영된 HTML을 서버에서 생성한다**는 뜻.

### 3. 전통적인 페이지 이동과 검색 흐름
서버가 페이지마다 HTML을 만들어 주는 웹에서는 **링크를 누르거나 폼을 제출하면 새 문서를 요청**하는 구성이 흔하다.

```html
<form action="/students" method="get">
  <input
    type="text"
    name="keyword"
    placeholder="학생 이름"
  />

  <button type="submit">검색</button>
</form>
```

`한`을 입력하고 제출하면 이 주소로 요청한다.

```text
/students?keyword=한
```

서버는 검색 결과를 포함한 HTML을 **새로** 응답한다.

```text
학생 목록 문서 표시
        ↓
검색어 입력 후 제출
        ↓
새 문서 요청
        ↓
서버에서 검색 결과 HTML 생성
        ↓
브라우저가 새 문서 표시
```

이 방식의 장점
- 서버에서 데이터와 HTML을 **함께 구성하기 쉽다.**
- 해당 기능을 **클라이언트 JavaScript 없이도** 구현할 수 있다.
- **주소에 검색 조건을 담아** 공유하거나 다시 방문할 수 있다.

단순한 목록·검색 화면에서는 충분히 유용하다.

### 4. 웹이 복잡해지면서 필요한 것도 늘어났다
웹이 문서를 읽는 용도를 넘어 **여러 작업을 하는 공간**이 되었다.
- 검색어를 입력하는 동안 추천 검색어 실시간 표시
- 메시지가 도착하면 대화 목록 갱신
- 장바구니에 넣고 개수 변경
- 글을 쓰면서 자동 저장
- 지도 위치를 옮기며 주변 정보 표시

이런 동작마다 새 문서를 요청하면 **새로 고침이 되면서 사용 흐름이 끊길 수 있다.**

학생 관리 화면의 예:

```text
┌─────────────────────────────┐
│ 상단 메뉴                    │
├──────────┬──────────────────┤
│ 사이드바  │ 학생 검색창       │
│          │ 학생 목록         │
│          │                  │
└──────────┴──────────────────┘
```

- 검색할 때 바꾸고 싶은 것은 주로 **학생 목록**이다. 상단 메뉴·사이드바까지 새 문서로 다시 만들 필요가 있을까?
- 입력 중인 값, 펼쳐 둔 메뉴 같은 **화면 상태도 유지**하고 싶을 수 있다.
- 해결 방법 중 하나: **JavaScript로 데이터를 요청하고 필요한 화면을 갱신**한다.

### 5. 필요한 데이터만 요청하고 화면 바꾸기 — 부분 갱신
앞에서 배운 `fetch`로 데이터만 요청한다.

```javascript
const response = await fetch("/api/students?keyword=한");
const students = await response.json();
```

> 💡 보충: `await`는 `async` 함수 안(또는 모듈의 맨 위)에서 쓸 수 있다. 이 두 줄은 흐름을 보여 주는 조각이다. `fetch`·`response.json()`은 [02_Promise-async-await](../05_비동기과정/02_Promise-async-await.md), [04_React-서버연결](../02_Node과정/04_React-서버연결.md) 4~5장에서 배웠다.

서버는 HTML 대신 **데이터**를 응답할 수 있다.

```json
[
  {
    "id": 1,
    "name": "한코딩",
    "className": "풀스택 A반"
  }
]
```

```text
기존 문서 유지
      ↓
JavaScript가 검색 API 요청
      ↓
서버가 JSON 응답
      ↓
JavaScript가 학생 목록 갱신
```

- **데이터가 필요하면 여전히 서버와 통신한다.** 문서 전체를 새로 요청하지 않는다 ≠ 서버 요청이 없다.
- **부분 갱신** = 기존 문서를 유지하면서 **필요한 부분의 내용만** 바꾸는 것. 검색 결과만 바꾸고 메뉴나 다른 입력 상태는 유지할 수 있다.
- 부분 갱신은 **React 없이 일반 JavaScript로도** 구현할 수 있다.

### 6. CSR — 브라우저에서 화면을 구성하는 방식
**CSR**(Client-Side Rendering) = **브라우저(클라이언트)의 JavaScript가 데이터를 이용해 화면 구조를 구성**하는 방식. 👉 [웹 렌더링 방식 안내](https://web.dev/articles/rendering-on-the-web)

이번 수업에서 만들 React CSR의 초기 흐름:

```text
① HTML과 JavaScript 불러오기
              ↓
② 브라우저에서 React 실행
              ↓
③ 학생 목록 API 요청
              ↓
④ JSON 데이터 수신
              ↓
⑤ React가 학생 목록 구성
```

초기 HTML은 **앱이 표시될 위치와 JavaScript**만 담을 수 있다.

```html
<!DOCTYPE html>
<html lang="ko">
  <head>
    <meta charset="UTF-8" />
    <title>학생 관리</title>
  </head>

  <body>
    <div id="root"></div>

    <script
      type="module"
      src="/src/main.jsx"
    ></script>
  </body>
</html>
```

- **Vite 개발 환경의 형태를 단순화한 예시**다. 배포 빌드 후에는 JavaScript 파일 경로 등이 달라진다.
- 이 초기 문서에는 **아직 학생 이름이 없다.** JavaScript 실행과 API 응답 처리를 거쳐 목록이 나타난다.

> 💡 보충: `<div id="root">`와 `src/main.jsx`가 React 화면을 연결하는 구조는 [04_React시작](../01_React과정/04_React시작.md) 4장에서 봤다.

**서버가 없어도 된다는 뜻인가?** 아니다. 이번 구성에서 Spring은 계속 다음을 맡는다.
- 학생 데이터 조회
- 검색 조건 처리
- 입력값 검사
- 접근 권한 확인
- 데이터 변경

달라지는 핵심은 **목록 HTML을 구성하는 위치**와 **서버가 전달하는 응답 형태**다.

### 7. SSR과 CSR의 응답 비교
같은 한코딩 학생을 표시해도 응답이 다르다.

SSR의 학생 목록 응답 — 서버가 학생 정보를 **HTML 구조에 넣었다.**

```html
<ul>
  <li>한코딩 — 풀스택 A반</li>
</ul>
```

CSR에서 쓰는 API 응답 — 브라우저의 JavaScript가 이 **데이터로 화면을 구성**한다.

```json
[
  {
    "id": 1,
    "name": "한코딩",
    "className": "풀스택 A반"
  }
]
```

| 비교 항목 | SSR 예제 | CSR 예제 |
|---|---|---|
| 응답 형태 | HTML | 목록 API는 JSON |
| 학생 목록 HTML 생성 | 서버 | 클라이언트 (브라우저의 JavaScript) |
| 스타일과 화면 배치 결정 | 서버 템플릿과 CSS 등 | React 코드와 CSS 등 |
| 데이터 조회 담당 | Spring | Spring |
| 최종 화면 표시 | 브라우저 | 브라우저 / iOS 앱 / 안드로이드 앱 |

- **화면이 비슷해 보여도 요청과 응답을 보면** 처리 방식의 차이를 확인할 수 있다.

> 💡 보충: 표의 "iOS 앱 / 안드로이드 앱"은 같은 JSON API를 다른 클라이언트도 쓸 수 있다는 뜻으로 보인다 (8장 ③). 이번 React CSR 예제의 화면은 **브라우저**가 표시한다.

### 8. CSR을 적용하면 좋은 점
1. **문서를 유지하며 화면을 갱신**할 수 있다 (새로고침 없이). 검색할 때 학생 목록만 바꾸고 메뉴·다른 영역은 유지하기 쉽다.
2. **상호작용이 많은 화면을 구성하기 좋다.** React의 **state**로 선택한 학생, 검색어, 열린 상세 창, 로딩 여부, 오류 메시지를 연결해 사용자 행동에 따른 화면 변화를 일관되게 관리한다.
3. **화면과 데이터 API의 역할을 나눌 수 있다.** React는 화면 구성, Spring은 데이터와 업무 처리. 같은 API를 모바일 앱 등 다른 클라이언트에서 쓸 수도 있다. 단, **API 재사용은 CSR만의 고유 기능이 아니다.**
4. **이후 동작을 빠르게 느끼도록** 만들 수 있다. 앱 코드가 로드된 뒤에는 필요한 데이터만 받아 갱신한다. 하지만 **CSR이라는 이유만으로 모든 동작이 빨라지지는 않는다** — API 응답 시간, JavaScript 실행량, 네트워크 상태의 영향을 받는다.

> 💡 보충: state로 화면을 바꾸는 방법은 [07_이벤트-state](../01_React과정/07_이벤트-state.md).

### 9. CSR에서 추가로 고려할 점

**초기 화면을 구성하는 과정** — JavaScript와 API 응답을 기다려 목록을 만들므로, 길어지면 **빈 영역이 오래 보일 수 있다.** 다음 상태를 명시적으로 처리한다.

```text
요청 중 → 로딩 안내
성공    → 학생 목록
결과 없음 → 빈 결과 안내
실패    → 오류 안내
```

> 💡 보충: 이 네 상태는 [04_React-서버연결](../02_Node과정/04_React-서버연결.md) 실습 4와 [04_느린API-화면](../05_비동기과정/04_느린API-화면.md) 7장에서 `isLoading`·`error`·빈 배열 검사로 직접 만들었다.

**브라우저의 처리 부담** — JavaScript의 다운로드·해석·실행에 시간이 들고, **기기 성능에 따라** 차이가 생긴다.

**검색엔진과 콘텐츠 전달** — 검색엔진이 JavaScript를 처리하는 방식과 시점에는 차이가 있다. 공개 콘텐츠를 어떤 형태로 전달할지 고려해야 한다. 그렇다고 **"CSR 페이지는 검색에 절대 나오지 않는다"고 단정하면 안 된다.**

> 💡 보충: 검색의 수집·색인 흐름은 [01_SEO-검색엔진](../04_SEO과정/01_SEO-검색엔진.md). SEO 과정에서 네이버는 소유확인 때 JavaScript를 실행하지 않아, 확인 태그를 **처음 전달되는 HTML**에 넣었다 ([03_사이트등록-소유확인](../04_SEO과정/03_사이트등록-소유확인.md) 7장).

**구현할 상태가 늘어난다** — 데이터 요청과 화면 표시가 나뉘므로 함께 생각할 것:
- 요청 실패
- 로딩 중 중복 요청
- 화면과 서버 데이터의 불일치
- 페이지 이동과 상태 유지

SSR과 CSR은 **서로 다른 장점과 비용을 가진 선택지**다.

### 10. 부분 갱신 · SPA · CSR은 같은 말일까?
비슷한 맥락에서 쓰지만 **같은 뜻이 아니다.** 구분하는 기준이 다르다.

| 용어 | 구분하는 기준 |
|---|---|
| 부분 갱신 | 화면의 **일부**를 갱신하는가? |
| SPA | **하나의 페이지를 유지**하며 주요 화면 전환을 처리하는가? |
| CSR | 브라우저의 **JavaScript가 화면 구조**를 구성하는가? |

**SPA**(Single-Page Application) = 기본 문서를 **한 번** 불러온 뒤, JavaScript로 화면과 내용을 바꾸는 애플리케이션 구조. 👉 [MDN SPA 설명](https://developer.mozilla.org/en-US/docs/Glossary/SPA)

```text
학생 목록 화면
      ↕
학생 상세 화면
      ↕
학생 등록 화면
```

- 이름에 'Single Page'가 있지만 **보이는 화면이 하나뿐이라는 뜻이 아니다.** 하나의 문서를 유지하면서 여러 화면을 표시하고, **주소도 바뀔 수 있다.**

꼭 기억할 구분
- SSR 페이지에도 JavaScript로 **부분 갱신을 추가**할 수 있다.
- 부분 갱신에 **React가 반드시 필요하지는 않다.**
- SPA는 CSR로 많이 구현하지만 **초기 HTML에 SSR을 쓸 수도** 있다.
- React도 **CSR만 가능한 도구가 아니다.**

이번 실습은 복잡한 조합보다 **JSP SSR과 React CSR의 기본 흐름**을 비교한다.

### 11. 이번 수업에서 쓰는 기술의 위치
Spring Boot·JSP·React·Thymeleaf는 **같은 종류의 기술이 아니다.**

| 기술 | 이번 실습에서의 역할 |
|---|---|
| Spring Boot | 요청을 처리하는 서버 애플리케이션 구성 |
| JSP | 서버에서 HTML 생성 |
| Thymeleaf | 서버에서 HTML 생성 |
| React | 브라우저에서 화면 구성과 상태 관리 |

```text
JSP SSR:        Spring → JSP → HTML → 브라우저
Thymeleaf SSR:  Spring → Thymeleaf → HTML → 브라우저
React CSR:      Spring → JSON → 브라우저의 React → 화면 구성
```

- **JSP를 Thymeleaf로 바꾸면 화면 템플릿 기술은 바뀌지만 SSR이라는 방식은 유지된다.**

> 💡 보충: Thymeleaf SSR(`/students` → HTML)과 React CSR(`/api/students` → JSON)은 Spring 과정 [06_JSON-API-React연결](../03_Spring과정/06_JSON-API-React연결.md)에서 같은 DB로 이미 만들어 봤다. 이번 과정에서는 [02_JSP-SSR화면](02_JSP-SSR화면.md), [03_SSR요청흐름](03_SSR요청흐름.md), [04_React-CSR화면](04_React-CSR화면.md)으로 이어진다.

### 정리

| 개념 | 핵심 |
|---|---|
| SSR | 서버에서 데이터를 반영한 HTML을 생성하여 응답 |
| CSR | 브라우저의 JavaScript로 화면 구조를 구성 |
| API 요청 | 이번 예제에서는 JSON 데이터를 받는 요청 |
| 부분 갱신 | 기존 문서를 유지하며 필요한 부분 변경 |
| SPA | 하나의 문서를 유지하며 주요 화면 전환 처리 |
| CSR이 활용된 배경 | 상호작용과 상태 변화가 많은 웹에 대한 요구 |
| CSR의 장점 | 유연한 화면 갱신과 클라이언트 상태 관리 |
| CSR의 고려 사항 | 초기 로딩, 브라우저 부담, 오류·상태 처리 |
| 선택 기준 | 콘텐츠·상호작용·성능·운영 조건을 함께 고려 |

## 실습 정리
이번 회차는 코드를 실행하는 실습 없이 개념과 **비교 활동** 하나만 있다.

### 비교 활동 (강의 7장)
SSR 응답(`<ul><li>한코딩 — 풀스택 A반</li></ul>`)과 CSR API 응답(JSON 배열)을 나란히 놓고 다음을 구분한다 → 7장 표.
1. 응답 형태 (HTML / JSON)
2. 학생 목록 HTML을 만드는 곳 (서버 / 브라우저의 JavaScript)
3. 스타일과 화면 배치를 정하는 곳 (서버 템플릿 + CSS / React 코드 + CSS)
4. 데이터 조회 담당 (둘 다 Spring)
5. 최종 화면 표시 (SSR: 브라우저 / CSR: 브라우저 / iOS 앱 / 안드로이드 앱)

> 💡 보충: Spring 06 프로젝트가 있으면 직접 볼 수 있다. `http://localhost:8080/students`에서 **페이지 소스 보기**를 하면 학생 이름이 든 HTML이, React 화면(`http://localhost:5173`)의 페이지 소스에는 이름 없이 `<div id="root"></div>`와 스크립트만 보인다. `http://localhost:8080/api/students`는 JSON이다. 페이지 소스 보기(서버가 보낸 HTML)와 개발자 도구 Elements(JavaScript 실행 후 화면)의 차이는 [03_사이트등록-소유확인](../04_SEO과정/03_사이트등록-소유확인.md) 7장.

## 헷갈리기 쉬운 점
- **서버가 보내는 것은 화면 이미지가 아니다.** HTML·CSS·JavaScript·데이터를 받아 브라우저가 화면을 그린다.
- **SSR에서도 화면을 그리는 것은 브라우저다.** "서버에서 렌더링" = 데이터가 반영된 HTML을 서버에서 만든다는 뜻.
- **JSP·Thymeleaf 템플릿 코드를 브라우저가 실행하지 않는다.** 브라우저는 처리된 결과 HTML만 받는다.
- **문서 전체를 새로 요청하지 않는다 ≠ 서버 요청이 없다.** 부분 갱신·CSR도 데이터가 필요하면 서버와 통신한다.
- **CSR이어도 서버는 필요하다.** 조회·검색 조건·입력값 검사·접근 권한·데이터 변경은 Spring이 맡는다. 바뀌는 것은 HTML을 구성하는 위치와 응답 형태.
- **CSR의 초기 HTML에는 학생 이름이 없다.** JavaScript 실행과 API 응답을 거쳐야 목록이 나타난다.
- **부분 갱신에 React가 꼭 필요하지 않다.** SSR 페이지에도 JavaScript로 부분 갱신을 넣을 수 있다.
- **SPA ≠ 화면이 하나.** 문서 하나를 유지하며 여러 화면을 보여 주고 주소도 바뀔 수 있다. SPA의 초기 HTML에 SSR을 쓸 수도 있고, React도 CSR만 하는 도구가 아니다.
- **API 재사용은 CSR만의 기능이 아니다.**
- **CSR이라고 모든 동작이 빨라지지 않는다.** API 응답 시간·JavaScript 실행량·네트워크 상태에 달렸다.
- **"CSR 페이지는 검색에 절대 안 나온다"고 단정하지 않는다.** 검색엔진의 JavaScript 처리 방식·시점이 다르니 공개 콘텐츠의 전달 형태를 고려한다.
- **SSR과 CSR 중 항상 나은 쪽은 없다.** 서로 다른 장점과 비용을 가진 선택지다.
- **JSP → Thymeleaf로 바꿔도 여전히 SSR이다.** 템플릿 기술만 바뀐다.
- 6장의 초기 HTML은 **Vite 개발 환경을 단순화한 예시**다. 배포 빌드 후에는 파일 경로가 달라진다.

## 빠른 참고 (치트시트)

| 하고 싶은 것 | 쓰는 것 | 예시 |
|---|---|---|
| 서버에서 데이터 넣은 HTML 만들기 (SSR) | Spring + JSP 또는 Thymeleaf | `Spring → JSP → HTML → 브라우저` |
| 브라우저에서 화면 구성 (CSR) | Spring JSON API + React | `Spring → JSON → 브라우저의 React → 화면 구성` |
| 검색 조건을 주소에 담아 새 문서 요청 | `<form method="get">` + `name` | `/students?keyword=한` |
| 문서는 두고 데이터만 요청 | `fetch` + `response.json()` | `await fetch("/api/students?keyword=한")` |
| React 앱이 들어갈 자리 (초기 HTML) | `<div id="root">` + `<script type="module">` | `src="/src/main.jsx"` |
| CSR 초기 화면 상태 처리 | 네 가지 상태 | 요청 중→로딩, 성공→목록, 결과 없음→빈 결과, 실패→오류 |
| 응답으로 방식 구분 | 응답 형태 확인 | HTML에 이름이 있음 = SSR / JSON + 브라우저 JS = CSR |
| 부분 갱신·SPA·CSR 구분 | 기준 질문 | 일부만 갱신? / 문서 하나 유지? / JS가 화면 구조를 만듦? |

## 확인 문제

<details><summary>Q. 웹사이트에 접속하면 서버는 브라우저에 무엇을 보내는가? 화면 이미지인가?</summary>

이미지가 아니다. 서버는 요청을 처리해 HTML·CSS·JavaScript·데이터 등을 응답하고, **브라우저가 이를 해석해** 화면에 표시한다. 처음 HTML을 받은 뒤 CSS·JavaScript·이미지를 추가로 요청하기도 한다.
</details>

<details><summary>Q. SSR에서 서버는 무엇을 만드는가? "서버에서 렌더링한다"는 무슨 뜻인가?</summary>

서버가 **데이터를 반영한 HTML**을 만들어 응답한다. 최종적으로 화면을 그리는 것은 SSR에서도 브라우저이고, "서버에서 렌더링"은 데이터가 들어간 HTML을 서버에서 생성한다는 뜻이다.
</details>

<details><summary>Q. JSP·Thymeleaf의 템플릿 코드(`th:text="${name}"` 등)는 어디서 실행되는가?</summary>

**서버**에서 처리된다. 브라우저는 템플릿 코드를 실행하지 않고, 처리 결과인 HTML(값이 들어간 `<li>한코딩</li>` 같은 형태)을 받는다.
</details>

<details><summary>Q. 전통적인 검색 폼(`method="get"`)을 제출하면 어떤 흐름이 되고, 장점은?</summary>

`/students?keyword=한`으로 **새 문서를 요청**하고, 서버가 검색 결과를 넣은 HTML을 새로 응답한다. 장점: 서버에서 데이터와 HTML을 함께 구성하기 쉽다, 클라이언트 JavaScript 없이 구현할 수 있다, 주소에 검색 조건이 담겨 공유·재방문할 수 있다.
</details>

<details><summary>Q. 상호작용이 많은 화면에서 동작마다 새 문서를 요청하면 무엇이 문제인가?</summary>

새로 고침이 되면서 **사용 흐름이 끊길 수 있다.** 바꾸고 싶은 것은 학생 목록뿐인데 상단 메뉴·사이드바까지 다시 구성되고, 입력 중인 값이나 펼쳐 둔 메뉴 같은 화면 상태도 유지하기 어렵다.
</details>

<details><summary>Q. 부분 갱신이란? 서버 요청이 없어지는가? React가 꼭 필요한가?</summary>

기존 문서를 유지하면서 **필요한 부분의 내용만** 바꾸는 것. 데이터가 필요하면 **여전히 서버와 통신**한다 (문서 전체를 새로 요청하지 않을 뿐). React 없이 일반 JavaScript로도 구현할 수 있다.
</details>

<details><summary>Q. CSR이란? CSR의 초기 HTML에 학생 이름이 들어 있는가?</summary>

브라우저의 **JavaScript가 데이터를 이용해 화면 구조를 구성**하는 방식. 초기 HTML에는 `<div id="root"></div>`와 스크립트 정도만 있고 **학생 이름은 없다.** JavaScript 실행 → API 요청 → JSON 수신 → React가 목록 구성을 거쳐 나타난다.
</details>

<details><summary>Q. CSR이면 서버가 없어도 되는가?</summary>

아니다. Spring이 학생 데이터 조회, 검색 조건 처리, 입력값 검사, 접근 권한 확인, 데이터 변경을 계속 맡는다. 달라지는 것은 **목록 HTML을 구성하는 위치**와 **서버의 응답 형태**(HTML → JSON)다.
</details>

<details><summary>Q. 같은 학생을 보여 주는 SSR과 CSR의 응답은 어떻게 다른가? 데이터 조회는 누가 하는가?</summary>

SSR은 학생 정보가 들어간 **HTML**(`<li>한코딩 — 풀스택 A반</li>`), CSR의 목록 API는 **JSON**(`{"id": 1, "name": "한코딩", ...}`)을 응답한다. 학생 목록 HTML은 SSR은 서버가, CSR은 브라우저의 JavaScript가 만든다. **데이터 조회는 둘 다 Spring**이 한다.
</details>

<details><summary>Q. CSR의 장점 네 가지는? API 재사용은 CSR만의 기능인가? CSR이면 항상 빠른가?</summary>

① 문서를 유지하며 화면 갱신 ② state로 상호작용 많은 화면 관리 ③ 화면(React)과 데이터 API(Spring) 역할 분리 ④ 앱 코드 로드 후 필요한 데이터만 받아 빠르게 느끼게 할 수 있음. API 재사용은 **CSR 고유 기능이 아니고**, CSR이라는 이유만으로 **모든 동작이 빨라지지 않는다** (API 응답 시간·JavaScript 실행량·네트워크 상태의 영향).
</details>

<details><summary>Q. CSR에서 초기 화면을 만들 때 명시적으로 처리할 상태 네 가지는?</summary>

요청 중 → 로딩 안내, 성공 → 학생 목록, 결과 없음 → 빈 결과 안내, 실패 → 오류 안내. JavaScript와 API 응답을 기다리는 동안 빈 영역이 오래 보일 수 있기 때문이다.
</details>

<details><summary>Q. CSR에서 추가로 고려할 점은? "CSR 페이지는 검색에 절대 안 나온다"는 맞는가?</summary>

초기 화면 구성(로딩·빈 결과·오류 처리), 브라우저의 처리 부담(다운로드·해석·실행, 기기 성능 차이), 검색엔진과 콘텐츠 전달, 늘어나는 상태(요청 실패, 로딩 중 중복 요청, 화면·서버 데이터 불일치, 페이지 이동과 상태 유지). 검색은 엔진마다 JavaScript 처리 방식·시점이 달라 고려해야 하지만 **"절대 안 나온다"고 단정하면 안 된다.**
</details>

<details><summary>Q. 부분 갱신·SPA·CSR은 같은 말인가? 각각 무엇을 기준으로 구분하는가?</summary>

같은 말이 아니다. 부분 갱신 = 화면의 **일부**를 갱신하는가, SPA = **하나의 페이지(문서)를 유지**하며 주요 화면 전환을 처리하는가, CSR = 브라우저의 **JavaScript가 화면 구조**를 구성하는가.
</details>

<details><summary>Q. SPA는 화면이 하나뿐인 앱인가?</summary>

아니다. 기본 문서를 한 번 불러온 뒤 JavaScript로 화면과 내용을 바꾸는 구조라서, 학생 목록·상세·등록처럼 **여러 화면**을 보여 줄 수 있고 **주소도 바뀔 수 있다.** SPA는 CSR로 많이 구현하지만 초기 HTML에 SSR을 쓸 수도 있다.
</details>

<details><summary>Q. JSP를 Thymeleaf로 바꾸면 CSR이 되는가?</summary>

아니다. JSP와 Thymeleaf는 둘 다 **서버에서 HTML을 생성**하는 템플릿 기술이라, 템플릿 기술만 바뀌고 **SSR 방식은 유지**된다. 이번 실습에서 CSR은 Spring이 JSON을 주고 브라우저의 React가 화면을 구성하는 구조다.
</details>
