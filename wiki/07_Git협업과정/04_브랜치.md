# 04. 브랜치 — 독립된 작업 공간 만들고 합치기

> 과정: Git협업과정 · [노션 원문](https://app.notion.com/p/41ce6d97109c804aa54bfc3e24abe3d4) · 최종 갱신일: 2026-11-20

## 한눈에 보기
- **브랜치**는 독립적인 작업 공간이다. 새로 만들면 지금 상태를 복사해서 새 작업을 시작하고, 원본(`main`)은 그대로 둔다. 브랜치끼리는 서로 영향을 주지 않는다.
- `git init`을 하면 기본으로 **`main`** 브랜치가 생긴다 (예전 기본 이름은 `master`).
- 명령: `git branch`(목록) · `git branch 이름`(생성) · `git checkout 이름`(이동) · `git checkout -b 이름`(생성 + 이동) · `git merge 이름`(지금 브랜치에 합치기) · `git branch -d 이름`(삭제).
- 새 기능은 브랜치에서 만들고, 끝나면 `main`으로 이동해서 `merge`한다. 작업 중 급한 버그가 생기면 `main`에서 `hotfix` 브랜치를 따로 만들어 고친다.
- **브랜치를 옮기기 전에 반드시 커밋한다.** 커밋하지 않은 파일은 이동한 브랜치로 따라온다.

## 학습 목표
강의 페이지에 학습 목표가 따로 없어 본문 제목으로 정리했다.
- 브랜치가 필요한 이유를 설명한다.
- 브랜치를 만들고, 이동하고, 합치고, 지운다.
- 작업 중 긴급 수정(hotfix) 흐름을 따라 한다.
- `git log --oneline --graph --all`로 브랜치 기록을 확인한다.
- 브랜치를 옮기기 전에 작업을 정리(커밋)한다.

## 핵심 개념

### 1. 브랜치 (Branch)
- 독립적인 작업 공간이다. **브랜치끼리 영향을 주지 않는다.**
- 브랜치를 새로 만들면 현재 작업 내용을 복사해서 새 작업을 시작할 수 있고, 원본을 유지할 수 있다.

강의 그림 (글로 옮김)

```text
그림 1
main   ●───●───●───●───●───
        \           /
login    ───●───●───          ← main 첫 커밋에서 갈라져 커밋 2개, main 4번째 커밋에서 다시 합쳐짐

그림 2 (그림 1 + 브랜치 2개 더)
board   main 첫 커밋에서 갈라져 커밋 3개 → main 5번째 커밋에서 합쳐짐
QnA     board 첫 커밋에서 갈라져 커밋 1개 → board 3번째 커밋에서 합쳐짐
```

- 브랜치에서 또 브랜치를 만들 수 있고(`board`에서 `QnA`), 합칠 때도 꼭 `main`이 아니라 갈라져 나온 브랜치로 합칠 수 있다.

### 2. main 브랜치
- `git init`으로 저장소를 만들면 기본으로 생기고 사용하는 브랜치다.
- 과거에는 `master`가 기본 브랜치였다 ([01회차](01_설치-환경설정.md) `init.defaultBranch main` 설정).

### 3. 브랜치 주요 명령어

| 하는 일 | 명령 | 설명 |
|---|---|---|
| 목록 확인 | `git branch` | 지금 브랜치 앞에 `*`가 붙는다 |
| 생성 | `git branch [이름]` | 만들기만 하고 이동은 안 한다 |
| 이동 | `git checkout [이름]` | |
| 생성 + 이동 | `git checkout -b [이름]` | |
| 삭제 | `git branch -d [이름]` | |
| 강제 삭제 | `git branch -D [이름]` | 합치지 않은 브랜치도 지운다 |
| 병합 | `git merge [브랜치명]` | **현재 브랜치에** 그 브랜치를 합친다 |

> 💡 보충
> - `merge`는 "지금 있는 브랜치로 가져온다"는 뜻이라 **어디서 치는지**가 중요하다. login을 main에 합치려면 `main`으로 이동한 뒤 `git merge login`.
> - `-d`는 합치지 않은 커밋이 있으면 지우지 않는다: `error: the branch 'feat-x' is not fully merged` (Git 2.50에서 확인). 정말 버릴 때만 `-D`.
> - 요즘 Git은 이동 전용 명령 `git switch 이름`, 생성 + 이동 `git switch -c 이름`도 있다. `checkout`과 같은 일을 한다.

## 실습 정리

### 기초 예제 — 로그인 기능 브랜치 (강의)

```bash
# 상황: 새로운 로그인 기능을 개발하고 싶다!
# 이 상황에서 main브랜치에 직접 개발하면, 나중에 잘못되었을 때 되돌리기 힘들어질 수 있음
# 그래서 안전하게 새로운 평행세계(브랜치)를 만들어 실험하는 것
# 새로 만든 브랜치에서 무슨짓을 해도 Main브랜치에 영향을 주지 못하므로 마음것 테스트할 수 있음

# 0. 현재 브랜치 목록 확인
git branch

# 1. 안전하게 실험하기 위해 브랜치 생성
git branch login    # login 브랜치 생성
git branch # 목록 확인
git checkout login  # login 브랜치로 이동

# 2. 로그인 기능 개발
echo "로그인 기능" > login.txt
git add login.txt
git commit -m "로그인 기능 추가"

# 3. main브랜치와 Login 브랜치를 자유롭게 이동하기
git checkout main
git checkout login

# 4. 메인에 병합하여 로그인 기능 적용하기
git checkout main        # 메인으로 이동
git merge login         # 로그인 기능 병합
git branch -d login     # 완료된 브랜치 삭제
bit branch          # 목록 확인

```

> 💡 보충: 마지막 줄 `bit branch`는 `git branch`의 오타다. 그대로 치면 `command not found: bit`가 나온다.
>
> 0번에서 `git branch`를 쳤는데 아무것도 안 나오면, 아직 커밋이 하나도 없어서다. 이 상태에서 1번 `git branch login`을 치면 `fatal: not a valid object name: 'main'`이 나온다. 브랜치는 커밋에서 갈라지므로 **커밋을 하나 이상 한 저장소**([02회차](02_3가지영역-기본명령.md) 예제 뒤)에서 시작한다. 3번에서 `main`으로 이동하면 `login.txt`가 폴더에서 사라지고, `login`으로 돌아오면 다시 생긴다 — 브랜치마다 파일 상태가 다르다.

### 상황 1 — 챗봇 개발 중 긴급 버그 수정 (강의)
1. 회사에서 운영 중인 웹 사이트가 있다.
2. 새 챗봇 기능을 만들려고 `chatbot` 브랜치를 만들어 작업한다.
3. 새벽에 운영 중인 사이트에 버그가 생겼다.
4. `chatbot` 작업을 멈추고 새 브랜치 `hotfix`를 만든다.
5. `hotfix`에서 버그를 급하게 고치고 `main`에 merge한다.
6. 다시 `chatbot`으로 돌아가 하던 일을 계속한다.

```bash
# 상황: 챗봇 개발 중에 긴급 버그 수정이 필요한 상황!

# 1. 메인 브랜치에서 시작
echo "회사 웹 사이트 코드" > main.txt
git add main.txt
git commit -m "웹 사이트 첫 버전"

# 2. 챗봇 기능 개발 시작
git checkout -b chatbot     # chatbot 브랜치 생성 및 이동
echo "챗봇 기능 1단계" > chatbot.txt
git add chatbot.txt
git commit -m "챗봇 1단계 개발 중"

# 3. 갑자기! 웹 사이트에 버그 발생
# 주의: 브랜치 이동하기 전에 반드시 모든 작업을 커밋해야 함
git checkout main          # 메인으로 이동
git checkout -b hotfix     # hotfix 브랜치 생성 및 이동

# 4. 버그 수정
echo "버그 수정" > bugfix.txt
git add bugfix.txt
git commit -m "긴급 버그 수정"

# 5. 수정사항 메인에 적용
git checkout main          # 메인으로 이동
git merge hotfix          # 버그 수정 병합
git log --oneline --graph --all # 로그 그래프 확인하기
# --all 옵션을 넣어야 모든 브랜치를 확인 가능
git branch -d hotfix      # hotfix 브랜치 삭제

# 6. 다시 챗봇 개발로 복귀
git checkout chatbot       # chatbot 브랜치로 이동
echo "챗봇 기능 2단계" >> chatbot.txt
git add chatbot.txt
git commit -m "챗봇 2단계 개발 완료"

# 7. 완성된 기능 main에 병합
git checkout main
git merge chatbot
git git log --oneline --graph --all

```

> 💡 보충: 마지막 줄 `git git log …`는 `git`이 두 번 들어간 오타다. 그대로 치면 `git: 'git' is not a git command.`가 나온다. `git log --oneline --graph --all`로 친다.

실행 결과 (Git 2.50에서 확인, 커밋 번호는 매번 다르다)

```text
# 5번 git merge hotfix
Updating 9f127a7..99f03e1
Fast-forward
 bugfix.txt | 1 +

# 5번 git log --oneline --graph --all
* 99f03e1 긴급 버그 수정
| * 6815074 챗봇 1단계 개발 중
|/
* 9f127a7 웹 사이트 첫 버전

# 7번 git merge chatbot
Merge made by the 'ort' strategy.
 chatbot.txt | 2 ++

# 7번 다음 git log --oneline --graph --all
*   e3a684b Merge branch 'chatbot'
|\
| * d57fb5e 챗봇 2단계 개발 완료
| * 6815074 챗봇 1단계 개발 중
* | 99f03e1 긴급 버그 수정
|/
* 9f127a7 웹 사이트 첫 버전
```

> 💡 보충: 두 merge의 모양이 다르다.
> - **5번 `Fast-forward`**: `hotfix`가 갈라진 뒤 `main`에 새 커밋이 없어서, `main`을 `hotfix`의 마지막 커밋으로 **앞으로 옮기기만** 했다. 새 커밋이 생기지 않는다.
> - **7번 `Merge made by …`**: 그사이 `main`에 hotfix 커밋이 생겨서 두 줄기가 갈라져 있다. 그래서 둘을 합친 **병합 커밋**(`Merge branch 'chatbot'`)이 새로 생긴다. 이때 병합 커밋 메시지를 쓰라고 **편집기(vim)가 열릴 수 있다.** 기본 메시지 그대로 두려면 `Esc` → `:wq` → Enter.
> - `git log` 출력이 화면보다 길면 아래에 `:`가 보이고 멈춘다. `q`를 누르면 빠져나온다.

## 헷갈리기 쉬운 점

> ⚠️ **브랜치 이동 전 반드시 현재 작업을 커밋해야 한다.** (강의)

**브랜치 이동할 때 주의사항** (강의)
1. **이동 전 상태 확인** — `git status`로 작업 중인 파일, 커밋하지 않은 변경이 있는지 본다.
2. **작업 중인 파일 처리** — **커밋하지 않은 파일은 다른 브랜치로 함께 이동된다.** (Untracked든 Tracked든 상관없다.) 그래서 작업 중인 파일을 정리한 뒤 이동해야 한다. 가장 쉽고 확실한 방법은 **commit**이다.
   - 예: `login` 브랜치에서 `login.txt`를 새로 만들어 작업하던 중 확인할 게 있어 `main`으로 checkout하면, `login.txt`(추적 여부와 상관없이)가 `main`으로 따라온다. 의도하지 않은 문제가 생길 수 있다.
3. **안전한 이동 방법** — 작업을 다 못 끝냈어도 **오류가 나지 않는 상태로 마무리**(주석 활용 등) → **커밋** → 이동.

> 💡 보충: 커밋하지 않은 변경이 이동할 브랜치의 같은 파일과 부딪히면 Git이 이동을 막는다.
> ```text
> error: Your local changes to the following files would be overwritten by checkout:
> 	chatbot.txt
> Please commit your changes or stash them before you switch branches.
> Aborting
> ```
> 이 메시지가 나오면 먼저 커밋한다. (`stash`는 커밋하지 않고 잠깐 치워 두는 명령인데 강의 범위 밖이다.)

- **`merge`는 지금 브랜치로 가져온다.** `login`에 있으면서 `git merge main`을 치면 반대로 `main`이 `login`에 합쳐진다. ([06회차](06_Organization-PR.md)에서는 일부러 이렇게 해서 작업 브랜치를 최신으로 맞춘다.)
- `git log --oneline --graph`에 `--all`을 빼면 **지금 브랜치의 기록만** 보인다.

## 확인 문제

<details><summary>Q. 새 기능을 main에서 바로 만들지 않고 브랜치를 만드는 이유는?</summary>

브랜치는 독립된 작업 공간이라 그 안에서 무엇을 해도 `main`에 영향이 없다. 잘못되면 브랜치만 버리면 되고, 완성되면 `main`에 merge한다.
</details>

<details><summary>Q. `login` 브랜치의 작업을 `main`에 합치는 명령 순서는?</summary>

`git checkout main` → `git merge login` (→ 다 쓴 브랜치는 `git branch -d login`). merge는 **지금 있는 브랜치에** 합친다.
</details>

<details><summary>Q. `git branch hotfix`와 `git checkout -b hotfix`의 차이는?</summary>

`git branch hotfix`는 만들기만 하고 지금 브랜치에 그대로 있다. `git checkout -b hotfix`는 만들고 바로 이동한다.
</details>

<details><summary>Q. 챗봇 작업 중 긴급 버그가 생겼을 때 강의의 처리 순서는?</summary>

챗봇 작업 커밋 → `main`으로 이동 → `hotfix` 브랜치 생성·이동 → 버그 수정·커밋 → `main`으로 이동해 `merge hotfix` → `hotfix` 삭제 → `chatbot`으로 돌아가 계속 작업.
</details>

<details><summary>Q. 커밋하지 않은 새 파일이 있는 채로 다른 브랜치로 이동하면?</summary>

그 파일이 이동한 브랜치로 따라온다 (Untracked든 Tracked든). 의도하지 않은 변경이 섞일 수 있으니 이동 전에 커밋한다.
</details>

## 완료 체크
원문에 완료 체크가 없어 강의 단계로 만든 목록이다.
- [ ] `login` 브랜치를 만들어 커밋하고, `main`·`login`을 오가며 파일이 바뀌는 것을 봤다.
- [ ] `main`에서 `git merge login`으로 합치고 브랜치를 지웠다.
- [ ] 상황 1(chatbot·hotfix)을 따라 하고 `git log --oneline --graph --all`로 갈라지고 합쳐진 기록을 봤다.
- [ ] 브랜치 이동 전에 `git status`로 커밋하지 않은 변경이 없는지 확인했다.
