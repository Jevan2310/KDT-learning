# 02. git의 3가지 영역 — Working Directory · Staging Area · Local Repository와 기본 명령

> 과정: Git협업과정 · [노션 원문](https://app.notion.com/p/41ce6d97109c8017a280f8d33bda7771) · 최종 갱신일: 2026-11-20

## 한눈에 보기
- 내 컴퓨터 안에서 파일은 **Working Directory → (`git add`) → Staging Area → (`git commit`) → Local Repository** 순서로 이동한다.
- **Local Repository에 들어오면 하나의 버전이 확정된다.** 버전 기록은 모두 `.git` 폴더에 있어서, `.git`을 지우면 기록이 전부 사라진다.
- 파일 상태: 새 파일은 **Untracked**, 스테이징하면 **Tracked**가 된다. Tracked는 다시 **Unmodified**(마지막 커밋과 같음) · **Modified**(다름) · **Staged**(커밋 준비 완료)로 나뉜다.
- 기본 명령: `git init`(처음 한 번) · `git status`(수시로) · `git add` · `git commit -m "메시지"` · `git diff`.
- 스테이징한 뒤 파일을 또 고치면 고친 부분은 커밋 대상이 아니다. **다시 `git add`** 해야 한다.

## 학습 목표
강의 페이지에 학습 목표가 따로 없어 본문 제목으로 정리했다.
- Git의 3가지 영역과 영역 사이를 옮기는 명령(`add`, `commit`)을 설명한다.
- 파일 상태(Untracked, Unmodified, Modified, Staged)를 구분한다.
- `init`, `status`, `add`, `commit`, `diff`를 쓴다.
- `git status` 결과를 보고 파일이 어느 상태인지 읽는다.

## 핵심 개념

### 1. Git의 3가지 영역
강의 그림: `a.txt`, `b.txt`가 **Working Directory —git add→ Staging Area —git commit→ Local Repository**로 옮겨 간다.

| 영역 | 무엇 | 특징 | 다음 영역으로 |
|---|---|---|---|
| **Working Directory** (작업 디렉토리) | 실제로 작업하는 공간 = 실제 내 폴더 | 파일을 만들고 고치고 지우는 곳 | `git add` → Staging Area |
| **Staging Area** (스테이징 영역) | 커밋할 파일을 골라 두는 공간 | 커밋 전의 **임시 저장소**. 여기 올라온 파일부터 Git이 변경을 추적한다 | `git commit` → Local Repository |
| **Local Repository** (내 컴퓨터의 저장소, `.git` 폴더) | 하나의 완성된 버전이 저장되는 공간 | 버전을 저장하는 **영구 저장소**. 과거 버전 기록을 모두 저장·관리한다. **들어오면 버전 확정** | (03회차) `git push` → 원격 저장소 |

- 실제 버전 정보는 `.git` 디렉토리에 저장된다. **`.git`을 삭제하면 기록이 모두 사라진다.**

> 💡 보충: 강의는 Working Directory를 "Git이 변경사항을 추적하지 않는 상태"라고 설명한다. 이건 **새로 만든 파일**(Untracked) 이야기다. 한 번 커밋된 파일은 Working Directory에서 고쳐도 Git이 바로 알아채서 `git status`에 `modified`로 나온다 (아래 2장 Modified).

### 2. 파일의 상태

| 상태 | 뜻 | 언제 |
|---|---|---|
| **Untracked** (추적 안 됨) | Git이 관리하지 않는 파일 | 새로 만든 파일 |
| **Tracked** (추적됨) | Git이 관리하는 파일 | 스테이징 영역으로 넘어간 적이 있는 파일 |
| └ Unmodified (수정 없음) | 마지막 커밋과 같은 상태 | 커밋 직후 |
| └ Modified (수정됨) | 마지막 커밋과 다른 상태 | 커밋한 뒤 파일을 고쳤을 때 |
| └ Staged (스테이징됨) | 커밋할 준비가 된 상태 | `git add` 직후 |

**상태 변화 과정** (강의)

```text
새 파일 생성 → [Untracked]
    │
    ▼
git add → [Staged]
    │
    ▼
git commit → [Unmodified]
    │
파일 수정 → [Modified]
    │
    ▼
git add → [Staged]
```

- 스테이징한 파일을 수정하면 수정한 부분은 **Modified** 상태가 된다.
- Modified 상태는 **커밋 대상이 아니다.**
- 수정 내용까지 커밋하려면 다시 `git add`로 스테이징해야 한다.

### 3. Git 기본 명령어
- Git Bash는 **CLI**(Command Line Interface) — 모든 동작을 명령어를 입력해서 실행한다.
- Git 명령어는 모두 `git`으로 시작한다.

| 명령 | 하는 일 | 기억할 것 |
|---|---|---|
| `git init` | 현재 Working Directory를 Git 저장소로 초기화. `.git` 폴더가 생긴다 | **처음 세팅할 때 한 번만** |
| `git status` | 현재 Git 상태(파일들의 상태)를 보여 준다 | 수시로 확인 |
| `git add 파일명` | 파일을 Staging Area로 옮긴다 → Tracked 상태가 된다 | 아래 사용법 표 |
| `git commit -m "커밋 메세지"` | Staging Area의 파일들을 Repository에 저장 → **하나의 버전 생성** | `-m`은 메시지를 바로 적는 옵션 |
| `git diff` | 파일의 변경 사항 비교 | 아래 diff 표 |

**`git status`가 보여 주는 3가지 묶음**

| `git status` 문구 | 파일 상태 |
|---|---|
| `Untracked files:` | Untracked (추적 안 됨) |
| `Changes not staged for commit:` | Modified (수정됐지만 아직 스테이징 안 함) |
| `Changes to be committed:` | Staged (커밋할 준비 됨) |

**`git add` 사용법**

| 명령 | 스테이징하는 것 |
|---|---|
| `git add 파일명` | 특정 파일만 |
| `git add .` | 현재 폴더의 모든 파일 |
| `git add 폴더명` | 특정 폴더의 모든 파일 |
| `git add *.txt` | 특정 확장자 파일만 |

**`git diff` 사용법**

| 명령 | 비교하는 것 |
|---|---|
| `git diff` | Working Directory의 변경 사항 (Staged는 제외) |
| `git diff --staged` | Staging Area의 변경 사항 |

출력에서 `+`는 추가된 줄, `-`는 삭제된 줄이다. 바뀐 부분 주변 코드도 함께 보여 준다.

**강의의 당부**
- `git status`로 현재 상태를 **수시로** 확인한다.
- 커밋 메시지는 무엇을 어떻게 바꿨는지 **알아보기 쉽게** 쓴다.
- **`.git` 폴더를 절대 지우지 않는다.**

## 실습 정리

### 기초 예제 (강의)

```bash
# 0. git 저장소로 초기화
git init

# 1. 새 파일 생성 (Untracked)
echo "Hello" > file.txt

# 2. 파일 상태 확인
git status

# 3. Staging Area에 추가 (Staged)
git add file.txt

# 4. 파일 상태 확인
git status

# 5. Repository에 저장 (Committed)
git commit -m "Add file.txt"

# 6. 파일 상태 확인
git status

# 7. 파일 수정 (Modified)
echo "World" >> file.txt

# 8. 다시 상태 확인
git status
```

> 💡 보충: `echo "글자" > 파일`은 그 글자로 파일을 **새로 쓰고**(있으면 덮어씀), `>>`는 파일 **끝에 한 줄 덧붙인다.** 실습에서 파일을 만들고 고치는 대신 쓰는 명령이다.

### 결과까지 보는 예제 (강의)

```bash
# 1. git 저장소 초기화
git init
# 결과: Initialized empty Git repository in [경로]/.git/

# 2. 새 파일 생성
echo "안녕하세요" > hello.txt
# 결과: hello.txt 파일 생성됨

# 3. 파일 상태 확인
git status
# 결과: Untracked files:
#         hello.txt

# 4. 파일을 스테이징
git add hello.txt
# 결과: 파일이 Staging Area로 이동

# 5. 상태 확인
git status
# 결과: Changes to be committed:
#         new file: hello.txt

# 6. 파일 수정
echo "반갑습니다" >> hello.txt
# 결과: hello.txt에 내용 추가됨

# 7. 상태 확인
git status
# 결과: Changes to be committed:
#         new file: hello.txt
#       Changes not staged for commit:
#         modified: hello.txt

# 8. 수정된 파일 스테이징
git add hello.txt
# 결과: 수정사항이 Staging Area로 이동

# 9. 상태 확인
git status
# 결과: Changes to be committed:
#         new file: hello.txt

# 10. 커밋하기
git commit -m "hello.txt 파일 생성 및 수정"
# 결과: [main (root-commit) xxxx] hello.txt 파일 생성 및 수정
#       1 file changed, 2 insertions(+)
#       create mode 100644 hello.txt

# 11. 최종 상태 확인
git status
# 결과: nothing to commit, working tree clean
```

7번에서 `hello.txt`가 **두 묶음에 동시에** 나온다. 첫 줄("안녕하세요")은 스테이징되어 있고, 덧붙인 줄("반갑습니다")은 아직 스테이징 전이기 때문이다. 8번에서 다시 `add`하면 하나로 합쳐진다.

> 💡 보충: 7번 상태에서 `git diff`와 `git diff --staged`를 쳐 보면 차이가 보인다 (Git 2.50에서 확인).
> ```text
> $ git diff            ← 아직 스테이징 안 한 변경
> +반갑습니다
>
> $ git diff --staged   ← 스테이징된 변경
> +안녕하세요
> ```
> (실제 출력에는 위에 `diff --git a/hello.txt b/hello.txt` 같은 머리 줄이 함께 나온다.)

## 헷갈리기 쉬운 점
- **`add`는 저장이 아니다.** 버전은 `commit`해야 생긴다. `add`는 다음 커밋에 넣을 것을 고르는 단계다.
- **스테이징 후 수정한 내용은 커밋되지 않는다.** 커밋 직전에 `git status`로 `Changes not staged for commit`이 남아 있지 않은지 본다.
- `git init`은 저장소마다 **처음 한 번만**. 이미 저장소인 폴더(또는 그 안쪽 폴더)에서 다시 하지 않는다.
- `.git` 폴더는 숨김 폴더라 탐색기·Finder에서 안 보일 수 있다. 지우면 버전 기록이 전부 사라진다.

> 💡 보충: `git commit`을 `-m` 없이 치면 메시지를 쓰라고 편집기(기본 vim)가 열린다. vim에서는 `i`를 눌러 메시지를 쓰고, `Esc` → `:wq` → Enter로 저장하고 나온다. 커밋을 취소하려면 `Esc` → `:q!` → Enter.

## 확인 문제

<details><summary>Q. Git의 3가지 영역과, 영역 사이를 옮기는 명령은?</summary>

Working Directory —`git add`→ Staging Area —`git commit`→ Local Repository. Local Repository에 들어와야 버전이 확정된다.
</details>

<details><summary>Q. 새 파일을 만들고 `git status`를 치면 어느 묶음에 나오나? `git add` 뒤에는?</summary>

처음엔 `Untracked files:`(Untracked), `git add` 뒤에는 `Changes to be committed:`(Staged).
</details>

<details><summary>Q. `git add hello.txt` 다음에 `hello.txt`를 또 고치고 바로 커밋하면 어떻게 되나?</summary>

`add` 때의 내용만 커밋된다. 그 뒤에 고친 부분은 Modified로 남는다. 고친 내용까지 넣으려면 커밋 전에 다시 `git add`.
</details>

<details><summary>Q. `git diff`와 `git diff --staged`의 차이는?</summary>

`git diff`는 Working Directory에서 아직 스테이징하지 않은 변경, `git diff --staged`는 스테이징된(다음 커밋에 들어갈) 변경을 보여 준다.
</details>

<details><summary>Q. `.git` 폴더를 지우면 어떻게 되나?</summary>

버전 정보가 `.git`에 저장되어 있으므로 과거 기록이 모두 사라진다. 파일 자체(Working Directory)는 남지만 더 이상 Git 저장소가 아니다.
</details>

## 완료 체크
원문에 완료 체크가 없어 강의 단계로 만든 목록이다.
- [ ] 새 폴더에서 `git init`을 하고 `.git` 폴더가 생긴 것을 확인했다.
- [ ] 파일을 만들고 `git status`로 Untracked를 봤다.
- [ ] `git add` → Staged, `git commit` → `working tree clean`까지 확인했다.
- [ ] 커밋 뒤 파일을 고쳐 Modified를 보고, 다시 `add`·`commit`했다.
- [ ] `git diff`와 `git diff --staged`로 변경 내용을 비교했다.
