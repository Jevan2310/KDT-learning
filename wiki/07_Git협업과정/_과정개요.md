# Git협업과정 — Git 활용 협업

> 과정: Git협업과정 · [노션 원문](https://app.notion.com/p/41ce6d97109c80e09ceff2311561b537) · 최종 갱신일: 2026-11-20

## 과정 소개
파일이 바뀐 기록을 **Git**으로 남기고, **GitHub**에 올려 여러 사람이 함께 작업하는 방법을 배운다.
설치·설정 → 내 컴퓨터 안의 3가지 영역(`add`·`commit`) → 원격 저장소(`push`·`pull`·`clone`) → 브랜치 → 충돌 해결 → Organization·Fork·PR로 팀 프로젝트 세팅 순서로 간다.

- 수업일: 2026-11-20
- 과정 페이지에는 학습 목표와 목차가 따로 없다. 본문은 "버전 관리와 Git·GitHub" 개념이고(아래), 회차는 하위 페이지 6개다.

## 과정 페이지 본문 — 버전 관리와 Git·GitHub

### 1. 버전
- **버전**은 특정 시점의 파일 상태다. 문서를 `초안.doc → 수정본.doc → 최종본.doc`으로 따로 저장하면 각 파일이 하나의 버전이다.
- 개발에서는 소스 코드의 특정 시점 상태, 기능이 추가될 때마다의 상태가 버전이다.

**버전 번호 체계 (참고)** — Semantic Versioning, `x.y.z` 형식 (예: `1.0.0`)

| 자리 | 이름 | 올리는 때 |
|---|---|---|
| x | 주 버전 (Major) | 큰 변화 |
| y | 부 버전 (Minor) | 기능 추가 |
| z | 수 버전 (Patch) | 버그 수정 |

**개발 단계 이름**

| 이름 | 뜻 |
|---|---|
| alpha | 초기 개발 버전 |
| beta | 모든 기능 구현이 끝난 테스트 버전 |
| RC (Release Candidate) | 대부분의 버그 수정이 끝난 출시 후보 버전 |
| stable | 정식 출시되는 안정화 버전 |

### 2. 버전 관리와 버전 관리 시스템(VCS)
- **버전 관리**: 파일의 변경 사항을 시간에 따라 기록·관리하는 것. **언제, 무엇이, 왜** 바뀌었는지 남긴다.
- **버전 관리 시스템(Version Control System)**: 파일이 언제, 어떻게 바뀌었는지 기록하는 프로그램. 과거의 특정 시점으로 돌아갈 수 있다 (예: 문서를 잘못 고쳤을 때 이전 상태로 되돌리기).
- 필요한 이유
  - **변경 이력 관리** — 언제·무엇을·왜 바꿨는지 기록해 두면, 문제가 생겼을 때 이전 버전으로 복원할 수 있다.
  - **백업** — 내 컴퓨터의 파일을 잃어도 복구할 수 있다.

### 3. Git과 GitHub

| | Git | GitHub |
|---|---|---|
| 무엇 | 버전 관리 시스템(VCS) 프로그램 | Git이 관리하는 버전 기록을 공유하는 웹 사이트 |
| 어디서 동작 | 내 컴퓨터(로컬) | 인터넷 |
| 하는 일 | 변경 기록을 남기고, 이전 버전으로 되돌린다 | 개인·팀 저장소를 제공하고, 파일을 올리고 내려받게 한다 |

## 전체 흐름 한 장
강의 그림(06회차 "GitHub 영역")을 글로 옮겼다. 화살표마다 배우는 회차를 적었다.

```text
[내 컴퓨터 — Local]
Working Directory ──git add──▶ Staging Area ──git commit──▶ Local Repository      ← 02
                                                                  │
                                                                  │ git push       ← 03
[GitHub] ─────────────────────────────────────────────────────────▼────────
Organization Repository ◀──Pull Request(PR)── Remote Repository(내 계정)          ← 06
     (팀 공용 저장소)                              (Fork한 내 저장소)
```

- 01: 이 흐름에 쓰이는 Git을 설치하고 내 이름·이메일을 등록한다.
- 04: 한 저장소 안에서 작업 줄기(브랜치)를 나누고 합친다.
- 05: 원격과 로컬이 서로 다르게 바뀌었을 때 생기는 충돌을 해결한다.

## 강의 목차
노션 하위 페이지 제목과 각 페이지의 주요 내용이다.

### 01. git 설치와 환경설정
- Git 설치 (Git Bash, 기본 브랜치 `main`, 편집기)
- 사용자 이름·이메일 설정 (`git config --global`)
- 설정 확인, 설정 범위 (`--system` / `--global` / `--local`)

### 02. git의 3가지 영역
- Working Directory · Staging Area · Local Repository
- 파일 상태: Untracked, Tracked(Unmodified · Modified · Staged)
- 기본 명령어: `init`, `status`, `add`, `commit`, `diff`
- 상태 변화 과정

### 03. 원격 저장소
- `remote` (add · -v · rename · rm), `push`, `pull`
- 로컬-원격 작업 흐름 (pull 먼저, push는 나중에)
- `clone`, 프로젝트를 시작하는 2가지 상황
- 주의사항: 작업 순서, 민감 정보와 `.gitignore`, 협업 규칙

### 04. 브랜치
- 브랜치의 뜻, `main` 브랜치
- `branch`, `checkout`, `checkout -b`, `branch -d/-D`, `merge`
- 예제: 로그인 기능 브랜치, 챗봇 개발 중 긴급 버그 수정(hotfix)
- 브랜치 이동 전 커밋하기

### 05. 원격 저장소와 충돌(fetch)
- 원격 저장소도 브랜치를 가진다, pull·push의 동기화
- push 거부(`fetch first`)와 pull 충돌
- 충돌 표시 읽고 해결하기

### 06. Organization과 PR
- Fork, Organization, Pull Request
- 팀장이 처음 하는 세팅, 팀원이 하는 세팅
- 작업할 때 순서 (GitHub Flow), PR 받을 때 팀장이 하는 일

## 실습 환경
- 강의는 **Windows의 Git Bash**에서 명령을 친다. 모든 Git 명령은 `git`으로 시작한다.
- 02·04회차는 내 컴퓨터만 있으면 된다. 03·05·06회차는 **GitHub 계정과 저장소**가 필요하다.

> 💡 보충
> - macOS에는 Git Bash가 없다. **터미널**(또는 VS Code·IntelliJ의 내장 터미널)에서 같은 명령을 그대로 친다.
> - 연습용 폴더는 새로 만든다. 이미 Git 저장소인 폴더 안에서 또 `git init`을 하면 저장소 안에 저장소가 생겨 바깥 저장소가 안쪽 파일을 제대로 기록하지 못한다.
