# 03. 원격 저장소 — remote · push · pull · clone

> 과정: Git협업과정 · [노션 원문](https://app.notion.com/p/41ce6d97109c805997e9ec25f23845fb) · 최종 갱신일: 2026-11-20

## 한눈에 보기
- **원격 저장소**는 인터넷·네트워크에 있어서 여러 사람이 함께 쓰는 저장소다 (GitHub, GitLab, Bitbucket 등).
- 내 저장소에 원격 저장소를 **별칭**으로 등록하고(`git remote add origin URL`), 커밋을 올리고(`git push origin main`), 받는다(`git pull origin main`).
- 작업 흐름은 **pull 먼저 → 작업 → 커밋 → push**. 순서가 바뀌면 충돌이 날 수 있다.
- 이미 원격에 있는 프로젝트는 `git clone URL`로 통째로 복제한다. `.git`까지 복제되고 원격도 자동으로 연결되므로 `init`·`remote add`가 필요 없다.
- `push -f`(강제 push)는 원격 기록을 덮어써서 **사용 금지**. 비밀번호·API 키는 커밋하지 않고 `.gitignore`로 뺀다.

## 학습 목표
강의 페이지에 학습 목표가 따로 없어 본문 제목으로 정리했다.
- 원격 저장소를 연결·확인·이름 변경·삭제한다 (`remote`).
- 커밋을 원격에 올리고(`push`) 원격의 커밋을 받는다(`pull`).
- 로컬-원격 작업 순서를 지킨다.
- `clone`으로 원격 저장소를 복제한다.
- 프로젝트를 시작하는 2가지 상황을 구분한다.

## 핵심 개념

### 1. 원격 저장소 (Remote Repository)
- 인터넷이나 네트워크에 있는 저장소
- 여러 사람이 함께 공유하는 저장소
- 대표적으로 GitHub, GitLab, Bitbucket

강의 그림: 내 컴퓨터(Local)의 Working Directory → Staging Area → Local Repository까지가 [02회차](02_3가지영역-기본명령.md)이고, Local Repository에서 **`git push`**로 GitHub의 **Remote Repository**로 올라간다. (그 뒤 Organization Repository로 보내는 PR은 [06회차](06_Organization-PR.md))

### 2. remote — 원격 저장소 관리

| 명령 | 하는 일 |
|---|---|
| `git remote add [별칭] [URL]` | 현재 저장소에 원격 저장소를 추가. **여러 원격 저장소와 연결할 수 있다** |
| `git remote -v` | 연결된 원격 저장소 목록 확인 |
| `git remote rename [기존별칭] [새별칭]` | 원격 저장소의 별칭 수정 |
| `git remote rm [별칭]` | 등록한 원격 저장소 삭제 |

> 💡 보충: `origin`은 정해진 단어가 아니라 **관례로 많이 쓰는 별칭**이다. 첫 번째(내) 원격을 보통 `origin`이라고 짓는다. `git remote rm`은 연결 정보만 지운다. GitHub의 저장소 자체는 그대로다.

### 3. push — 원격 저장소에 업로드

| 명령 | 하는 일 |
|---|---|
| `git push [별칭] [브랜치]` | 로컬의 커밋을 원격에 업로드. `git push origin main` → origin의 main에 올린다 |
| `git push -f [별칭] [브랜치]` | **강제 push.** 원격과 로컬의 커밋 기록이 달라도 밀어 넣어 **원격의 내용을 모두 덮어쓴다.** 매우 위험하므로 **사용 금지** |

### 4. pull — 원격 저장소에서 다운로드

| 명령 | 하는 일 |
|---|---|
| `git pull [별칭] [브랜치]` | 원격의 커밋을 로컬에 다운로드. `git pull origin main` → origin의 main에서 받는다 |

### 5. 로컬-원격 작업 흐름
1. **원격 저장소 내용 pull (중요!!!)** — 혹시 모를 변경 사항을 먼저 로컬에 반영한다.
2. 로컬에서 작업한다.
3. 변경 사항을 커밋한다.
4. 원격 저장소에 push한다.

### 6. clone — 원격 저장소를 로컬로 복제
- `git clone [원격저장소 URL] [복제 경로]`
- 원격 저장소를 **통째로** 로컬에 복제한다.
- 원격의 `.git` 폴더까지 복제되므로 **`git init`이 필요 없다.**
- 원격이 자동으로 연결되므로 **`remote add`도 필요 없다.** (그래도 `git remote -v`로 확인은 한다)
- 복제 경로에 `.`을 쓰면 **현재 폴더**에 모든 파일을 복제한다.

> 💡 보충
> - 복제 경로를 생략하면 저장소 이름으로 새 폴더를 만들고 그 안에 복제한다.
> - `.`(현재 폴더)로 복제하려면 그 폴더가 **비어 있어야** 한다. 파일이 있으면 `fatal: destination path '.' already exists and is not an empty directory.`가 나온다 (Git 2.50에서 확인).
> - clone하면 원격 별칭은 자동으로 `origin`이 된다.

### 7. 프로젝트를 시작할 때 2가지 상황

| 상황 | 순서 |
|---|---|
| **로컬에서 처음부터 시작** | `git init`으로 저장소 생성 → 파일 작성·커밋 → 원격 연결(`remote add`) → 원격에 업로드(`push`) |
| **원격에 있는 프로젝트를 이어서 시작** | GitHub의 원격 저장소를 `git clone`으로 복제 → 파일 작성·커밋 → 원격에 업로드(`push`) |

## 실습 정리

### 기초 예제 — 로컬에서 시작해서 GitHub에 올리기 (강의)

```bash
# 1. GitHub에서 새 저장소 만들기 (README 없이)

# 2. 로컬 저장소 설정
git init  # 현재 폴더를 Git 저장소로 만들기
git add .  # 모든 파일 스테이징
git commit -m "first commit"  # 첫 버전 만들기

# 3. 원격 저장소 연결
git remote add origin [GitHub URL]  # origin이라는 별칭으로 연결
git remote -v  # 연결된 원격 저장소 확인

# 4. 원격 저장소에 업로드
git push origin main  # 로컬의 main 브랜치를 origin에 push

# 5. 다른 사람의 변경사항 받기
git pull origin main  # origin의 main 브랜치 내용을 받기

```

> 💡 보충
> - **README 없이** 만드는 이유: GitHub에서 README를 체크하면 원격에 커밋이 하나 먼저 생긴다. 그러면 내 로컬 기록과 달라서 첫 push가 `! [rejected] … (fetch first)`로 거부된다 ([05회차](05_원격충돌-fetch.md)).
> - `git remote -v`는 같은 주소가 `(fetch)`·`(push)` 두 줄로 나오는 게 정상이다.
> - 처음 push할 때 GitHub 로그인을 묻는다. GitHub는 계정 **비밀번호로는 push를 받지 않는다** — 브라우저 로그인 창(Git Credential Manager)이나 토큰으로 인증한다. 자세한 것은 [00_개발환경/git](../00_개발환경/git.md) "문제 생겼을 때".

### 원격 저장소를 복제해서 시작하기 (강의)

```bash

# 원격 저장소 복제하기
git clone [URL] [복제 경로]
# 파일 수정
git add .
git commit -m "작업 내용"
git push origin main

```

## 헷갈리기 쉬운 점
강의의 주의사항 ⚠️
1. **작업 순서**
   - **pull 먼저, push는 나중에.** 순서가 바뀌면 충돌이 생길 수 있다.
   - 충돌이 나면 로컬에서 해결한 뒤 push한다 ([05회차](05_원격충돌-fetch.md)).
2. **보안**
   - 비밀번호, API 키 같은 민감한 정보는 **커밋하지 않는다.**
   - `.gitignore`로 민감한 파일을 뺀다.
   - 실수로 올렸으면 **즉시 비밀번호를 바꾼다.**
3. **협업**
   - 팀 규칙과 커밋 메시지 규칙을 지킨다.
   - 공유 코드는 신중하게 고친다.

> 💡 보충
> - `.gitignore`는 저장소 맨 위 폴더에 두는 글자 파일이다. 한 줄에 하나씩 뺄 파일·폴더를 적는다 (예: `.env`, `node_modules/`). **이미 커밋한 파일은 `.gitignore`에 적어도 계속 추적된다.** 그래서 처음부터 넣어 둔다.
> - 비밀번호를 커밋했다가 다음 커밋에서 지워도 **과거 버전에는 남는다.** 강의가 "즉시 비밀번호 변경"이라고 하는 이유다.
> - `clone`과 `pull`의 차이: `clone`은 **처음 한 번** 저장소 전체를 복제하는 것, `pull`은 이미 연결된 저장소에서 **새 커밋만** 받는 것.

## 빠른 참고 (치트시트)

| 하고 싶은 것 | 쓰는 것 | 예시 |
|---|---|---|
| 원격 연결 | `git remote add 별칭 URL` | `git remote add origin https://github.com/<아이디>/<저장소>.git` |
| 연결 확인 | `git remote -v` | |
| 별칭 바꾸기 | `git remote rename 기존 새` | `git remote rename origin my` |
| 연결 끊기 | `git remote rm 별칭` | |
| 올리기 | `git push 별칭 브랜치` | `git push origin main` |
| 받기 | `git pull 별칭 브랜치` | `git pull origin main` |
| 복제해서 시작 | `git clone URL 경로` | `git clone <URL> .` (빈 폴더에서) |
| 올리면 안 되는 파일 빼기 | `.gitignore` | `.env` |

## 확인 문제

<details><summary>Q. pull과 push 중 무엇을 먼저 하나? 이유는?</summary>

pull 먼저. 다른 사람이 올린 변경을 먼저 내 로컬에 반영해야 한다. 순서가 바뀌면 충돌이 나거나 push가 거부될 수 있다.
</details>

<details><summary>Q. `git clone`으로 시작하면 `git init`과 `git remote add`가 필요 없는 이유는?</summary>

원격의 `.git` 폴더까지 통째로 복제되어 이미 저장소이고, 복제한 원격이 자동으로 `origin`으로 연결되기 때문이다. `git remote -v`로 확인만 한다.
</details>

<details><summary>Q. `git push -f`를 쓰면 안 되는 이유는?</summary>

원격과 로컬의 기록이 달라도 강제로 밀어 넣어 **원격의 내용을 덮어쓴다.** 다른 사람이 올린 커밋이 사라질 수 있다.
</details>

<details><summary>Q. 프로젝트를 시작하는 2가지 상황의 순서는?</summary>

- 로컬에서 처음: `init` → 작성·커밋 → `remote add` → `push`
- 원격 프로젝트 이어서: `clone` → 작성·커밋 → `push`
</details>

<details><summary>Q. API 키를 실수로 커밋해서 GitHub에 올렸다. 무엇을 해야 하나?</summary>

즉시 그 키·비밀번호를 바꾼다(폐기). 파일을 지우고 다시 커밋해도 과거 버전에 남아 있기 때문이다. 앞으로는 `.gitignore`로 빼 둔다.
</details>

## 완료 체크
원문에 완료 체크가 없어 강의 단계로 만든 목록이다.
- [ ] GitHub에서 README 없이 새 저장소를 만들었다.
- [ ] 로컬에서 `init → add → commit` 후 `remote add origin`, `remote -v`로 확인했다.
- [ ] `git push origin main`으로 올리고 GitHub에서 파일을 확인했다.
- [ ] `git pull origin main`으로 원격 변경을 받았다.
- [ ] 다른 빈 폴더에서 `git clone`으로 복제하고 `remote -v`를 확인했다.
